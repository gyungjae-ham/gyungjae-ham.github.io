쇼핑 서비스에서 쿠폰을 안내할 때 고객이 카카오 채널을 추가했는지 조회하는 기능이 있습니다. 서버가 카카오 API에 물어본 결과를 화면에 전달하는 부가 정보인데, 이 통신이 간헐적으로 끊기면서 우리 API도 500을 반환했습니다. 응답 내용이 잘못된 경우가 아니라 응답을 받기 전에 연결이 닫히는 `RemoteDisconnected` 오류였습니다.

외부 요청에는 연결을 보관했다가 다시 쓰는 HTTP 커넥션풀을 사용하고 있었습니다. 매번 연결을 새로 맺는 비용을 줄이기 위한 구조입니다. 오류가 시작된 시점과 풀 도입 시점을 대조하고, 같은 연결을 얼마 동안 재사용할 수 있는지 직접 확인하면서 연결 종료와 재사용이 겹치는 경우를 살펴봤습니다. 이때 필요한 것은 연결 재사용을 유지하면서도 조회 실패를 복구하고, 같은 클라이언트로 보내는 결제 요청은 함부로 반복하지 않는 것이었습니다.

## 풀에 남은 연결을 상대 서버도 유지하고 있을까

클라이언트가 연결을 풀에 보관한다고 상대 서버가 계속 기다려 주는 것은 아닙니다. 카카오 연결을 일정 간격으로 다시 사용한 조사에서는 6초 간격의 재사용은 성공했고 10초부터 종료를 관찰했습니다. 이는 당시 호출에서 확인한 값으로, 카카오의 고정된 연결 유지 규약으로 취급하지 않았습니다.

이미 끊긴 연결은 라이브러리도 검사합니다. 사용 중인 Requests 2.32.3 아래의 urllib3 1.26.20은 풀에서 연결을 꺼낼 때 끊김을 확인하고, 끊겼다면 닫도록 구현돼 있습니다. 다만 검사 직후 상대가 연결을 닫는 경우까지 그 검사 한 번으로 막을 수는 없습니다. [urllib3 1.26.20의 연결 회수 처리](https://github.com/urllib3/urllib3/blob/1.26.20/src/urllib3/connectionpool.py#L240-L273)

예를 들어 앞선 요청이 끝난 연결을 풀에 돌려놓고 한동안 쓰지 않다가 다음 조회에 가져온다고 해보겠습니다. 꺼내는 순간에는 살아 있던 연결이 상대의 유휴 시간 제한에 도달해 닫히면 다음 요청은 응답을 받지 못할 수 있습니다. 그래서 오래 쉰 연결을 다시 쓰기 전에 닫도록 바꿨습니다. 풀에 반납할 때 경과 시간 측정용 시각을 기록하고, 꺼낼 때 마지막 반납 후 4초를 초과했으면 새 연결을 맺게 했습니다.

4초는 이번 구현에서 정한 정책입니다. 그 안의 연속 호출은 재사용하지만, 간격이 긴 호출은 새 연결 비용을 냅니다. HTTP와 HTTPS 풀에 적용했고 프록시를 사용하는 경로는 이 폐기 정책의 대상에 포함하지 않았습니다. 상대가 더 빨리 닫거나 다른 이유로 통신이 실패할 수도 있으므로 유휴 연결 폐기만으로 모든 연결 오류를 없앴다고 볼 수는 없습니다.

## 연결 끊김과 느린 응답에 다른 재시도 규칙 적용하기

기존 클라이언트는 요청을 보낸 뒤 응답을 받지 못한 경우의 재시도를 막고 있었습니다. 결제 요청은 상대가 처리한 뒤 응답만 유실될 수 있기 때문입니다. 하지만 이 정책이 채널 조회에도 적용돼 일시적인 연결 끊김이 바로 실패로 끝났습니다.

여기서는 읽기 전용으로 사용하는 GET·HEAD·OPTIONS의 연결 끊김에만 한 번의 재시도를 허용했습니다. POST·PUT·DELETE는 요청을 보낸 뒤 응답 없이 끊겨도 다시 보내지 않습니다. PUT이 HTTP 의미상 멱등 메서드라는 점과 외부 서비스의 실제 쓰기를 자동 반복해도 되는지는 별도로 판단했습니다. 요청을 보내기 전 연결 수립 단계의 실패에 대한 기존 재시도 설정은 유지했습니다.

`read=1` 설정만 바꾸면 충분하지 않았습니다. urllib3 1.26.20의 읽기 오류 분류에는 `ProtocolError`와 `ReadTimeoutError`가 함께 들어갑니다. 연결이 끊긴 조회를 복구하려다 느린 응답까지 재시도하면, 이미 기다린 요청을 다시 기다리게 됩니다. 그래서 재시도 횟수를 갱신하는 지점에서 `ReadTimeoutError`는 그대로 올리고, 허용한 메서드의 연결 끊김만 재시도하도록 구분했습니다. [urllib3 1.26.20의 오류 분류와 재시도 처리](https://github.com/urllib3/urllib3/blob/1.26.20/src/urllib3/util/retry.py#L399-L410)

채널 조회 자체에도 실패 시 응답을 정했습니다. 연결 실패나 타임아웃이면 전체 API를 실패시키는 대신 채널 미추가를 뜻하는 값으로 200을 반환합니다. 쿠폰 안내용 부가 조회가 화면 요청 전체를 실패시키지 않게 한 선택이지만, 응답만으로는 실제 미추가와 일시적인 조회 실패를 구별할 수 없다는 제약이 있습니다.

## 실제 소켓으로 재사용과 재시도 횟수 확인하기

테스트에서는 로컬 HTTP 서버가 연결을 유지하거나 첫 요청을 응답 없이 끊게 했습니다. 짧은 간격의 두 요청이 같은 연결을 쓰는지, 폐기 기준을 넘으면 새 연결을 쓰는지 클라이언트 포트로 확인했습니다. 첫 GET을 끊었을 때 다음 요청으로 성공하고, POST와 PUT은 서버에 한 번만 도달하는지도 검사했습니다. 느리게 응답하는 GET은 타임아웃 뒤 추가 요청이 없어야 합니다.

이 소켓 회귀를 포함한 core 단위 테스트는 통과했습니다. 변경한 클라이언트로 실제 카카오 API를 0~12초 간격으로 호출한 확인에서도 연결 실패가 없었습니다. 다만 제한된 호출 결과이며 운영에서의 오류율이나 지연 변화를 측정한 것은 아닙니다. 반면 회원과 쿠폰 발급 이력을 사용하는 채널 조회 통합 테스트는 작성했지만, 안전한 테스트 DB 호스트를 확인하지 못해 실행하지 않았습니다. 결제 관련 DB 통합 검증도 남아 있습니다.

구현은 10월 16일 main에 병합됐습니다. 이후 확인할 것은 배포된 클라이언트의 연결 오류 추이와 새 연결 비율, 응답 지연입니다. 같은 `RemoteDisconnected`라도 풀 도입 전부터 발생한 결제 승인 오류는 별도 조사 대상으로 남겼습니다. 조회를 한 번 더 보내는 이번 정책을 결제 결과 복구에 그대로 적용할 수는 없습니다.

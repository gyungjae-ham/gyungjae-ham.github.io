> 도구를 도입한 뒤에도 주석과 PR 형식, 설계 확인 순서를 계속 고쳤습니다. 6주간의 변경에서 가장 눈에 띄는 것은 자동화의 깊이보다 구현과 리뷰의 역할을 나누고 중간 판단을 확인한 과정입니다.

## 기본 설정만으로 팀의 작업 방식은 전달되지 않았다

코딩 에이전트가 파일을 수정할 수 있다는 것과 팀이 그 결과를 검토할 수 있다는 것은 다른 문제였습니다. 코드의 동작 외에도 PR에서 무엇을 설명할지, 설계 문서를 어느 순서로 읽을지, 주석에 어떤 정보를 남길지를 정해야 했습니다.

초기에는 명령과 규칙의 기본 구조를 만들고, 이후 PR 가독성과 문서 형식, 자동 검사 결과의 안내를 보강했습니다. 규칙은 한 번에 완성하지 않았습니다. 실제 작업에서 반복되는 문제를 확인한 뒤 해당 경계에 추가했습니다.

## 잘못된 설계가 구현 끝까지 이어지지 않게 했다

설계부터 구현과 PR까지 한 번에 진행하면, 초기 가정이 틀려도 많은 파일을 만든 뒤에야 알아차릴 수 있습니다. 그래서 설계 확인과 구현 시작 등 중간 단계에 확인 지점을 두었습니다. 산출물을 보고 다음 작업을 판단할 수 있도록 한 것입니다.

게이트가 많다고 좋은 것은 아닙니다. 같은 내용을 반복 승인하게 만들면 작업이 멈추고, 아무 근거 없이 통과하면 게이트의 의미가 없습니다. 확인할 결정과 관련 코드, 예상 영향이 드러나는 단위로 나누는 것이 필요했습니다.

## 수정하는 역할과 검토하는 역할을 분리했다

운영 중 리뷰 흐름을 수정 중심에서 검토 중심으로 바꾼 변경이 있습니다. 지적을 발견하자마자 코드를 고치면 원래 문제와 수정의 의도가 섞입니다. 먼저 문제가 되는 근거와 재현 조건을 제시하고, 수정은 별도 단계에서 수행하도록 역할을 구분했습니다.

프로덕션 주석에 설계 단계의 임시 식별자가 남지 않도록 하는 규칙도 추가했습니다. 작업을 조율하기 위한 메타 정보와, 다음 개발자가 코드에서 읽어야 할 설명은 다릅니다. PR 본문에는 문제와 변경 결과를 남기고 내부 작업 단계는 분리했습니다.

이런 규칙은 모델에게 긴 설명을 주는 것만으로 끝나지 않습니다. 반복되는 오류는 검사로 확인하고, 검사 결과를 사람이 해석할 수 있게 보여주는 흐름이 함께 필요했습니다.

## 한 사례의 속도를 전체 생산성으로 환산하지 않았다

실제 광고 랜딩 API에서 설계·구현·리뷰를 연결한 사례가 남아 있습니다. 다만 도입 이전의 평균 작업 시간과 동일 조건의 비교 자료는 없습니다. 한 작업이 빠르게 끝났다는 사실을 팀 전체의 생산성 개선율로 바꾸지는 않았습니다.

확인 가능한 결과는 작업 규칙이 여러 차례 수정되었고, 구현과 리뷰의 역할이 분리되었으며, 중간 설계를 확인하는 지점이 생겼다는 점입니다. 다음 평가에는 작업 유형별 리드타임과 리뷰 재작업을 함께 봐야 합니다. 규칙이 늘어난 양보다 실제로 줄인 반복 작업이 중요합니다.

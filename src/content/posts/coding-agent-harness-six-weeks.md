백엔드 기능 하나를 개발할 때는 코드만 만드는 것으로 끝나지 않습니다. 기존 모델과 요구사항을 맞춰 설계하고, 테스트와 리뷰를 거친 뒤 다른 사람이 이해할 수 있는 PR을 남겨야 합니다. Claude Code를 업무에 쓰기 시작하면서 이 과정 중 어디까지 맡기고 어디서 결과를 확인할지 정할 필요가 있었습니다.

2026년 4월 말부터 약 6주 동안 개인 작업에 맞춰 규칙을 수정했습니다. 여기서 말하는 하네스는 별도의 모델이 아니라, 에이전트가 읽을 지침과 작업 단계, 검토 절차를 묶은 것입니다. 실제 작업에서 특히 많이 고친 부분은 중간 설계를 확인하는 시점과 리뷰의 역할이었습니다.

## 틀린 전제를 일찍 읽을 수 있어야 했다

설계부터 구현과 PR 작성까지 이어서 맡기면 처음 세운 가정이 여러 산출물에 반복됩니다. 그 가정이 틀렸다는 사실을 구현 끝에 발견하면 코드뿐 아니라 설계 문서와 테스트도 돌아봐야 합니다. 그래서 설계 결과를 확인한 뒤 구현으로 넘어가는 지점을 뒀습니다.

그때 필요한 것은 단순한 진행 허가가 아니었습니다. 무엇을 바꾸려는지, 어떤 기존 코드에 기대는지, 영향 범위가 어디까지인지 읽을 수 있어야 판단할 수 있습니다. 에이전트가 결론만 요약하는 대신 관련 근거를 함께 제시하도록 작업 규칙을 보강했습니다.

[광고 상품 API](/posts/ad-landing-pinned-product/)에서는 구현 중 상품에 브랜드가 반드시 있다는 모델 제약을 확인하고, 브랜드가 없는 경우까지 고려한 앞선 설계를 수정했습니다. 단계를 나눠 둔 덕분에 돌아갈 위치는 분명했습니다. 다만 이 경험은 확인 단계가 있다는 것만으로 충분하지 않다는 점도 보여줬습니다. 모델 제약을 읽는 순서 자체가 앞에 있어야 했습니다.

## 리뷰에서 바로 코드를 고치지 않게 했다

리뷰가 문제를 발견하자마자 수정까지 하면, 검토자는 원래 코드의 문제와 수정안의 적절성을 한꺼번에 판단해야 합니다. 지적이 맞는지 확인하기 전에 변경부터 쌓이기도 합니다.

리뷰 단계에서는 문제 위치, 발생 조건, 영향, 근거를 먼저 남기도록 했습니다. 그 내용을 읽고 채택한 지적을 별도 수정 단계로 넘긴 뒤 다시 검토했습니다. 역할을 나눈다고 리뷰가 항상 맞아지는 것은 아니지만, 적어도 어떤 이유로 코드를 바꿨는지는 추적할 수 있었습니다.

```text
설계와 영향 범위 확인 → 구현 → 문제와 근거를 적은 리뷰
                                  ↓
                         채택한 지적 수정 → 재검토
```

## 작업 중 메모와 최종 산출물을 구분했다

작업을 나눠 진행하자 코드 주석에 설계 문서의 임시 식별자가 남거나, PR에 구현 순서만 길게 나열되는 문제도 다뤄야 했습니다. 작업을 조율할 때 필요한 정보가 다음 개발자에게도 유용한 설명인 것은 아니었습니다.

PR은 어떤 문제가 있었고 변경 후 무엇이 달라지는지 중심으로 쓰게 했습니다. 코드 주석에는 임시 작업 번호 대신 그 코드에서 알아야 하는 이유를 남기도록 했습니다. 기본 설정에서 시작해 설계 확인, 리뷰 역할, PR과 주석 규칙을 실제 산출물을 보며 차례로 고쳤습니다.

이 흐름으로 광고 랜딩 API의 설계·구현·리뷰를 약 하루에 진행한 사례는 있습니다. 비교할 이전 작업의 평균 시간을 측정하지 않았으므로 생산성 개선율을 계산할 근거는 부족합니다. 6주 동안 구체적으로 바뀐 것은 검토 방식입니다. 구현을 읽기 전에 설계의 전제를 확인하고, 수정 코드를 읽기 전에 리뷰의 근거를 확인할 수 있게 됐습니다.

코딩 에이전트가 파일을 수정하는 데 성공해도 그 결과를 바로 검토하기 쉬운 것은 아니었습니다. 설계가 맞는지, PR에는 무엇을 설명해야 하는지, 코드에 남길 주석은 무엇인지까지 프로젝트의 작업 방식에 맞춰야 했습니다.

2026년 4월 말부터 약 6주 동안 Claude Code 작업 규칙을 수정했습니다. 가장 큰 변화는 자동화 단계를 늘린 것보다 **구현하는 역할과 검토하는 역할을 분리한 것**이었습니다.

## 처음부터 끝까지 맡기면 처음의 가정도 끝까지 간다

설계부터 PR까지 한 번에 진행하면 초기 판단이 구현 전체에 퍼집니다. 뒤늦게 가정을 바꾸려면 이미 만들어진 문서와 코드도 함께 되돌려야 합니다.

설계 확인과 구현 시작 같은 단계에 사람이 산출물을 확인하는 지점을 뒀습니다. 단순히 계속 진행해도 되는지 묻는 절차보다, 결정과 관련 코드·영향 범위를 함께 보여주는 것이 필요했습니다.

실제 [광고 상품 API](/posts/ad-landing-pinned-product/)에서는 구현 중 모델 제약을 확인하고 앞선 설계를 수정했습니다. 구간을 나눈 덕분에 어디로 돌아가야 하는지는 분명했습니다. 다만 제약을 늦게 확인한 문제까지 게이트가 대신 해결해 주지는 않았습니다.

## 리뷰가 바로 수정을 시작하면 근거가 사라진다

운영 중 리뷰 흐름을 수정 중심에서 검토 중심으로 바꿨습니다. 지적을 발견하자마자 코드를 바꾸면 원래 코드가 왜 문제였는지와 수정이 적절한지를 한꺼번에 검토해야 합니다.

리뷰 단계는 문제 위치, 재현 조건, 영향과 근거를 먼저 제시하도록 했습니다. 수정은 그 판단을 받아 별도 단계에서 진행했습니다. 역할을 나누니 리뷰 결과를 읽고 어떤 지적을 받아들일지 결정할 수 있게 됐습니다.

```text
설계 결과 확인 → 구현 → 근거를 포함한 리뷰
                              ↓
                     채택한 지적 수정 → 재검토
```

이 흐름에서도 잘못된 리뷰는 나올 수 있습니다. 역할 분리는 정확도를 보장하는 장치보다 판단을 추적할 수 있게 하는 구조에 가깝습니다.

## 규칙을 늘릴 때는 남을 산출물부터 봤다

PR 본문에는 문제와 변경 결과가 보이도록 Summary 형식을 정리했습니다. 코드 주석에는 설계 문서의 임시 식별자가 남지 않도록 했습니다. 작업 중 조율 정보가 실제 코드 설명처럼 굳어지는 것을 막기 위해서입니다.

규칙을 한 번에 완성하지는 않았습니다. 기본 설정, PR 가독성, 마일스톤 확인, 리뷰 역할, 주석 규정 순서로 실제 작업에서 필요한 부분을 추가했습니다. 같은 내용을 긴 프롬프트에 반복하는 것보다 산출물별 책임을 좁히는 방식이었습니다.

## 한 작업의 속도를 생산성 개선율로 계산하지 않았다

규칙이 정착된 시점에 광고 랜딩 API를 설계·구현·리뷰까지 약 하루에 진행한 사례는 있습니다. 하지만 도입 전 같은 종류의 작업 평균 시간은 측정하지 않았습니다. 이 한 사례로 팀 전체가 몇 배 빨라졌다고 말할 수는 없습니다.

확인한 변화는 중간 설계를 검토하고, 리뷰의 근거를 읽고, 채택한 수정만 진행하는 흐름을 만들었다는 점입니다. 다음 평가는 규칙 수나 커밋 수보다 작업 유형별 리드타임과 리뷰 후 재작업을 봐야 합니다.

6주 동안 계속 고친 것은 모델이 만드는 코드만이 아니었습니다. 사람이 결과를 읽고 판단할 수 있도록 일을 전달하는 방식이었습니다.

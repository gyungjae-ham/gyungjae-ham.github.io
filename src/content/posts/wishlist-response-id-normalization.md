고객은 관심 있는 상품을 찜하고 나중에 목록에서 다시 볼 수 있습니다. 같은 상품을 동시에 찜하는 요청은 DB 고유 제약과 충돌할 수 있어, 단건 생성과 여러 상품을 한 번에 저장하는 벌크 생성에 중복 방어가 추가됐습니다. 최초 동시성 수정은 Datadog Bits가 작성한 초안이며, 저는 그 뒤 응답을 만드는 조회와 상품 ID 처리를 보완했습니다.

벌크 생성은 충돌을 무시한 뒤 실제 저장된 찜을 다시 읽습니다. 생성 시도에 사용한 객체만으로는 어떤 행이 저장됐고 어떤 요청이 먼저 만들었는지 확정하기 어렵기 때문입니다. 경쟁 요청이 먼저 저장한 상품도 현재 찜 상태라면 응답에 포함하는 흐름입니다.

## 문자열 입력과 정수 키가 만났을 때

예를 들어 상품 ID를 문자열 `"123"`으로 보냈다고 해보겠습니다. DB에는 상품 123의 찜이 저장됐지만, 재조회한 행으로 만든 맵의 키는 정수 `123`입니다. 원래 문자열로 그 맵을 찾으면 같은 상품을 찾지 못합니다. 저장은 성공했는데 응답 목록에서는 빠지는 결과가 됩니다.

벌크 입력을 먼저 정수로 변환하고, 중복 제거·가격 조회·응답 재조회에서 같은 키 타입을 사용하도록 했습니다. `"123"`과 `123`이 섞여도 같은 상품으로 취급합니다. 정수로 변환할 수 없는 ID는 400으로 거절합니다. 이는 현재 허용하던 문자열 숫자를 맞춘 처리이며, 존재하지 않는 상품까지 유효하게 만든다는 뜻은 아닙니다.

## 응답 재조회가 새 반복 조회를 만들지 않도록

재조회한 찜을 직렬화할 때 상품과 브랜드·판매자 정보가 필요했습니다. 이 관계를 지연 조회하면 찜마다 추가 SQL이 발생할 수 있어 필요한 관계를 `select_related`로 함께 읽었습니다. 다만 벌크 처리 안에는 상품별 존재 검사도 남아 있으므로 전체 함수의 모든 반복 조회를 제거한 결과로 표현할 수는 없습니다.

단건에서도 기존 찜인데 가격부터 조회하던 부분을 보완했습니다. `get_or_create`에 가격 조회 결과를 미리 넘기는 대신 callable을 기본값으로 전달합니다. 사용 중인 Django 3.2에서는 생성할 때 callable 기본값을 평가하므로, 기존 찜을 찾은 경우 그 가격 조회를 건너뜁니다. [Django 3.2의 get_or_create 설명](https://docs.djangoproject.com/en/3.2/ref/models/querysets/#get-or-create)

로컬 MySQL 회귀에서는 삽입 직전 경쟁 요청이 먼저 저장하는 경우와 문자열·잘못된 ID를 확인했습니다. 문자열 응답 누락은 수정 전 실패를 재현한 뒤 보완했습니다. 후속 커밋을 포함한 변경은 10월 30일 main에 병합됐습니다.

응답의 기존 차이는 남아 있습니다. 단건에서 이미 찜한 상품은 빈 목록을 반환하지만 벌크에서는 경쟁 요청이 먼저 저장한 상품도 반환합니다. 또 MySQL의 충돌 무시 삽입 때문에 벌크의 존재하지 않는 상품은 건너뛰고 201을 반환하며 단건의 기존 오류 처리는 남아 있습니다. 이 입력·응답 차이와 별개로 운영 배포, 전체 쿼리 비용과 오류 빈도의 변화는 아직 확인하지 않았습니다.

> 계절이 바뀌었는데 여름 상품 fallback이 계속 남았습니다. 겨울 하의 후보가 비는 이유를 확인하니 코드의 카테고리 이름과 운영 카탈로그의 이름이 달랐습니다.

## fallback이 원인을 가리고 있었다

추천은 시즌 후보가 부족하면 다른 풀로 보충하도록 되어 있었습니다. 그래서 사용자에게 빈 목록이 나가는 대신 이전 계절 상품이 계속 노출되었습니다. 응답이 채워진다는 사실만 보면 후보 선정의 실패를 놓칠 수 있습니다.

원본의 진단은 운영 데이터를 읽기 전용으로 확인하고 실제 필터 조건과 대조하는 방식이었습니다. fallback 상품을 직접 바꾸는 것보다 왜 1차 후보가 없었는지 확인하는 데 초점을 두었습니다.

## 정확한 문자열 비교가 운영 이름과 어긋났다

코드의 겨울 하의 상수는 짧은 이름을 사용했지만 운영 Tab에는 팬츠까지 포함된 이름이 저장되어 있었습니다. exact-match 조건이었으므로 의미가 비슷해도 다른 문자열은 결과에 포함되지 않았습니다.

상수를 실제 운영 이름에 맞추고, 여름·상의의 규칙과 후보 부족 fallback은 유지했습니다. 변경 범위를 문제가 된 시즌 조건으로 제한했습니다. 관련 Query 회귀와 시즌 상수 테스트에 운영에서 쓰는 이름을 포함시켰습니다.

## 표시 이름을 조회 키로 쓰는 한계는 남는다

이번 수정은 작은 변경으로 현재 불일치를 바로잡았습니다. 하지만 운영에서 이름을 다시 바꾸면 같은 종류의 문제가 생길 수 있습니다. 표시 문구와 안정적인 식별자를 구분하는 것은 후속 설계 관점이며 이번 PR에서 도입했다고 표현하지 않았습니다.

관측에서도 최종 결과 개수만으로는 부족합니다. 1차 후보 수와 fallback 사용 여부를 나눠 보면 화면이 채워져 있어도 원래 의도한 후보가 사라졌는지 알 수 있습니다. 이는 당시 장애를 바탕으로 정리한 후속 확인 항목입니다.

## 복구된 후보는 노출 성과와 다르다

기록에는 운영 읽기 전용 조회에서 겨울 하의 후보가 0건에서 다시 확보된 결과와 테스트 통과, 병합이 남아 있습니다. 내부 후보 수의 절대값은 공개하지 않았습니다. 최종 선택 수와 실제 노출, CTR 개선은 별도 결과입니다.

확인한 변화는 코드와 운영 카탈로그의 조회 조건을 맞췄다는 점입니다. fallback은 후보 부족을 처리하는 정책이지만 잘못된 필터를 정상으로 만드는 장치는 아닙니다. 보충 결과와 원래 후보 경로를 따로 확인해야 했습니다.

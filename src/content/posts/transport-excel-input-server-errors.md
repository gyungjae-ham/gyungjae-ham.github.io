판매자는 배송하거나 회수할 상품의 운송장 정보를 엑셀로 올립니다. 파일의 주문 번호가 잘못됐다면 내용을 고쳐 다시 올려야 하지만, 서버 내부 조회가 실패했다면 같은 파일을 수정해도 해결되지 않습니다. 두 실패를 같은 입력 오류로 안내하면 판매자가 다음에 무엇을 해야 할지 알기 어렵습니다.

이 업로드에서는 예외 객체를 응답에 직접 넣어 JSON 렌더링이 실패하는 문제가 먼저 있었습니다. 초기 직렬화 수정 초안은 Datadog Bits가 작성했습니다. 저는 그 뒤에 남은 오류 분류와 내부 정보 보호, 손상된 파일의 처리 범위를 보완했습니다.

## 문자열로 바꾼 뒤에도 남는 문제

예외를 문자열로 바꾸면 JSON으로 보낼 수는 있습니다. 하지만 모든 예외를 400으로 반환하면 DB 조회 같은 내부 실패도 파일 탓으로 안내하게 됩니다. 예외 원문에는 서버 내부 정보가 들어갈 수도 있습니다.

엑셀 읽기와 필수 열, 주문 상세 번호, 회수 번호를 검사하면서 확인한 입력 실패만 전용 예외로 변환했습니다. 배송·반품 회수·교환 회수 경로의 기존 error 문자열 형태는 유지하되, 응답은 필수 항목과 번호를 확인하라는 고정 안내로 통일했습니다. 예상하지 못한 내부 실패는 일반적인 500 안내를 보내고 서버 로그에 traceback을 남겨 조사할 수 있게 했습니다.

## 열리는 ZIP도 정상 엑셀은 아닙니다

파일 파서가 던지는 예외의 범위도 확인해야 했습니다. XLSX는 ZIP 내부에 XML 문서를 담는 형식입니다. ZIP 자체가 정상이어도 안쪽 문서가 손상될 수 있습니다.

정상 XLSX에서 workbook XML만 손상시킨 파일을 만들어 실제 multipart 업로드에 넣었습니다. 배송·반품·교환의 세 경로 모두 입력 오류 안내 대신 500을 반환했습니다. XML 파싱의 ParseError가 기존 변환 목록에서 빠져 있었기 때문입니다. 이 예외를 확인된 파일 입력 오류에 포함한 뒤 같은 파일이 400 안내로 이어지도록 보완했습니다.

검증은 응답 객체의 값만 비교하는 데서 멈추지 않았습니다. DRF의 JSON 렌더러까지 실행해 최종 응답이 만들어지는지 확인했고, 내부 조회 실패를 넣어 예외 원문이 응답에 없으면서 서버에는 traceback이 남는지도 확인했습니다.

변경은 11월 3일 main에 병합됐습니다. DB를 사용하지 않는 실제 업로드·렌더링 회귀는 통과했지만 DB 쓰기 통합과 운영 배포는 확인되지 않았습니다. 변경 파일의 포맷 검사는 통과했으며 전체 pre-commit은 공용 파일의 기존 Ruff 오류로 실패했습니다. 파일을 고칠 수 있는 실패와 서버를 조사해야 하는 실패를 나눈 결과까지 확인한 작업입니다.

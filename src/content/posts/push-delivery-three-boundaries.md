쇼핑몰에는 어제 출석했지만 오늘은 아직 출석하지 않은 고객에게 앱 알림을 보내는 기능이 있었습니다. 서버가 대상 고객을 골라 Braze에 발송을 요청하면, Braze에 설정된 메시지 흐름을 거쳐 고객의 기기로 푸시가 전달됩니다. 이 메시지 흐름을 Braze에서는 Canvas라고 부릅니다.

운영 환경에서는 알림이 왔지만 테스트 서버에서는 오지 않아 QA가 막혔습니다. 서버 발송은 성공으로 보였습니다. 제가 조사를 이어받았을 때는 “서버 DB의 푸시 토큰과 Braze의 토큰이 다른 것 같다”는 가설이 남아 있었습니다.

## 먼저 실제 발송 경로를 확인했다

연동 코드를 읽어보니 서버는 사용자 ID로 Canvas 실행을 요청할 뿐, DB의 토큰을 Braze에 보내지 않았습니다. 기기의 푸시 토큰은 앱에 들어 있는 Braze SDK가 직접 등록하고 있었습니다. 서버 DB와 Braze의 토큰을 비교하는 것만으로는 이 발송 경로가 어디서 끊겼는지 알 수 없었습니다.

Braze REST API로 대상 사용자 프로필을 조회했습니다. 사용자는 있었지만 연결된 디바이스와 토큰이 모두 없었습니다. 토큰이 서로 다른 것이 아니라, Braze가 보낼 기기를 찾을 수 없는 상태였습니다. 앱과 서버가 같은 워크스페이스를 사용하는지 확인했고, 로그인 이후 디바이스와 토큰이 생기는 것을 보고 앱의 등록 흐름을 따라갔습니다.

이후에는 성공 로그를 한 번 더 확인하기보다 다음 단계의 기록이 있는지 봤습니다.

```text
서버의 대상 선정 → Canvas 실행 요청 → 사용자 진입
    → 푸시 발송 단계 → 등록된 기기 → 실제 알림 수신
```

## 토큰이 있어도 알림을 허용한 것은 아니었다

iOS 토큰은 등록됐지만 알림은 활성화되어 있지 않았습니다. 기기 설정에도 앱의 알림 항목이 없었고, 앱에서 권한 요청을 호출하지 않은 것을 확인했습니다. 권한을 허용한 뒤 활성 토큰이 생겼습니다.

그런데 다시 시도해도 QA 알림이 오지 않았습니다. 이번에는 테스트 사용자가 오늘도 출석한 상태였습니다. “어제 출석, 오늘 미출석”이라는 발송 조건에서 정상적으로 제외된 것입니다. 권한 설정을 고친 뒤의 모든 미수신을 같은 문제로 보면 이 조건을 놓치기 쉬웠습니다.

## 발송 요청 성공과 Canvas 진입은 달랐다

대상 조건까지 맞춘 뒤에는 서버 기록과 Celery 작업 성공, Canvas ID를 확인했습니다. 그런데 Braze의 Canvas 진입 수는 0이었습니다. 해당 사용자가 이미 한 번 진입했고, Canvas 설정에서 재진입을 허용하지 않았기 때문입니다.

실행 요청 API는 성공을 반환했지만 사용자는 메시지 흐름에 들어가지 못했습니다. 재진입을 허용하자 진입·발송 기록이 생겼고, iOS 기기에서 실제 알림도 받았습니다. 이 지점에서야 요청 접수부터 수신까지 이어진 것을 확인할 수 있었습니다.

Android는 별도로 남았습니다. 워크스페이스에 세션은 들어오지만 대상 사용자 프로필에 디바이스가 없어, 로그인 시 SDK의 `changeUser`로 사용자를 연결하는 부분을 조사 대상으로 좁혀 모바일 팀에 전달했습니다. iOS 수신 확인을 근거로 Android도 해결됐다고 볼 수는 없었습니다. 두 환경 모두 같은 발송 API를 호출하더라도, 이후의 기기 연결 상태는 각각 확인해야 했습니다.

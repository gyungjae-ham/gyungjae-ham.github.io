테스트 서버에서 출석 리마인더 푸시가 오지 않았습니다. 서버 발송은 성공으로 보였고 운영 환경에서는 정상 수신됐습니다. 여러 차례 조사를 거친 뒤 제가 이어받았을 때도 '서버 DB 토큰과 Braze 토큰이 다른 것 같다'는 가설이 남아 있었습니다.

그 가설을 확인하기 전에 연동 코드를 먼저 읽었습니다. 서버는 사용자 ID로 Canvas를 실행할 뿐, DB의 푸시 토큰을 Braze로 보내지 않았습니다. Braze 토큰은 앱 SDK가 직접 등록했습니다. **비교하려던 두 토큰이 같은 발송 경로의 데이터가 아니었습니다.**

## 성공을 더 확인하지 않고 다음 단계의 흔적을 찾았다

서버 로그를 반복해서 보는 대신 Braze REST API로 대상 사용자 프로필을 조회했습니다. 처음에는 사용자는 존재하지만 디바이스와 토큰이 모두 없었습니다. '다른 토큰' 문제가 아니라 '수신할 기기가 연결되지 않은 상태'였습니다.

앱과 서버가 서로 다른 워크스페이스를 쓰는지도 확인했지만 같은 환경이었습니다. 로그인 이후 디바이스와 토큰이 생기는 것을 보고 앱 쪽으로 범위를 좁혔습니다.

조사 순서는 다음처럼 잡았습니다.

```text
서버 발송 대상 → 비동기 작업 → Canvas 진입
                              → 푸시 단계 → 사용자 디바이스
```

한 단계의 성공이 다음 단계의 성공까지 의미하지 않습니다. 각 단계에서 어떤 기록이 있어야 하는지 확인했습니다.

## 토큰이 생겨도 권한이 없었다

iOS 토큰은 등록됐지만 알림이 활성화되지 않은 상태였습니다. 기기 설정에도 앱의 알림 항목이 없었습니다. 앱이 알림 권한 요청을 호출하지 않은 것이 원인이었습니다.

권한을 허용한 뒤 활성 토큰을 확인했습니다. 그래도 QA 발송은 대상에서 제외됐습니다. 데이터를 보니 테스트 사용자가 당일에도 출석해서 '어제 출석했고 오늘은 미출석'이라는 조건을 만족하지 않았습니다. 이 부분은 서버의 오류가 아니라 정상 제외였습니다.

권한 문제와 대상 자격을 구분하지 않으면 설정을 고친 뒤에도 같은 문제라고 오해하기 쉽습니다.

## 자격까지 맞췄는데 Canvas 진입은 0이었다

대상 조건을 맞춘 뒤 서버 발송 기록과 Celery 성공을 확인했습니다. Canvas ID도 같았습니다. 그런데 Canvas 진입 수는 여전히 0이었습니다.

해당 사용자는 이미 Canvas에 진입한 이력이 있었고 재진입이 허용되지 않았습니다. trigger API는 성공을 반환했지만 사용자 진입은 건너뛰었습니다. 재진입을 허용한 뒤에는 진입·발송 기록과 사용자 수신 단계가 생겼고 iOS 기기에서 실제 알림을 받았습니다.

발송 API의 성공은 요청이 받아들여졌다는 뜻이었습니다. 제가 찾던 것은 최종 수신까지의 증거였습니다.

## iOS 해결을 Android 해결로 넓히지 않았다

Android에서는 워크스페이스에 세션이 들어오는데 대상 사용자 프로필에는 디바이스가 없었습니다. 로그인 시 SDK의 `changeUser` 연결 문제로 좁혀 모바일 팀에 전달했습니다. 이 기록에서 실제 도달을 확인한 것은 iOS이고 Android는 후속 조치 단계였습니다.

이번에는 한 원인을 고치면 끝나는 문제가 아니었습니다. 권한, 발송 자격, Canvas 재진입, 사용자·기기 연결이 겹쳐 있었습니다. 각 단계의 기록을 나눠 보면서 서버 코드를 불필요하게 바꾸지 않고 끊긴 지점을 찾아갈 수 있었습니다.

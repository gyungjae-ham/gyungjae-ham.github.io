쇼핑몰에서 어제 출석했지만 오늘은 아직 출석하지 않은 고객에게 알림을 보내는 기능을 확인하던 중, 운영 환경과 달리 테스트 서버에서는 푸시가 오지 않아 QA가 막혔습니다. 서버의 발송 요청은 성공으로 기록되고 있었습니다.

서버는 대상 고객을 고른 뒤 Braze의 메시지 흐름인 Canvas 실행을 요청합니다. Canvas에 들어간 고객에게 설정된 순서로 메시지가 발송되고 기기로 전달됩니다. 요청 접수와 실제 수신 사이에 여러 단계가 있어, 성공 로그가 어디까지의 성공인지부터 확인해야 했습니다.

## 서버 DB의 토큰을 보내는 구조가 아니었습니다

조사를 이어받았을 때 남아 있던 가설은 서버 DB와 Braze의 푸시 토큰이 다르다는 것이었습니다. 연동 코드를 읽어 보니 서버는 사용자 ID로 Canvas를 실행할 뿐 DB의 토큰을 보내지 않았습니다. 기기 토큰은 앱의 Braze SDK가 직접 등록하고 있었습니다.

REST API로 대상 프로필을 조회하니 사용자는 있지만 디바이스와 토큰이 모두 없었습니다. 토큰이 다른지 비교하기 전에 Braze가 보낼 기기 자체를 찾을 수 없는 상태였습니다. 앱과 서버의 워크스페이스를 확인하고, 로그인 후 디바이스와 토큰이 생기는 것을 보며 등록 흐름을 따라갔습니다.

```text
서버의 대상 선정 → Canvas 실행 요청 → 사용자 진입
  → 푸시 발송 단계 → 연결된 기기 → 알림 수신
```

각 단계의 기록이 있는지 확인하면서 어디서 멈추는지 좁혀 갔습니다.

## 토큰 등록 후에도 알림이 오지 않은 이유

iOS 토큰은 등록됐지만 알림이 활성화돼 있지 않았습니다. 기기 설정에도 앱의 알림 항목이 없었고 앱에서 권한 요청을 호출하지 않은 것을 확인했습니다. 권한을 허용한 뒤 활성 토큰이 생겼습니다.

다시 테스트했을 때에도 알림이 오지 않았는데, 이번에는 테스트 고객이 오늘도 출석한 상태였습니다. “어제 출석, 오늘 미출석” 조건에서 정상적으로 제외된 것입니다. 한 문제를 수정한 뒤에도 같은 증상이 보일 수 있어, 테스트 입력부터 다시 확인해야 했습니다.

## Canvas에 다시 들어갈 수 있는지 확인하기

대상 조건을 맞춘 뒤 서버 기록, Celery 성공, Canvas ID를 확인했습니다. 그런데 Braze의 Canvas 진입 수는 0이었습니다. 해당 사용자가 이미 한 번 들어갔고 재진입이 허용되지 않은 설정이었습니다.

실행 요청 API의 성공이 사용자 진입을 뜻하지는 않았습니다. 재진입을 허용하자 진입·발송 기록이 생겼고 iOS 기기에서 실제 알림도 받았습니다. 이때 요청 접수부터 수신까지 연결된 것을 확인했습니다.

Android는 조사 범위가 달랐습니다. 워크스페이스에 세션은 들어왔지만 대상 사용자 프로필에 디바이스가 없었습니다. 로그인 시 SDK의 `changeUser`로 사용자를 연결하는 부분을 조사 대상으로 좁혀 모바일 팀에 전달했습니다. iOS 수신을 확인한 것으로 두 플랫폼의 해결을 함께 판단하지는 않았습니다.

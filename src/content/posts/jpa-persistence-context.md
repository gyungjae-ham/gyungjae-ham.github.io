> 김영한님의 JPA 로드맵을 따라 학습하면서 정리한 노트입니다.

## 영속성 컨텍스트

영속성 컨텍스트는 관리 중인 엔티티의 상태와 동일성을 추적하는 범위입니다. `EntityManager`의 persist·find·remove 같은 작업을 통해 엔티티를 관리합니다. 메모리에서 관리 중이라는 사실만으로 DB에 commit된 것은 아닙니다.

## 엔티티의 생명주기

- **비영속 (new/transient)**: 영속성 컨텍스트와 무관한, 새로 생성된 객체 상태입니다.
- **영속 (managed)**: 영속성 컨텍스트에서 관리되는 상태입니다. `persist()`로 관리 대상이 될 수 있습니다. INSERT 시점은 ID 생성 전략과 flush 시점에 따라 달라지며, IDENTITY처럼 식별자 확보를 위해 일찍 INSERT가 필요한 경우도 있습니다.
- **준영속 (detached)**: 영속성 컨텍스트에서 분리된 상태로, `detach()`, `clear()`, `close()` 메서드로 전환됩니다.
- **삭제 (removed)**: `remove()` 메서드로 DB 삭제를 요청한 상태입니다.

## 영속성 컨텍스트의 주요 이점

- **1차 캐시**: 엔티티 타입과 식별자에 해당하는 인스턴스를 관리해 같은 엔티티의 반복 로딩을 줄일 수 있습니다. 모든 JPQL 결과를 캐싱한다는 뜻은 아닙니다.
- **동일성 보장**: 같은 영속성 컨텍스트에서 같은 타입·식별자의 managed 엔티티는 같은 인스턴스로 관리됩니다. DB 전체의 반복 읽기 격리 수준을 보장하는 기능은 아닙니다.
- **쓰기 지연**: 변경 SQL을 flush 시점까지 미룰 수 있습니다. JDBC 배치 실행 여부는 ID 전략·드라이버·배치 설정에 따라 달라집니다.
- **변경 감지**: 관리 중인 엔티티의 변경을 flush 때 감지하여 SQL에 반영하므로 필드 변경마다 명시적 UPDATE 메서드를 부를 필요는 없습니다.

## Flush (플러시)

영속성 컨텍스트의 변경사항을 데이터베이스에 동기화하는 작업입니다. 1차 캐시는 유지되며, 쓰기 지연 SQL 저장소의 쿼리들이 DB로 전송됩니다.

**발생 시점**

- `em.flush()` 직접 호출
- 트랜잭션 커밋
- AUTO 모드에서 쿼리 결과에 영향을 줄 변경이 있을 때, 필요한 쿼리 실행 전 동기화

**플러시 모드**

- `FlushModeType.AUTO` (기본값, 커밋·쿼리 실행 시)
- `FlushModeType.COMMIT` (커밋 시 동기화, 쿼리에 대한 미반영 변경의 영향은 보장되지 않음)

플러시는 영속성 컨텍스트를 비우는 작업이 아니라, 변경사항을 DB와 동기화하는 작업입니다.

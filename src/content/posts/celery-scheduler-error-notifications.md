새벽 한 시간 동안 서로 다른 비동기 작업의 오류가 운영 채널에 쌓였습니다. 메시지는 있었지만 어디서 실패했는지 알아보려면 작업 목록과 로그를 다시 찾아야 했습니다. API 오류는 Sentry로 바로 연결되는데, Celery와 Scheduler 오류는 여전히 별도의 문자열을 보내고 있었습니다.

제가 줄이려던 것은 알림을 보내는 코드보다 **알림을 받은 뒤 원인을 찾기까지의 이동**이었습니다. Slack에는 판단에 필요한 짧은 설명을 남기고, 자세한 예외는 Sentry 링크로 이어지게 했습니다.

## 작업마다 붙이면 다음 작업은 빠질 수 있다

기존 비동기 작업은 Celery 태스크 95개와 Scheduler 잡 30개 이상이었습니다. 각각에 데코레이터를 붙이면 명시적이지만, 새 작업을 추가할 때마다 적용 여부를 확인해야 합니다.

이미 Celery 실패 시그널과 Scheduler 이벤트 리스너가 있었으므로 그 후크에서 공통 알림을 만들었습니다. 태스크 본문을 일괄 수정하지 않아도 되고, 이후 작업에도 같은 방식이 적용됩니다.

대신 호출부만 읽으면 후크가 보이지 않습니다. 전역 처리라는 선택은 적용 누락을 줄이는 만큼 연결 위치를 문서에 남겨야 합니다.

## traceback을 모두 보내는 대신 찾아갈 곳을 넣었다

Slack 메시지에는 작업 식별 정보와 핵심 오류, Sentry 링크를 담았습니다. traceback 전체를 메시지에 붙이면 길이가 늘고 정작 지금 봐야 할 오류가 묻힙니다. API 모니터링에서 이미 사용하던 캡처·링크 생성 코드를 재사용했습니다.

Scheduler의 실행 오류와 예정 시각을 놓친 이벤트도 구분했습니다. 두 이벤트를 모두 같은 심각도의 메시지로 보내면 실행 실패와 스케줄 지연을 구별하기 어렵습니다. 처리한 핸들러에서는 일괄 담당자 멘션도 제거했습니다.

## 공통 코드를 import했더니 워커가 시작하지 못했다

알림 코드는 재사용했지만 연결 시점은 그대로 가져올 수 없었습니다. 시그널 모듈에서 공통 모니터링을 import하자 DRF와 인증 모듈을 거쳐 Django 모델까지 로드됐습니다. 앱 레지스트리가 준비되기 전이어서 `AppRegistryNotReady`가 발생했습니다.

패키지의 `__init__.py`에서 시그널을 불러오던 연결을 `AppConfig.ready()`로 옮겼습니다. 함수 내부에 import를 흩뿌려 부팅을 우연히 통과시키는 대신, Django 초기화 이후에 연결하도록 시점을 명시했습니다.

Celery 내부 오류에서는 `task.request`가 아직 준비되지 않을 수 있어 시그널이 전달한 request 정보를 우선 사용했습니다. 오류를 알리는 코드가 같은 오류 상황에서 다시 실패하지 않도록 한 보강입니다.

## 알림 개선과 장애 해결 시간은 구분했다

신규 단위·통합 테스트 40건을 추가했고 기존 API 알림 경로는 유지했습니다. 운영 경험상 로그를 찾아다니던 동선이 링크 한 번으로 짧아졌습니다. 다만 회상에 기반한 시간을 장애 해결 시간의 개선율로 계산하지는 않았습니다.

링크로 예외에 도착하는 것과 실제 원인을 해결하는 것은 다릅니다. 이번 변경의 결과는 알림에서 조사를 시작할 수 있게 된 것입니다. Sentry 이벤트가 저장되지 않아 링크가 의미 없어지는 경우의 fallback은 후속으로 남았습니다.

> 비동기 작업이 실패하면 Slack 알림을 받은 뒤 다시 로그를 찾아야 했습니다. 알림에는 작업과 에러 요약을, 상세 추적에는 Sentry 링크를 두어 조사 경로를 통일했습니다.

## 알림은 도착했는데 어디서 실패했는지 몰랐다

API 오류 알림은 정리되어 있었지만 Celery와 Scheduler는 서로 다른 문자열을 보냈습니다. 메시지를 읽고 관리자 화면이나 CloudWatch에서 작업을 다시 찾는 순서였습니다. 같은 운영자가 처리하는 오류인데 진입점마다 조사 방식이 달랐습니다.

모든 알림에 담당자를 자동 멘션하는 것도 문제였습니다. 일시적인 외부 API 실패와 즉시 대응이 필요한 장애가 같은 무게로 도착했습니다. 메시지의 모양을 맞추는 것과, 사람을 언제 호출할지 정하는 것을 함께 정리해야 했습니다.

## 태스크마다 데코레이터를 붙이지 않았다

기존 Celery 실패 시그널과 APScheduler 리스너를 수정했습니다. 각 작업 함수에 데코레이터를 추가하는 방식은 호출 위치가 명시적이지만, 기존 작업 전체를 수정해야 하고 신규 작업에서 부착을 빠뜨릴 수 있습니다. 이미 존재하는 공통 후크에서 처리하는 편이 이번 범위에 맞았습니다.

Slack에는 작업 식별 정보와 핵심 에러 메시지를 넣고, 전체 traceback은 Sentry로 연결했습니다. 링크를 만들지 못할 때 어떻게 조사할지는 별도 운영 과제로 남습니다. 알림 본문을 짧게 만든다고 오류 정보의 보존까지 해결되는 것은 아닙니다.

Scheduler의 실행 실패와 실행 시각을 놓친 이벤트도 별도 핸들러로 나눴습니다. 실행되지 않은 작업과 실행하다 실패한 작업은 대응 방법이 다르기 때문입니다. 모든 알림에 붙던 자동 멘션은 이 작업이 다룬 핸들러에서 제거했습니다.

## 공통 함수를 import하다 부팅이 깨졌다

API 쪽 모니터링 모듈을 재사용하면서 Django 모델까지 이어지는 import 체인이 열렸습니다. Celery 시그널을 패키지 import 시점에 등록하니 앱 레지스트리가 준비되기 전에 모델을 읽어 `AppRegistryNotReady`가 발생했습니다.

시그널 등록을 `AppConfig.ready()`로 옮겨 초기화 순서를 맞췄습니다. 함수 안에서 import를 숨기는 우회보다, 언제 등록해야 하는지 명시하는 쪽을 택했습니다. 공통 함수의 기능뿐 아니라 import 부수 효과도 재사용 비용에 포함됩니다.

또한 내부 오류 시그널에서는 평소와 같은 request 객체가 준비되지 않을 수 있었습니다. 시그널 인자로 전달된 request를 우선 읽고, dict와 객체 형태를 모두 처리하도록 보완했습니다.

## 줄어든 것은 조사 경로의 단계였다

작업 당시 테스트 기록은 메시지 형식, 링크 생성, 실패 이벤트 분리를 확인합니다. 원본에는 조사 시간이 크게 줄었다는 운영자 회상도 있지만, 동일 조건의 시간 측정은 아닙니다. 이를 정밀한 개선율로 환산하지 않았습니다.

확실한 변화는 비동기 오류도 API 오류와 같은 형식으로 읽을 수 있고, 상세 추적으로 넘어가는 링크가 생겼다는 점입니다. 글로벌 후크는 새 작업에도 적용되므로, 팀이 그 존재와 멘션 정책을 문서에서 쉽게 찾을 수 있게 하는 것이 후속 운영의 조건입니다.

상품 이미지 처리나 결제 관련 확인처럼, 사용자 요청과 별개로 백그라운드에서 실행되는 작업이 있습니다. 서버에서는 Celery로 이런 작업을 처리하고, APScheduler로 정해진 시각에 실행할 작업을 관리하고 있었습니다. 실패하면 운영 Slack 채널로 알림을 보냈습니다.

어느 날 새벽 한 시간 동안 서로 다른 작업의 오류가 연달아 올라왔습니다. 오류 문자열은 있었지만 발생 위치를 찾으려면 작업 목록과 로그를 다시 뒤져야 했습니다. 반면 웹 API의 오류 알림에는 Sentry 링크가 있어 예외 기록으로 바로 이동할 수 있었습니다. 백그라운드 작업에도 이 조사 동선을 연결하는 것이 이번 작업의 출발점이었습니다.

## 새 작업에도 빠짐없이 적용하려면

기존 Celery 태스크는 95개, Scheduler 작업은 30개 이상이었습니다. 각 함수에 알림용 데코레이터를 붙일 수도 있지만, 이후 추가할 작업에도 매번 같은 처리가 필요합니다. 이미 마련된 공통 실패 통지를 쓰는 편이 적용 누락을 줄이기 좋았습니다.

Celery가 작업 실패를 알리는 시그널과 Scheduler의 이벤트 리스너에서 공통 알림 함수를 호출하도록 했습니다. 작업 본문은 그대로 두고, 실패가 모이는 위치를 수정했습니다. 호출부에 알림 코드가 직접 보이지 않는 만큼, 연결 위치는 문서에도 남겼습니다.

Slack에는 작업을 구별할 정보, 핵심 오류, Sentry 링크만 담았습니다. 긴 traceback은 Sentry에서 읽게 했습니다. Scheduler가 작업을 실행하다 실패한 경우와 예정된 실행 시각을 놓친 경우도 구분했습니다. 후자는 실행 중 예외와 원인이 다를 수 있어 같은 메시지로 취급하지 않았고, 처리한 알림의 일괄 담당자 멘션도 제거했습니다.

## 알림 코드를 불러오는 시점에서 워커가 멈췄다

웹 API에서 쓰던 캡처·링크 생성 코드를 재사용하자 새로운 문제가 생겼습니다. 시그널 모듈이 공통 코드를 import하는 과정에서 DRF, 인증 모듈, Django 모델까지 연달아 불러왔습니다. 아직 Django가 앱을 초기화하기 전이어서 `AppRegistryNotReady`가 발생했습니다. 실패 알림을 개선하려던 변경 때문에 작업을 실행하는 워커가 시작하지 못한 것입니다.

시그널을 패키지의 `__init__.py`에서 연결하던 코드를 `AppConfig.ready()`로 옮겼습니다. Django 앱 레지스트리가 준비된 뒤에 공통 모니터링 코드를 불러오도록 순서를 맞췄습니다. import 위치만 여기저기 늦추기보다, 어느 초기화 단계에서 연결해야 하는지 명확히 했습니다.

오류 상황에서는 평소 존재하던 정보도 없을 수 있었습니다. Celery 내부 오류에서 `task.request`가 준비되지 않은 경우를 위해, 실패 시그널이 전달한 request 정보를 우선 사용했습니다. 알림을 만드는 코드가 다시 예외를 내지 않도록 확인한 부분입니다.

신규 단위·통합 테스트 40건을 추가하고 기존 API 알림 경로는 유지했습니다. 변경 후에는 Slack 메시지에서 Sentry 예외 기록으로 바로 이동할 수 있게 됐습니다. 다만 Sentry 이벤트 저장 자체가 실패하면 링크만으로는 조사할 수 없습니다. 이 경우에 남길 대체 정보는 후속 과제로 남겼습니다.

어느 날 새벽 한 시간 동안 서로 다른 백그라운드 작업의 오류 알림이 연달아 올라왔습니다. 오류 문자열은 있었지만 어느 코드에서 발생했는지 보려면 작업 목록과 로그를 다시 찾아야 했습니다. 웹 API 알림에는 Sentry 링크가 있어 예외 기록으로 바로 이동할 수 있었는데, 백그라운드 작업에는 그 연결이 없었습니다.

서버는 이미지 처리나 결제 관련 확인을 Celery로 실행하고, 정해진 시각에 동작할 작업은 APScheduler로 관리했습니다. 두 경로의 실패 알림에도 Sentry 기록을 연결하기로 했습니다.

## 작업 함수마다 알림 코드를 넣지 않으려면

Celery 태스크는 95개, Scheduler 작업은 30개 이상이었습니다. 함수마다 데코레이터를 붙이면 기존 작업을 모두 고쳐야 하고 새 작업을 추가할 때도 빠뜨릴 수 있습니다. 대신 실패가 모이는 지점에 공통 함수를 연결했습니다.

Celery는 작업 실패 시그널에서, Scheduler는 이벤트 리스너에서 알림 함수를 호출하도록 했습니다. Slack에는 작업을 구별할 정보와 핵심 오류, Sentry 링크를 담고 긴 traceback은 Sentry에서 읽도록 했습니다. 작업 본문만 보고는 알림 연결을 알기 어려우므로 시그널과 리스너의 연결 위치는 문서에 남겼습니다.

Scheduler에서는 실행 중 예외와 실행 시각을 놓친 경우도 구분했습니다. 예를 들어 실행한 함수가 DB 오류를 낸 것과 서버가 늦게 시작해 예정 시각을 넘긴 것은 조사할 곳이 다릅니다. 두 상황을 같은 오류 문구로 보내지 않게 했고, 처리한 알림의 일괄 담당자 멘션도 제거했습니다.

## 공통 코드를 가져오자 워커가 시작하지 못했습니다

웹 API에서 쓰던 예외 캡처와 링크 생성 코드를 재사용했는데 `AppRegistryNotReady`가 발생했습니다. 작업 실패 후가 아니라 워커 초기화 과정에서 난 오류였습니다.

시그널 모듈이 공통 코드를 import하면서 DRF, 인증 모듈, Django 모델까지 차례로 불러왔습니다. 이 시점에는 Django 앱 초기화가 끝나지 않았습니다. 패키지의 `__init__.py`에서 시그널을 연결하던 코드를 `AppConfig.ready()`로 옮겨 앱 레지스트리가 준비된 뒤 모니터링 코드를 불러오도록 했습니다.

실패 상황의 입력도 다시 확인했습니다. Celery 내부 오류에서는 평소 쓰던 `task.request`가 준비되지 않을 수 있어, 실패 시그널이 전달한 request 정보를 우선 사용했습니다. 오류를 알리는 코드가 필요한 정보 하나 때문에 다시 실패하지 않게 하기 위한 처리입니다.

새 단위·통합 테스트 40건을 추가하면서 기존 API 알림도 유지되는지 확인했습니다. 변경 후 Slack 메시지에서 해당 Sentry 예외로 바로 이동할 수 있게 됐습니다. Sentry 이벤트 저장 자체가 실패하는 경우에는 이 링크만으로 조사할 수 없으므로, 그때 남길 대체 정보는 후속 과제로 남겼습니다.

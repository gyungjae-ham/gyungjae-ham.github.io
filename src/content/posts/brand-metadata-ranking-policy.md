상품 랭킹을 자동으로 계산하더라도 운영자가 특정 브랜드의 노출을 조정해야 하는 경우가 있습니다. 이번 요구사항은 두 가지였습니다. 어떤 브랜드는 추천에서 빼고, 어떤 브랜드는 계속 보여주되 순위를 낮추는 것입니다.

운영자가 브랜드에 분류를 지정하면 해당 정책이 추천과 랭킹에 적용되도록 만들었습니다. 같은 설정 화면에서 관리하지만 두 정책을 같은 위치에서 처리할 수는 없었습니다. 제외할 상품은 후보에서 빠져야 하고, 순위만 낮출 상품은 후보에 남아 있어야 하기 때문입니다.

## 제외 조건을 상품 조회에 넣기

처음에는 제외할 브랜드 ID를 먼저 조회한 뒤 상품 쿼리에 `brand_id__in` 조건을 넣었습니다. 코드를 읽기는 쉬웠지만 기존 단일 집계 쿼리 테스트가 실패했습니다. 브랜드 목록을 가져오는 조회가 하나 추가됐습니다.

별도로 ID 목록을 읽는 대신, 후보 조회와 주문 집계 안에서 브랜드의 분류 관계를 검사하도록 바꿨습니다. 한 SQL 안에서 제외 여부를 판단하므로 기존 집계의 조회 횟수는 유지할 수 있었습니다. 관계를 검사하는 SQL 비용 자체가 없어지는 것은 아니어서 쿼리 횟수와는 구분해야 합니다.

## 순위를 낮출 때 어떤 값을 바꿀까

랭킹에는 별도 점수 컬럼이 없었고, 첫 정렬 기준으로 중복을 제거한 구매자 수를 사용하고 있었습니다. 이 값을 보정하려면 먼저 어디에 쓰이는지 확인해야 했습니다. 고객에게 “20명이 구매한 상품”이라고 표시하는 값이라면 순위 조정을 위해 10으로 바꿀 수는 없기 때문입니다.

저장과 응답 경로를 확인해 보니 이 값은 내부 정렬과 저장에만 쓰였고 상품 카드에는 나오지 않았습니다. 관리 대상 브랜드는 이 첫 정렬값에 감점을 적용하고, 동점일 때의 다음 정렬 기준은 유지했습니다.

예를 들어 실제 구매자가 20명인 상품 A와 15명인 상품 B가 있다고 해보겠습니다. A의 내부 정렬값을 10으로 보정하면 B, A 순서가 됩니다. 실제 구매자가 10명이 됐다는 뜻은 아닙니다. 이 숫자는 실제 감점식이 아니라 원본 집계와 정렬값의 차이를 설명하기 위한 예시입니다.

현재 필드를 이런 용도로 사용한다는 사실은 이후 기능에서도 알아야 합니다. 같은 값을 구매자 수로 표시하는 기능이 생긴다면 원본 집계와 보정 점수를 분리해야 합니다.

제외 정책은 쿼리에서, 감점은 집계 결과를 처리하는 서비스에서 적용했습니다. 두 분류가 함께 붙은 브랜드는 후보에서 먼저 제외되므로 감점 단계까지 들어오지 않습니다. 브랜드에는 여러 분류를 허용하되 종류는 코드의 선택값으로 제한했습니다. 운영자가 새 이름을 입력하는 것만으로 서버의 처리 방식까지 생기는 것은 아니므로, 새 정책은 처리 코드와 함께 추가하도록 했습니다.

모델·집계·감점 관련 테스트 55건을 통과했고 단일 집계 쿼리도 유지했습니다. 확인한 범위는 설정에 따른 제외와 순위 계산이며, 실제 브랜드 지정 이후 노출이나 구매 전환의 변화까지 측정한 작업은 아닙니다.

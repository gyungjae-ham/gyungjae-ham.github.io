자동 추천과 상품 랭킹에 운영자가 브랜드 단위로 개입할 수 있게 하는 작업이었습니다. 어떤 브랜드는 추천 후보에서 완전히 제외하고, 어떤 브랜드는 계속 보여주되 순위를 낮춰야 했습니다. 운영자가 브랜드에 분류를 지정하면 두 노출 경로에 해당 정책이 적용되는 방식입니다.

같은 브랜드 설정을 읽더라도 “목록에서 빼기”와 “순위 낮추기”는 처리할 위치가 달랐습니다. 특히 랭킹에는 별도의 점수 컬럼이 없어, 어떤 값을 바꿔도 되는지부터 확인해야 했습니다.

## 제외 목록을 먼저 읽자 쿼리가 하나 늘었다

처음에는 제외 대상 브랜드 ID를 조회한 뒤 상품 쿼리에 `brand_id__in` 조건을 넣었습니다. 이해하기 쉬운 방식이지만 기존 단일 집계 쿼리 테스트가 실패했습니다. 브랜드 목록을 가져오는 조회가 추가됐기 때문입니다.

후보 조회와 주문 집계 안에서 브랜드의 분류 관계를 조건으로 검사하도록 바꿨습니다. 미리 ID 목록을 가져오지 않고 한 SQL 안에서 제외 여부를 판단합니다. 관계 조건 자체의 비용은 남지만 기존 집계의 조회 횟수는 유지할 수 있었습니다.

## 실제 구매자 수를 화면에 보여주는지 확인했다

랭킹의 첫 번째 정렬 기준은 중복을 제거한 구매자 수였습니다. 이 숫자를 낮춰 순위를 바꾸기 전에 저장과 응답 경로를 따라갔습니다. 고객에게 실제 구매자 수를 보여주는 값이라면, 순위 조정을 위해 숫자를 바꾸는 것은 다른 문제가 됩니다.

해당 값은 내부 정렬과 저장에 사용되고 상품 카드에는 노출되지 않았습니다. 관리 대상 브랜드에는 첫 정렬값에 감점을 적용하고, 값이 같을 때 사용하는 다음 정렬 기준은 유지했습니다. 후보에서 완전히 뺄 브랜드는 쿼리에서 제외하고, 남겨 둘 브랜드의 감점은 집계 결과를 처리하는 서비스에서 적용했습니다.

예를 들어 같은 브랜드 분류가 붙어도 제외 대상이면 순위를 계산할 후보에 들어가지 않습니다. 감점 대상이면 후보로 남아서 다른 상품과 다시 순위를 비교합니다. 두 정책을 하나의 필터로 처리하지 않은 이유입니다.

브랜드에 붙일 분류는 여러 개를 허용하되 종류는 코드의 선택값으로 제한했습니다. 운영자가 새로운 이름을 입력해도 서버가 그에 맞는 정렬 동작을 저절로 알 수는 없기 때문입니다. 새로운 정책은 분류와 처리 코드를 함께 추가하도록 했습니다.

모델·집계·감점 관련 테스트 55건을 통과했고 단일 집계 쿼리도 유지했습니다. 확인한 것은 분류에 따른 제외와 순위 계산입니다. 실제 브랜드 지정 후의 노출 변화나 구매 전환 효과는 별도의 관측이 필요합니다.

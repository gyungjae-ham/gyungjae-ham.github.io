최근 본 상품 목록을 저장할 때는 같은 사용자와 상품의 기록을 중복으로 만들지 않습니다. 기존 기록을 조회하고 없는 항목만 한꺼번에 INSERT하는 구조였습니다. 그런데 조회와 저장 사이에 다른 요청이 같은 상품을 먼저 저장하면 DB의 중복키 제약에 걸려 500 응답이 발생했습니다.

예를 들어 두 요청이 거의 동시에 같은 상품을 조회하면 둘 다 “기록 없음”을 볼 수 있습니다. 각 요청 안에서 입력 중복을 제거해도 이 경쟁은 막히지 않습니다. 정상 일괄 저장은 유지하면서 이 경우만 복구하는 수정을 만들었습니다. 당시 리뷰 중 변경으로, 운영 적용 결과는 아직 없습니다.

## 정상 요청의 일괄 저장은 유지했다

모든 항목을 처음부터 개별 조회·생성하면 충돌을 다루기는 쉽지만 정상 요청의 비용도 늘어납니다. 기존 `bulk_create`와 배치 크기를 유지하고, 특정 중복키가 발생했을 때만 항목별 생성·갱신으로 복구하도록 했습니다. 다른 요청이 먼저 만든 행에는 최근 조회 시각을 반영합니다.

그렇다고 모든 `IntegrityError`를 복구 대상으로 삼지는 않았습니다. 이 예외에는 중복뿐 아니라 외래키 등 다른 제약 위반도 포함됩니다. MySQL 중복키 코드와 사용자·상품의 제약이 일치하는 경우만 처리하고, 나머지 오류는 그대로 전파했습니다. 처음 조회했을 때부터 모든 상품이 이미 존재하는 요청의 기존 오류 응답도 유지했습니다.

## 복구는 실패한 트랜잭션을 벗어난 뒤에 했다

DB 오류가 발생한 트랜잭션 안에서 쿼리를 더 실행하면 복구 쿼리도 실패할 수 있습니다. 일괄 저장이 실패하면 먼저 롤백하고, 별도 트랜잭션에서 전체 입력을 복구하도록 경계를 나눴습니다.

```text
일괄 저장 → 성공하면 기존 응답
    ↓ 실패·롤백
해당 중복키인가? → 맞으면 별도 트랜잭션으로 복구
                → 다른 오류면 그대로 전파
```

배치 크기가 100이어서 101개 입력도 확인했습니다. 두 번째 배치에서 충돌하면 앞 배치가 포함된 전체 입력을 어떻게 복구하는지 봐야 합니다. 저장 개수만 확인하지 않고 응답 순서와 최신 시각도 함께 검증했습니다.

실제 MySQL의 별도 연결로 수정 전 경쟁 실패를 재현했고, 수정 후 경합·회귀 테스트 10건이 통과했습니다. 같은 사용자·상품의 행이 하나만 남는지, 101개 입력을 복구하는지, 외래키 오류는 숨기지 않는지를 확인했습니다. 운영 워커에서의 재발률은 이후 관측할 항목입니다.

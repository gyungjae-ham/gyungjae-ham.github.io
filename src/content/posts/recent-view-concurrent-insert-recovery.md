최근 본 상품을 저장할 때는 같은 사용자와 상품의 기록을 하나만 남깁니다. 기존 코드는 저장된 기록을 먼저 조회하고 없는 항목만 `bulk_create`로 넣었습니다. 그런데 거의 동시에 같은 상품을 저장하는 요청이 들어오면 중복키 오류로 500 응답이 발생했습니다.

두 요청이 모두 “기록 없음”을 확인한 뒤 첫 번째 요청이 먼저 INSERT할 수 있기 때문입니다. 두 번째는 자기 조회 결과대로 저장하지만 그사이 다른 요청이 만든 행과 충돌합니다. 요청 안의 중복 상품을 제거하는 것만으로는 막을 수 없는 상황입니다.

## 충돌한 경우에만 개별 복구하기

처음부터 모든 항목을 개별 조회·생성하면 정상 요청의 비용도 늘어납니다. 기존 일괄 저장과 배치 크기를 유지하고, 사용자·상품의 특정 중복키가 발생했을 때만 항목별 생성·갱신으로 복구하도록 했습니다. 다른 요청이 먼저 만든 행에는 최신 조회 시각을 반영합니다.

모든 `IntegrityError`를 같은 방식으로 처리하지는 않았습니다. 이 예외에는 외래키 등 다른 제약 위반도 포함됩니다. MySQL 중복키 코드와 사용자·상품 제약이 모두 맞는 경우만 복구하고 나머지는 그대로 전파했습니다. 최초 조회부터 모든 상품이 이미 존재하는 요청에 대한 기존 오류 응답도 유지했습니다.

## 실패한 트랜잭션 밖에서 다시 처리하기

DB 오류가 난 트랜잭션 안에서 복구 쿼리를 실행하면 그 쿼리도 실패할 수 있습니다. 일괄 저장을 먼저 롤백하고 별도 트랜잭션에서 전체 입력을 복구하도록 나눴습니다.

```text
일괄 저장 성공 → 기존 응답
일괄 저장 실패 → 롤백 → 해당 중복키인지 검사
                      → 맞으면 새 트랜잭션에서 복구
                      → 다른 오류는 그대로 전파
```

배치 크기가 100이어서 입력 101개도 확인했습니다. 두 번째 배치에서 충돌했을 때 첫 번째 배치의 항목까지 포함해 전체 입력을 복구해야 합니다. 단순 저장 개수 외에 응답 순서와 최신 시각도 검사했습니다.

실제 MySQL의 별도 연결로 수정 전 경합을 재현했고, 수정 후 경합·회귀 테스트 10건이 통과했습니다. 사용자·상품별 행이 하나만 남는지, 101개 입력이 복구되는지, 외래키 오류가 숨겨지지 않는지를 확인했습니다.

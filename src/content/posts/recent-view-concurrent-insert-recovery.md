최근 본 상품을 조회했을 때는 기록이 없었습니다. 새 행을 저장하기 전 다른 요청이 같은 사용자·상품을 먼저 저장했고 중복키 오류가 났습니다. 요청 안에서 중복을 제거했어도 요청 사이의 경쟁은 남았습니다.

저는 정상 `bulk_create` 경로를 유지하면서 이 충돌만 별도로 복구했습니다. 모든 무결성 오류를 성공으로 바꿔 500을 줄이는 방식은 택하지 않았습니다. 당시 변경은 리뷰 중이며 운영 적용 결과는 아직 없습니다.

## 대부분의 요청에 복구 비용을 얹지 않았다

모든 항목을 처음부터 개별 조회·생성하면 중복을 다루기는 쉽지만 정상 배치의 비용이 늘어납니다. 기존 bulk 저장과 배치 크기는 유지했습니다. 경합이 발생한 예외 경로에서만 항목별 생성·갱신을 수행합니다.

이 경로는 더 비쌉니다. 대신 정상 처리 비용을 바꾸지 않고 다른 요청이 만든 행에는 최신 조회 시각을 반영할 수 있습니다.

## IntegrityError라는 이름만 보고 복구하지 않았다

무결성 오류에는 중복키뿐 아니라 외래키와 다른 제약 실패도 있습니다. 모든 오류를 무시하면 저장하지 못한 데이터까지 성공처럼 응답할 수 있습니다.

MySQL 중복키 코드와 사용자·상품 제약이 일치할 때만 복구했습니다. 다른 무결성 오류는 그대로 전파하고, 모두 이미 존재하는 상품인 경우의 기존 오류 응답도 유지했습니다.

이 분기는 관측한 경쟁을 해결하려는 것입니다. 저장 오류 전부를 정상 상태로 해석하는 정책은 아닙니다.

## 실패한 트랜잭션 안에서 복구하지 않았다

예외가 난 트랜잭션에 쿼리를 더 보내면 복구도 실패할 수 있습니다. 먼저 실패한 변경을 롤백한 뒤 별도 트랜잭션으로 복구했습니다.

아래는 트랜잭션 경계를 설명한 의사코드입니다.

```text
bulk 저장 트랜잭션 실행
  ├─ 성공: 기존 응답
  └─ 실패 후 롤백
       ├─ 특정 중복키: 별도 트랜잭션으로 복구
       └─ 다른 무결성 오류: 전파
```

## 100개를 넘는 입력에서 앞 배치도 확인했다

배치 크기가 100이라 101개 입력을 검증했습니다. 두 번째 배치에서 충돌해도 전체 입력을 기준으로 복구하고 응답 순서와 최신 시각을 유지해야 했습니다. 저장 개수만 보면 앞 배치 일부 유실이나 순서 변경을 놓칠 수 있습니다.

실제 MySQL의 별도 연결로 수정 전 경쟁 실패를 재현했고, 수정 후 경합·회귀 10건이 통과했습니다. 단일 행 유지, 성공 응답, 101개 복구, 외래키 오류 전파를 확인했습니다. 운영 worker와 재발률은 아직 확인하지 않았습니다.

이번에는 예외를 잡는 코드보다 어떤 예외를 복구해도 되는지에 기준을 뒀습니다. 정상 저장과 복구의 응답 계약을 같이 검증해야 했습니다.

> 없는 기록을 확인한 뒤 저장하는 사이 다른 요청이 먼저 같은 행을 만들었습니다. 정상 bulk 경로는 유지하고, 확인한 중복키 충돌만 롤백 이후 별도 경로로 복구했습니다.

## 조회와 INSERT 사이에는 다른 요청이 들어온다

최근 본 상품은 사용자와 상품 조합으로 기록됩니다. 기존 기록을 조회해 새 항목을 골라도 INSERT까지 그 상태가 유지되지는 않습니다. 두 요청이 모두 없다고 판단하면 한쪽은 MySQL 중복키 오류를 받을 수 있습니다.

이 기록은 실제 MySQL 연결을 분리해 경합을 재현한 PR 자료에 근거합니다. 원본 확인 시점에는 리뷰 중이며 병합·운영 적용이 끝난 상태는 아닙니다. 운영 재발률을 줄였다고 표현하지 않았습니다.

## 모든 IntegrityError를 무시하지 않았다

중복키를 피하려 모든 무결성 오류를 무시하면 잘못된 외래키나 다른 제약 실패까지 숨길 수 있습니다. 오류 코드와 충돌한 사용자·상품 제약이 맞는 경우에만 복구하도록 범위를 제한했습니다.

정상 경로는 기존 `bulk_create`와 배치 크기를 유지했습니다. 경합이 없는 대부분의 요청에 항목별 조회 비용을 추가하지 않고 예외 경로에서만 생성·갱신을 수행합니다. 이 경로는 더 비싸지만 실패의 의미를 잃지 않는 선택입니다.

## 복구는 실패한 트랜잭션 밖에서 한다

무결성 오류 이후에는 실패한 변경을 롤백하고 별도 트랜잭션에서 복구했습니다. 깨진 트랜잭션 안에서 추가 쿼리를 시도하면 복구 자체가 다시 실패할 수 있습니다. 이미 다른 요청이 만든 기록은 새 조회 시각을 반영하도록 처리했습니다.

입력이 배치 경계를 넘는 경우도 확인했습니다. 두 번째 배치에서 충돌하면 앞서 처리한 항목만 남기거나 응답 순서가 바뀌지 않도록 전체 입력을 기준으로 복구합니다. 저장 개수만 확인하지 않고 순서와 최신 시각까지 검증한 이유입니다.

## 정상 계약도 예외 처리와 함께 유지했다

원본에는 변경 전 경합 실패의 재현과 변경 후 단일 행 유지, 성공 응답, 배치 경계 복구, 외래키 오류 전파 테스트가 남아 있습니다. 모두 이미 존재하는 상품인 경우의 기존 오류 응답도 유지했습니다.

이번 작성에서 해당 테스트를 다시 실행하지 않았고 실제 worker나 운영 경합도 검증하지 않았습니다. 확인한 구현 결과는 특정 충돌을 명시적으로 복구하면서 다른 데이터 오류를 숨기지 않게 했다는 점입니다. 예외를 잡는 범위와 정상 경로의 계약을 같은 검증으로 남겨야 했습니다.

쇼핑몰 판매자는 관리 화면이나 외부 연동 API로 상품을 등록합니다. 화장품에는 소비자가 확인할 품목과 고시 내용이 필요하고, 지정된 관리 카테고리의 신규 상품은 사람이 검수하도록 하는 서비스 정책도 있었습니다. 그런데 품목만 화장품으로 선택하고 내용을 비워 저장할 수 있었고, 외부 API는 검수를 생략해 바로 승인했습니다.

11월 4~5일에는 저장되는 내용의 검증과 검수 전 공개 조회를 함께 보완했습니다. 두 변경은 아직 리뷰 중입니다. 이 글에서 다루는 것은 서비스의 입력·검수 정책 구현이며 법적 적합성을 판정한 결과는 아닙니다.

## 요청에 없는 값도 최종 상품에는 남습니다

예를 들어 기존 상품의 설명만 수정한다고 해보겠습니다. 요청에서 고시를 생략해도 저장된 고시는 남습니다. 반면 고시 내용을 명시적으로 비우면 저장 결과가 달라집니다. 요청에 필드가 있는지만 검사하면 앞의 정상 수정을 막거나 뒤의 빈 값을 놓칠 수 있습니다.

그래서 최종 관리 카테고리와 실제로 저장할 고시를 기존 트랜잭션 안에서 검사하도록 연결했습니다. 대상 카테고리에서는 먼저 품목을 확인하고, 운영 폼의 필수 내용이 누락·null·빈 문자열·공백인지 확인합니다. 실패하면 상품과 고시, 카테고리 변경을 함께 롤백합니다. 중간 저장 뒤 오류 응답만 보내 상품 일부가 바뀐 채 남는 상황을 막기 위한 순서입니다.

외부 연동 상품은 관리 화면으로 수정해도 원래 연동 데이터가 고시의 원천인 경우가 있습니다. 이때 별도 입력으로 원본 검증을 우회하지 않도록 원천을 구분했습니다. 고시를 생략하는 수정은 기존 내용을 유지하고, 해당 경로에서 변경하지 않는 품목 매핑도 함께 보호했습니다.

## 저장 검증과 상세 표시가 같은 번호를 해석해야 합니다

연동 데이터는 항목 번호와 값을 배열로 전달합니다. 배열 위치만 믿지 않고 번호로 내용을 대응시켰지만, 저장을 통과한 번호가 상세 화면에서는 다르게 해석될 수 있었습니다. 추가 번호나 앞자리 0을 허용하면 필수 내용을 검사했는데도 실제 상세에서 일부 항목만 표시되는 문제가 남았습니다.

번호와 값 배열의 길이, 중복 여부, 허용 번호 표현을 함께 제한했습니다. 정상 입력은 상세 표시 로직에서 필수 항목이 모두 나오는지 확인했습니다. 빈 품목을 수정에 보낸 경우에도 요청값만 보고 거절하지 않고, 기존 저장 규칙이 적용된 뒤의 최종 품목으로 검증하도록 보완했습니다.

초기 변경의 로컬 DB 통합 회귀는 통과했습니다. 그러나 후속 번호·매핑 보완 당시에는 테스트 DB 준비 문제로 추가 통합 회귀를 재실행하지 못했습니다. 이후 검수 변경을 포함한 확대 회귀에서 관련 동작을 확인했으므로, 초기 통과 기록을 모든 후속 변경의 단독 통합 검증으로 확대하지는 않습니다.

## 검수 중으로 저장해도 상세 URL은 열렸습니다

외부 API 신규 등록에서는 기존 카테고리 저장 계획을 재사용해 검수 대상을 결정했습니다. 상품을 한꺼번에 INSERT하기 전에 대상의 승인 상태를 false로 정하고, 그 값에 맞춰 검수 중 정보를 생성합니다. 고시 검증이 실패하면 검수 정보도 같은 트랜잭션에서 롤백합니다.

하지만 이 상태를 저장하는 것만으로 공개가 막히지는 않았습니다. 실제로 검수 중 상품을 등록한 뒤 회원·비회원 공개 상세를 조회하면 200을 반환하는 문제를 먼저 재현했습니다. 목록에 보이지 않는 것과 상세 주소로 조회할 수 없는 것은 다른 조건이었습니다.

공개 조회에서는 대상 카테고리이면서 미승인인 상품을 제외해 404로 처리했습니다. 카테고리 소속은 기존 상품 SELECT 안의 EXISTS로 확인합니다. 모든 상품에 새 승인·진열 조건을 강제하면 비대상 상품의 기존 동작까지 바뀌므로 조건은 대상 화장품으로 한정했습니다. 승인·선승인 뒤의 공개 조회, 판매자 자신의 전용 조회, 기존 삭제 행 제외는 유지했습니다.

로컬 테스트 DB에서 대상 등록과 혼합 배치, 고시 오류 롤백, 회원·비회원 공개 상세를 검증했습니다. 확대 회귀에는 기존 가격 테스트 실패가 남았으며 부모 변경에서도 같은 실패가 재현됐습니다. 전체 회귀 성공이나 운영 노출 차단 성과를 뜻하지는 않습니다. 두 변경 모두 main에 병합되지 않았고 QA 배포·실제 인증 요청 검증도 남아 있습니다. 기존 상품의 카테고리를 바꿀 때 재검수하는 정책은 별도 작업입니다.

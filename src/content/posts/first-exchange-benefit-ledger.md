쇼핑몰에서 첫 구매 고객의 교환 배송비를 한 번 지원하는 기능을 개발했습니다. 고객에게는 무료교환이지만, 서버는 누가 어느 교환에 혜택을 썼는지 알아야 합니다. 교환 신청을 취소하면 다시 쓸 수 있도록 혜택을 돌려주는 처리도 필요합니다.

예를 들어 고객이 교환 A를 신청했다가 취소하고, 다시 교환 B를 신청했다고 해보겠습니다. 이때 A의 취소 처리가 뒤늦게 한 번 더 들어오더라도 B에 사용한 혜택까지 되돌아가면 안 됩니다. 사용 여부만 저장하는 것으로는 어떤 교환에 대한 취소인지 판단하기 어렵습니다.

## 결제 기록 대신 혜택을 사용한 교환을 남겼다

고객에게 받을 돈이 없으므로 결제대행사(PG)에 0원 결제를 요청하지 않았습니다. 대신 혜택을 사용한 대상과 현재 상태를 별도로 저장했습니다. 이 글에서 혜택 원장이라고 부르는 기록입니다. 모든 이벤트를 복제한 이력 테이블이 아니라, 현재 어느 교환에 적용되어 있는지 판단하는 데 필요한 정보입니다.

첫 구매 조건은 실제 배송된 원주문에서 확인했습니다. 무료교환을 확정할 때는 교환 주문, 회수할 상품을 묶는 반송 그룹, 혜택 사용 상태를 같은 DB 트랜잭션에서 처리했습니다. 교환은 생성됐는데 혜택이 사용되지 않은 상태로 남는 일을 피하려는 것입니다. 고객 부담 금액은 0원으로 두되 판매자에게 정산하는 기준은 유지했습니다.

고객당 한 번이라는 조건에는 탈퇴·재가입도 고려했습니다. 회원 ID만 바꾸면 다시 사용할 수 있는 구조를 피하기 위해 정규화 전화번호의 HMAC과 혜택 종류에 유일 제약을 뒀습니다. 전화번호 원문을 추가 저장하지 않고 같은 번호를 대조하는 방식이지만, 번호가 다른 사람에게 재할당되는 경우와 키 관리는 별도 한계로 남습니다.

## 취소가 현재 사용한 교환을 가리키는지 확인했다

앞의 예에서 A를 취소하면 혜택은 다시 사용 가능한 상태가 됩니다. 이후 B에 사용했다면 현재 기록은 B를 가리켜야 합니다. 늦게 도착한 A의 취소로 그 상태를 바꾸면, 고객은 B에도 혜택을 쓴 채 또 다른 교환에 사용할 수 있게 됩니다.

그래서 취소 처리에서는 적용 대상과 시각을 확인하고, 현재 사용을 가리키는 경우에만 복원하도록 했습니다. DB 유일 제약과 잠금, 상태 검사를 함께 사용해 동시에 확정하거나 같은 요청이 반복되는 경우도 다뤘습니다.

```text
A에 사용 → A 취소로 복원 → B에 사용 → 늦은 A 취소 도착
                                        B의 사용 상태 유지
```

테스트에서는 같은 취소의 반복, 취소 후 재사용, 이전 반송 그룹의 지연 이벤트, 일부 품목 처리가 완료된 경우를 각각 확인했습니다. 단순히 “취소하면 사용 가능으로 변경”하는 코드였다면 구분하지 못했을 상황들입니다.

## 무료 안내를 본 시점과 확정 시점도 달랐다

상품 화면에서 무료교환 가능성을 안내한 뒤 실제 교환을 확정할 때까지는 시간이 흐릅니다. 그 사이 주문이나 사용 이력이 달라질 수 있어 확정 직전에 적용 조건을 다시 확인했습니다. 화면에서 혜택을 봤다는 사실이 사용권 예약을 뜻하지는 않습니다.

다시 검사했을 때 자격이 없다면 유료 교환으로 자동 전환하지 않았습니다. 무료라고 생각한 요청을 비용 확인 없이 결제로 바꾸는 대신, 충돌 응답으로 변경된 조건을 확인하게 했습니다. 무료교환의 확정과 취소를 구현하면서 고객이 동의한 비용과 서버가 기록한 혜택 사용을 함께 맞춰야 했습니다.

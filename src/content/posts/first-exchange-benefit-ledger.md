첫 구매 고객에게 교환 배송비를 한 번 지원하는 기능을 개발했습니다. 고객 입장에서는 무료로 교환을 신청하면 되지만, 서버에서는 누가 어느 교환에 혜택을 썼는지 알아야 합니다. 신청을 취소하면 다음 교환에서 다시 쓸 수 있게 돌려줘야 하기 때문입니다.

처음에는 사용 여부만 있으면 충분해 보일 수 있습니다. 하지만 교환 A를 취소하고 새로 B를 신청한 뒤 A의 취소 요청이 한 번 더 도착한다면 어떻게 될까요. 단순히 “사용 안 함”으로 바꾸면 B에 이미 쓴 혜택도 다시 사용 가능한 상태가 됩니다.

## 혜택을 사용한 교환을 기록하기

고객에게 받을 돈이 없어 PG에 0원 결제를 요청하지 않았습니다. 대신 혜택을 적용한 교환과 현재 사용 상태를 별도 기록으로 관리했습니다. 여기서 혜택 원장은 현재 어느 교환이 혜택을 사용하는지 판단할 정보입니다.

첫 구매 자격은 실제 배송된 원주문에서 확인했습니다. 무료교환을 확정할 때 교환 주문, 회수할 상품의 반송 그룹, 혜택 사용 상태를 같은 DB 트랜잭션으로 처리했습니다. 교환만 생성되고 혜택은 미사용으로 남으면 다른 요청에서 같은 혜택을 다시 쓸 수 있기 때문입니다. 고객 부담은 0원으로 두면서 판매자 정산 기준은 유지했습니다.

고객당 한 번이라는 조건에는 탈퇴와 재가입도 고려했습니다. 회원 ID만 기준으로 하면 재가입 후 다시 쓸 수 있어 정규화 전화번호의 HMAC과 혜택 종류에 유일 제약을 뒀습니다. 전화번호 원문을 추가 저장하지 않고 같은 번호인지 대조하는 방식입니다. 번호의 재할당과 HMAC 키 관리는 별도로 다뤄야 합니다.

## 이전 교환의 취소가 다시 들어오면

앞의 A와 B 예시를 순서대로 보면 다음과 같습니다.

```text
A에 혜택 사용 → A 취소로 복원 → B에 혜택 사용
                                → 늦은 A 취소 도착
```

마지막 요청은 A를 취소하라는 뜻이지 현재 B에 쓰는 혜택을 반환하라는 뜻이 아닙니다. 그래서 취소 대상과 시각이 현재 사용 기록을 가리키는 경우에만 복원하도록 했습니다. DB 유일 제약, 잠금, 상태 검사를 함께 사용해 동시에 확정하는 요청과 반복 요청도 처리했습니다.

테스트에서도 취소 한 번만 확인하지 않았습니다. 같은 취소의 반복, 취소 후 재사용, 이전 반송 그룹의 지연 이벤트, 일부 품목 처리가 이미 끝난 경우를 나눠 확인했습니다. 어느 교환의 취소인지를 기록해야 이 상황들을 구분할 수 있습니다.

## 무료 안내를 본 뒤 조건이 바뀔 수 있습니다

상품 화면에서 무료교환 가능 안내를 봤더라도 실제 교환을 확정할 때까지 시간이 흐릅니다. 그사이 다른 교환에 혜택을 사용했을 수 있으므로 확정 직전에 조건을 다시 검사했습니다. 화면 조회가 사용권을 예약하는 것은 아닙니다.

이때 자격이 없어졌다고 자동으로 유료 교환을 진행하지는 않았습니다. 고객은 무료라고 생각하고 요청했으므로 비용이 바뀌었다는 확인이 먼저 필요합니다. 충돌 응답으로 변경된 조건을 확인하게 하고, 동의 없이 새로운 결제로 이어지지 않도록 했습니다.

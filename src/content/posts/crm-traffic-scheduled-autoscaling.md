CRM 메시지를 보낸 직후에는 링크를 누른 사용자가 짧은 시간에 몰립니다. 발송 시각을 이미 알고 있는데도 CPU가 오른 뒤 서버를 늘리면 새 태스크가 준비되기 전에 트래픽이 들어올 수 있습니다. 기존에는 개발자가 ECS 용량을 미리 조정하고 발송이 끝나면 되돌렸습니다.

발송 담당자가 Slack 모달에 유형·일시·대상 수를 입력하면 예약을 등록하도록 바꿨습니다. 입력 이벤트를 EventBridge로 넘기고, Lambda가 공지를 기록한 뒤 Application Auto Scaling에 발송 전·후 예약 액션을 만듭니다. Slack에는 등록 결과를 돌려줍니다.

## 발송 전 준비와 평소의 확장은 함께 필요하다

예약 확장을 선택한 이유는 부하가 올 시간을 미리 알기 때문입니다. 동적 확장 정책이 불필요해졌다는 뜻은 아닙니다. 예상보다 큰 유입이나 예정에 없던 트래픽은 여전히 메트릭 기반 정책으로 대응할 수 있습니다.

구현에서는 발송 5분 전에 최소 용량을 올리고, 발송 1시간 40분 뒤에 원래 최소·최대 범위를 복원하도록 예약했습니다. 증설량은 발송 대상 수와 등록 시점의 기준 용량으로 계산했습니다. 정책 계산을 API 호출에서 떼어내면 대상 수 경계와 `minCapacity <= maxCapacity`를 따로 검사할 수 있습니다.

## 범위를 복원하는 것과 태스크 수를 줄이는 것은 다르다

Application Auto Scaling의 예약 액션은 최소·최대 용량을 바꿉니다. 현재 용량이 새 최소값보다 작으면 늘리고, 새 최대값보다 크면 줄입니다. 범위 안에 있으면 최소값을 낮추는 것만으로 즉시 축소되지 않습니다. [AWS 예약 확장 동작](https://docs.aws.amazon.com/autoscaling/application/userguide/scheduled-scaling-policy-overview.html)

예를 들어 평소 범위가 2~20이고 발송 전에 최소값을 12로 올렸다고 해보겠습니다. 발송 후 범위를 다시 2~20으로 돌려도 현재 12개는 그 범위 안에 있습니다. 실제 태스크 수가 내려가는지는 동적 축소 정책 등 다음 동작에 달려 있습니다.

따라서 이 자동화의 복귀 예약은 **용량 범위의 복원**으로 설명하는 것이 정확합니다. 고정 시각에 특정 개수로 줄이려면 다른 발송과 평소 부하를 확인한 별도 정책이 필요합니다. 무조건 최대값까지 낮추면 진행 중인 트래픽을 해칠 수 있습니다.

## 두 예약이 모두 등록됐는지 확인해야 한다

증설과 복귀를 같은 처리 흐름에서 등록하면 사람이 나중에 복귀 예약을 잊는 일을 줄일 수 있습니다. 하지만 두 AWS API 호출은 하나의 트랜잭션이 아닙니다. 증설 등록 후 복귀 등록이 실패하는 경우가 남습니다.

다음은 등록 성공과 별개로 다뤄야 할 운영 조건입니다.

- 두 예약의 실제 존재와 값을 확인하고, 일부만 성공한 경우 재시도 또는 보상 처리합니다.
- 예약 이름을 발송별로 구분해 재시도가 중복 등록으로 이어지지 않게 합니다.
- 발송 취소·시각 변경과 여러 발송의 시간 겹침을 처리합니다.
- 등록 후 평소 용량이 바뀌면 예전 기준값을 그대로 복원해도 되는지 확인합니다.

1회성 시각이 지났다는 사실만으로 예약 리소스가 삭제됐다고 가정하지도 않습니다. 실행 내역과 예약 목록은 각각 확인해야 합니다.

## 실패를 발송 담당자에게 돌려준다

현재 용량 조회에 실패하면 스케일링 예약을 건너뛰고 수동 확인이 필요하다고 알리도록 했습니다. 공지 저장과 예약 처리가 같은 이벤트에서 시작되기 때문에, 재시도로 공지만 중복 생성되지 않게 각 작업의 성공 상태를 구분해야 했습니다.

이 변경으로 발송 담당자는 콘솔 조작을 요청하는 대신 기존 공지 입력 과정에서 증설 예약을 시작할 수 있게 됐습니다. 다만 예약 등록 성공은 실제 증설 성공이나 장애 방지의 증거가 아닙니다. 발송별 태스크 수·CPU·응답시간과 복귀 이후 용량을 함께 확인해야 자동화가 의도대로 동작했는지 알 수 있습니다.

> 표시용 안내를 만들려고 금융 실행의 전역 조회를 재사용했습니다. 쿼리는 몇 번 안 나갔지만 많은 행을 읽었습니다. 안내에 필요한 범위만 조회하고 실행 단계의 안전 검증은 유지했습니다.

## 한 번의 쿼리도 충분히 무거울 수 있다

주문 상세와 셀러 목록이 공통 검증용 조회를 호출했습니다. PK 조건과 JSON 조건을 OR로 묶은 검색이 큰 범위를 스캔했습니다. 쿼리 카운트 테스트만으로는 어떤 행을 읽는지, 얼마나 오래 걸리는지 알 수 없었습니다.

이 기록의 문제는 안내 화면에 금융 실행의 넓은 탐색 범위가 그대로 들어갔다는 점입니다. 공통 함수 재사용이 항상 같은 비용과 권한 경계를 갖는 것은 아니었습니다.

## 표시용 snapshot을 별도로 만들었다

안내 조회를 Payment PK 경로와 고객 범위의 JSON 검색으로 나눴습니다. 필요한 고객 데이터로 후보를 제한해 기존 인덱스를 활용하도록 했습니다. 셀러 목록도 표시 전용 batch snapshot으로 연결했습니다.

반면 금융 실행에서 다른 소유자의 고아 시도를 확인하는 검증은 유지했습니다. 화면이 빠르게 보이도록 범위를 줄이는 것과 실제 금융 처리가 허용되는지 검사하는 것은 다른 책임입니다. 성능 때문에 권한 검증까지 같은 방식으로 좁히지 않았습니다.

새 인덱스와 migration 없이 조회 구성을 바꿨지만, 이것도 데이터 분포에 따라 비용이 달라집니다. 기존 인덱스를 사용한다는 사실만으로 운영 지연이 일정해지는 것은 아닙니다.

## 실행 계획과 측정 구간을 함께 남겼다

당시 기록에는 새 JSON 검색의 `EXPLAIN`과 반복 실행한 표시 서비스 시간이 있습니다. 측정은 로컬에서 테스트 DB를 조회한 서비스 구간입니다. 전체 HTTP 응답과 운영 p95를 측정한 결과가 아닙니다.

이전 문제 기록과 새 측정의 조건도 완전히 같다고 확정할 수 없습니다. 따라서 두 숫자를 나누어 수백 배 개선이라고 표현하지 않았습니다. 내부 행 수와 개별 주문 식별자도 공개하지 않았습니다.

## 검증 가능한 결과는 조회 책임의 분리였다

관련 조회·정책·HTTP 회귀 기록은 있지만 원본 확인 시점의 PR은 열려 있었습니다. 실제 운영 적용과 재발 여부는 후속 확인이 필요합니다.

구현에서는 안내가 필요한 데이터만 모아 읽고 금융 실행의 전역 검증은 따로 유지했습니다. 앞으로의 성능 검증도 조회 수뿐 아니라 읽은 행, 실행 계획, 실제 응답 구간을 함께 봐야 합니다. 공통 함수의 범용성보다 호출자의 질문에 맞는 범위가 중요했던 변경입니다.

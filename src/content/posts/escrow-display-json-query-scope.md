결제 안내 화면이 금융 실행용 조회를 재사용하고 있었습니다. 필요한 것은 한 고객의 표시 정보였는데 PK 조건과 JSON 조건이 OR로 묶인 전역 검색이 따라왔습니다. 쿼리가 여러 번 늘어나는 N+1과는 다른 병목이었습니다.

쿼리 횟수가 일정해도 한 SQL이 테이블 전체를 읽으면 요청은 느립니다. 저는 안내 조회의 범위를 줄이되 금융 실행에 필요한 검증은 그대로 남겼습니다. 당시 변경은 리뷰 중이었습니다.

## 표시 요청이 실행 검증의 비용을 물려받았다

금융 실행에서는 잘못된 소유자의 고아 시도 등도 확인해야 합니다. 이 함수를 표시에도 쓰면 안내를 읽는 모든 요청이 넓은 범위의 검증 비용을 지불합니다.

Payment는 PK로 찾고 JSON 검색은 해당 고객 범위로 나눴습니다. 셀러 목록도 표시용 batch snapshot을 사용하게 연결했습니다. 조회 목적이 다르므로 범위도 달라야 했습니다.

실행 검증 자체를 고객 범위로 축소하지는 않았습니다. 표시를 빠르게 만들면서 금융 검증까지 약하게 만드는 변경이 되어서는 안 됐습니다.

## 새 인덱스 전에 기존 인덱스를 쓸 조건을 만들었다

고객 인덱스를 사용할 수 있는 쿼리 형태로 나눴습니다. 새 인덱스나 마이그레이션 없이 `EXPLAIN`에서 `ref` 접근과 추정 행 수 14를 확인했습니다.

추정 행 수는 실제 읽은 행 수와 다릅니다. 실행 시간도 함께 봤습니다. 새 JSON 조회는 테스트 DB에서 약 12ms, 표시 서비스 전체는 세 번 실행해 약 67~74ms였습니다. 전체 서비스의 SELECT는 10회였습니다.

이 값은 로컬에서 테스트 DB를 읽은 서비스 구간입니다. 운영 HTTP 전체 시간이나 p95가 아니며 기존 문제 기록과 같은 조건의 개선 배수로 계산하지 않았습니다.

## 쿼리 수 검증에 실행 계획을 더했다

조회·정책·HTTP 관련 회귀 135건의 통과 기록이 있습니다. 실제 운영 배포 후 측정은 남아 있습니다.

이번 사례에서 반복 조회를 줄이는 접근만으로는 핵심을 놓칩니다. 요청에 SQL이 몇 번 나가는지와 각 SQL이 얼마나 넓게 읽는지를 함께 봐야 했습니다. 표시와 실행이 같은 데이터를 쓴다는 이유로 같은 조회 함수가 필요했던 것은 아니었습니다.

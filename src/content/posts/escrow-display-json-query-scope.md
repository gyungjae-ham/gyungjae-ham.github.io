에스크로 결제는 고객이 낸 돈을 바로 판매자에게 지급하지 않고 구매 진행 상태에 따라 처리합니다. 주문 상세와 판매자 목록에서는 이 결제의 진행 상태를 안내해야 합니다. 고객에게 보일 정보를 읽는 요청인데, 실제 금융 처리를 실행할 때 쓰는 넓은 조회를 재사용하고 있었습니다. 결제 준비 기록의 ID 조건과 JSON 내부 조건이 OR로 묶인 검색에서 전체 스캔이 발생했습니다.

N+1처럼 쿼리가 반복되는 문제는 아니었습니다. SELECT가 일정 횟수로 나가도 그중 하나가 테이블 전체를 읽으면 느릴 수 있습니다. 표시용 조회의 범위를 줄이되 금융 실행에서 필요한 검증은 유지하는 방향으로 수정했습니다. 이 글의 측정은 변경을 테스트 DB에서 확인한 결과입니다. 이후 PR은 병합됐지만 운영 성능까지 확인한 것은 아닙니다.

## 화면 안내와 금융 실행이 확인할 범위가 달랐다

금융 실행에서는 잘못된 소유자로 연결된 시도처럼 넓게 찾아야 할 상태도 있었습니다. 이 검증을 화면 표시에도 그대로 사용하면 고객 한 명의 안내를 읽을 때마다 전역 검색 비용을 지불합니다.

표시 경로는 Payment를 PK로 조회하고, JSON 검색은 해당 고객 범위로 제한해 별도로 수행하도록 나눴습니다. 판매자 목록은 표시용 정보를 일괄로 준비하는 batch snapshot에 연결했습니다. 반면 실제 금융 실행의 검증 범위는 줄이지 않았습니다. 화면을 빠르게 읽는 변경 때문에 실행 시 찾아야 할 잘못된 상태가 가려지면 안 되기 때문입니다.

## 조회 조건을 나누자 기존 인덱스를 사용할 수 있었다

새 인덱스를 추가하기 전에 기존 고객 인덱스를 활용할 수 있는 형태로 조건을 나눴습니다. `EXPLAIN`에서는 인덱스 값으로 대상을 찾는 `ref` 접근과 추정 14행을 확인했습니다. 추정치는 실제로 읽은 행 수와 같다는 뜻이 아니므로 실행시간도 함께 봤습니다.

테스트 DB에서 새 JSON 조회는 약 12ms, 표시 서비스 전체는 세 번 실행해 약 67~74ms였습니다. 서비스 전체의 SELECT는 10회였습니다. 동일 조건의 변경 전 시간은 없어 이 수치만으로 개선 배수를 계산할 수는 없습니다. 이 측정은 로컬에서 테스트 DB를 읽은 서비스 구간이며, 운영 HTTP 응답시간이나 p95는 아닙니다.

조회·정책·HTTP 관련 회귀 테스트 135건도 통과했습니다. 운영 배포 후 측정은 남아 있습니다. 쿼리 횟수를 확인하는 검사만 있었다면 이번 병목은 놓쳤을 것입니다. 한 번의 조회가 고객 한 명의 데이터로 좁혀지는지, 전체 테이블로 넓어지는지를 실행 계획으로 확인해야 했습니다.

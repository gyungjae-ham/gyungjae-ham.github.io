주문 상세 화면에는 결제가 어디까지 진행됐는지 보여주는 안내가 있습니다. 에스크로 결제는 고객이 낸 돈을 즉시 판매자에게 지급하지 않고 구매 진행 상태에 따라 처리하므로, 화면에서도 현재 결제 상태를 읽어야 합니다.

이 안내를 만드는 코드가 실제 금융 처리를 실행하는 조회 코드를 함께 사용하고 있었습니다. 이름이 비슷한 결제 조회지만 필요한 범위는 달랐습니다. 고객 한 명에게 상태를 보여주는 요청에서 전체 결제 기록까지 검색할 필요가 있는지 살펴봤습니다.

## 쿼리 횟수만으로는 확인하기 어려운 문제

문제가 된 조회는 결제 준비 기록의 ID 조건과 JSON 내부 값을 찾는 조건을 `OR`로 묶고 있었습니다. 실행 계획을 확인해 보니 이 쿼리에서 전체 스캔이 발생했습니다.

예를 들어 전체 고객의 결제 기록이 들어 있는 테이블에서 고객 A의 주문 하나를 조회한다고 해보겠습니다. A의 기록만 먼저 좁힌 뒤 필요한 값을 확인하면 읽을 범위가 작아집니다. 반대로 전체 기록의 JSON 값을 검색한다면 A와 관계없는 데이터까지 확인할 수 있습니다. 두 방식 모두 SQL은 한 번 실행하지만, DB가 처리하는 양은 다릅니다.

따라서 이번에는 반복 쿼리를 합치는 것보다 한 쿼리가 어디까지 읽는지부터 바꿔야 했습니다.

## 화면 표시용 조회를 분리했습니다

실제 금융 처리에서는 소유자가 잘못 연결된 결제 시도도 찾아야 해서 넓은 조회가 필요했습니다. 이 조건을 무작정 줄이면 처리 전에 발견해야 할 잘못된 상태를 놓칠 수 있습니다.

화면 표시에는 별도 조회를 사용하도록 나눴습니다. `Payment`는 PK로 찾고, JSON 검색은 해당 고객의 기록으로 범위를 제한해 따로 수행합니다. 판매자 목록에서는 표시할 결제 정보를 미리 한 번에 준비해 사용하도록 연결했습니다. 기존 금융 처리 경로의 검증 범위는 그대로 뒀습니다.

이렇게 조건을 나누자 새 인덱스를 추가하지 않고 기존 고객 인덱스를 활용할 수 있었습니다. `EXPLAIN`에서는 인덱스 값으로 대상을 찾는 `ref` 접근과 추정 14행을 확인했습니다. 14행은 실행 계획의 추정치이므로 실제 실행시간도 함께 확인했습니다.

## 테스트 DB에서 확인한 결과

새 JSON 조회는 약 12ms가 걸렸습니다. 표시 서비스 전체는 세 번 실행해 약 67~74ms였고, SELECT는 10회였습니다. 로컬에서 테스트 DB를 읽어 측정한 서비스 구간의 값입니다. 같은 조건에서 측정한 변경 전 시간이 없어 개선 배수를 계산하지는 않았습니다.

조회·정책·HTTP 관련 회귀 테스트 135건도 통과했고 PR은 병합됐습니다. 운영 환경의 응답시간은 아직 확인하지 못했습니다. 이후 배포에서 확인할 것은 같은 SQL이 호출되는 횟수와 함께, 고객 데이터가 늘어날 때에도 조회 범위가 해당 고객으로 제한되는지입니다.

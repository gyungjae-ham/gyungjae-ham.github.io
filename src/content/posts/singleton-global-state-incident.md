회사에서 대학 학습관리 시스템(LMS)과 Canvas를 연결하는 로그인 기능을 개발했습니다. 외부 시스템의 인증 결과를 전달받는 SAML 방식을 사용했습니다. LMS에서 특정 강의실로 이동하려면 외부 인증을 마친 뒤에도 처음 요청한 강의실 정보를 알고 있어야 했습니다. 그런데 돌아오는 콜백만으로는 그 정보를 이어 붙이기 어려웠습니다.

당시에는 로그인 시작 때 받은 정보를 서버의 공유 변수에 넣었습니다. 콜백이 오면 이 값을 읽어서 다음 처리를 하면 된다고 생각했습니다. 혼자 로그인하고 결과를 확인할 때는 정상적으로 동작했습니다.

문제는 여러 사람이 함께 사용한 시연에서 나왔습니다. 로그인한 사람과 다른 사용자의 이름이나 정보가 보였습니다. 한 명씩 확인하던 테스트에서는 보지 못한 상황이었습니다.

## 값을 지워도 해결되지 않는 이유

처음에는 사용한 값을 바로 지우는 식으로 대응했습니다. 문제가 나타나는 빈도는 줄었지만 원인을 없앤 수정은 아니었습니다. 두 로그인 요청이 겹치면 값을 읽기도 전에 다른 요청이 덮어쓸 수 있기 때문입니다.

예를 들어 두 사용자의 요청이 다음 순서로 처리될 수 있습니다.

```text
A가 로그인 시작 → 공유 변수에 A의 강의실 정보 저장
B가 로그인 시작 → 같은 변수에 B의 강의실 정보 저장
A의 콜백 도착   → B의 강의실 정보로 후속 처리
```

A의 처리가 끝난 뒤 값을 비워도 이미 잘못된 정보를 읽은 뒤입니다. 문제는 오래된 값이 남아 있다는 것보다, 서로 다른 로그인에 필요한 값을 같은 공간 하나에 넣었다는 데 있었습니다.

## 로그인마다 정보를 따로 보관하기

당시에는 인증 전후에 필요한 정보를 암호화한 쿠키로 보관하는 방향으로 변경했고, 관찰했던 사용자 간 정보 혼합은 해결됐습니다. 서버의 모든 요청이 한 변수를 공유하던 상태에서 브라우저별로 정보를 전달하도록 바꾼 것입니다.

그렇다고 암호화한 쿠키 하나로 로그인 과정의 모든 문제가 해결되는 것은 아닙니다. 같은 브라우저에서 여러 탭으로 로그인을 시작하면 어떻게 연결할지, 오래된 값을 다시 보내면 어떻게 거절할지, 값의 변조를 어떻게 확인할지도 별도로 다뤄야 합니다. 인증 전후의 상태 전달과 SAML 응답의 서명·대상·유효 시간 검증 역시 구분해야 합니다. [OWASP의 SAML 검토 항목](https://cheatsheetseries.owasp.org/cheatsheets/SAML_Security_Cheat_Sheet.html)도 이 검증을 따로 다룹니다.

이 일을 겪고 나니 “한 번 로그인해 보니 된다”는 확인이 얼마나 좁은지 알게 됐습니다. 같은 기능을 두 사람이 동시에 사용할 때도 각자의 요청이 이어지는지 확인해야 했습니다. 다시 검증한다면 사용자 수부터 크게 늘리기보다, 위 예시처럼 두 로그인 순서를 일부러 엇갈리게 하는 테스트부터 작성할 것입니다.

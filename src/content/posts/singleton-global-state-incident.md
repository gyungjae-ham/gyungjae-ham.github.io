대학 LMS와 외부 학습 시스템을 연결하는 로그인 흐름에서 요청별 부가 정보가 섞이는 문제가 있었습니다. 로그인 시작 때 받은 강의실 정보를 콜백 이후에도 사용해야 했는데, 이를 서버의 공유 변수 하나에 저장한 것이 원인이었습니다.

혼자 순서대로 요청할 때는 드러나지 않았습니다. 두 사용자의 흐름이 겹치면 다음과 같은 순서가 가능합니다. 아래 A·B는 문제를 설명하기 위한 예시입니다.

```text
A가 로그인 시작 → 공유 변수에 A의 강의실 저장
B가 로그인 시작 → 같은 변수에 B의 강의실 저장
A의 콜백 도착   → B의 강의실을 읽음
```

사용 직후 값을 지워도 A가 읽기 전에 B가 덮어쓰는 순서는 남습니다. 개별 쓰기 연산을 잠그는 것만으로도 로그인 시작과 나중의 콜백이 하나의 요청으로 묶이지는 않습니다.

## 필요한 것은 요청 흐름의 식별자였다

문제는 서버 메모리라는 저장 위치 자체가 아닙니다. 서로 다른 로그인 시도를 같은 저장 공간 하나로 구분 없이 처리한 것입니다. 한 HTTP 요청 안에서만 필요한 값은 지역 변수나 request scope로 관리할 수 있습니다. 그러나 외부 인증을 거쳐 돌아오는 콜백은 별도 요청이므로 요청 수명만으로는 이어지지 않습니다.

요청 흐름별 식별자와 상태를 연결해야 합니다. 서버 저장소를 사용한다면 충분히 예측하기 어려운 식별자, 유효 기간, 한 번만 소비하는 처리와 원래 브라우저·로그인 시도와의 연결을 고려합니다. 여러 서버에서는 인스턴스 간 공유와 재시작 시 소실 조건도 봐야 합니다.

당시에는 클라이언트 쿠키에 컨텍스트를 보관하는 방향으로 바꿨습니다. 다만 암호화했다는 사실만으로 올바른 로그인과의 연결, 재사용 방지, 만료가 보장되는 것은 아닙니다. 같은 브라우저의 여러 로그인 탭이 값을 덮어쓸 가능성도 검토해야 합니다.

## SAML의 상태 전달도 인증 검증을 대신하지 않는다

`RelayState`는 흐름을 이어갈 상태를 전달하는 데 활용할 수 있지만, 그 값만으로 사용자를 인증하면 안 됩니다. SAML 응답의 서명·발급자·대상·시간·요청 연계 등은 검증된 라이브러리의 절차를 따라 확인해야 합니다. 상태 값의 무결성과 허용된 이동 경로도 별도 조건입니다. [OWASP SAML 검토 항목](https://cheatsheetseries.owasp.org/cheatsheets/SAML_Security_Cheat_Sheet.html)

이 유형의 회귀 검증은 동시 사용자 수를 크게 만드는 것부터 시작할 필요가 없습니다. 두 흐름의 시작과 콜백 순서를 엇갈리게 하고, 각각 자기 컨텍스트만 소비하는지 확인하면 공유 변수 하나로는 성립하지 않는다는 것을 작은 사례로 드러낼 수 있습니다. 만료·중복 콜백·같은 브라우저의 두 로그인도 이어서 확인할 조건입니다.

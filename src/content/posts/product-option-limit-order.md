판매자가 색상과 사이즈를 입력하면 서버는 구매 가능한 옵션 조합을 만듭니다. 색상 10개에 사이즈 10개면 실제 조합은 100개입니다. 선택지를 조금씩 늘려도 조합 수는 곱으로 증가해 신규 상품에 500개 상한을 적용했습니다.

문제는 이미 500개를 넘긴 상품이었습니다. 저장할 때 무조건 상한만 검사하면 600개를 550개로 줄이는 수정도 거절됩니다. 앞으로 늘어나는 것은 막되 기존 상품을 줄여 갈 수는 있어야 했습니다.

## 신규 생성과 기존 초과 상품의 조건 나누기

신규 상품은 저장 전에 예상 조합 수를 계산해 500개 초과를 막았습니다. 이미 상한을 넘은 상품은 현재 수와 변경 후 수를 비교해 유지·감소는 허용하고 증가만 거절했습니다.

| 현재 조합 수 | 변경 후 | 결과            |
| ------------ | ------- | --------------- |
| 신규         | 501     | 거절            |
| 600          | 550     | 감소이므로 허용 |
| 600          | 600     | 유지이므로 허용 |
| 600          | 601     | 증가이므로 거절 |

검사 후 저장하기 전에 다른 요청이 옵션을 바꾸면 비교 기준이 달라질 수 있습니다. 상품 잠금 안에서 검증과 저장을 처리하고, 여러 상품의 현재 조합 수는 일괄 조회해 상품마다 쿼리가 추가되지 않도록 했습니다.

## 순서만 바꾸는 요청은 다시 생성하지 않기

옵션 생성·재생성 경로에는 순번이 모두 0으로 저장되는 문제도 있었습니다. 판매자가 색상과 사이즈 순서를 지정했다면 그 순서대로 조합을 만들고 연속 순번을 저장하도록 고쳤습니다. 옵션 추가, 재정렬, 엑셀 수정에서 같은 규칙을 사용하게 했습니다.

예를 들어 블랙과 화이트의 표시 순서를 바꾸는 요청을 생각해보겠습니다. 옵션 자체는 같은데 조합 데이터를 다시 만들면 기존 데이터나 상품 실측 종류까지 영향을 받을 수 있습니다. 후속 보완에서는 순서만 바뀌는 요청을 구분해 불필요한 재생성을 하지 않도록 했습니다.

상한 정책의 DB 비의존 테스트 20건은 통과했습니다. 순번의 초기 검증은 17건 중 12건이 통과했고 5건은 fixture 오류로 실패했습니다. 관련 변경은 병합됐지만 후속 보완 전체의 최종 API 회귀 성공은 추가 확인이 필요합니다. 개수 정책의 통과 결과와 표시 순서 전체의 검증 범위는 구분해 두었습니다.

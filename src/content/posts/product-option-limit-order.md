판매자가 상품을 등록할 때 색상과 사이즈를 각각 지정하면, 서버는 실제 구매할 수 있는 조합을 만듭니다. 예를 들어 색상 10개와 사이즈 10개면 조합은 100개입니다. 각 선택지를 조금씩 늘려도 전체 조합은 곱으로 증가하므로 신규 상품에 500개 상한을 넣었습니다.

문제는 이미 판매 중인 데이터였습니다. 상한을 넘는 기존 상품에 같은 검사를 그대로 적용하면 옵션을 줄이는 수정도 거절할 수 있습니다. 예를 들어 600개에서 550개로 줄여도 여전히 500개를 넘기 때문입니다. 신규 생성과 기존 데이터 수정의 허용 조건을 나눠야 했습니다.

## 상한 초과 여부만으로 거절하지 않았다

신규 상품은 저장 전에 예상 조합 수를 계산해 500개를 넘으면 막았습니다. 기존 초과 상품은 현재 수와 변경 후 수를 비교해 유지하거나 줄이는 수정은 허용하고, 더 늘어나는 수정은 막았습니다. 당장 모든 과거 상품을 규칙 안으로 바꾸지 않아도 정상 범위로 줄여 갈 수 있게 한 것입니다.

검증이 끝난 뒤 다른 요청이 옵션을 바꾸면 계산의 전제가 달라질 수 있어 상품 잠금 안에서 검증과 저장을 처리했습니다. 여러 상품의 현재 조합 수는 일괄 조회했습니다. 개수 제한을 확인하려고 상품마다 추가 쿼리를 내지 않도록 했습니다.

## 개수와 별개로 표시 순서도 저장해야 했다

옵션 조합을 생성·재생성하는 경로에는 순번이 모두 0으로 저장되는 문제도 있었습니다. 판매자가 지정한 순서대로 선택지가 보이려면 조합에 그 순서를 부여해야 합니다. 표시 순서로 조합을 만들고 연속 순번을 저장하도록 고쳤습니다.

옵션 추가와 재정렬뿐 아니라 엑셀 수정도 같은 규칙을 사용하게 했습니다. 이후에는 순서만 바꾸는 요청이 기존 조합 데이터나 상품 실측 종류까지 다시 만들지 않도록 보강했습니다. 색상 순서를 바꾸는 것과 상품의 옵션 내용을 바꾸는 것을 같은 재생성으로 처리하지 않기 위해서입니다.

상한 정책의 DB 비의존 테스트 20건은 통과했습니다. 순번 초기 검증에서는 17건 중 12건이 통과했고 5건은 fixture 오류가 있었습니다. 관련 변경은 병합됐지만 후속 보강 전체의 최종 API 회귀 성공은 확인이 필요합니다. 개수 정책의 검증 결과를 순서 변경 전체의 검증으로 대신할 수는 없었습니다.

> 옵션 조합이 제한 없이 늘어나고, 새로 만든 조합의 순번은 모두 같은 값으로 저장되었습니다. 조합 개수 정책과 표시 순서의 계약을 나누어 생성·수정 경로에 반영했습니다.

## 옵션 개수보다 조합 수가 빠르게 늘어난다

색상과 사이즈처럼 여러 축이 있으면 최종 조합은 각 축의 개수의 곱입니다. 옵션값 몇 개를 추가하는 작은 수정도 많은 조합을 만들 수 있습니다. 조합을 모두 생성한 뒤 거절하기보다 저장 전에 예상 개수를 계산하는 검증을 두었습니다.

신규 상품의 상한을 기존 상품에 무조건 적용하면 이미 판매 중인 상품은 아무 수정도 하지 못할 수 있습니다. 기존에 상한을 넘은 상품은 현재 개수를 유지하거나 줄이는 변경을 허용하고, 더 늘리는 변경은 막았습니다. 신규 입력의 정책과 기존 데이터의 이행 정책을 구분한 것입니다.

## 검증한 개수가 저장할 때도 같아야 한다

서로 다른 요청이 같은 상품의 옵션을 바꾸면 각자 읽은 상태는 유효해도 결과는 상한을 넘을 수 있습니다. 상품 잠금 안에서 검증과 저장을 연결하도록 했습니다. 여러 상품의 현재 조합 수는 모아서 조회해 검증 대상마다 반복 쿼리가 생기지 않도록 했습니다.

이는 카테시안 곱 계산의 정확성과 별개의 동시성 조건입니다. 순수 계산 테스트가 통과했다고 저장 경합까지 확인한 것으로 볼 수는 없습니다. 적용한 잠금 범위와 실제 변경 경로를 함께 검토해야 합니다.

## 새 조합뿐 아니라 재정렬 경로도 바꿨다

표시 순서를 기준으로 연속 순번을 부여했습니다. 생성 함수만 수정하면 옵션 추가나 재정렬, 엑셀 수정 뒤에는 다시 순서가 달라질 수 있습니다. 같은 계약을 여러 입력 경로에 적용했습니다.

엑셀에서 순서만 바꿨을 때 기존 조합 데이터와 상품의 실측 종류를 보존하는 후속 보강도 확인했습니다. 순서를 바꾼다는 이유로 조합 전체를 새로 만들면 식별자에 연결된 다른 데이터가 영향을 받을 수 있기 때문입니다.

## 초기 테스트 결과와 최종 변경 범위를 구분했다

원본에는 상한 정책의 DB 비의존 테스트 통과가 남아 있습니다. 순번 변경의 초기 검증은 일부 fixture 오류로 전체가 통과하지 않았고, 최종 diff에는 그 이후의 보강도 포함됩니다. 이를 모두 합쳐 전체 API 회귀 성공이라고 적지 않았습니다.

관련 변경의 병합은 확인되지만 운영 성과는 별도 근거가 필요합니다. 확인 가능한 결과는 상한의 적용 조건을 명시하고, 표시 순번을 만드는 여러 경로를 정리했다는 점입니다.

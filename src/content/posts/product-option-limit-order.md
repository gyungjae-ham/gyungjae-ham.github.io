상품 옵션 조합에 상한을 넣는 작업이었습니다. 색상과 사이즈가 각각 늘면 조합은 곱으로 증가합니다. 생성 후 개수를 확인하는 것보다 저장 전에 예상 조합 수를 계산해야 했습니다.

그런데 신규 상품의 상한을 기존 상품에 그대로 적용하면 이미 상한을 넘는 상품은 옵션을 줄이려는 수정조차 거절됩니다. 저는 새로 만드는 규칙과 이미 판매 중인 데이터를 수정하는 규칙을 나눴습니다.

## 현재 수와 변경 후 수를 같이 봤다

신규 상품에는 조합 500개 상한을 적용했습니다. 기존 초과 상품은 유지하거나 감소하는 변경을 허용하고 추가 증가를 막았습니다. 현재 수와 예상 수를 비교해야 가능한 정책입니다.

상품 잠금으로 검증·저장 사이의 경합을 방어하고 여러 상품의 현재 조합 수는 일괄 조회했습니다. 예상 개수를 올바르게 계산해도 저장 전 다른 변경이 들어오면 판단 기준이 달라질 수 있기 때문입니다.

## 개수 다음에는 순서 문제가 남았다

조합 생성·재생성에서 순번이 모두 0으로 저장되면 옵션 표시 순서와 응답 순서가 맞지 않습니다. 표시 순서로 조합을 만들고 연속 순번을 부여했습니다.

옵션 추가와 재정렬뿐 아니라 엑셀 수정 경로도 같은 규칙으로 연결했습니다. 후속 변경에서는 순서만 바꿀 때 기존 조합 데이터와 상품 실측 종류를 유지하도록 보강했습니다. 정렬 수정이 다른 데이터 재생성으로 번지지 않아야 했습니다.

## 두 변경의 테스트 결과를 합치지 않았다

상한 정책의 DB 비의존 테스트 20건은 통과했습니다. 순번 초기 검증은 17건 중 12건 통과와 fixture 오류 5건이었고, 후속 보강 전체의 최종 통과 수는 아직 확인이 필요합니다. 두 변경은 병합됐지만 전체 API 회귀가 끝났다고 표현할 수는 없습니다.

범위가 작은 정책 변경이어도 기존 데이터에 적용하는 순간 다른 문제를 만납니다. 이번에는 규칙을 지키지 못한 과거 데이터를 무조건 막기보다, 새 증가를 제한하면서 정상 범위로 줄여갈 수 있게 했습니다.

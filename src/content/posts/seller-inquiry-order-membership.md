> 없는 주문은 DB 오류가 되었고, 다른 주문의 상품은 문의에 연결될 수 있었습니다. 저장 전에 주문의 존재와 주문상품의 소속 관계를 각각 검증했습니다.

## 외래키가 보장하지 않는 관계

DB 외래키는 참조한 주문과 주문상품이 존재하는지 확인할 수 있습니다. 하지만 두 값이 서로 같은 주문 관계인지는 별도의 조건입니다. 유효한 ID 두 개를 받았다고 유효한 연결이 되는 것은 아니었습니다.

수정 전 재현 기록에는 없는 주문의 외래키 오류와, 다른 주문의 상품이 혼입된 문의가 성공한 결과가 남아 있습니다. 예외 처리만 추가하면 존재 오류는 응답으로 바꿀 수 있어도 잘못된 연결은 그대로 남습니다.

## 부수 효과를 준비하기 전에 검증한다

주문 존재와 각 주문상품의 부모 ID를 확인하는 검증을 첨부파일 준비와 mutation 이전에 두었습니다. 요청이 잘못된 것을 알면서 파일을 먼저 처리하면 정리해야 할 외부 효과가 생길 수 있습니다.

잘못된 주문과 소속 불일치는 기존 오류 형식의 400으로 반환하도록 했습니다. 정상 생성의 201 응답과 주문번호 선택 입력은 유지했습니다. 새로운 검증이 기존에 주문 연결 없이 허용하던 문의까지 막지 않도록 입력 계약을 함께 확인했습니다.

## 모든 상품을 다시 단건 조회하지 않았다

소속 판정에 필요한 부모 정보를 조회하고 상품마다 추가 쿼리를 만들지 않았습니다. 검증을 넣는다고 요청 크기에 비례해 같은 정보를 반복해서 읽을 필요는 없습니다. 입력 목록의 존재와 관계를 모아 확인한 뒤 저장 흐름을 진행합니다.

다만 소속 검증은 사용자나 셀러의 접근 권한 전체를 대신하지 않습니다. 존재, 부모 관계, 호출자의 권한은 서로 다른 질문입니다. 이 기록에서 확인한 수정 범위를 더 넓은 권한 검증 완료로 표현하지 않았습니다.

## 회귀 통과와 외부 업로드는 별도 범위다

원본에는 격리 MySQL에서의 재현과 신규·관련 확대 회귀 통과가 있습니다. 테스트 범위가 겹치므로 통과 수를 합산하지 않았습니다. 실제 S3 업로드와 관리자 브라우저 연결은 검증 범위 밖이었고, 확인 시점의 PR은 열려 있었습니다.

확인한 구현 결과는 잘못된 관계를 저장 전에 거절하고 기존 응답 계약을 유지한 것입니다. 데이터 검증은 DB가 오류를 던지게 만드는 장치보다, 어떤 관계가 성립해야 다음 효과를 시작할 수 있는지 표현하는 단계였습니다.

여러 판매자가 입점한 쇼핑몰에서는 같은 브랜드 상품을 서로 다른 판매자가 팔 수 있습니다. 쿠폰 계약이 특정 판매자와 브랜드의 조합에만 적용된다면, 브랜드만 보고 할인해서는 안 됩니다. 예를 들어 판매자 A의 브랜드 X 상품에 쓸 쿠폰이 판매자 B의 같은 브랜드 상품까지 할인하면 계약 범위를 벗어납니다.

판매자와 브랜드를 모두 만족하는 조건을 공통으로 만들고 상품 화면부터 결제까지 연결했습니다. 그런데 쿠폰은 사용으로 끝나지 않습니다. 주문을 취소하면 다시 사용할 수 있게 돌아오고, 반품·교환으로 주문이 나뉘면 할인액과 비용 분담도 따라가야 합니다. 9월 말 관계 모델을 추가한 뒤 10월 8일까지 적용·관리 기능을 보완했습니다. 관련 변경은 main에 병합됐으며, 실제 배포·결제·정산 결과는 아직 확인하지 못했습니다.

## 화면에 보인 쿠폰도 결제할 때 다시 확인했다

상품 카드, 장바구니, 브랜드관과 검색의 쿠폰 표시가 같은 대상 조건을 사용하게 했습니다. “판매자가 맞거나 브랜드가 맞으면”이라는 OR 조건이 아니라 둘 다 맞는 AND 조건입니다.

다만 화면에서 한 번 보여줬다는 이유로 결제 요청의 쿠폰을 그대로 적용하지는 않았습니다. 실제 결제 직전에 다시 검증했습니다. 장바구니 일부 상품만 선택한 요청에서는 적용 대상 목록이 필요하며, 이 입력이 없으면 전체 상품으로 넓혀 해석하지 않고 거절했습니다. 어떤 상품에 할인할지를 서버가 추측하지 않도록 한 것입니다.

## 취소로 돌아온 쿠폰에도 같은 제한이 있어야 했다

취소 후 쿠폰을 되살릴 때 원래의 판매자·브랜드 관계와 사용 유형을 유지했습니다. 새로 쓸 수 있게 된 쿠폰에서 관계가 빠지면 처음에는 적용되지 않던 다른 상품에도 사용할 수 있기 때문입니다.

할인액의 합계만 맞추는 것도 충분하지 않았습니다. 할인 비용을 플랫폼과 판매자가 나눠 부담하는 경우, 고객이 받은 총 할인액이 같아도 어느 쪽의 정산 금액에서 빼는지가 달라질 수 있습니다. 반품·교환으로 주문을 분할하거나 롤백할 때 총 할인액과 양쪽 분담액을 함께 복원하도록 했습니다.

예를 들어 10,000원 할인 중 플랫폼이 3,000원, 판매자가 7,000원을 부담했다고 해보겠습니다. 이 금액은 설명용입니다. 주문을 나눈 뒤에도 각 조각의 총 할인 합계는 10,000원, 양쪽 부담 합계는 각각 3,000원과 7,000원이어야 합니다. 총액만 보존하고 부담액을 다시 임의 계산하면 고객 화면은 같아도 판매자 정산이 달라집니다. 실제 배분에는 대상 상품 금액과 원 단위 나머지 처리까지 확인해야 합니다.

```text
적용 대상 확인 → 결제 직전 재검증 → 쿠폰 사용
    → 취소·분할 시 대상 제한과 비용 분담을 함께 복원
```

## 잘못된 설정은 운영 입력에서도 알려줬다

기존 관리 화면에 검색 가능한 관계 편집을 추가하고, 적용 대상의 혼합과 지원 유형, 분담 비율 범위를 검사했습니다. 결제 시점에도 검증하지만 설정한 사람이 입력 단계에서 고칠 수 있어야 했습니다.

화면에서 막은 조합도 CSV 가져오기로 저장할 수 있다면 같은 쿠폰이 입력 경로에 따라 달라집니다. 10월 보완에서는 저장 후 남을 적용 대상을 구성해 공통 정책으로 검증하도록 연결했습니다. CSV에서 관계 열을 생략하면 기존 관계를 유지하고, 명시적으로 비우면 삭제 후 상태를 검사합니다. 관리자 화면에서도 삭제 표시만 믿지 않고 실제 삭제 권한과 DB에 남는 관계를 함께 확인했습니다. 관계를 삭제할 권한이 없는 요청이 다른 대상을 추가해 제한을 우회하는 경우와, 정상 삭제 후 대상을 전환하는 경우를 구분했습니다.

관계만 바꾼 저장도 캐시 갱신의 계기가 되어야 했습니다. 쿠폰의 기본 필드는 그대로여도 판매자·브랜드 관계를 추가·변경·삭제하면 DB 커밋 후 브랜드 쿠폰 캐시를 무효화하는 작업을 예약했습니다. 관계가 바뀌지 않은 저장은 유지합니다. 예약 뒤 비동기 작업과 다음 조회를 거쳐 반영되므로 관리자 저장 직후 모든 화면이 바뀐다는 보장은 아닙니다.

## 할인액을 비교하기 전에 쓸 수 있는 후보인지 걸렀다

예를 들어 비활성 쿠폰의 할인액이 활성 쿠폰보다 크다고 해보겠습니다. 추천에서 금액만 비교하면 실제로 쓸 수 없는 쿠폰이 선택되어 정상 후보를 밀어낼 수 있습니다. 상품의 다운로드·보유 쿠폰 조회와 장바구니 다운로드 추천에 활성 조건을 적용했습니다. 장바구니 추천의 공통 조회를 수정해 상품·브랜드·기획전과 판매자·브랜드 관계가 같은 조건을 쓰게 했습니다. 추천은 발급할 후보를 찾는 단계이며 쿠폰 발급 자체를 수행하지 않습니다.

검증에서는 비활성 단독 후보와 더 큰 비활성 할인액이 활성 후보와 경쟁하는 경우를 실제 로컬 DB·API 경로에서 수정 전 실패로 재현하고 수정 후 차단했습니다. 관리자 입력과 CSV의 검증 우회, 관계 변경 때 캐시 무효화 예약 여부도 확인했습니다. 후보와 관계를 일괄 조회하는 기존 검증에서는 장바구니 상품 1개와 20개 모두 조회 11회를 유지했고, 분할·정산 회귀도 검증했습니다. 다만 QA 통합 검증에서 기존 보유쿠폰 순서 비교 실패가 수정 전후 모두 재현돼 조사 대상으로 남았으며, 기존 마이그레이션 오류로 기본 테스트 DB를 사용한 재검증도 남았습니다. 격리 환경의 검증과 main 병합까지 확인한 범위이며 실제 결제·정산 결과는 후속 확인이 필요합니다.

예를 들어 고객이 같은 상품 세 개를 사고 그중 하나만 반품하면, 서버는 반품할 한 개와 남길 두 개를 구분해 관리해야 합니다. 이 서비스는 주문 상품을 분할하고 회수할 상품을 반품 묶음에 연결한 뒤 접수를 진행합니다. 상태 검증이나 유료 교환 결제가 실패하면 준비 과정에서 만든 데이터를 정리합니다.

문제는 정리 함수가 현재 연결된 데이터를 이번 요청의 생성분으로 간주했다는 점입니다. 이미 접수된 상품의 중복 신청을 거절하면서 기존 반품 묶음을 삭제할 수 있었습니다. 그 묶음에 회수 기록이 있으면 삭제 보호 예외 때문에 의도한 400 대신 500이 나올 수도 있었습니다.

## 연결되어 있다는 이유만으로 되돌리지 않기

예를 들어 어제 한 개를 분할해 반품 접수를 마쳤고, 오늘 같은 상품에 다시 접수를 시도했다고 해보겠습니다. 오늘 요청이 실패했다고 어제 분할까지 원상품에 합치면 기존 접수의 수량과 금액 근거가 달라집니다. 오늘 생성한 분할이 없었다면 정리할 분할도 없어야 합니다.

그래서 준비 결과에 처리 대상 상품과 주문뿐 아니라 이번에 생성한 분할 ID 집합을 넣었습니다. 실패 시에는 실패한 상품 ID와 생성 ID의 교집합만 되돌립니다. 여러 상품 중 일부가 성공했다면 그 성공분까지 정리 대상에 넣지 않습니다. 상품에 부모가 있다는 사실은 과거 분할일 수도 있으므로 정리 근거로 쓰지 않습니다.

반품 묶음도 같은 기준을 적용했습니다. 이번 요청이 만든 묶음 ID를 명시적으로 전달한 경우에만 삭제를 검토하고, 다른 상품이 사용하지 않는 빈 묶음인지 함께 확인합니다. 기존 묶음은 삭제 대상으로 추정하지 않습니다. 새로 만들었다는 근거와 더 이상 사용하지 않는다는 조건이 모두 필요합니다.

## 정리가 한 번 더 실행되는 경우

실패 처리를 재시도할 때 오래된 상품 객체를 그대로 합산하면, 이미 복원하고 지운 분할의 수량이나 금액을 다시 더할 위험도 있습니다. 정리 함수는 잠금을 얻어 상품을 다시 읽고 그 결과에서 이번 생성 ID에 해당하는 분할만 처리하도록 바꿨습니다. 이미 삭제된 분할은 재조회 결과에 없어 다시 합산하지 않습니다.

로컬 MySQL과 외부 결제 대역을 사용한 회귀에서는 기존 접수·회수 기록과 과거 분할을 보존하는지, 실패한 신규 분할만 수량·금액·수수료를 복원하는지 확인했습니다. 정리를 반복해도 값이 늘지 않는 경우, 사용 중인 신규 묶음을 남기는 경우와 일부 상품만 실패하는 경우도 포함했습니다. 이는 테스트한 정리 경로의 검증이며 모든 동시 요청에서 중복이나 유실이 없다는 보장은 아닙니다.

변경은 10월 30일 main에 병합됐습니다. 실제 PG 연동과 운영 배포, 이미 연결이 사라진 운영 데이터의 복구는 별도 확인 대상입니다. 새 정리 경계는 앞으로 실패하는 요청이 과거 데이터를 건드리는 범위를 줄이는 변경이지, 과거 접수를 자동 복원하는 기능은 아닙니다.

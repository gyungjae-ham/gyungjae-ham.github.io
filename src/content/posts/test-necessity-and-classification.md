테스트를 붙이는 가장 직접적인 이유는 변경 뒤에도 필요한 동작이 유지되는지 확인하기 위해서입니다. 예를 들어 무료배송 기준이 30,000원인 가상의 서비스라면, `29,999원`, `30,000원`, `30,001원`의 배송비를 검사하면 `>=`를 `>`로 잘못 바꾸는 회귀를 잡을 수 있습니다. 몇 줄을 실행했는지보다 어떤 경계를 확인했는지가 중요합니다.

테스트가 있다고 설계 원칙을 모두 지킨 것은 아닙니다. 테스트하기 어려운 코드에서 시간·네트워크·DB 의존성을 발견하고 분리할 수는 있지만, 테스트 개수만으로 단일 책임이나 치환 가능성을 증명할 수는 없습니다. 구현을 그대로 따라가는 테스트는 내부 구조를 바꿀 때 함께 깨지기도 합니다.

## 클래스 수보다 필요한 실행 환경을 보기

Google의 테스트 분류는 주로 실행에 필요한 자원을 기준으로 합니다. 아래는 그 구분을 간추린 것으로, 모든 조직이 따라야 하는 명칭은 아닙니다.

| 규모   | 실행 제약의 중심                   | 예시                          |
| ------ | ---------------------------------- | ----------------------------- |
| Small  | 한 프로세스에서 외부 I/O 없이 실행 | 배송비·만료 시각 계산         |
| Medium | 한 머신 안에서 DB 등과 통합 가능   | 실제 DB 매핑과 쿼리 검증      |
| Large  | 여러 머신·서비스까지 포함 가능     | 주문에서 외부 결제까지의 흐름 |

한 테스트가 여러 클래스를 함께 검증해도 외부 I/O 없이 동작하면 작게 실행될 수 있습니다. 반대로 메서드 하나를 확인하더라도 실제 외부 서버를 부르면 실행 비용과 실패 요인이 늘어납니다. `unit/integration/E2E`라는 검증 범위와 `small/medium/large`라는 실행 규모를 일대일로 고정하면 이 차이를 놓칩니다. 분류의 원문은 [Software Engineering at Google의 Testing Overview](https://abseil.io/resources/swe-book/html/ch11.html)에 있습니다.

## 배송비 계산과 주문 저장을 같은 방식으로 검사할까

앞의 배송비 계산은 금액을 바꿔 가며 외부 환경 없이 확인할 수 있습니다. 하지만 같은 주문번호가 중복 저장되지 않는지 확인하려면 DB 제약이 실제로 동작하는지도 봐야 합니다. Mock이 정해진 오류를 반환하는 테스트만으로는 잘못된 unique 설정을 발견할 수 없습니다.

작고 빠른 테스트를 충분히 두면 자주 실행하기 좋습니다. 다만 소형 테스트를 반드시 80%로 맞추는 식의 목표보다는 어떤 실패를 놓칠 수 있는지에 따라 환경을 고르는 편이 낫습니다.

배송비 계산은 작은 테스트로 여러 경계를 확인하고, 주문 저장의 유일 제약은 실제 DB로, 결제와 주문 상태의 연결은 통합 환경에서 확인하는 식으로 역할을 나눕니다. 각 계층의 예는 [계층별 테스트 전략](/posts/layered-testing-strategy/)에서 이어집니다.

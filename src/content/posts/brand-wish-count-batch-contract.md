> 브랜드 목록에 찜 수를 추가하면서 항목마다 COUNT하지 않도록 집계했습니다. 이후 검색과 목록의 표시 기준 차이를 수정하되 실제 사용자 수와 표시값의 의미는 구분했습니다.

## 브랜드 개수만큼 COUNT하지 않는다

판매 브랜드 목록에 찜 수를 전달해야 했습니다. Serializer가 각 브랜드의 관계를 세면 목록이 길어질수록 쿼리가 늘어납니다. 브랜드 ID를 모아 집계하고 결과를 응답에 연결했습니다.

집계에서는 중복 사용자를 제외했습니다. 찜 관계 행의 수와 찜한 사용자 수가 같다는 가정을 하지 않은 것입니다. JOIN이나 중복 관계가 추가되더라도 무엇을 세는지 명확해야 합니다.

## 실제 값과 화면 표시값이 달랐다

초기 변경은 실제 찜 수를 반환했습니다. 테스트 서버 확인 이후 검색 API에서 사용하는 보정값을 목록에도 더하는 후속 수정이 있었습니다. 같은 브랜드를 서로 다른 화면에서 보았을 때 숫자가 달라지는 문제를 맞춘 것입니다.

이 보정값이 실제 사용자 행동을 늘린 것은 아닙니다. 표시값을 집계 원본이나 참여 성과로 재사용하면 의미가 달라집니다. 원본 기록에서 확인한 구현을 설명하되 보정된 숫자를 실제 찜한 사용자 수의 증거로 제시하지 않았습니다.

장기적으로는 보정의 목적과 사용자에게 표시하는 이름까지 검토해야 합니다. 다만 이번 변경에서 그 정책까지 해결되었다고 가정하지 않습니다. 실제 집계와 표시 규칙을 나누어 읽는 것이 우선입니다.

## 내부 값보다 HTTP 계약을 확인했다

응답은 `wishCount`라는 camelCase 계약으로 전달했습니다. 서비스가 올바른 값을 만들었다고 Serializer와 HTTP의 키도 자동으로 맞는 것은 아니므로 출력 계약을 함께 확인했습니다.

브랜드 수를 늘려도 조회 횟수가 증가하지 않는지 로컬 합성 데이터로 검증했습니다. 원본에는 1개·30개·100개 브랜드에서 각각 네 번의 조회가 기록되어 있습니다. 이는 검증한 표본의 조회 수이며 DB 집계 시간까지 고정이라는 뜻은 아닙니다.

## 일관성 수정과 운영 성과를 나눴다

관련 테스트와 보정 회귀, 두 변경의 병합은 확인되었습니다. 운영 지연의 개선량이나 실제 찜 활동 변화는 측정되지 않았습니다. 이번 글 작성에서도 당시 테스트를 재실행하지 않았습니다.

구현 결과는 목록의 반복 COUNT를 제거하고 표시 기준을 검색과 맞춘 것입니다. 조회 계약을 공통으로 사용하는 것과 데이터 의미까지 올바르게 전달하는 것은 함께 검토해야 했습니다.

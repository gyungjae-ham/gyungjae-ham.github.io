> 규칙 문서는 있었지만 대상 소스 경로에 연결되지 않았습니다. 적용 설정을 정리하고, 정적으로 확정할 수 있는 위반과 맥락이 필요한 리뷰를 다른 평가로 관리했습니다.

## 문서가 있다는 사실은 적용되고 있다는 증거가 아니다

리뷰 도구 설정의 glob과 실제 레이어 경로를 맞췄습니다. 정본 문서 링크와 설정 schema도 검증했습니다. 규칙을 더 자세히 쓰기 전에 해당 파일에 도구가 그 지침을 읽는지 확인해야 했습니다.

또 다른 문제는 코드의 fallback 값을 운영 설정값으로 오인하는 리뷰였습니다. 문법에서 확정되는 위반과 실행 환경의 맥락이 필요한 판단을 한 정확도 수치에 섞으면 개선해야 할 대상을 알 수 없습니다.

## 전체 저장소 대신 새로 들어온 위반을 본다

direct base와 head의 AST를 비교해 신규 위반을 검사했습니다. 기존 위반을 새 PR의 문제로 반복 보고하지 않고, 동일 코드의 이동도 새 도입과 구분하려 했습니다. PR이 실제로 추가한 변경을 기준으로 범위를 정한 것입니다.

AST는 함수와 호출 구조를 읽을 수 있지만 외부 상속이나 동적 설정, 모든 타입의 흐름을 완전히 알지는 못합니다. 확정할 수 없는 결과는 추정으로 표시하거나 별도 맥락 평가로 남겨야 합니다. 검사 도구의 탐지 범위도 계약입니다.

## 평가할 사례가 없으면 100%가 아니다

정적 재생 사례와 사람이 판정한 실제 리뷰 관측을 분리했습니다. 분모가 0이거나 관측이 빠진 경우는 미평가 또는 null로 기록했습니다. 오류가 관측되지 않았다는 이유만으로 완벽한 성능이라고 계산하지 않았습니다.

합성 사례에서 규칙을 잘 찾았다는 사실도 실제 PR의 정확도 향상과 다릅니다. 검사기 구현의 커버리지, 합성 사례 통과, 실제 리뷰의 적중률은 각기 다른 지표입니다. 검증 결과를 나눠 저장한 이유입니다.

## 검사 도구 자체를 가볍게 재검증한다

Django·DB·AWS 없이 읽기 전용 PR CI에서 검사 도구의 회귀를 실행하도록 했습니다. 앱을 기동하지 않아도 설정과 정적 분석 계약을 확인할 수 있도록 경계를 줄였습니다.

원본에는 초기 설정 변경의 병합과 후속 도구 테스트가 남아 있습니다. 후속 PR은 확인 시점에 열려 있었으며 실제 리뷰 정확도가 개선되었다는 실측은 없습니다. 확인한 결과는 문서의 적용 경로를 검증하고, 탐지 가능한 규칙과 맥락 판단의 평가를 분리했다는 점입니다.

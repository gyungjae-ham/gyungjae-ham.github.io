프로젝트에서는 CodeRabbit으로 자동 코드 리뷰를 받고, 리뷰 때 확인할 규칙도 문서로 관리했습니다. 그런데 문서를 고쳐도 필요한 파일에 규칙이 적용되지 않는 부분이 있었습니다. 실제 소스 경로와 설정의 glob 패턴이 맞지 않았습니다. glob은 어떤 경로의 파일을 대상으로 할지 고르는 패턴입니다.

먼저 경로, 정본 문서 링크, 설정 스키마를 정비했습니다. 이어 코드 형태로 판단할 수 있는 규칙은 소스를 구문 구조로 읽는 AST 검사로 옮겼습니다.

## 이번 PR에서 추가된 위반 찾기

최신 코드 전체를 검사하면 예전부터 있던 문제도 이번 PR의 지적으로 나옵니다. 그러면 작성자는 자기 변경 때문에 생긴 문제인지부터 다시 찾아야 합니다.

기준 커밋인 direct base와 최신 커밋인 head의 AST를 비교해 새로 생긴 위반을 찾도록 했습니다. 예를 들어 기준 코드에 A 위반이 있고 최신 코드에 A와 B가 있다면 새 지적은 B입니다. A의 내용은 그대로이고 파일만 이동했다면 새 위반으로 세지 않아야 합니다.

기존 문제를 전부 정리하는 작업과 현재 PR에서 위반을 늘리지 않는 검사는 범위가 다릅니다. 이번 검사는 변경한 코드에 어떤 수정을 요구하는지 알 수 있도록 하는 쪽으로 맞췄습니다.

## 도구 테스트 통과가 AI 리뷰 정확도는 아닙니다

문법 형태로 판정할 수 있는 규칙은 같은 입력으로 반복 테스트할 수 있습니다. 반면 코드에 적힌 fallback이 실제 운영 설정값인지 판단하려면 코드 밖의 맥락도 필요합니다. 외부 상속과 동적 설정, 완전한 타입 추적까지 이 검사 하나로 다루기는 어렵습니다.

그래서 정적 도구의 회귀 결과와 사람이 판정한 실제 리뷰 관측을 나눴습니다. 실제 관측이 없거나 평가할 사례 수가 0이면 정확도를 100%로 기록하지 않고 `null`로 뒀습니다. 평가한 내용이 없는 상태와 모두 맞힌 상태는 다르기 때문입니다.

도구 테스트 57건, 정적 회귀 10건의 실패 0건, 구현 커버리지 94%를 확인했습니다. CI는 Django·DB·AWS를 기동하지 않고 소스만 읽도록 구성했습니다. 이 숫자는 검사 도구 자체의 결과입니다.

지침 정리는 병합됐지만 후속 검사·평가 구현 PR은 10월 1일 미병합으로 종료됐습니다. 따라서 후속 CI가 실제로 적용됐거나 CodeRabbit의 리뷰 정확도가 높아졌다는 결과로 보지는 않습니다. 그 효과는 적용 후 리뷰의 누락과 오탐을 관측해야 확인할 수 있습니다.

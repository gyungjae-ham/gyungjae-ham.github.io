> 자동 계정의 댓글을 저장하는 기능보다, 그 댓글이 다른 도메인에서 무엇을 만들 수 있는지가 중요했습니다. 생성 이후의 응모권 적립·소급 처리·선택 경로를 따로 확인했습니다.

## 댓글 하나가 여러 도메인의 입력이었다

본문을 읽어 자동으로 댓글을 생성하는 작업이 있었습니다. 기존 사용자 댓글 흐름에는 응모권 적립 같은 부수 효과가 연결되어 있었습니다. 생성 서비스를 그대로 호출하면 자동 계정이 실제 보상 대상에 섞일 수 있었습니다.

그래서 댓글 저장과 사용자 보상 처리를 나눴습니다. 이 글은 당시 구현의 도메인 경계를 정리합니다. 자동 생성임을 사용자에게 어떻게 표시했는지, 실제 참여 지표에서 어떻게 구분했는지는 기록으로 확인하지 못했으며 구현 완료로 단정하지 않습니다.

## 생성 시점의 차단만으로는 부족했다

후속 경로를 따라가며 세 지점을 확인했습니다. 추첨 후보 조회, 나중에 경품 기능을 연결할 때 기존 댓글 작성자에게 응모권을 소급 발급하는 처리, 운영자가 베스트 댓글을 선택해 당첨자로 연결하는 처리였습니다.

자동 생성 경로에서 응모권을 만들지 않아도 소급 처리에서는 다시 대상이 될 수 있습니다. 운영자 선택도 별도 변경 경로이므로 조회 필터만으로 보호되지 않습니다. 후보 조회와 소급 적립에는 제외 조건을, 부적격 선택에는 오류를 반환하는 계약을 두었습니다.

자동 계정 식별은 당시 기존 ID 범위 관례를 재사용했습니다. 마이그레이션은 줄었지만 범위 안에 실제 사용자가 없다는 가정이 생깁니다. 그 범위의 순도를 검증하지 않았다면 안전하다고 확정할 수 없습니다. 실제 ID 값은 공개하지 않았습니다.

## 예약은 되었지만 워커가 함수를 몰랐다

게시 시각을 개별 예약하는 방식으로 진행했는데, 예약이 실행되는 시점에 태스크가 등록되어 있지 않았습니다. 서브패키지의 태스크가 기존 자동 탐색 경로에 포함되지 않은 것이 원인이었습니다.

워커 기동 시 import되는 등록 목록에 추가하고 변경 전후의 등록 상태를 대조했습니다. 스케줄 테이블에 예약이 있다는 사실은 worker가 해당 작업을 실행할 수 있다는 뜻이 아니었습니다. 생성·예약·실행을 각각 관찰해야 했습니다.

## 보상 제외와 서비스 효과를 구분했다

당시 테스트 기록에는 보상 경로의 제외와 태스크 등록 수정이 남아 있습니다. 실제 생성 성공률과 사용자 참여 효과는 별도로 측정할 항목이었습니다. 자동 댓글 수를 사용자 참여 증가로 바꾸어 설명하지 않았습니다.

기능을 추가할 때 생성 함수만 검토하면 이후 데이터를 소비하는 경로를 놓치기 쉽습니다. 이번에는 저장 이후의 보상 계약을 따라가며 직접 생성하지 않은 응모권이 생길 수 있는 지점을 찾아 분리했습니다.

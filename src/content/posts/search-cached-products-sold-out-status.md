쇼핑몰에서 상품을 검색한 고객은 결과의 순서와 품절 표시를 보고 무엇을 살지 고릅니다. 그런데 검색 상위에 품절 상품이 남는 문제가 있었습니다. 검색 점수에는 품절 상품을 뒤로 보내는 처리가 있었지만, 검색 인덱스의 상태와 현재 DB의 상태는 다를 수 있었습니다. 관찰한 품절 노출이 단순한 갱신 지연인지, 오래된 품절 상태가 재색인에도 반영되지 않은 것인지는 별도 조사가 필요했습니다.

이번 수정은 인덱스 갱신 구조를 바꾸는 대신, 이미 선택된 응답 페이지 안에서 현재 품절 상품을 뒤로 보내는 범위로 잡았습니다. 검색 조건과 집계, 페이지 크기를 유지하면서 판매 가능한 상품을 먼저 보여주려는 변경입니다.

## 상품 객체도 캐시되어 있었습니다

처음에는 응답 직전 상품 객체의 품절 값을 보고 순서를 바꿨습니다. 하지만 검색 결과는 상품 객체까지 캐시하고 있었습니다. 캐시를 만든 뒤 품절된 상품이라면 그 객체는 여전히 판매 중이라고 답합니다. 정렬을 한 번 더 한다고 조회 기준까지 최신이 되는 것은 아니었습니다.

그래서 현재 페이지의 상품 ID를 모아 DB에서 품절 ID를 한 번에 읽도록 보완했습니다. 예를 들어 검색 순서가 A, B, C, D이고 DB에서 B와 D가 품절이라고 해보겠습니다. 응답은 A, C, B, D가 됩니다. 판매 상품끼리, 품절 상품끼리의 상대 순서는 유지하므로 검색이 정한 관련도를 그룹 안에서는 그대로 사용합니다.

이는 전체 검색 결과를 다시 정렬하는 방식은 아닙니다. 다음 페이지의 판매 상품을 현재 페이지로 끌어오지 않고, 품절 상품을 결과에서 제외하지도 않습니다. 페이지를 넘나드는 순위와 검색 인덱스 자체의 상태는 이 변경으로 해결되지 않습니다.

## 뒤로 옮긴 상품의 표시도 같은 기준으로

DB 기준으로 순서만 바꾸면 다른 문제가 남습니다. 앞의 B를 뒤로 보냈는데 직렬화할 때 캐시된 객체를 그대로 사용하면 화면에는 판매 중으로 표시될 수 있습니다. 반대로 캐시에는 품절이지만 DB에서는 다시 판매 중인 상품도 있습니다.

정렬 결과와 함께 그때 읽은 품절 ID 집합을 반환하고, 응답의 품절 표시도 같은 집합으로 덮어쓰도록 했습니다. 공유 캐시에 들어 있는 상품 객체를 수정하지 않고 요청마다 만드는 응답 데이터만 보완합니다. 정렬과 표시 사이에 DB를 또 읽지 않으므로 두 판단의 기준도 갈라지지 않습니다. 다만 그 조회 이후 발생한 재고 변경까지 반영하는 실시간 보장은 아닙니다.

테스트에는 캐시 판매 중·DB 품절과 캐시 품절·DB 판매 중을 모두 넣었습니다. 어느 방향으로 상태가 달라도 순서와 표시가 일치하고, 캐시 객체는 바뀌지 않는지 확인했습니다. 읽기 전용 DB·검색 인덱스를 이용한 표본에서도 품절 상품을 페이지 뒤로 옮기는 동안 판매 상품의 상대 순서가 유지됐습니다. 이 검증에서는 Redis 쓰기와 비동기 작업 발행을 차단했습니다.

변경은 10월 26일 main에 병합됐습니다. 관련 테스트는 통과했지만 확대 실행에는 변경 전에도 재현되는 실패가 남아 있습니다. 응답 페이지마다 추가한 DB 조회의 운영 지연과 배포 후 품절 상위 노출 빈도는 아직 측정하지 않았습니다. 인덱스 갱신 문제를 조사하는 동안에도 응답의 순서와 표시가 서로 다른 상태를 말하지 않도록 맞춘 수정입니다.

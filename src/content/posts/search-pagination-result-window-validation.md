쇼핑몰의 상품 목록은 페이지 번호와 한 페이지에 볼 개수를 받아 검색합니다. 운영 요청에서 page=1000, num=20이 들어왔을 때 서버가 500을 반환했습니다. 두 값 모두 양의 정수였지만, 검색 가능한 범위까지 보장하는 입력은 아니었습니다.

이 요청의 검색 시작 위치는 (1000 - 1) × 20 = 19,980입니다. 서비스는 조회 한도 10,000 안에서 남은 수만 요청하도록 계산하고 있었는데, 시작 위치가 이미 한도를 넘으면 남은 수가 음수가 됩니다. 이 값이 검색 엔진으로 전달됐습니다.

## 정상 페이지의 계산을 유지하며 초과만 거절하기

공통 검색 진입점에서 시작 위치를 계산하고 한도보다 크면 입력 오류를 발생시키도록 했습니다. 검사는 캐시 조회보다 먼저 실행합니다. 캐시에 결과가 있는지, 오타 교정 경로를 사용하는지에 따라 같은 페이지의 유효성이 달라지지 않게 하기 위해서입니다.

한도 근처의 정상 요청은 기존 계산을 유지했습니다. 예를 들어 page=500, num=20이면 시작 위치는 9,980이고 남은 20개만 조회합니다. 시작 위치가 9,999라면 유효 크기는 1입니다. 정확히 10,000인 경우에는 기존 크기 0 계산을 유지하고, 이를 넘는 경우를 새로 거절합니다. 이 구분은 계산 함수의 회귀로 확인했으며 크기 0 요청의 실제 검색 엔진 연동을 새로 검증한 것은 아닙니다.

[OpenSearch의 페이지 조회 문서](https://docs.opensearch.org/latest/search-plugins/searching-data/paginate/)에서도 from과 size로 조회 범위를 정합니다. 여기서 사용한 10,000은 이 서비스 코드의 조회 한도이며, 이번 수정은 인덱스 설정 변경이나 더 깊은 페이지를 탐색하는 방식의 도입을 포함하지 않습니다.

## 공통 예외를 각 API가 어떻게 돌려주는지

공통 함수가 예외를 발생시켜도 실제 응답이 기존 클라이언트와 맞는지는 따로 확인해야 했습니다. 일반 상품 목록과 연령대별 목록은 표준 오류 객체를 사용하고, 키워드 검색은 message를 바로 반환하는 기존 형태가 있었습니다. 실제 View를 호출하는 회귀에서 각각의 400 응답을 확인했습니다.

DB 비사용 회귀는 통과했고, DB 연결이 필요한 기존 헬퍼 테스트는 환경 준비 오류 뒤 최종 실행에서 제외했습니다. 따라서 전체 검색 회귀를 통과했다고 볼 수는 없습니다. 변경은 11월 5일 main에 병합됐으며 실제 OpenSearch 연동과 운영 배포 후 확인은 남아 있습니다. 확인한 것은 잘못된 범위를 검색 전에 거절하면서 정상 경계 계산과 기존 오류 형식을 유지한 동작입니다.

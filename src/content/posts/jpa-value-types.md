> 김영한님의 JPA 로드맵을 따라 학습하면서 정리한 노트입니다.

## JPA의 데이터 타입 분류

### 엔티티 타입

- `@Entity` 로 정의하는 객체
- 데이터가 변해도 식별자로 지속해서 추적 가능
- 예) 회원의 이름이나 나이를 바꿔도 같은 식별자로 추적합니다. 식별자 자체는 바꾸지 않습니다.

### 값 타입

- `int`, `Integer`, `String` 처럼 단순히 값으로 사용하는 자바 기본 타입이나 객체
- 식별자가 없고, 값만 있으므로 변경 시 추적이 불가능합니다.
- 예) 숫자 100 을 200 으로 변경하면 완전히 다른 값으로 대체됩니다.

## 값 타입 분류

- **기본값 타입**
  - 자바 기본 타입 (`int`, `double`)
  - 래퍼 클래스 (`Integer`, `Long`)
  - `String`
- **임베디드 타입** (embedded type, 복합 값 타입)
- **컬렉션 값 타입** (collection value type)

### 기본값 타입

- 생명주기를 엔티티에 의존합니다.
  - 예) 회원을 삭제하면 이름, 나이 필드도 함께 삭제됩니다.
- 변경 가능한 값 객체를 여러 소유자가 공유하면 한쪽 수정이 다른 쪽에 영향을 줄 수 있습니다. 불변 값 객체의 공유는 이 문제와 구분합니다.
  - 예) 회원 이름 변경 시 다른 회원의 이름도 함께 변경되면 안 됩니다.

## 임베디드 타입

- 새로운 값 타입을 직접 정의할 수 있습니다.
- `JPA` 는 임베디드 타입 (embedded type) 이라 부릅니다.
- 주로 기본값 타입을 모아서 만들어서 복합 값 타입이라고도 합니다.
- `int`, `String` 과 같은 타입입니다.

### 임베디드 타입 사용법

- **`@Embeddable`**: 값 타입을 정의하는 곳에 표시
- **`@Embedded`**: 값 타입을 사용하는 곳에 표시
- 기본 생성자 필수

### 임베디드 타입의 장점

- 재사용
- 높은 응집도
- `Period.isWork()` 처럼 해당 값 타입만 사용하는 의미 있는 메소드를 만들 수 있습니다.
- 임베디드 타입을 포함한 모든 값 타입은, 값 타입을 소유한 엔티티에 생명주기를 의존합니다.

### 임베디드 타입과 테이블 매핑

- 임베디드 타입은 엔티티의 값일 뿐입니다.
- 임베디드 타입을 사용하기 전과 후에 **매핑하는 테이블은 같습니다**.
- 객체와 테이블을 아주 세밀하게 (fine-grained) 매핑하는 것이 가능합니다.
- 잘 설계한 `ORM` 어플리케이션은 매핑한 테이블의 수보다 클래스의 수가 더 많습니다.

### @AttributeOverride: 속성 재정의

- 한 엔티티에서 같은 값 타입을 사용하려면?
- 컬럼이 중복되는 문제가 발생합니다.
- **`@AttributeOverrides`, `@AttributeOverride`** 를 사용해서 컬럼명 속성을 재정의할 수 있습니다.

### 객체 타입의 한계

- 항상 값을 복사해서 사용하면 `공유 참조` 로 인한 부작용을 피할 수 있습니다.
- 문제는 임베디드 타입처럼 **직접 정의한 값 타입은 자바의 기본 타입이 아니라 객체 타입**입니다.
- 자바 기본 타입은 값을 대입하면 값을 복사하지만, **객체 타입은 참조 값을 직접 대입하는 것을 막을 방법이 없습니다 (공유 참조를 피할 수 없음)**.

### 불변 객체

- 객체 타입을 수정할 수 없게 만들면 **부작용을 원천 차단할 수 있습니다**.
- **값 타입은 불변 객체 (immutable object) 로 설계해야 합니다.**
- **불변 객체**: 생성 시점 이후 절대 값을 변경할 수 없는 객체
- Setter를 없애는 것만으로 충분하지는 않습니다. 다른 변경 메서드와 내부 가변 객체의 노출도 막아야 합니다. JPA가 사용하는 기본 생성자·필드 접근은 별도로 고려합니다.
- 참고: `Integer`, `String` 은 자바가 제공하는 대표적인 불변 객체입니다.

## 값 타입의 비교

- 값 타입은 인스턴스가 달라도 그 안의 값이 같으면 같은 것으로 봐야 합니다.
- **동일성 (identity) 비교**: 인스턴스의 참조 값을 비교, `==` 사용
- **동등성 (equivalence) 비교**: 인스턴스의 값을 비교, `equals()` 사용
- 값 타입은 `a.equals(b)` 를 사용해서 동등성 비교를 해야 합니다.
- 값 타입의 `equals()` 메소드를 적절하게 재정의합니다 (주로 모든 필드 사용).

## 값 타입 컬렉션

- 값 타입을 하나 이상 저장할 때 사용합니다.
- `@ElementCollection`, `@CollectionTable` 사용
- JPA의 일반적인 `@ElementCollection` 매핑은 소유자 테이블과 별도인 컬렉션 테이블을 사용합니다. DB에 JSON·배열 타입이 있는지와는 별개의 매핑 선택입니다.

### 값 타입 컬렉션의 제약사항

- 값 타입은 엔티티와 다르게 식별자 개념이 없습니다.
- 값은 변경하면 추적이 어렵습니다.
- Hibernate의 bag 형태 컬렉션은 특정 원소 변경 시 소유자의 컬렉션 행을 지우고 다시 넣는 방식이 될 수 있습니다. Set·순서 컬럼 유무·매핑과 구현 버전에 따라 SQL이 달라지므로 항상 전체 재삽입한다고 단정하지 않습니다.
- 모든 컬럼을 반드시 PK로 묶어야 한다는 JPA 규칙은 없습니다. 중복·null 허용 여부는 컬렉션 의미와 실제 테이블 제약을 확인합니다.
- 예를 들어 배송지 이력을 한 건씩 추적·수정해야 한다면 별도 ID가 있는 엔티티가 다루기 쉽습니다. 단순 태그 집합과 같은 모델로 취급하지 않습니다.

### 값 타입 컬렉션 대안

- 실무에서는 상황에 따라서 **값 타입 컬렉션 대신에 일대다 관계를 고려합니다**.
- 일대다 관계를 위한 엔티티를 만들고, 여기에서 값 타입을 사용하는 방식으로 합니다.
- 영속성 전이 (Cascade) + 고아 객체 제거를 사용해서 값 타입 컬렉션처럼 사용합니다.

## 정리

- **엔티티 타입의 정리**
  - 식별자가 있습니다.
  - 생명 주기 관리
  - 공유
- **값 타입의 특징**
  - 식별자가 없습니다.
  - 생명 주기를 엔티티에 의존합니다.
  - 변경 가능한 객체를 공유하지 않도록 주의합니다. 불변 값의 공유는 구분합니다.
  - 불변 객체로 만드는 것이 안전합니다.
- 값 타입은 정말 값 타입이라 판단될 때만 사용합니다.
- 엔티티와 값 타입을 혼동해서 엔티티를 값 타입으로 만들면 안 됩니다.
- **식별자가 필요하고, 지속해서 값을 추적·변경해야 한다면 그것은 값 타입이 아니라 엔티티입니다.**

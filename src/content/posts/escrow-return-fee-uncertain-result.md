주문 결제 후 배송정보를 보내고 구매확정이나 취소 통지를 받는 에스크로 연동을 작업했습니다. 여기서 에스크로는 고객이 낸 돈을 바로 판매자에게 지급하지 않고 구매 진행 상태에 따라 처리하는 결제 흐름입니다. 반품 시 고객이 별도로 내는 반품비와 원래 주문 금액의 환불도 연결해야 했습니다.

외부 결제 시스템과 통신할 때는 응답을 받지 못한 경우를 따로 다뤄야 합니다. 예를 들어 결제대행사(PG)는 요청을 처리했는데 응답만 유실되어 서버에서 timeout이 났다고 해보겠습니다. 이를 실패로 저장하고 같은 처리를 반복하면 중복 금융 처리로 이어질 수 있습니다. 다음 내용은 2026년 9월 구현부터 10월 8일까지의 후속 보완과 격리 환경 검증을 다룹니다. 기반 PR은 main에, 의존 PR은 각 선행 브랜치에 병합됐습니다. 아래 전체 취소 API는 별도로 main 병합을 확인했지만 운영 배포와 실제 PG 연동까지 확인한 사례는 아닙니다.

## timeout 뒤에는 결과를 아직 모른다는 상태가 필요했다

로컬 DB에 요청 기록이 있다는 사실만으로 PG의 처리 결과를 알 수는 없습니다. 반대로 응답을 못 받았다는 이유만으로 PG가 아무것도 하지 않았다고 볼 수도 없습니다. 명확한 성공, 명확한 실패, 결과 불명을 구분했습니다.

같은 요청을 여러 번 보내도 한 번만 처리하는 원격 멱등성이 없는 경로에서는 자동 재전송이 특히 조심스러웠습니다. 결과 불명 요청을 보존하고, 결과 조회나 운영 확인으로 근거를 얻은 뒤 다음 처리를 결정하도록 했습니다. 자동 복구가 늦어질 수 있지만 확인되지 않은 금융 요청을 곧바로 반복하지 않게 됩니다.

예를 들어 PG가 처리를 완료한 직후 응답만 유실되고, 뒤늦게 성공 통지가 도착하는 순서를 생각할 수 있습니다. timeout 시점에는 로컬 기록을 `UNKNOWN`으로 남기고 자동 재전송을 멈춥니다. 이후 인증된 통지나 결과 조회로 같은 거래의 성공을 확인하면 성공 상태로 확정합니다. 같은 통지가 또 와도 이미 확정한 거래를 다시 실행하는 근거로 쓰지 않습니다. 이 예는 불명 상태를 보존하는 이유를 설명하며, PG별 조회·통지 계약의 검증까지 완료됐다는 뜻은 아닙니다.

## 외부로 보낼 일과 외부에서 받은 통지를 기록했다

배송정보 전송처럼 밖으로 보낼 작업은 Outbox로, 구매확정·취소처럼 들어오는 통지는 Inbox로 추적했습니다. 각각 “무엇을 보내야 하는가”와 “어떤 이벤트를 받았는가”를 DB에 남기는 기록입니다.

같은 통지가 여러 번 오거나 오래된 통지가 늦게 도착할 수 있어 식별자와 현재 상태를 확인했습니다. Outbox에 기록했다고 PG가 중복 요청을 알아서 막아주는 것은 아닙니다. 요청 기록과 실제 외부 처리의 성공은 계속 구분해야 합니다.

## 같은 주문의 돈이라도 거래는 분리했다

원래 상품 대금의 환불과 반품비의 결제·환불은 금액과 거래가 다릅니다. 같은 주문을 가리킨다고 하나의 결제 상태로 처리하면 무엇을 취소하거나 환불했는지 모호해집니다. 반품 사유에 따른 비용 부담과 납부 안내도 나누어 연결했습니다.

반품비는 기존 결제 준비 정보와 실제 결제 정보, 프론트의 결제 준비 요청 흐름을 재사용했습니다. 별도 시도 상태를 더한 부분이 기존 재시도 흐름과 충돌해 정리하기도 했습니다. 같은 요청의 진행 상태를 두 곳에서 다르게 해석하지 않도록 맞추는 작업이었습니다.

금액·권한·상태·환불 회귀는 전용 MySQL 모델로 검증했고 일부 환불 모듈의 라인·분기 커버리지도 확인했습니다. 다만 PG 소켓을 차단한 테스트 환경이었습니다. 실제 migration과 PG 샌드박스, 프론트 연동 및 결과 불명 상태의 운영 복구는 다음 검증으로 남았습니다.

## 전체를 선택해도 PG에는 부분 취소가 나갈 수 있었다

10월에는 배송 전 주문 전체 취소에서도 같은 결과 불명·복구 흐름을 사용했습니다. 기존 상품별 취소 API는 고객이 모든 상품을 선택해도 PG에 상품별 금액을 나누어 요청했습니다. 에스크로에서 부분 취소를 허용하지 않는다면 화면의 ‘전체 선택’만으로는 전액 취소가 되지 않습니다.

주문 전체 상품을 서버가 결정하고 원결제 전액을 한 번 요청하는 전용 API를 추가했습니다. 주문 소유권과 모든 상품의 결제·배송·교환·반품·환불 이력을 확인한 뒤 기존 환불 실행 기록에 취소를 예약합니다. 성공을 확인하면 취소 원장, 상품 상태, 재고, 포인트, 쿠폰과 응모권을 함께 반영합니다. 요청자가 상품 목록이나 금액을 줄여 보내 부분 취소로 바꾸지 못하도록 입력 범위도 제한했습니다.

PG 성공 뒤 DB 반영이 실패하는 순서도 다뤘습니다. 업무 변경은 롤백하되 재요청에서는 저장된 성공 근거나 PG 조회 결과를 사용해 DB 반영을 복구합니다. 완료 여부가 불명확한 거래에 취소 요청을 곧바로 다시 보내는 방식은 피했습니다. 출고 변경도 상품 잠금 뒤 최신 상태와 환불 예약을 다시 확인하게 해, 최초 조회 뒤 취소가 시작된 상품에 송장·배송 이벤트를 만드는 일을 막도록 했습니다.

로컬 DB·API 회귀에서는 PG 성공 후 DB 실패, 응답 유실, 중복 요청과 최초 조회·잠금 사이의 상태 변경 및 행 삭제를 다뤘습니다. 외부 PG·알림은 대체한 검증이며 별도 연결의 실제 동시 부하 검증으로 확대할 수는 없습니다. 상품별 부분 취소 거절을 보완하던 별도 구현은 미병합 종료됐고, 전액 취소 API가 10월 8일 main에 병합됐습니다. 현재 지원 범위는 배송 전 Toss 에스크로 주문 전체 취소이며, 프론트 호출 변경과 판매자 품절 취소 연동은 남아 있습니다.

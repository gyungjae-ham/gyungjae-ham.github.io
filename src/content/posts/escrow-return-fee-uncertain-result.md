결제대행사(PG)에 요청을 보냈는데 응답을 받지 못하면 실패로 처리해도 될까요. 서버에는 timeout으로 보이지만, 결제대행사는 이미 처리를 끝냈을 수 있습니다. 같은 요청을 곧바로 다시 보내면 돈과 관련된 처리가 중복될 가능성이 있습니다.

에스크로와 반품비 연동을 구현하면서 이 상황을 따로 다뤘습니다. 에스크로는 고객이 낸 돈을 바로 판매자에게 지급하지 않고 구매 진행 상태에 따라 처리하는 결제 방식입니다. 배송정보를 보내고 구매확정·취소 통지를 받는 흐름에 더해, 반품비 결제와 원래 상품 대금의 환불도 연결해야 했습니다.

## 응답을 못 받은 요청의 상태

요청이 명확히 성공한 경우, 명확히 거절된 경우, 결과를 모르는 경우를 나눴습니다. 로컬 DB에 요청 기록이 남았다고 외부 처리가 성공한 것은 아니고, 응답이 없다고 아무 일도 일어나지 않은 것도 아니기 때문입니다.

예를 들어 다음 순서를 생각해보겠습니다.

```text
서버가 취소 요청 전송
  → PG에서 취소 완료
  → 응답 유실로 서버에서 timeout
  → 뒤늦게 성공 통지 도착
```

timeout 시점에는 `UNKNOWN`으로 남기고 자동 재전송을 멈춥니다. 인증된 통지나 결과 조회로 같은 거래의 성공을 확인한 뒤 상태를 확정합니다. 같은 통지가 또 오더라도 금융 요청을 다시 보내는 계기로 삼지 않습니다.

이 예시는 결과 불명 상태가 필요한 이유입니다. 실제로는 PG별 조회·통지 규칙도 검증해야 합니다. 특히 원격 시스템이 같은 요청의 중복을 막아주지 않는 경로라면, 재시도를 빨리 하는 것보다 이전 요청의 결과를 먼저 확인해야 합니다.

## 보낼 작업과 받은 통지를 DB에 남기기

배송정보처럼 외부로 보낼 작업은 Outbox에, 구매확정·취소처럼 외부에서 받은 통지는 Inbox에 기록했습니다. 각각 앞으로 보내야 할 일과 이미 받은 이벤트를 DB에서 추적하기 위한 기록입니다.

통지는 반복해서 오거나 순서가 바뀔 수 있어 식별자와 현재 상태를 확인합니다. 다만 Outbox에 저장했다는 이유로 PG도 요청을 한 번만 처리하는 것은 아닙니다. 전송 기록을 남기는 처리와 외부의 중복 방지는 별개로 확인해야 합니다.

반품에서도 거래를 나눴습니다. 고객에게 돌려주는 원래 상품 대금과 고객이 새로 내는 반품비는 같은 주문에 연결돼도 다른 돈입니다. 하나의 결제 상태로 합치면 어떤 거래를 취소하거나 환불했는지 구분하기 어렵습니다.

반품비는 기존 결제 준비 정보와 실제 결제 정보, 프론트의 준비 요청 흐름을 재사용했습니다. 새 시도 상태를 추가했다가 기존 재시도 흐름과 충돌한 부분은 정리했습니다. 같은 요청을 두 곳에서 서로 다른 상태로 판단하지 않게 맞추는 작업이었습니다.

## 화면의 전체 선택과 PG 전액 취소

10월에는 배송 전 주문 전체 취소 API를 추가했습니다. 기존 상품별 취소 API는 고객이 모든 상품을 선택해도 PG에 상품별 금액을 나눠 요청했습니다. 상품 두 개를 모두 선택했다고 해도 각각 취소하면 외부에는 두 번의 부분 취소가 됩니다. 부분 취소를 허용하지 않는 에스크로에서는 화면의 전체 선택만으로 해결할 수 없었습니다.

전용 API는 서버가 주문의 모든 상품을 결정하고 원결제 전액을 한 번 요청하도록 했습니다. 소유권과 각 상품의 결제·배송·교환·반품·환불 이력을 확인한 뒤 기존 환불 실행 기록에 취소를 예약합니다. 고객이 상품 목록이나 금액을 줄여 보내 부분 취소로 바꿀 수 없도록 입력도 제한했습니다.

성공이 확인되면 취소 원장, 상품 상태, 재고, 포인트, 쿠폰, 응모권을 함께 반영합니다. 여기서 PG는 성공했지만 DB 반영에 실패하는 경우도 있습니다. 업무 변경은 롤백하되, 재요청에서는 저장된 성공 근거나 PG 조회 결과로 DB 반영을 복구하도록 했습니다. 결과를 모르는 거래에 취소부터 다시 요청하지 않습니다.

출고 처리와 겹치는 경우도 고려했습니다. 처음 조회할 때는 취소 전이었어도 상품 잠금을 얻기 전에 환불이 예약될 수 있습니다. 출고 변경은 잠금 뒤 최신 상태와 환불 예약을 다시 확인하도록 해, 취소가 시작된 상품에 송장과 배송 이벤트를 만들지 않게 했습니다.

## 전액 취소 확인과 은행 환불 대기 구분하기

10월 12일에는 가상계좌 결제의 전액 취소가 확인됐는데도 내부 취소 처리가 보류되는 조건을 보완했습니다. PG의 결제 취소와 은행 계좌로 돈을 돌려주는 절차가 서로 다른 시점에 진행되기 때문입니다. 예를 들어 PG에서 전액 취소를 확인했지만 계좌 환불은 대기 중인 경우, 환불 대기라는 이유만으로 주문 취소와 재고·포인트 복원까지 계속 막을 것인지 구분해야 합니다.

처음 수정에서는 전액 취소를 검증한 뒤 계좌 환불 완료를 기다리지 않고 내부 취소를 진행하도록 했습니다. 그런데 후속 리뷰에서 이 조건이 명시적인 환불 실패도 통과시킨다는 문제가 확인됐습니다. 같은 날 보완해 환불 대기는 허용하되, 실패나 부분 실패가 명시되면 내부 반영을 보류하도록 바꿨습니다. 응답의 상태 값이 배열이나 객체처럼 예상한 자료형이 아닌 경우도 성공으로 해석하지 않고 보류합니다.

보류된 요청을 다시 받을 때에는 PG 취소를 재전송하지 않고 결과를 조회합니다. 로컬 테스트에서는 환불 실패 응답에 주문·재고·포인트가 바뀌지 않는지, 이후 허용 가능한 환불 대기 상태가 조회되면 추가 취소 요청 없이 내부 반영을 복구하는지 확인했습니다. 관련 변경은 10월 12일 main에 병합됐습니다. 준비된 로컬 MySQL 스키마와 PG HTTP 대역을 사용한 검증이며, 실제 은행 환불이나 기존 보류 주문의 운영 복구 결과는 아직 확인하지 못했습니다.

이 보완은 현재 응답에서 확인한 실패를 처리하는 범위입니다. 환불 대기 상태를 허용해 내부 취소를 완료한 뒤 나중에 은행 환불이 실패하는 경우의 감지와, 이미 완료한 건의 재점검까지 포함하지는 않습니다.

## 배송 중 취소에서도 성공 근거를 먼저 남기기

10월 22일에는 판매자 관리 화면의 취소 경로에 같은 복구 원칙을 연결했습니다. 기존에는 에스크로 상품에 송장이나 배송 이벤트가 있으면 원결제 전액을 취소할 수 있는 경우에도 반품 경로를 거쳐야 했습니다. 후속 구현은 구매확정·교환·반품·환불 이력이 없고, 선택 상품의 결제금액이 원결제 전액과 같은 경우 배송 중 취소를 허용합니다. 일부 금액만 취소하는 요청에는 적용하지 않습니다.

이 경로에는 품절 처리와 보상 같은 후처리도 있습니다. 예를 들어 PG가 전액 취소를 완료한 뒤 품절 후처리 저장이 실패한다고 해보겠습니다. 성공 근거까지 함께 롤백하면 다음 요청에서 이미 끝난 PG 취소를 다시 보내야 하는지 판단하기 어렵습니다. 그래서 취소 예약을 먼저 커밋하고 DB 트랜잭션 밖에서 PG를 호출한 뒤, 검증된 성공 결과를 별도로 저장하도록 했습니다. 환불 내역·상품 상태·포인트·품절 후처리는 그다음 트랜잭션에서 함께 반영합니다.

후처리만 실패했다면 같은 API의 재요청이나 운영자 복구에서 저장된 성공 결과를 읽고 내부 처리만 재개합니다. 응답 자체를 받지 못했다면 PG 결과를 조회하며 새 취소 요청부터 보내지 않습니다. 취소 대상과 품절 여부도 예약에 남겨, 복구 때 다른 상품을 취소하거나 일반 주문취소의 후처리로 바뀌지 않게 했습니다. 성공 근거 저장마저 끝나지 않은 경우에는 저장된 성공이 있다고 가정할 수 없으므로 결과 확인이 필요합니다.

배송 이벤트를 보내는 작업도 취소 예약과 같은 상품 잠금 안에서 상태를 확인합니다. 배송 전송 중에는 취소를 보류하고, 취소 예약 중에는 배송 전송을 보류하도록 맞췄습니다. 새 예약 형식은 새 버전 서버에서 복구해야 하고 배송 작업자에도 변경이 반영돼야 합니다. API 서버만 교체하는 것으로 적용이 끝나는 변경은 아닙니다.

로컬 테스트에서는 PG 성공 후 상태·품절·보상 저장에 실패를 넣고, 같은 요청과 운영자 복구가 금융 요청을 반복하지 않고 내부 처리를 완료하는지 확인했습니다. 실제 HTTP 클라이언트와 로컬 PG 대역으로 응답 유실 뒤 결과 조회도 검증했습니다. 변경은 10월 22일 main에 병합됐지만 실제 PG 상점 환경과 운영 배포는 확인되지 않았습니다.

## 구현과 검증을 진행한 범위

9월 구현부터 10월 8일 후속 보완까지 금액·권한·상태·환불을 전용 MySQL 환경에서 검증했습니다. PG 성공 뒤 DB 실패, 응답 유실, 중복 요청, 조회와 잠금 사이의 상태 변경·행 삭제를 테스트했습니다. 외부 PG와 알림은 대체했으며 실제 동시 부하나 PG 연동을 검증한 결과는 아닙니다.

기반 PR은 main에, 의존 PR은 각 선행 브랜치에 병합됐습니다. 상품별 부분 취소 거절을 보완하던 별도 구현은 미병합으로 종료됐고, 주문 전액 취소 API는 10월 8일 main에 병합됐습니다. 고객 전용 API는 배송 전 Toss 에스크로 주문의 전체 취소를 지원합니다. 10월 22일의 판매자 관리 화면 취소 확장은 위에서 설명한 별도 조건을 따릅니다. 실제 migration, PG 샌드박스, 프론트 호출 변경과 결과 불명 거래의 운영 복구는 후속 확인이 남았습니다.

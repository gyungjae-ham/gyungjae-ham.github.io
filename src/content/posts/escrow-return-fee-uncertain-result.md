> 결제 요청이 실패한 것인지 응답만 사라진 것인지 모르면 같은 요청을 다시 보내기 어렵습니다. 에스크로와 반품비 구현에서는 중복 이벤트, 결과 불명 상태, 운영 복구를 서로 다른 계약으로 다뤘습니다.

## timeout은 결제 실패의 증거가 아니다

외부 PG가 요청을 처리한 뒤 응답이 유실될 수 있습니다. 원격 멱등성이 없는 경로에서 무조건 재전송하면 동일 금융 처리를 반복할 위험이 있습니다. 실패 응답과 결과를 모르는 상태를 나누고 증거 조회와 운영 복구 경계를 두었습니다.

이 글은 진행 중인 구현의 변경 기록입니다. 원본 확인 시점에 관련 PR은 아직 열려 있었으며 운영 적용이 완료되었다고 표현하지 않습니다. 고객 결제 결과를 공개하거나 실제 거래의 해결 사례로 확장하지도 않았습니다.

## 보낼 이벤트와 받은 이벤트를 구분했다

결제 식별자와 Outbox·Inbox 기반을 먼저 정리한 뒤 배송정보, 구매확정과 취소 callback을 단계적으로 연결했습니다. 외부로 보낼 요청과 외부에서 도착한 통지를 같은 처리로 묶지 않았습니다.

중복 callback이나 지연 통지가 오더라도 어떤 거래와 상태에 대한 이벤트인지 확인해야 합니다. DB에서 상태를 저장했다는 사실과 PG가 처리를 끝냈다는 사실도 별도 근거입니다. 재시도 가능한 단계와 확인 후 복구해야 하는 단계를 나눈 이유입니다.

## 반품비를 원결제와 섞지 않았다

반품비 결제에는 기존 Staging·Payment와 프론트 ready 계약을 재사용했습니다. 별도 attempt 상태와 중복 ready 경로를 정리해 재시도 때 서로 다른 상태 체계가 충돌하지 않도록 했습니다.

원결제 전체 환불, 반품비 환불, 귀책 저장, 납부 안내는 각각 분리했습니다. 한 주문을 가리킨다고 같은 금액과 거래는 아닙니다. 입금 지연과 결과 불명, 중복 차감을 각 경계에서 확인했습니다. 선행 변경이 먼저 반영되어야 하는 PR 의존성도 유지했습니다.

## 테스트의 높은 숫자가 외부 연동을 대신하지 않는다

기록에는 전용 모델을 이용한 MySQL 검증과 PG 소켓을 차단한 회귀 결과가 있습니다. 일부 환불 모듈의 라인·분기 커버리지도 남아 있지만 저장소 전체 커버리지는 아닙니다. 여러 실행의 테스트 수는 중첩되어 합산하지 않았습니다.

실제 migration, PG 샌드박스, 프론트 배포를 연결한 검증은 이 결과와 별개입니다. 확인한 범위는 구현된 오류·상태·금액·권한 계약입니다. 이 기록에서 가장 중요한 경계는 결과를 모르는 금융 요청을 단순 실패로 취급하지 않았다는 점입니다.

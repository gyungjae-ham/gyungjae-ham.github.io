외부 결제 요청이 timeout으로 끝났습니다. 애플리케이션은 응답을 받지 못했지만 PG가 처리하지 않았다는 뜻은 아닙니다. 이 상태를 실패로 저장하고 다시 보내면 같은 금융 처리를 반복할 수 있습니다.

에스크로와 반품비를 연결하면서 제가 구현한 경계는 **확정 실패와 결과 불명을 다른 상태로 다루는 것**이었습니다. 이 글은 2026년 9월의 리뷰 중 구현을 다루며 운영 배포 완료 사례는 아닙니다.

## 재시도 전에 무엇을 모르는지 남겼다

원격 멱등성이 없는 경로에서는 같은 요청을 다시 보내도 중복을 막는다는 보장이 없습니다. 결과를 모르는 요청은 그대로 보존하고 증거 조회와 운영 복구로 이어지게 했습니다.

로컬 DB에 요청을 기록했다는 사실과 PG가 처리를 끝냈다는 사실은 별개입니다. 성공 응답이나 결과 조회처럼 확정할 근거를 구분하고, 근거 없이 실패로 바꾸지 않았습니다.

| 상태        | 다음 처리                    |
| ----------- | ---------------------------- |
| 명확한 실패 | 실패 원인과 재시도 조건 판단 |
| 확정 성공   | 로컬 상태·후속 이벤트 반영   |
| 결과 불명   | 결과 조회·운영 확인 후 처리  |

이 분리는 자동 복구가 일부 늦어지는 비용이 있습니다. 대신 불확실한 금융 요청을 바로 반복하지 않습니다.

## 보내는 이벤트와 받는 이벤트를 분리했다

배송정보 전송과 구매확정·취소 callback을 단계적으로 연결했습니다. Outbox는 외부로 보낼 작업을, Inbox는 들어온 이벤트를 추적합니다.

같은 callback의 중복과 늦게 도착한 통지가 현재 거래를 다시 변경하지 않도록 식별자와 상태를 검사했습니다. Outbox가 있다고 외부 요청이 자동으로 멱등해지는 것은 아닙니다. 외부 처리 결과를 어떻게 확인할지는 별도 계약입니다.

## 반품비가 같은 주문을 가리켜도 같은 결제는 아니었다

원결제 환불과 반품비 결제·환불은 거래와 금액이 다릅니다. 귀책과 납부 안내도 나눠 연결했습니다.

반품비에는 기존 Staging·Payment와 프론트 ready 계약을 재사용했습니다. 별도 attempt 상태가 기존 재시도 흐름과 충돌하는 부분을 정리했습니다. 새 상태를 더하는 것이 독립성을 주기도 하지만 두 흐름이 같은 요청을 다르게 해석하면 오히려 복구가 어려워집니다.

## 많은 테스트가 PG 연동의 증거는 아니었다

여러 의존 PR에서 전용 MySQL 모델로 금액·권한·상태·환불 회귀를 검증했습니다. 일부 환불 모듈은 라인·분기 커버리지를 확인했고 PG 소켓은 차단한 환경이었습니다. 실행 범위가 겹치므로 테스트 수를 합산하지 않았습니다.

이 검증은 실제 migration, PG 샌드박스, 프론트 연결을 대신하지 않습니다. 다음 확인 대상은 그 연동과 결과 불명 상태의 운영 처리입니다.

지금 단계에서 확인한 것은 실패 응답을 만드는 것보다 불확실한 상태를 잃지 않는 구현입니다. timeout 뒤에 무엇을 다시 실행해도 되는지 판단할 근거를 남겼습니다.

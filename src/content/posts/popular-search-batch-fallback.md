인기검색어는 실제 검색 트렌드보다 오래된 수동 입력을 보여주고 있었습니다. 값을 바꾸려면 운영자가 DB를 직접 수정해야 했습니다. 저는 기존 검색 로그로 매시간 갱신하는 배치와 제외어 관리 화면을 만들었습니다.

새 집계가 성공하는 경우보다 먼저 정한 것은 **집계가 실패하거나 결과가 부족할 때 무엇을 보여줄지**였습니다. 자동화를 붙였다는 이유로 정상 목록까지 지우고 싶지는 않았습니다.

## 로그는 있었으므로 새 파이프라인은 만들지 않았다

기존 Athena 검색 로그와 통계 조회 패턴을 재사용했습니다. 검색어별 사용자 수를 집계하고 제외 규칙을 적용했습니다. 새 수집 인프라를 만들지 않은 대신 기존 로그의 날짜 경계와 결과 캐시를 확인해야 했습니다.

Athena 조회의 기본 결과 캐시가 하루 단위라면 매시간 실행해도 같은 결과를 읽을 수 있었습니다. 이 집계에서는 해당 캐시를 끄고 새 로그를 보도록 했습니다.

## 지우고 다시 넣는 대신 새 배치를 추가했다

기존 목록을 삭제한 뒤 새 결과를 넣으면 갱신 중에 비거나 새 집계가 부족한 상태를 덮어쓸 수 있습니다. 배치 시각을 붙여 새 결과를 추가하고 최근 두 배치를 유지했습니다.

후보가 최소 기준보다 적으면 새 적재를 건너뛰고 직전 배치를 계속 읽습니다. 알림으로 갱신 실패를 드러내되 화면까지 빈 목록으로 만들지 않도록 했습니다.

이 구조는 이전 데이터를 남기는 만큼 정리 작업이 필요합니다. 자동 갱신만 추가하면 데이터가 계속 쌓이므로 cleanup도 같은 흐름에 포함했습니다.

## 제외어는 다음 정각까지 기다리지 않았다

수집할 때만 제외하면 운영자가 방금 등록한 단어가 다음 배치까지 남습니다. 읽기에서도 같은 제외 규칙을 한 번 더 적용했습니다.

상위 열 개만 저장하면 제외 후 빈자리를 채우기 어렵습니다. 후보는 서른 개를 준비하고 읽기에서 제외·보충한 뒤 표시 순번을 다시 매겼습니다. 후보가 모두 부족한 경우까지 개수를 보장하는 것은 아니지만 정상 풀 안에서 제외된 자리를 채울 수 있습니다.

## 더 좋은 메타가 기존 응답을 깨뜨렸다

갱신 시각을 넣으려 응답을 객체로 감싸는 설계도 있었지만 기존 프론트는 배열을 받고 있었습니다. 자동 갱신을 붙이면서 계약까지 바꿀 이유는 없어 배열 형태로 되돌렸습니다.

어드민에서 제외어 삭제는 문자열 경로 대신 ID를 사용했습니다. 검색어에 슬래시가 포함되면 라우팅으로 해석돼 삭제가 실패한 사례 때문입니다.

백엔드와 어드민 프론트까지 실작업 3일에 구현했습니다. 신규 인프라를 추가하지 않고 운영자의 DB 수정 경로를 화면으로 옮겼습니다. 인기검색어 클릭률은 아직 측정하지 않았습니다. 이 작업에서 확인한 결과는 수동 고정값을 갱신하면서 실패 시 직전 목록과 기존 응답 계약을 지킨 것입니다.

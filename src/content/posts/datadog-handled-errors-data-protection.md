쇼핑 서비스의 요청이 실패하면 개발자는 API 응답만으로 어느 단계가 문제인지 알기 어렵습니다. 요청 안의 DB 조회와 외부 호출을 따라가는 trace와 오류 로그가 필요합니다. 10월 27일부터 29일까지 기존 Sentry 연동을 제거하고 Django·Python 워커에 Datadog 계측을 연결하면서, 어떤 실패를 남기고 어떤 데이터를 보내지 않을지 함께 수정했습니다.

SDK를 교체해도 기존에 보던 오류가 그대로 옮겨지는 것은 아니었습니다. 예외를 잡은 뒤 기본값이나 오류 응답을 반환하는 코드에서는 명시적인 오류 전송을 지우면 기록이 사라집니다. 반대로 새 계측은 애플리케이션이 정상적인 4xx 응답으로 처리한 예외까지 view 오류로 남겼습니다.

## 예외가 발생한 곳과 최종 응답이 다른 경우

먼저 예외를 잡고 계속 진행하는 지점에 traceback을 포함한 오류 로그를 남겼습니다. 반환값과 기존 알림 흐름은 유지하면서, 실패가 로그 없이 사라지는 구간을 줄이려는 변경입니다. 다만 Sentry 전용 리포트와 감지 작업도 제거했으므로 오류 로그를 추가한 것만으로 기존 관측 기능 전체를 대체했다고 볼 수는 없습니다.

전환 뒤에는 정상 4xx가 오류 이슈로 쌓이는 현상이 관측됐습니다. 예를 들어 만료된 인증 정보로 요청하면 인증 예외가 발생할 수 있지만, DRF가 이를 처리해 401로 응답합니다. 그런데 최종 요청 상태와 별개로 view 실행을 감싼 계측 구간에는 예외가 남을 수 있습니다. trace 안에서 각 실행 구간을 기록하는 단위를 span이라고 하는데, 요청 span과 view span이 같은 판단을 하고 있지 않았습니다.

후속 필터는 같은 trace 조각에서 view span의 부모를 따라 요청 span을 찾습니다. 최종 응답이 500 미만으로 확인되면 view의 오류 표시와 메시지·stack을 지우고 예외 종류는 남깁니다. 실제 서버 오류와 DB·Redis·외부 HTTP 구간의 오류는 유지합니다. 요청 span이 조각에 없거나 상태를 해석할 수 없다면 오류를 보존합니다. 판정할 근거가 없는 경우까지 정상으로 지우지 않기 위해서입니다. 적용한 계측 버전은 ddtrace 4.16이며, 요청과 view를 나누는 동작은 [해당 버전의 Django 계측 소스](https://github.com/DataDog/dd-trace-py/blob/v4.16.0/ddtrace/contrib/internal/django/patch.py)와 대조했습니다.

## 정상 실행뿐 아니라 실패 메시지도 확인하기

관측 데이터를 외부로 보내기 전에는 담긴 내용도 줄여야 했습니다. 요청·응답 본문과 query를 그대로 기록하던 경로에서는 이름·연락처·토큰 같은 값이 섞일 수 있습니다. 일부 필드만 가리는 대신 공통 로그에서 본문과 query를 제외하고, 요청 경로·메서드·상태·크기와 처리 식별자 중심으로 남겼습니다. 기존 로그 전송 경로는 유지하고 JSON 로그에 trace ID를 연결했습니다.

Redis도 정상 명령 태그만 정리해서 끝나지 않았습니다. 키·값을 제거했어도 pipeline 실패나 알 수 없는 명령의 오류 메시지에 인자가 다시 들어갈 수 있었습니다. 오류 메시지와 stack에서도 해당 인자를 지우고 명령 이름은 보존하도록 보완했습니다. 다른 종류의 오류 정보까지 일괄 삭제하지는 않았습니다.

이 선택은 원문을 이용한 진단 정보를 줄입니다. 대신 오류 종류와 상태, trace 연결을 남겨 실패 위치를 따라가도록 했습니다. 모든 로그의 개인정보를 제거하는 범용 필터는 아니며, nginx 에러 로그나 기존 임의 메시지처럼 별도로 점검할 경로도 남아 있습니다.

## 로컬 계측과 실제 수신을 나눠 확인했습니다

로컬에서는 실행 wrapper를 거쳐 Django·Redis span이 생성되고 로그 ID가 연결되는지, 가짜 개인정보가 출력에 남지 않는지 확인했습니다. 후속 4xx 필터는 실제 Django·DRF·ddtrace로 404의 view 오류 표시를 지우면서 예외 종류를 유지하고, 미처리 예외의 500은 보존하는지 검증했습니다. DB나 Datadog Agent 전송을 사용한 검증은 아닙니다.

연동 제거와 계측, 4xx 필터는 10월 29일 main에 병합됐습니다. 전환 후 정상 4xx가 오류로 수집된 운영 관측은 있지만, 필터 배포 후 감소 효과를 확인한 결과는 아직 없습니다. 로컬 trace 생성과 별개로 AWS에서 수신한 로그·trace의 연결, 실제 비동기 워커 전파, 제거한 감지 기능의 공백을 확인해야 전환의 적용 범위를 판단할 수 있습니다.

## 요청 조건을 진단하기 위한 query 수집 조정

11월 2일에는 서버 요청 span의 query 수집을 켰습니다. 초기의 일괄 미수집 정책으로는 GET 요청의 페이지·필터 조건이 사라져 실패한 입력을 구분하기 어려웠기 때문입니다. 외부 HTTP 호출의 query 수집은 계속 끄고 resource 이름도 route 기준으로 유지했습니다. 앞서 설명한 공통 로그 본문·query 제외와 APM 요청 span의 수집 정책은 별개입니다.

서버 query에는 ddtrace의 기본 마스킹을 적용했습니다. 다만 token·password 같은 기본 패턴만으로 전화번호·이메일·검색어까지 보호되는 것은 아닙니다. 사용자 정의 마스킹 정규식도 기본 패턴에 추가되는 방식이 아니므로, 교체할 때 기본 보호 항목을 함께 포함해야 합니다. 이 동작은 [ddtrace 4.16의 설정 소스](https://github.com/DataDog/dd-trace-py/blob/v4.16.0/ddtrace/internal/settings/_config.py)와 대조했습니다. 실제 수집 파라미터 확인과 추가 민감값 마스킹은 남아 있습니다.

로컬 smoke 회귀는 페이지 조건 보존, 가짜 token 마스킹, 외부 호출 query 제외를 확인했습니다. 변경은 11월 2일 main에 병합됐지만 실제 운영 APM 수신과 배포 결과를 확인한 것은 아닙니다.

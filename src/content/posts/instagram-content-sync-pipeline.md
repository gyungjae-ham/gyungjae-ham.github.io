athlog는 인스타그램 게시물을 앱 안에서 볼 수 있게 옮기는 콘텐츠 화면입니다. 운영자가 게시물의 설명과 미디어를 직접 등록하던 과정을, Graph API로 수집하고 S3에 저장하는 Celery 작업으로 바꿨습니다. 정기 수집 외에 운영자가 즉시 실행하는 경로도 필요했습니다.

수집 자체보다 까다로운 부분은 중간 실패였습니다. 외부 다운로드는 끝났는데 DB 등록이 실패할 수 있고, 운영자 실행과 정기 실행이 겹칠 수도 있습니다. 파일과 DB 레코드를 어떤 순서로 만들고 남은 데이터를 어떻게 정리할지 함께 정해야 했습니다.

## 서버가 직접 다운로드하고 업로드한다

수동 등록은 클라이언트가 presigned URL을 받아 S3로 직접 올리는 방식입니다. 수집 작업은 서버가 외부 미디어를 받아야 하므로 워커의 AWS 권한으로 업로드했습니다. presigned URL은 브라우저 전용 기능은 아니지만, 이 경로에서는 별도 서명 URL을 발급할 이유가 크지 않았습니다.

다운로드 응답 전체를 `BytesIO`에 담는 대신 `requests`의 streaming 응답을 `upload_fileobj`에 전달했습니다. 큰 파일을 통째로 잡지 않으려는 선택입니다. 다만 multipart 내부 버퍼와 동시 업로드 수가 있으므로 워커 메모리가 항상 단일 청크 크기에 고정된다고 보장할 수는 없습니다.

`Content-Length`로 큰 파일을 일찍 거르는 검사도 넣었습니다. 이 헤더가 없거나 잘못된 경우, 압축 해제 후 크기가 달라지는 경우에는 충분하지 않습니다. 강제 크기 제한에는 실제 읽은 바이트의 누적 검사와 업로드 중단·정리가 필요합니다. 헤더 검사만으로 제한을 완성했다고 설명해서는 안 됩니다.

## 중복 실행과 중복 적재는 별개다

정기 작업과 운영자 실행이 겹치지 않도록 Redis의 원자적 키 생성과 만료 시간을 사용했습니다. 하지만 만료 시간이 있는 락은 작업 시간이 그보다 길어질 수 있다는 조건을 가집니다.

예를 들어 작업 A의 락이 만료된 뒤 작업 B가 새 락을 얻었는데, A가 뒤늦게 종료하며 같은 키를 무조건 지우면 B의 락까지 삭제됩니다. 소유자마다 다른 토큰을 두고 **자기 토큰과 일치할 때만 원자적으로 해제**해야 합니다. 필요하면 소유권을 확인하며 만료를 연장하는 방식도 검토합니다. [Redis의 락 해제 설명](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

락만으로 게시물 중복을 방지할 수도 없습니다. 수집한 외부 게시물 ID의 유일성을 DB에서 보호하고, 충돌 시 기존 결과를 다루는 흐름이 필요합니다. 일시적인 통신 실패는 재시도하되 인증 만료처럼 같은 요청으로 복구되지 않는 오류는 운영자가 알 수 있게 분리했습니다.

## 파일과 DB를 한 번에 롤백할 수는 없다

처리 순서는 외부 미디어를 임시 경로에 업로드하고, 콘텐츠 행을 만든 뒤, 정식 키로 이동하고 미디어 행을 저장하는 방식입니다. 외부 다운로드와 업로드를 긴 DB 트랜잭션에 묶지 않도록 경계를 나눴습니다.

대신 보상 처리가 필요해졌습니다. DB 등록 실패로 남은 임시 파일은 해당 prefix의 Lifecycle 정책 대상이지만, 이미 정식 경로로 옮긴 파일까지 같은 규칙이 지워주는 것은 아닙니다. S3의 이동도 복사와 삭제로 구성되므로 실패 위치에 따라 남은 객체가 달라집니다. 콘텐츠 행 정리와 파일 정리를 각각 확인해야 합니다. Lifecycle의 만료 조건 역시 정확히 그 시각에 삭제가 끝난다는 보장은 아닙니다.

## 수집 완료를 공개 승인으로 쓰지 않는다

사진만 있는 게시물과 영상이 있는 게시물은 준비 과정이 다릅니다. 영상에는 HLS 변환이 추가되므로 초기 비공개 상태와 변환 준비 상태를 구분했습니다. 자동 공개가 허용된 콘텐츠인지, 운영자 승인이 필요한 콘텐츠인지도 공개 조건에 포함해야 합니다. 변환 완료만으로 검수가 끝났다고 취급하지 않습니다.

외부 파일 검증도 같은 원칙입니다. 호스트 허용 목록과 리다이렉트 제한은 다운로드 경로를 좁히지만 모든 SSRF 조건을 해결하지는 않습니다. `image/*`라는 MIME 범주만 확인하면 `image/svg+xml`도 통과하므로 SVG 차단 근거가 되지 않습니다. 허용할 정확한 형식과 파일 내용 검증, 제공할 때의 Content-Type 정책이 필요합니다.

한 번의 수집 실행에서는 69건이 처리되고 실패가 없었던 기록이 있습니다. 이 결과로 장기 실패율이나 메모리 상한까지 입증할 수는 없습니다. 운영에서는 새 게시물을 놓치지 않는지, 만료된 인증과 중간 실패를 재처리할 수 있는지, 최종 공개 조건이 지켜지는지를 계속 확인해야 합니다. 영상 쪽의 상태 문제는 [HLS 변환 글](/posts/athlog-video-hls-redesign/)에서 더 다룹니다.

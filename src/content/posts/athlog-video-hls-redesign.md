athlog는 쇼핑몰 안에서 사진과 영상을 보고 관련 상품으로 이동하는 콘텐츠 화면입니다. 인스타그램에서 수집한 게시물과 운영자가 직접 올린 파일이 같은 화면에 들어옵니다. 영상은 원본 MP4를 그대로 제공하고 있었고, 모바일에서 재생 시작이 늦거나 재생이 불안정한 문제가 있었습니다.

2026년 5월 BIND에서 이 경로에 HLS 변환을 추가했습니다. HLS는 영상을 여러 조각과 재생 목록으로 제공하고, 클라이언트가 네트워크 상황에 맞춰 화질을 선택할 수 있게 합니다. 이 작업에서는 재생 방식뿐 아니라 **변환을 기다리는 콘텐츠를 언제 공개할지**도 함께 바꿔야 했습니다.

## MediaConvert 설계에서 기존 워커를 쓰는 구현으로

초기 설계는 S3에 올라온 원본을 AWS MediaConvert가 변환하고 EventBridge로 완료를 받는 방식이었습니다. 최종 구현에서는 ffmpeg를 Celery의 indexing 워커에서 실행했습니다. 이미 쓰고 있던 작업 큐와 S3 업로드 경로를 재사용할 수 있었고, 다루는 영상도 주로 60초 안팎이었습니다.

영상 길이만으로 관리형 서비스가 과하다고 결론 낼 수는 없습니다. 이 선택은 당시 입력 영상과 기존 인프라를 전제로 한 것이었습니다. MediaConvert를 쓰면 변환 실행 기반을 맡길 수 있고, 자체 ffmpeg를 쓰면 프로세스 종료·메모리·재시도를 직접 관리해야 합니다. 외부 변환 서비스 요금이 없어져도 워커와 저장·전송 비용은 남습니다.

HTTP 요청 안에서 변환하지 않은 이유는 분명했습니다. 운영자는 등록 응답을 기다리는데, CPU를 쓰는 변환까지 요청 처리기에 묶어둘 필요가 없었습니다. 등록 뒤 별도 작업으로 넘기고, ffmpeg에는 10분 제한을 두었습니다.

## 원본 업로드부터 재생 목록까지

```text
임시 S3 업로드
  → 원본 검증과 정식 경로 저장
  → 콘텐츠를 변환 대기 상태로 등록
  → Celery indexing 큐에서 ffmpeg 실행
  → HLS 파일 업로드와 재생 목록 확인
  → 미디어 준비 상태 갱신
  → 콘텐츠의 공개 조건 확인
  → CloudFront를 통해 재생
```

1080p·720p·480p 화질과 6초 단위 segment를 사용했습니다. 테스트 서버의 샘플에서는 segment가 2MB 미만이었습니다. 다만 100MB 원본 전체와 segment 하나의 크기를 비교해 재생 속도가 50배 빨라졌다고 말할 수는 없습니다. MP4도 배치와 HTTP range 지원에 따라 전체 파일을 받기 전에 재생할 수 있습니다. 첫 재생 지연은 파일 크기 외에 인코딩, 메타데이터 위치, 네트워크, 플레이어 버퍼링을 함께 봐야 합니다.

일반 작업과 변환 작업은 다른 큐로 라우팅했습니다. 이는 일반 워커가 직접 영상 변환을 맡지 않게 하는 조치입니다. 공유 DB·스토리지·네트워크나 indexing 워커 자체의 자원 경합까지 없어지는 것은 아닙니다. 특히 검색 색인 작업이 늘면 같은 워커를 계속 공유할지 다시 판단해야 합니다.

## 변환 완료와 공개 승인은 다르다

운영자가 비공개로 등록한 영상은 변환이 끝나도 비공개여야 합니다. 그런데 완료 콜백에서 무조건 `PUBLISHED`로 바꾸면 그 의도를 잃습니다. 영상이 포함된 콘텐츠는 우선 숨기고, 등록 시 요청한 상태를 `desired_status`로 전달해 변환 완료 후 복원하는 방식을 택했습니다.

여러 영상이 있는 콘텐츠는 준비되지 않은 영상이 남았는지도 검사했습니다. 이 검사는 조기 공개를 줄이기 위한 조건이지만, 조회 후 갱신만으로 동시 실행이 직렬화되는 것은 아닙니다. 두 작업이 동시에 “남은 영상 없음”을 확인할 수 있습니다. 또한 변환 도중 운영자가 다시 숨긴 경우에는 처음 캡처한 상태가 최신 의도와 다릅니다.

따라서 이 구현을 ‘마지막 작업만 실행되는 멱등 처리’로 설명하지 않습니다. 공개 상태까지 확실하게 보호하려면 콘텐츠 단위 잠금 또는 버전 조건부 갱신, 최신 공개 의도 확인, 중복 완료 처리의 안전성을 함께 검증해야 합니다. 변환 성공 여부와 공개 승인을 별도로 관리하는 설계도 이 문제를 풀 수 있습니다.

## 두 등록 경로에서 같은 검사를 하도록

단건 등록과 벌크 등록은 같은 파일 처리를 하면서도 검사가 달랐습니다. 특히 임시 키를 정식 경로로 옮기는 함수가 복사 후 원본을 삭제하므로, 이미 정식 경로에 있는 키가 들어오면 의도하지 않은 삭제가 생길 수 있었습니다. 임시 경로 검증을 공통 함수로 모아 두 진입점에 적용했습니다.

외부 영상 다운로드에서는 허용 호스트와 리다이렉트 정책도 확인했습니다. 인스타그램 CDN만 허용한 초기 설정은 운영자가 올린 자체 CDN 영상까지 차단했습니다. 수집 경로와 직접 업로드 경로를 함께 검증해야 발견할 수 있는 문제였습니다.

## 확인한 결과와 남은 측정

테스트 서버에서 원본을 HLS로 변환하고 재생 목록을 만드는 흐름을 검증했습니다. 새 영상을 추가할 때는 추가된 미디어만 작업 대상으로 넘기도록 바꿔 기존 영상까지 다시 변환하지 않게 했습니다.

첫 재생 1초 이내는 이 작업의 목표입니다. 사용자 기기에서 측정한 전후 분포는 확보하지 못했으므로 달성한 성과로 쓰지 않습니다. 이어서 볼 지표는 재생 요청부터 첫 프레임까지의 시간, 재버퍼링, 변환 소요 시간과 실패율입니다. 웹 페이지의 LCP와 영상 첫 프레임 시간도 구분해서 측정해야 합니다.

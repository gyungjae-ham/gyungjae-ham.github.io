athlog는 쇼핑몰에서 사진과 영상을 보고 관련 상품으로 이동할 수 있는 콘텐츠 화면입니다. 인스타그램에서 수집한 게시물과 운영자가 직접 올린 콘텐츠를 함께 제공합니다. 기존에는 원본 MP4를 그대로 내려줬는데, 모바일에서 재생 시작이 늦거나 재생이 불안정한 문제가 있었습니다.

2026년 5월 BIND에서 영상 제공 방식에 HLS를 추가했습니다. HLS는 영상을 여러 조각으로 나누고 재생 목록과 함께 제공합니다. 클라이언트는 목록을 읽어 필요한 조각을 요청하고, 네트워크 상황에 맞춰 화질을 선택할 수 있습니다.

문제는 영상 변환만 끝내면 되는 작업이 아니라는 점이었습니다. 운영자는 업로드 후 콘텐츠를 공개할 수 있어야 하지만, 변환 중인 영상은 아직 재생할 준비가 되지 않았습니다. 등록, 변환, 공개가 어떤 순서로 이어져야 할지 함께 정리했습니다.

## 기존 작업 큐에서 변환하기

초기에는 S3 원본을 AWS MediaConvert로 변환하고 EventBridge로 완료를 받는 방식을 설계했습니다. 실제 구현은 기존 Celery indexing 워커에서 ffmpeg를 실행하는 쪽으로 진행했습니다. 다루는 영상이 주로 60초 안팎이었고, 이미 사용하던 작업 큐와 S3 업로드 경로를 재사용할 수 있었습니다.

이 선택에는 관리할 일이 남습니다. 관리형 변환 서비스가 맡아 줄 프로세스 종료, 메모리 사용, 재시도를 이제 직접 다뤄야 합니다. 외부 변환 서비스 비용이 없어져도 워커와 저장·전송 비용은 발생합니다.

변환은 HTTP 요청에서 분리했습니다. 운영자가 파일 등록 응답을 받기 위해 인코딩이 끝날 때까지 기다릴 필요가 없도록 등록 후 Celery 작업으로 넘겼고, ffmpeg 실행에는 10분 제한을 뒀습니다.

```text
원본 검증·정식 S3 경로 저장
  → 콘텐츠를 변환 대기 상태로 등록
  → Celery에서 ffmpeg 실행
  → HLS 파일 업로드·재생 목록 확인
  → 미디어 준비 상태 갱신
  → 공개 조건 확인
```

1080p·720p·480p 화질과 6초 단위 조각을 만들고 CloudFront를 통해 재생하도록 했습니다. 일반 작업과 영상 변환의 큐를 나눠 일반 워커가 인코딩을 직접 맡지 않게 했습니다. 다만 indexing 워커는 검색 색인 작업도 처리하므로 두 작업이 많아지면 같은 자원을 두고 경쟁할 수 있습니다.

## 변환이 끝났다고 바로 공개하면

예를 들어 운영자가 다음 주에 공개할 영상을 미리 비공개로 등록했다고 해보겠습니다. 변환 완료 코드에서 콘텐츠를 무조건 `PUBLISHED`로 바꾸면, 업로드가 끝난 시점에 의도하지 않은 공개가 일어납니다.

영상이 포함된 콘텐츠는 우선 숨기고, 등록 당시 요청한 공개 상태를 `desired_status`로 전달하도록 했습니다. 변환이 끝나면 이 값을 사용해 상태를 복원합니다. 콘텐츠에 영상이 여러 개라면 준비되지 않은 영상이 남았는지도 검사했습니다.

이 방법에도 남은 문제가 있습니다. 변환을 시작할 때는 공개를 원했지만 작업 도중 운영자가 다시 숨겼을 수 있습니다. 처음 저장한 `desired_status`만 사용하면 나중에 바꾼 의도를 덮어씁니다. 완료 작업 두 개가 동시에 남은 영상이 없다고 판단하는 상황도 단순 조회 후 갱신만으로는 막지 못합니다.

공개 상태까지 안전하게 처리하려면 최신 공개 의도를 다시 확인하고, 콘텐츠 단위 잠금이나 버전을 비교하는 조건부 갱신이 필요합니다. 중복 완료 요청도 함께 검증해야 합니다. 현재 구현은 변환 대기 상태와 공개 요청을 구분했지만, 이 동시 실행 문제까지 해결한 구조로 보지는 않습니다.

## 파일을 등록하는 두 경로 맞추기

단건 등록과 여러 파일을 한 번에 등록하는 경로에서도 검사가 달랐습니다. 임시 S3 키를 정식 경로로 옮기는 함수는 복사 후 원본을 삭제합니다. 이미 정식 경로에 있는 키를 이 함수에 넣으면 의도하지 않은 파일 삭제로 이어질 수 있어, 임시 경로 검증을 공통 함수로 모았습니다.

다운로드 허용 호스트도 두 경로를 함께 확인했습니다. 인스타그램 CDN만 허용한 설정은 운영자가 올린 자체 CDN 영상까지 차단했습니다. 수집 영상과 직접 업로드한 영상을 모두 테스트해야 발견할 수 있는 차이였습니다.

테스트 서버에서는 원본 변환, HLS 파일 업로드, 재생 목록 생성까지 확인했습니다. 새 영상을 추가할 때에는 추가분만 작업에 넘겨 기존 영상을 다시 변환하지 않도록 했습니다.

샘플의 영상 조각은 2MB 미만이었지만, 원본 전체 크기와 조각 하나를 비교해 재생 속도 개선을 계산할 수는 없습니다. MP4도 HTTP range와 파일 구성에 따라 전체 다운로드 전에 재생할 수 있습니다. 첫 재생 1초 이내를 목표로 뒀으며, 달성 여부를 판단하려면 실제 기기에서 첫 프레임까지의 시간과 재버퍼링을 측정해야 합니다.

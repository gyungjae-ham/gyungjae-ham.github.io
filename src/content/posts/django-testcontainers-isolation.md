DB 테스트 설정을 읽다가 테스트가 로컬 또는 외부 MySQL을 향할 수 있는 구성을 발견했습니다. 테스트 DB 이름도 실제 DB와 같게 지정할 수 있었습니다. 실제 commit과 flush를 수행하는 테스트가 있어 접속 대상이 틀리면 공유 데이터에 영향을 줄 수 있었습니다.

저는 '올바른 환경변수를 넣어야 안전한 테스트'를 유지하지 않기로 했습니다. pytest가 세션 전용 MySQL을 만들고, 그 준비를 거치지 않은 연결은 실패하도록 바꿨습니다.

## SQLite로 빠르게 만드는 작업은 아니었다

이 테스트는 MySQL 함수와 트랜잭션, migration을 확인해야 했습니다. SQLite로 바꾸면 빠르더라도 실제 엔진의 계약을 확인하지 못합니다.

개발자의 로컬 MySQL에 별도 테스트 DB만 만드는 방식도 서버 설치 상태와 권한에 계속 의존합니다. 수동 Docker Compose는 준비·종료를 사람이 관리해야 합니다. Testcontainers를 pytest 세션 단위로 띄워 생명주기를 테스트 실행에 묶었습니다.

| 범위                    | 선택                                         |
| ----------------------- | -------------------------------------------- |
| DB 없는 단위 테스트     | 컨테이너를 시작하지 않음                     |
| DB 테스트가 포함된 세션 | MySQL 한 번 기동·migration 적용              |
| 개별 테스트 격리        | Django와 pytest-django의 rollback·flush 사용 |

테스트마다 컨테이너를 새로 만들지는 않았습니다. 물리 격리를 세션에 두고 테스트 간 격리는 기존 프레임워크에 맡겼습니다.

## 준비가 실패하면 외부 DB로 돌아가지 않게 했다

정적 설정은 `.invalid` 호스트와 빈 자격 증명을 사용했습니다. fixture가 동적 포트와 세션 자격 증명을 넣어줘야만 접속할 수 있습니다. 외부 `DB_TEST_*` 값을 읽는 fallback도 제거했습니다.

Django의 테스트 DB 생성과 migration은 유지했습니다. 컨테이너에 단순히 연결하는 것보다 실제 테스트 DB가 생성됐는지, `django_migrations`가 존재하는지, ORM 왕복이 가능한지를 확인했습니다.

매번 폐기되는 컨테이너여서 `--reuse-db`는 유지할 실익이 없었습니다. 기존 명령과 문서도 함께 수정했습니다.

## 종료 순서도 테스트 환경의 일부였다

Django 연결을 먼저 닫고 MySQL 컨테이너를 종료하도록 했습니다. Testcontainers의 정리 장치도 활성화했습니다. 정상 종료뿐 아니라 의도적으로 실패하는 실행에서 컨테이너 정리를 확인했습니다.

어떤 종료 상황에서도 잔존 컨테이너가 절대 없다는 보장으로 넓히지는 않았습니다. 확인한 것은 정상·실패 종료의 cleanup 경로입니다.

## 약 2분의 시작 비용을 받아들였다

컨테이너 기동과 전체 migration에 로컬에서 약 110~140초가 걸렸습니다. 빠른 테스트 전환이라고 소개할 수는 없습니다. DB 없는 테스트는 그대로 빠르게 실행하고, 실제 DB 검증에서는 재현 가능한 초기 상태를 우선했습니다.

설정·migration·ORM·rollback을 확인하는 대표 테스트 3건과 cleanup을 검증했습니다. 전체 DB 스위트는 실행하지 않았습니다.

이번 변경으로 테스트가 어디에 붙는지 기억하고 실행할 필요를 줄였습니다. 다음 비용 개선은 migration 준비 시간과 DB 테스트 묶음의 실행 방식을 관측한 뒤 판단할 일입니다. 외부 DB fallback을 되살리는 방식으로 줄일 비용은 아니었습니다.

> 공유 DB의 상태에 기대던 테스트를 pytest 세션 전용 MySQL로 옮겼습니다. DB 없는 테스트는 그대로 빠르게 실행하고, DB가 필요한 경우에만 컨테이너와 실제 migration 비용을 지불하도록 나눴습니다.

## 테스트 DB 이름만 바꿔서는 서버가 격리되지 않는다

Django가 별도 테스트 DB를 만들어도 기반 MySQL이 로컬 설치나 공유 서버에 의존하면 권한과 스키마 상태가 달라집니다. 실제 commit과 flush를 수행하는 테스트에서는 잘못된 연결 설정이 데이터에 영향을 줄 위험도 있습니다.

컨테이너를 수동으로 띄우는 방법 대신 pytest 세션 생명주기에 연결했습니다. 테스트마다 만들면 시작과 migration 비용을 반복하므로 세션당 한 번 준비하고, 테스트 사이의 격리는 Django와 pytest-django에 맡겼습니다.

## DB 테스트가 요청할 때만 시작한다

설정 주입은 `django_db_modify_db_settings` 확장점에서 처리했습니다. 동적으로 할당된 host·port·자격 증명을 넣고, 테스트 DB 생성과 migration은 기존 프레임워크 흐름을 유지했습니다. ORM 왕복뿐 아니라 실제 migration 테이블이 있는지도 확인했습니다.

DB 없는 단위 테스트는 이 준비 경로를 요청하지 않으므로 컨테이너가 시작되지 않습니다. 빠른 테스트에 인프라 비용을 일괄 부과하지 않는 것이 중요한 조건이었습니다. 반대로 DB 테스트에는 Docker가 필요하다는 의존성을 명시했습니다.

## 실패하면 외부 DB로 돌아가지 않는다

정적 설정은 접속할 수 없는 호스트와 빈 자격 증명으로 두었습니다. 컨테이너 fixture를 거치지 않은 연결이 조용히 기존 DB를 사용하지 않도록 외부 테스트 DB 환경변수 경로도 제거했습니다. Docker가 없거나 기동이 실패하면 테스트는 실패해야 합니다.

컨테이너가 매 세션 폐기되므로 이전 DB를 재사용하는 옵션의 의미도 정리했습니다. 자격 증명은 해당 세션에서 만들고, 종료할 때 Django 연결을 먼저 닫은 뒤 MySQL을 내립니다. 정상 종료와 의도적인 실패 후 cleanup을 각각 확인했습니다.

이 생명주기 관리가 모든 강제 종료에서 즉시 정리를 보장하는 것은 아닙니다. 런타임의 정리 장치와 Docker 상태를 관찰하는 확인이 필요합니다.

## 검증한 범위를 전체 스위트로 부풀리지 않았다

당시 확인은 설정 계약, 실제 migration, ORM 저장·조회, 대표 rollback 테스트, 종료 정리였습니다. 전체 DB 테스트 스위트는 실행하지 않았습니다. 초기화에는 로컬 환경에서 분 단위 비용이 들었지만 전체 개발 대기시간이 얼마나 바뀌었는지는 측정하지 않았습니다.

사용한 라이브러리 버전은 레거시 런타임에서 선택한 당시 조합이며 현재 권장 버전으로 제시하지 않습니다. 운영 DB 버전과의 차이, 전체 회귀는 후속 확인 대상입니다. 이 변경의 결과는 외부 DB를 조용히 사용하는 경로를 닫고 테스트 스키마를 재현 가능하게 준비한 것입니다.

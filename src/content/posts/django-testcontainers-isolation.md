로컬에서 Django DB 테스트를 실행할 때 어떤 MySQL에 연결되는지 설정을 조사했습니다. 환경변수에 따라 로컬 또는 외부 MySQL을 향할 수 있었고, 테스트 DB 이름을 실제 DB 이름과 같게 지정해 별도 DB 생성을 우회할 수도 있었습니다. 실제 commit과 데이터 초기화를 수행하는 테스트가 있어 연결 대상을 잘못 잡으면 공유 데이터에 영향을 줄 위험이 있었습니다.

실제 데이터 손상이 발생했다는 기록은 아닙니다. 테스트 설정에서 발견한 위험을 없애는 작업이었습니다. 개발자가 환경변수를 매번 올바르게 맞추는 대신, pytest가 테스트 전용 MySQL을 만들고 그 준비가 실패하면 실행도 실패하도록 바꿨습니다.

## 필요한 것은 실제 MySQL의 분리된 실행 환경이었다

이 테스트는 MySQL 함수와 트랜잭션, migration을 확인하므로 SQLite로 대체할 수 없었습니다. 개발자의 MySQL 서버 안에 DB만 하나 더 만들면 설치 상태와 권한, 서버 설정에는 계속 의존합니다.

Testcontainers를 사용해 테스트가 Docker의 MySQL 컨테이너를 직접 시작하고 종료하게 했습니다. DB 없는 단위 테스트는 컨테이너를 띄우지 않습니다. DB 테스트가 포함된 pytest 세션에서 한 번 시작하고, 개별 테스트 사이의 rollback과 flush는 Django와 pytest-django에 맡겼습니다. 매 테스트마다 서버를 새로 띄우는 방식은 피했습니다.

## 준비 실패가 다른 DB 접속으로 이어지지 않게 했다

정적 설정에는 접속할 수 없는 `.invalid` 호스트와 빈 자격 증명을 뒀습니다. 컨테이너 준비 fixture가 실제 포트와 세션 자격 증명을 넣어야만 연결됩니다. 외부 `DB_TEST_*` 환경변수로 돌아가는 fallback도 제거했습니다.

컨테이너에 접속하는 것만 확인하지는 않았습니다. Django가 테스트 DB를 만들고 실제 migration을 적용하는 흐름을 유지했습니다. `django_migrations` 테이블이 있는지, ORM으로 쓴 값을 읽을 수 있는지, 테스트 변경이 rollback되는지 확인했습니다. 매번 폐기하는 DB라 `--reuse-db` 사용 명령과 문서도 함께 정리했습니다.

## 시작은 느려졌고 종료도 확인해야 했다

로컬에서 컨테이너 기동과 전체 migration에는 약 110~140초가 걸렸습니다. DB 테스트를 빠르게 만든 변경은 아닙니다. DB 없는 테스트는 기존처럼 실행하고, 실제 MySQL이 필요한 경우에 재현 가능한 초기 상태를 준비하는 비용을 받아들였습니다.

종료할 때는 Django 연결을 먼저 닫고 컨테이너를 내리도록 했습니다. 정상 종료와 의도적으로 실패한 테스트 실행에서 정리되는지 확인했고, Testcontainers의 정리 장치도 활성화했습니다.

검증 범위는 설정·migration·ORM·rollback을 확인하는 대표 테스트 3건과 정상·실패 종료의 정리 경로입니다. 전체 DB 테스트 스위트는 실행하지 않았습니다. 시작 비용은 남지만, 준비가 실패했을 때 남아 있던 외부 DB 자격 증명으로 접속하는 경로는 제거했습니다.

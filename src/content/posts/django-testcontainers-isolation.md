Django DB 테스트의 연결 설정을 살펴보니 환경변수에 따라 로컬 또는 외부 MySQL을 사용할 수 있었습니다. 테스트 DB 이름을 실제 DB 이름과 같게 지정해 별도 DB 생성을 우회하는 설정도 가능했습니다. 테스트 중에는 실제 commit과 데이터 초기화도 수행하므로 접속 대상을 잘못 잡으면 공유 데이터에 영향을 줄 수 있었습니다.

실제로 데이터가 손상된 사건은 아닙니다. 발견한 설정 위험을 없애기 위해 pytest가 테스트 전용 MySQL을 준비하고, 준비에 실패하면 테스트도 실패하도록 바꿨습니다.

## 테스트할 DB를 세션이 직접 만들기

이 테스트들은 MySQL 함수와 트랜잭션, migration을 확인합니다. SQLite로 교체하면 확인하려던 동작과 다른 DB에서 실행하게 됩니다. 개발자 MySQL 안에 DB만 하나 더 만드는 방법도 설치 상태와 권한에 계속 의존합니다.

Testcontainers로 Docker의 MySQL 컨테이너를 테스트 세션이 시작하고 종료하게 했습니다. DB 테스트가 있는 세션에서 한 번 기동하며, 테스트 사이의 rollback과 flush는 Django와 pytest-django에 맡깁니다. DB를 쓰지 않는 단위 테스트는 컨테이너를 띄우지 않습니다.

## 컨테이너가 시작하지 못하면

예를 들어 Docker가 꺼져 있어 컨테이너 생성에 실패했다고 해보겠습니다. 이때 기존 환경변수의 MySQL 주소로 돌아가면 격리하려던 목적을 잃습니다. 테스트는 실패하는 편이 맞습니다.

정적 설정에는 접속할 수 없는 `.invalid` 호스트와 빈 자격 증명을 뒀습니다. 준비 fixture가 컨테이너의 실제 포트와 세션 자격 증명을 넣어야만 연결할 수 있습니다. 외부 `DB_TEST_*` 값을 fallback으로 사용하는 경로는 제거했습니다.

연결 성공만 확인하지 않고 Django가 테스트 DB를 만들고 실제 migration을 적용하는 흐름도 유지했습니다. `django_migrations` 테이블 생성, ORM 쓰기·읽기, 테스트 변경의 rollback을 검사했습니다. 매번 폐기하는 DB에 맞춰 `--reuse-db`를 사용하던 명령과 문서도 정리했습니다.

## 격리를 위해 추가된 비용

로컬에서 컨테이너 기동과 전체 migration에는 약 110~140초가 걸렸습니다. DB 테스트 시작이 빨라지는 변경은 아니었습니다. 실제 MySQL이 필요한 테스트에 재현 가능한 초기 상태를 제공하는 비용으로 받아들였고, DB 없는 테스트는 기존처럼 실행하도록 뒀습니다.

종료할 때에는 Django 연결을 먼저 닫고 컨테이너를 내립니다. 정상 종료와 의도적으로 실패한 테스트에서 모두 정리되는지 확인했고 Testcontainers의 정리 장치도 켰습니다.

검증은 설정·migration·ORM·rollback을 확인하는 대표 테스트 3건과 종료 정리 경로까지 진행했습니다. 전체 DB 테스트 스위트는 실행하지 않았습니다. 테스트할 범위는 남았지만, 컨테이너 준비 실패가 남아 있던 외부 DB 자격 증명의 사용으로 이어지는 경로는 제거했습니다.

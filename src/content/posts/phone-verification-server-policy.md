전화번호 인증을 서버로 옮기는 작업은 처음에는 비교 로직의 위치를 바꾸는 일처럼 보였습니다. 실제로는 인증번호를 몇 번 입력할 수 있는지, 몇 번 다시 받을 수 있는지, 이미 배포된 앱을 어떻게 유지할지를 함께 결정해야 했습니다.

기존 흐름에는 서버가 관리하는 검증 횟수와 발급 한도가 없었습니다. 저는 새 검증 경로에 제한을 넣되, 구버전 앱의 요청과 응답은 유지하는 방식으로 전환했습니다. 이 선택은 배포 위험을 줄였지만 이전 경로를 정리하는 후속 과제도 남겼습니다.

## 자릿수를 늘리기 전에 시도와 발급을 나눴다

인증번호를 길게 만들면 추측은 어려워집니다. 하지만 계속 시도할 수 있거나 SMS를 무한히 요청할 수 있다면 자릿수만으로 해결되지 않습니다. 신규 흐름에서는 다음을 서로 다른 제한으로 관리했습니다.

- 인증번호 하나의 틀린 입력 횟수
- 재발급까지 기다려야 하는 시간
- 전화번호별 시간·일 단위 발급량
- 인증번호 자체의 유효시간

재발급하면 입력 횟수는 새 코드 기준으로 시작합니다. 대신 발급 한도가 반복 재발급을 제한합니다. 두 카운터를 하나로 묶으면 SMS를 받지 못해 다시 요청한 정상 사용자까지 이전 오입력의 영향을 받습니다.

시간 단위 제한은 고정 시각에 초기화하는 방식보다 sliding window를 택했습니다. 정각 직전과 직후에 요청을 몰아 보내는 상황에서도 최근 시간 범위의 발급량을 보려는 선택입니다.

## 기존 경로에 정책을 얹는 설계를 바꿨다

초기에는 기존 API에도 새 정책을 적용하면서 응답 필드를 유지하려 했습니다. 그러나 응답 모양이 같아도 실패 조건이 달라지면 구버전 앱은 새로운 오류를 처리하지 못할 수 있습니다.

그래서 신규 발급·검증 API를 분리하고 기존 경로는 보존했습니다. 새 흐름은 서버에 인증 상태를 저장하고 `hmac.compare_digest`로 입력을 비교합니다. 기존 앱은 기존 계약을 유지합니다.

| 선택               | 얻는 것               | 남기는 것                         |
| ------------------ | --------------------- | --------------------------------- |
| 기존 API 동작 변경 | 한 경로로 빠르게 통합 | 구버전 오류 처리와 화면 동작 위험 |
| 신규 API 분리      | 앱별로 전환 가능      | 이전 경로의 제한 부족과 종료 계획 |

여기서 새 API 구현 완료를 전체 인증 보안 개선 완료로 표현하면 안 됩니다. 이전 경로를 언제 닫을지까지 정해져야 전환이 끝납니다.

## 테스트를 맞추려고 유효시간을 바꾸지 않았다

Redis 기반 상태와 시간 경계를 fakeredis로 검증하다가, 테스트 도구의 시간 처리 차이를 피하려 인증 상태 TTL을 늘린 변경이 들어왔습니다. 요구한 유효시간보다 테스트 편의를 먼저 맞춘 셈입니다.

TTL은 정책대로 되돌렸습니다. 상태가 Redis에서 이미 사라진 경우와 애플리케이션이 만료를 판정한 경우를 테스트가 모두 받아들이도록 수정했습니다. 사용자가 볼 유효시간을 테스트 환경 때문에 늘릴 이유는 없었습니다.

동시 요청의 카운터 증가는 Redis 원자 연산을 사용했습니다. 다만 개별 증가 연산의 원자성이 발급·SMS 전송·상태 저장 전체를 하나의 원자적 작업으로 만드는 것은 아닙니다. 이 구분은 별도로 봐야 합니다.

## 검증한 정책과 아직 남은 전환

신규 경로에는 검증 시도, 발급량, 재발급 대기, 만료, SMS 실패 시 상태 저장 여부를 확인하는 테스트를 두었습니다. 적용처가 아직 하나여서 범용 인증 라이브러리로 추출하지 않고 사용자 도메인 안에 구현했습니다.

이번 작업에서 중요한 결정은 더 강한 검증 로직을 만드는 것과 앱을 안전하게 전환하는 것을 분리한 점입니다. 다음 확인 대상은 신규 API 사용 비중과 구버전 경로의 종료 조건입니다. 그 수치가 있어야 호환성을 위해 남긴 경로를 정리할 수 있습니다.

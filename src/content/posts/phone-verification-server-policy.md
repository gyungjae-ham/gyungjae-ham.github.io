회원가입이나 로그인할 때 SMS로 받은 번호를 앱에 입력하는 기능을 작업했습니다. 번호가 맞는지 판단하는 일을 앱에서 서버로 옮기고, 서버에서 인증 상태와 요청 횟수를 관리하도록 했습니다.

번호를 계속 추측하는 요청과 문자를 계속 발급하는 요청은 서로 다른 문제입니다. 첫 번째는 계정 보호에, 두 번째는 문자 발송 비용에도 영향을 줍니다. 기존에는 서버가 관리하는 검증 횟수와 발급 한도가 없어 두 동작을 나눠 제한해야 했습니다.

## 입력 실패 횟수와 발급량을 따로 세기

인증번호 하나에 대해서는 틀린 입력의 횟수와 유효시간을 관리합니다. 재발급에는 대기시간과 전화번호별 시간·일 단위 한도를 적용합니다. 새 번호를 받으면 그 번호의 입력 횟수는 새로 시작할 수 있지만, 계속 재발급해서 시도 제한을 피하지는 못하게 한 것입니다.

시간 단위 발급량은 정각마다 카운터를 지우는 방식 대신 sliding window를 사용했습니다. 예를 들어 10시 직전에 여러 번 받고 10시 직후 다시 요청하면, 정각 초기화 방식에서는 짧은 시간의 발급이 두 구간으로 나뉩니다. 최근 일정 시간의 요청을 함께 세면 이 차이를 줄일 수 있습니다.

## 응답 모양이 같아도 이전 앱이 처리하지 못할 수 있습니다

초기에는 기존 API의 JSON 필드를 유지하면 새 제한을 넣어도 괜찮다고 봤습니다. 그런데 이전에 성공하던 요청이 발급량 초과로 실패하게 되면 앱에는 새 오류를 처리할 화면이 필요합니다. 필드 이름만 같은 것으로는 호환성을 유지할 수 없었습니다.

신규 발급·검증 API를 분리하고 Redis에 인증 상태를 저장해 서버가 입력을 비교하도록 했습니다. 이미 설치된 구버전 앱의 기존 API는 유지하며 새 흐름으로 순차 전환할 수 있게 했습니다.

이 선택은 이전 경로의 제한 부족도 당분간 남긴다는 뜻입니다. 새 API를 만들었다고 전체 인증 경로의 전환이 끝나지는 않습니다. 최소 지원 앱 버전, 업데이트 유도 방식, 남은 사용자의 로그인 경로를 함께 정해야 기존 API를 종료할 수 있습니다. 당시에는 종료 날짜나 특정 전환율 기준을 확정하지 않았습니다.

## 테스트 편의 때문에 유효시간을 바꾸지 않기

Redis 만료를 테스트하는 과정에서 fakeredis와 실제 만료 처리의 차이를 피하려고 TTL을 늘린 변경이 들어왔습니다. TTL은 저장 후 유지 시간으로, 여기서는 고객이 인증번호를 쓸 수 있는 시간과 연결됩니다. 테스트가 편해지도록 늘리면 인증 정책도 달라집니다.

TTL은 원래 값으로 되돌리고, 저장 상태가 먼저 사라진 경우와 애플리케이션이 만료를 판단하는 경우를 각각 테스트했습니다. 틀린 입력, 재발급 제한, 만료, SMS 전송 실패 후 남는 상태도 확인했습니다.

동시 요청의 카운터 증가는 Redis 원자 연산을 사용했습니다. 다만 카운터 증가와 외부 SMS 발송이 한 트랜잭션으로 처리되는 것은 아닙니다. 신규 API의 동작과 함께 이전 API 사용 비중과 종료 조건을 계속 확인해야 하는 작업으로 남았습니다.

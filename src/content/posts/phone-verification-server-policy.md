> 인증번호가 맞는지 확인하는 것만으로는 부족했습니다. 서버가 발급과 검증 횟수를 관리하도록 바꾸되, 구버전 앱이 호출하는 기존 경로는 별도로 유지했습니다.

## 클라이언트가 제한하는 인증은 우회할 수 있다

전화번호 인증의 검증 횟수와 발급 한도가 서버 정책으로 묶여 있지 않았습니다. 화면에서 재전송 버튼을 막더라도 API를 직접 호출하는 요청에는 같은 제한이 적용되지 않습니다. 인증번호 비교를 서버로 옮기는 일과, 서버가 허용할 요청 횟수를 정하는 일을 함께 처리해야 했습니다.

정책은 인증번호별 실패 횟수, 짧은 재발급 대기 시간, 시간 단위와 일 단위의 발급 한도로 나눴습니다. 하나의 카운터로 모두 표현하면 정상 사용자의 재발급과 반복 공격을 구분하기 어렵습니다. 코드의 유효 기간과 발급 횟수의 관찰 기간도 서로 다릅니다.

## Redis 키를 정책의 수명에 맞췄다

인증번호와 실패 횟수는 TTL이 있는 hash에 저장하고, 재발급 대기 시간은 별도 키로 관리했습니다. 발급 이력은 sorted set을 이용해 시간창 안의 요청을 계산했습니다. 실패 카운터는 `HINCRBY`로 증가시켜 동시에 들어오는 증가 요청이 서로 덮어쓰지 않도록 했습니다.

여러 쓰기 명령은 pipeline으로 묶어 왕복 횟수를 줄였습니다. 다만 카운터 증가가 원자적이라는 사실만으로 전체 발급·검증 절차가 원자적이라고 말할 수는 없습니다. 제한 검사와 상태 변경 사이에 다른 요청이 들어올 수 있는지는 별도로 확인해야 합니다.

인증번호 비교에는 `hmac.compare_digest`를 사용했습니다. 이것도 요청 제한을 대신하는 도구는 아닙니다. 비교 과정의 시간 차이를 줄이는 보완책과, 시도 횟수를 제한하는 정책을 함께 두었습니다.

## 마지막 허용 시도의 정답을 어떻게 볼 것인가

실패 횟수를 먼저 올릴지, 정답을 먼저 확인할지도 정책이었습니다. 카운터를 먼저 증가시키고 경계에서 즉시 무효화하면 마지막 허용 시도에 정답을 입력한 사용자까지 거절할 수 있습니다. 구현에서는 코드 비교를 먼저 하고, 불일치할 때 실패 횟수를 증가시키는 순서를 택했습니다.

처음부터 여러 인증 도메인을 위한 공통 라이브러리로 만들지는 않았습니다. 적용 대상이 한 곳이었기 때문에 해당 도메인 내부에 정책 상수와 조회·변경 함수를 두었습니다. 공통화는 두 번째 적용처의 요구를 확인한 뒤 진행할 수 있습니다.

## 기존 앱과 새 정책을 동시에 운영한다

구버전 앱이 사용하는 경로에 새 응답과 정책을 그대로 덮어씌우지 않았습니다. 기존 경로를 보존하고 새 검증 흐름을 분리했습니다. 이는 호환성을 위한 선택이지만, 이전 경로에 같은 보안 정책이 자동으로 적용된다는 뜻은 아닙니다. 구버전 사용 비중과 종료 시점을 따로 관리해야 합니다.

당시 기록에는 fakeredis와 시간 고정을 이용한 경계·TTL 테스트 결과가 남아 있습니다. 공격 성공 확률이나 발급량 감소 수치는 정책을 바탕으로 계산한 가설이며 실제 공격 감소를 측정한 값은 아닙니다. 이 작업의 확인 가능한 결과는 인증 정책을 서버 코드와 테스트로 표현하고, 호환 경로를 명시적으로 분리했다는 점입니다.

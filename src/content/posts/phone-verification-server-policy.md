회원가입이나 로그인에서 전화번호를 확인할 때, 사용자는 SMS로 받은 번호를 앱에 입력합니다. 이 번호가 맞는지 판단하는 일을 앱에서 서버로 옮겼습니다. 서버가 인증 상태를 관리해야 틀린 번호를 계속 입력하는 시도와 SMS를 반복 발급하는 요청을 제한할 수 있었기 때문입니다.

여기에는 서로 다른 두 문제가 있었습니다. 인증번호를 계속 추측하면 계정 보호가 약해지고, 문자만 반복 요청해도 발송 비용이 발생합니다. 기존에는 서버가 관리하는 검증 횟수와 발급 한도가 없었습니다. 다만 이미 설치된 구버전 앱도 계속 로그인할 수 있어야 해서, 새 로직을 기존 API에 바로 덮어쓸 수는 없었습니다.

## 번호를 틀리는 일과 문자를 다시 받는 일을 나눴다

인증번호 하나를 여러 번 틀리는 경우에는 그 번호의 검증 시도를 제한했습니다. 문자를 받지 못해 새 번호를 요청하는 경우에는 재발급 대기시간과 전화번호별 발급량을 확인했습니다. 번호 자체의 유효시간도 별도로 관리했습니다.

이렇게 나누면 재발급한 번호의 입력 횟수는 새로 시작할 수 있습니다. 그렇다고 번호를 계속 새로 받아 제한을 피할 수 있는 것은 아닙니다. 시간·일 단위 발급 한도가 그 반복을 막습니다. 두 종류의 제한이 서로 다른 행동을 맡는 셈입니다.

시간 단위 발급량은 정각마다 카운터를 비우는 대신 최근 시간 범위를 기준으로 계산했습니다. 예를 들어 정각 직전과 직후에 요청이 몰려도, 실제로 짧은 시간 안에 보낸 문자 수를 함께 볼 수 있도록 sliding window를 사용했습니다.

## 응답 필드가 같아도 구버전 앱은 깨질 수 있었다

초기에는 기존 API의 응답 모양만 유지하면 새 제한을 적용할 수 있다고 봤습니다. 하지만 예전에는 성공하던 요청이 새 정책에서는 발급량 초과로 실패할 수 있습니다. 앱에 그 실패를 처리하는 화면이 없다면 JSON 필드를 유지하는 것만으로 호환성이 보장되지 않습니다.

그래서 신규 발급·검증 API를 분리하고, 앱이 새 흐름으로 전환할 수 있게 했습니다. 신규 API는 Redis에 인증 상태를 저장하고 서버에서 입력값을 비교합니다. 구버전 앱이 호출하는 기존 경로는 유지했습니다. 이 선택 덕분에 앱을 순차적으로 전환할 수 있지만, 이전 경로의 제한 부족도 당분간 남습니다. 새 API 구현과 이전 API 종료는 별도로 관리해야 하는 작업입니다.

## 테스트 때문에 인증 유효시간을 늘릴 수는 없었다

시간에 따라 상태가 사라지는 Redis 동작은 테스트에서도 다뤄야 했습니다. 테스트용 Redis 구현인 fakeredis와 실제 만료 처리의 차이를 피하려고 인증 상태의 TTL, 즉 저장 후 유지 시간을 늘린 변경이 들어왔습니다. 그러면 테스트는 편해져도 사용자가 인증번호를 쓸 수 있는 시간이 정책과 달라집니다.

TTL은 원래 정책대로 되돌렸습니다. 대신 저장된 상태가 먼저 사라지는 경우와 애플리케이션이 만료를 판단하는 경우를 테스트에서 모두 다루도록 했습니다. 잘못된 입력, 재발급 제한, 만료, SMS 전송 실패 후 상태가 남는지도 함께 확인했습니다.

동시 요청의 카운터 증가는 Redis 원자 연산을 사용했습니다. 다만 카운터 하나를 안전하게 늘리는 것과 SMS 발송까지 모두 한 번에 처리하는 것은 다릅니다. 외부 전송이 포함된 흐름까지 원자적이라고 가정하지 않았습니다.

구현 뒤에 남은 일은 구버전 앱의 전환입니다. 신규 API 사용 비중과 이전 경로의 종료 조건을 확인해야, 호환성을 위해 남겨 둔 제한 없는 경로까지 정리할 수 있습니다.

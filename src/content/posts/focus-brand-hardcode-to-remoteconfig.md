상품 상세 화면에는 운영팀이 집중해서 소개할 브랜드를 고르는 영역이 있습니다. 브랜드 이름이 코드 상수에 들어 있어 캠페인이 바뀔 때마다 코드 수정과 배포가 필요했습니다. 값 하나의 변경을 위해 개발 일정에 맞춰야 하는 구조였습니다.

이미 운영팀이 사용하는 RemoteConfig 화면이 있어 이 값을 옮겼습니다. 새 관리 화면을 만드는 대신 기존 설정 저장소를 재사용하고, 화면 응답과 검색 조건이 같은 조회 함수를 사용하도록 바꿨습니다.

## 설정을 바꾸면 어디까지 달라져야 하나

브랜드 이름을 보여주는 API만 바꾸면 실제 상품 검색은 이전 브랜드로 남을 수 있습니다. 두 호출부가 동일한 값을 읽게 하는 것이 먼저였습니다. 조회 실패나 잘못된 입력도 한 함수에서 처리하면 fallback 정책이 갈라지지 않습니다.

아래는 값 검증만 분리한 설명용 예시입니다. 문자열이 아닌 값과 공백 문자열은 기본값으로 처리합니다.

```python
def normalize_brand_name(value, default):
    if not isinstance(value, str):
        return default
    normalized = value.strip()
    return normalized if normalized else default
```

`"   "`는 비어 있지 않은 문자열이므로 `not value`는 `False`입니다. 공백을 제거한 뒤 검사해야 합니다. 또 `str(None)`은 빈 문자열이 아닌 `"None"`이므로, 무조건 문자열로 바꾸기 전에 입력 타입부터 확인해야 합니다.

설정 항목이 없을 때와 저장소 연결이 실패했을 때는 운영상 의미도 다릅니다. 기본값으로 응답하더라도 실패를 관측할 수 있어야 잘못된 설정이 계속 숨겨지지 않습니다.

## 즉시 반영과 캐시

기존 설정 조회의 캐시 정책을 그대로 쓰면 변경 후에도 이전 브랜드가 남을 수 있었습니다. 이 항목은 변경 직후 화면에서 확인해야 해서 캐시를 사용하지 않는 경로를 택했습니다.

즉시 반영이 필요하면 항상 캐시를 꺼야 하는 것은 아닙니다. 조회량이 커지면 저장 후 캐시 무효화나 설정 버전을 함께 관리하는 방법도 있습니다. 이 작업에서는 작은 설정 조회를 직접 수행하는 단순한 방식이 요구에 맞았습니다.

결과적으로 브랜드 교체는 코드 배포를 기다리는 작업에서 운영 설정을 바꾸는 작업으로 옮겨갔습니다. 절감 시간을 연간 성과로 환산하려면 실제 변경 빈도와 처리 시간을 기록해야 합니다. 여기서 분명한 변경은 두 호출부가 같은 설정을 읽고, 캠페인 값 변경 때문에 애플리케이션을 배포할 필요가 없어졌다는 점입니다.

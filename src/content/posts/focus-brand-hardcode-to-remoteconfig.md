상품 상세 화면에는 운영팀이 집중해서 소개할 브랜드를 고르는 영역이 있습니다. 이 브랜드 이름이 코드 상수로 들어 있어 캠페인이 바뀔 때마다 개발자가 코드를 고치고 배포해야 했습니다.

운영팀이 이미 사용하던 RemoteConfig 화면에 이 값을 옮겼습니다. 새 관리 화면을 만들기보다 기존 설정 저장소를 재사용하고, 상품 화면 응답과 검색 조건이 같은 함수에서 값을 읽게 했습니다.

## 표시만 바뀌고 검색은 그대로라면

예를 들어 운영자가 집중 브랜드를 A에서 B로 바꿨다고 해보겠습니다. 화면 문구는 B인데 상품 검색 조건은 여전히 A라면 고객은 B 영역에서 A 상품을 보게 됩니다. 상수 한 곳을 바꾸는 것뿐 아니라 이 값을 읽는 호출부를 모두 맞춰야 했습니다.

화면과 검색에서 공통 조회 함수를 사용하게 하고, 값이 없거나 잘못됐을 때의 기본값도 한곳에서 처리했습니다. 문자열 검증만 단순화하면 다음과 같습니다.

```python
def normalize_brand_name(value, default):
    if not isinstance(value, str):
        return default
    normalized = value.strip()
    return normalized if normalized else default
```

`"   "`는 공백만 있지만 빈 문자열은 아니어서 `not value` 검사에 걸리지 않습니다. 먼저 공백을 지워야 합니다. `None`을 무조건 문자열로 바꾸면 `"None"`이라는 이름이 되므로 타입도 먼저 확인합니다.

설정 항목이 없는 경우와 저장소 연결에 실패한 경우는 운영상 의미가 다릅니다. 둘 다 기본값으로 응답하더라도 연결 실패를 별도로 볼 수 있어야 오래된 값이 나오는 이유를 조사할 수 있습니다.

## 변경 직후 확인할 수 있도록

기존 설정 조회의 캐시를 그대로 쓰면 저장 후에도 이전 브랜드가 보일 수 있었습니다. 이 항목은 운영자가 값을 바꾼 직후 화면에서 확인해야 해, 캐시를 사용하지 않는 조회 경로를 선택했습니다.

조회량이 커지면 저장 후 캐시를 무효화하거나 설정 버전을 관리하는 방법도 검토할 수 있습니다. 이번에는 작은 설정값을 직접 읽는 방식으로 처리했습니다. 운영자는 설정을 바꾸고 화면과 검색에 같은 브랜드가 반영되는지 확인할 수 있으며, 브랜드 이름을 교체하기 위해 애플리케이션 배포를 기다릴 필요가 없어졌습니다.

고객이 북마크한 판매 브랜드를 모아 보는 화면에서 Sentry의 N+1 경고가 발생했습니다. 브랜드 목록을 읽은 뒤 각 브랜드의 페이지 정보와 북마크 수를 다시 조회하고 있었습니다. 브랜드가 늘어날수록 같은 형태의 쿼리도 늘어나는 상황이었습니다.

응답을 만드는 Serializer는 여러 화면에서 공유했습니다. 경고가 난 화면만 고치면 같은 Serializer를 쓰는 다른 목록에 반복 조회가 남을 수 있어 호출부를 함께 확인했습니다.

## 준비한 관계의 한 단계 뒤에서 추가 조회

브랜드 홈은 prefetch로 가져오지만 홈에 연결된 페이지는 포함하지 않았습니다. 예를 들어 브랜드 다섯 개의 홈을 미리 읽어도, 응답에서 각 홈의 페이지를 확인하면 추가 쿼리가 생깁니다. 북마크 수도 브랜드마다 `.count()`로 계산했습니다.

페이지까지 함께 가져오고 북마크 수는 일괄 집계해 Serializer에 전달했습니다. 값이 없을 때 다시 `.count()`하는 fallback은 제거했습니다. fallback이 남으면 호출부가 데이터를 준비하지 않아도 응답은 나오지만, 같은 반복 조회가 조용히 계속되기 때문입니다.

사용처 네 곳이 필요한 데이터를 준비하도록 맞췄고, 로컬에서 브랜드 5개를 조회할 때 14쿼리가 4쿼리로 줄었습니다. 공통 필드뿐 아니라 각 화면의 응답도 확인했습니다.

## 검사 규칙이 ORM과 딕셔너리 접근을 혼동했습니다

수정 중에는 Serializer 메서드의 `.get()`을 ORM 조회로 보는 검사와 `dict.get()`을 권장하는 Ruff 규칙이 충돌했습니다. 당시 표현 처리를 `to_representation()`으로 옮겨 검사를 통과시켰습니다.

하지만 코드 위치가 검사 대상 밖으로 바뀌었다고 DB 조회가 줄어드는 것은 아닙니다. 실제 ORM 호출과 쿼리 수를 별도로 확인했습니다. 검사기가 딕셔너리와 DB 접근을 구분하지 못하는 문제는 후속 개선으로 남겼습니다.

## 같은 찜 수라도 화면마다 계산이 달랐습니다

9월에는 판매 브랜드 목록에 찜 수를 추가하면서도 일괄 집계를 사용했습니다. 같은 사용자를 중복해서 세지 않았고 브랜드 1개·30개·100개 모두 4쿼리를 확인했습니다.

그런데 테스트 서버에서 목록과 검색의 숫자가 달랐습니다. 목록에는 실제 찜 수만 넣었고 검색은 표시용 보정값을 더하고 있었습니다. 후속 수정에서 검색과 같은 표시 기준을 적용했습니다. 이 합산값은 실제 찜을 누른 고유 사용자 수와는 구분해야 합니다.

6월 조회 개선과 9월 찜 수 추가는 별도 작업이었습니다. 같은 필드 이름과 Serializer를 써도 데이터를 준비하는 쿼리와 표시 계산이 모두 같아지는 것은 아니어서, 호출부와 다른 화면의 결과까지 함께 대조했습니다.

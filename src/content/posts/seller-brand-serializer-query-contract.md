고객이 북마크한 판매 브랜드를 모아 보는 화면에서 Sentry의 N+1 경고가 발생했습니다. N+1은 목록을 한 번 읽은 뒤 각 항목의 추가 정보를 다시 조회해, 항목이 늘수록 쿼리도 늘어나는 패턴입니다. 이 화면에서는 브랜드의 홈 페이지 정보와 북마크 수를 만들 때 추가 조회가 발생했습니다.

처음 경고가 난 화면만 고칠 수도 있었지만, DB 객체를 API 응답으로 바꾸는 같은 Serializer를 여러 화면이 공유하고 있었습니다. 표현 코드를 바꾸려면 각 화면이 어떤 데이터를 미리 가져오는지도 함께 확인해야 했습니다.

## 미리 읽은 브랜드 안에 읽지 않은 관계가 있었다

브랜드 홈은 prefetch로 미리 읽고 있었지만, 그 홈에 연결된 페이지는 포함하지 않았습니다. 응답을 만들면서 페이지에 접근할 때마다 쿼리가 추가됐습니다. 북마크 수 역시 브랜드별 `.count()`로 계산했습니다.

연결된 페이지까지 가져오고 북마크 수는 일괄 집계해 Serializer에 전달했습니다. 여기서 집계 값이 없으면 예전처럼 `.count()`하는 fallback을 남길지 결정해야 했습니다. 남기면 다른 화면이 데이터를 준비하지 않아도 응답은 나오지만, 그 화면의 반복 조회도 계속됩니다.

fallback을 없애고 사용처 네 곳이 필요한 값을 준비하도록 맞췄습니다. 로컬에서 브랜드 5개를 읽는 경우 14쿼리가 4쿼리로 줄었습니다. 공통 Serializer가 만든 필드뿐 아니라 각 호출부의 응답도 확인했습니다.

## 정적 검사 통과와 실제 조회 감소는 따로 확인했다

수정 중에는 검사 규칙끼리 충돌했습니다. Serializer 메서드의 `.get()`을 ORM 조회로 오인하는 검사와 딕셔너리에 `dict.get()`을 권장하는 Ruff 규칙이 함께 적용됐습니다. 당시에는 표현 처리를 `to_representation()`으로 옮겨 검사를 통과시켰습니다.

다만 검사 대상 밖으로 코드를 옮겼다고 반복 조회가 사라지는 것은 아닙니다. 실제 ORM 호출 여부와 쿼리 수를 별도로 검증했습니다. 검사기가 딕셔너리 접근과 DB 접근을 구별하지 못하는 문제는 후속 개선이 필요했습니다.

## 9월에는 찜 수의 표시 기준도 맞췄다

후속으로 판매 브랜드 목록에 찜 수를 추가할 때도 브랜드별 COUNT 대신 일괄 집계를 사용했습니다. 같은 사용자를 중복으로 세지 않고, 브랜드 1개·30개·100개에서 모두 4쿼리인지 확인했습니다.

그런데 테스트 서버에서 목록과 검색 화면의 숫자가 달랐습니다. 목록에는 실제 찜 수만 넣었고, 검색 응답에는 표시용 보정값도 더하고 있었기 때문입니다. 집계 쿼리가 맞아도 고객은 같은 브랜드의 찜 수를 화면마다 다르게 보게 됩니다. 후속 수정에서 검색과 같은 표시 기준을 적용했습니다.

6월의 북마크 조회와 9월의 찜 수 추가는 별도 작업이지만 같은 점을 확인하게 했습니다. 여러 화면이 필드 이름과 Serializer를 공유해도, 조회 데이터와 표시 계산까지 자동으로 같아지지는 않습니다. 공통 응답을 바꿀 때는 데이터를 준비하는 호출부와 그 값을 보여주는 다른 화면도 함께 대조해야 했습니다.

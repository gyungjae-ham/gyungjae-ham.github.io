예외 알림을 통합했는데, 코드를 읽으려면 여전히 두 곳을 따라가야 했습니다. 한쪽에서 알림을 보내고 다른 쪽에서는 같은 예외인지 확인해 중복을 막고 있었습니다. 동작은 맞아도 다음 변경을 맡은 사람이 이해하기에는 불편한 구조였습니다.

제가 고치려던 것은 알림의 형식보다 **같은 일을 두 번 할 수 있어서 방어 코드가 필요한 구조**였습니다. 다만 이미 모니터링을 사용하는 245개 View의 응답은 그대로 유지해야 했습니다.

## 중복 방지 조건을 지우려면 진입점부터 줄여야 했다

모니터링은 Mixin의 `handle_exception()`과 전역 exception handler에 나뉘어 있었습니다. 전역 핸들러는 `isinstance`로 Mixin 적용 여부를 검사해 캡처를 건너뛰었습니다. 새 응답 포맷을 추가할 때도 이 관계를 알아야 했습니다.

처음 떠올릴 수 있는 위치는 Django 미들웨어입니다. 하지만 DRF 내부에서 예외를 응답으로 바꾼 경우에는 미들웨어의 예외 후크까지 원래 예외가 넘어오지 않습니다. 응답의 상태 코드만으로는 stack trace와 예외별 그룹핑에 필요한 정보를 복구할 수 없습니다.

기존 Mixin에 모니터링을 모두 맡기는 방법도 있었지만, 다중 상속 순서를 알아야 하는 부담은 남습니다. 그래서 응답 핸들러를 선택하는 `get_exception_handler()` 쪽으로 모았습니다.

| 위치                            | 이 작업에서 남는 문제                                |
| ------------------------------- | ---------------------------------------------------- |
| Django 미들웨어                 | DRF가 처리한 원래 예외를 받지 못함                   |
| `handle_exception()` Mixin      | 상속 순서와 응답 포맷 책임이 계속 얽힘               |
| 응답 핸들러를 감싸는 데코레이터 | 포맷별 핸들러를 유지하면서 모니터링만 공통 적용 가능 |

## 응답을 만드는 함수는 남기고 모니터링만 감쌌다

`with_monitoring(handler)`가 기존 응답 핸들러를 감싸도록 했습니다. Mixin은 어떤 포맷으로 응답할지만 결정하고, Sentry 캡처와 서버 오류 알림은 데코레이터가 맡습니다.

이렇게 하면 사용자 View의 상속 선언을 바꿀 필요가 없습니다. 변경 범위를 245개 호출부로 넓히는 대신, 공통 구현 안에서 책임을 정리할 수 있었습니다. `isinstance` 가드도 더 이상 필요하지 않았습니다.

## 구현보다 테스트에서 한 번 더 막혔다

처음에는 모듈 변수에 `with_monitoring(drf_default_handler)`를 할당했습니다. 그런데 테스트에서 기본 핸들러를 patch해도 mock이 호출되지 않았습니다. 래퍼가 import 시점의 함수 참조를 closure에 붙잡고 있었기 때문입니다.

해결은 데코레이터 문법 자체에 있지 않았습니다. **감싸진 함수 본문에서 기본 핸들러를 조회하도록 바꾼 것**이 중요했습니다. 실행 시점에 조회하니 테스트의 patch도 반영됐습니다.

아래는 그 차이를 설명하기 위해 단순화한 예시입니다.

```python
# 생성 시점의 함수 참조를 붙잡는다.
monitored_handler = with_monitoring(default_handler)

# 함수 본문에서 실행 시점에 조회한다.
@with_monitoring
def monitored_handler(exc, context):
    return default_handler(exc, context)
```

## 변경의 크기는 호출부가 아니라 계약으로 확인했다

기존 단위·통합 테스트 31건이 통과했고, 외부 View 코드 변경은 없었습니다. 모니터링 진입점은 두 곳에서 한 곳으로 줄었습니다. 응답 본문·상태 코드·헤더를 유지하는 것이 이 리팩토링의 기준이었습니다.

알림 누락이나 중복을 조건문으로 막는 데서 시작했지만, 이번에는 조건문이 필요해진 이유를 없앴습니다. 다음 응답 포맷을 추가할 때도 기존 핸들러를 감싸면 됩니다. 어느 쪽이 먼저 알림을 보냈는지부터 추적할 필요가 없어졌습니다.

> 같은 예외를 두 곳에서 잡고, 중복 알림을 막기 위해 다시 분기하고 있었습니다. 응답 핸들러를 감싸는 방식으로 모니터링을 모으면서 기존 View의 호출 방식은 유지했습니다.

## 중복을 막는 코드가 구조를 설명하고 있었다

처음에는 View별로 흩어진 예외 알림을 공통 Mixin과 전역 예외 핸들러로 옮겼습니다. 알림을 빠뜨리는 문제는 줄었지만, 이번에는 두 진입점이 같은 예외를 처리할 수 있었습니다. 전역 핸들러에서 View의 Mixin 상속 여부를 검사해 한쪽 처리를 건너뛰었습니다.

그 가드는 단순한 방어 코드가 아니었습니다. 코드를 읽으려면 Mixin의 상속 관계, DRF의 예외 처리 순서, 전역 설정까지 함께 따라가야 했습니다. 응답 형식을 정의하는 Mixin이 모니터링까지 책임지면서 상속 순서에 대한 의존도 남았습니다.

## 미들웨어로 옮기면 원본 예외를 놓친다

Django 미들웨어에 모니터링을 모으는 방법부터 비교했습니다. 다만 DRF 내부에서 처리된 예외는 이미 Response로 바뀌어 미들웨어의 예외 후크에 도달하지 않을 수 있습니다. 응답 상태만 보면 알림 여부는 정할 수 있어도, 원본 예외를 이용한 스택 추적과 그룹핑은 유지하기 어렵습니다.

그래서 응답 핸들러를 감싸는 `with_monitoring` 데코레이터를 두었습니다. 각 Mixin은 `get_exception_handler()`에서 자기 응답 함수를 선택하고, 데코레이터가 Sentry 캡처와 서버 오류 알림을 붙입니다. 기존 View의 상속 선언은 바꾸지 않았습니다.

응답을 만드는 위치에서 예외와 응답을 함께 볼 수 있게 되니, 어떤 Mixin을 쓰는지 검사하는 중복 방지 가드도 제거할 수 있었습니다. 응답 포맷과 모니터링 정책을 따로 읽을 수 있다는 점이 더 큰 변화였습니다.

## 테스트가 잡아낸 import 시점의 참조

처음에는 모듈 변수에 `with_monitoring(default_handler)` 결과를 바로 저장했습니다. 그런데 이 방식은 원래 함수를 import 시점에 캡처합니다. 테스트에서 모듈의 `default_handler`를 mock으로 바꿔도 이미 잡힌 참조는 바뀌지 않았습니다.

해결은 데코레이터로 감싼 함수의 본문에서 기본 핸들러를 호출하는 것이었습니다. 호출 시점에 모듈 속성을 찾도록 바꾸니 patch가 반영되었습니다. 데코레이터 문법 자체가 문제를 해결한 것이 아니라, 참조를 찾는 시점을 바꾼 것이 핵심입니다.

## 응답은 유지하고 진입점만 줄였다

작업 당시 기록에서는 기존 단위·통합 테스트가 모두 통과했고, 운영 View의 사용 코드는 바뀌지 않았습니다. 이번 글 작성에서 당시 테스트를 재실행한 것은 아닙니다. 운영 중 알림 누락률이 얼마나 줄었는지에 대한 별도 측정도 확보하지 않았습니다.

확인한 변화는 명확합니다. 모니터링 진입점을 한 곳으로 모았고, Mixin 상속 여부를 검사하던 가드를 없앴습니다. 새로운 응답 형식이 필요해져도 응답 함수에 같은 데코레이터를 적용하면 됩니다.

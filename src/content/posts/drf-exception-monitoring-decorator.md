운영 중인 API에서 오류가 나면 해야 할 일이 두 가지 있습니다. 앱에는 약속된 형태의 오류 응답을 돌려주고, 개발자에게는 원인을 조사할 수 있는 기록을 남기는 일입니다. 제가 작업하던 Django REST Framework(DRF) 서버는 오류를 Sentry에 기록하고 서버 오류를 Slack으로 알리고 있었습니다.

처음에는 API마다 알림을 직접 보내다 보니 누락과 중복이 생겨 공통 처리를 도입했습니다. 그런데 도입 후 코드를 다시 살펴보니, 같은 예외를 처리하는 코드가 여전히 두 군데에 있었습니다. 한쪽이 알림을 보내면 다른 쪽은 “이미 처리하는 View인가?”를 확인하고 건너뛰는 구조였습니다. API 요청을 받는 View 245개에 적용된 상태라, 이를 정리하면서 앱이 받는 응답까지 바꿔서는 안 됐습니다.

## 예외가 응답으로 바뀌기 전에 모아야 했다

DRF는 View에서 발생한 예외를 잡아 오류 응답으로 바꿀 수 있습니다. 이 때문에 모니터링을 Django 미들웨어로 옮기는 것만으로는 충분하지 않았습니다. DRF가 이미 처리한 예외라면 미들웨어에는 원래 예외가 넘어오지 않습니다. 응답에 적힌 500이라는 숫자만으로는 어느 코드에서 실패했는지 복원할 수 없습니다.

기존 구현은 View에 기능을 더하는 Mixin의 `handle_exception()`과 전역 예외 핸들러 양쪽에서 모니터링했습니다. 전역 핸들러의 `isinstance` 검사는 같은 예외를 두 번 보내지 않기 위한 장치였습니다. 어느 한쪽만 수정하려 해도 다른 쪽의 동작을 알아야 했습니다.

그래서 응답을 만드는 핸들러를 선택하는 `get_exception_handler()`에서 공통 모니터링을 붙였습니다. `with_monitoring(handler)`가 기존 핸들러를 감싸고, 오류 기록과 알림을 맡도록 했습니다. Mixin에는 각 API에 맞는 응답 형식을 선택하는 역할만 남겼습니다. 기존 View의 상속 선언은 유지할 수 있어 245개 호출부를 수정하지 않았습니다.

## 테스트가 예전 함수를 계속 호출한 이유

구조를 옮긴 뒤에는 테스트에서 예상하지 못한 문제가 나왔습니다. 기본 핸들러를 mock으로 교체했는데도 mock이 호출되지 않았습니다. 모듈을 읽는 시점에 `with_monitoring(default_handler)`를 실행하면서, 래퍼가 교체 전 함수 참조를 붙잡고 있었기 때문입니다.

아래는 차이를 설명하기 위한 축약 코드입니다.

```python
# 이 시점의 default_handler를 래퍼 안에 저장한다.
monitored_handler = with_monitoring(default_handler)

# 호출될 때 default_handler를 찾는다.
@with_monitoring
def monitored_handler(exc, context):
    return default_handler(exc, context)
```

두 번째 형태에서는 함수 본문이 실행될 때 기본 핸들러를 찾으므로 테스트에서 바꾼 함수가 호출됩니다. `@` 문법으로 바꾼 것 자체보다, 함수 참조를 조회하는 시점이 달라진 것이 핵심이었습니다.

기존 단위·통합 테스트 31건을 통과하면서 응답 본문·상태 코드·헤더가 유지되는지 확인했습니다. 모니터링 코드는 한 곳으로 모였고 중복 방지용 `isinstance` 검사도 제거했습니다. 이제 새 응답 형식이 필요하면 해당 핸들러를 만들고 같은 래퍼를 적용하면 됩니다. 알림을 이미 보냈는지 다른 처리 경로부터 추적할 필요가 없어졌습니다.

상품을 보여주는 페이지를 복제하면 새 페이지에서 필터나 상품 구성을 독립적으로 수정할 수 있어야 합니다. 그런데 복제본에 새 UUID를 발급했는데도 필터 편집과 탭의 상품 조회가 원본을 따라가고 있었습니다.

페이지는 한 행으로 끝나지 않았습니다. 페이지 요소와 필터가 있고, 필터는 화면 뒤에서 후보 상품을 관리하는 별도 pool을 참조했습니다. 이 연결 중 일부가 DB의 외래키가 아니라 JSON 안의 UUID와 URL로 저장되어 있었습니다. 행을 복사하고 새 ID를 주는 것만으로 JSON 문자열까지 바뀌지는 않았습니다.

## 함께 복사한 대상을 다시 연결했다

복제 과정에서 원본 ID·UUID와 새 값을 짝지은 매핑을 유지했습니다. 페이지 요소뿐 아니라 함께 복제하는 숨김 상품 pool의 요소도 매핑에 넣었습니다. 새 객체를 만든 뒤 JSON 안의 내부 참조가 새 대상을 가리키도록 변환했습니다.

```text
원본 페이지의 필터 → 원본 상품 pool
        ↓ 복제              ↓ 복제
새 페이지의 필터   → 새 상품 pool로 연결
```

참조 변환을 설명하기 위해 UUID와 필드명을 줄이면 다음과 같습니다. 실제 저장 JSON의 발췌는 아닙니다.

```json
{ "before": { "poolRef": "old-pool" }, "after": { "poolRef": "new-pool" } }
```

`old-pool → new-pool` 매핑이 있어야 바꿀 수 있습니다. 복제 대상 내부 참조인데 대응값이 없다면 원본을 계속 가리키게 두는 대신 복제를 실패시켜야 합니다. 복제 범위 밖의 링크는 이 치환 대상이 아닙니다.

상품 순서와 노출 기간도 함께 옮겼습니다. 원본의 구성을 유지하면서 이후 수정은 새 페이지 안에서 이루어져야 했기 때문입니다. 생성과 참조 변환을 한 트랜잭션으로 처리하고 필요한 pool을 찾지 못하면 전체를 롤백하도록 했습니다. 중간까지만 복사된 페이지를 남기지 않으려는 처리입니다.

## 페이지 밖으로 가는 링크는 그대로 뒀다

JSON에서 UUID처럼 보이는 문자열을 모두 새 값으로 바꾸면 수동 URL이나 외부 대상까지 잘못 바꿀 수 있습니다. 복제 대상 pool 소속임을 확인한 상품 URL만 변환하고, 그 밖의 연결은 유지했습니다.

예를 들어 복제한 페이지 안의 필터는 새 pool로 옮겨야 하지만, 운영자가 직접 지정한 외부 링크까지 새 페이지 주소로 바뀌어서는 안 됩니다. 문자열 형식보다 그 참조가 복제 범위 안에 속하는지가 기준이었습니다.

참조 변환 단위 테스트 5건은 통과했습니다. 다만 API 회귀 테스트는 당시 테스트 DB의 컬럼 누락으로 준비 단계에서 막혀 전체 성공을 확인하지 못했습니다. 변경은 병합됐지만, 실제 운영에서 복제한 뒤 필터를 편집하는 과정까지 확인한 기록은 추가로 필요합니다.

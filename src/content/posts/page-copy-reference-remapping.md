페이지를 복제하고 새 UUID를 발급했는데 복제본의 필터는 원본을 보고 있었습니다. 필터에 연결된 숨김 상품 pool과 JSON 안의 참조까지 같이 바뀌어야 독립적으로 편집할 수 있었습니다.

이 작업에서 복제는 행을 하나 더 만드는 일이 아니었습니다. **같이 복사할 연결과 그대로 둘 연결을 구분하는 일**이었습니다.

## 새 객체를 만들면 새 참조가 자동으로 생기지는 않는다

페이지와 요소를 새로 만들어도 JSON에 저장된 UUID와 URL은 기존 값입니다. 필터 편집이나 탭 조회가 원본에 종속되는 이유였습니다.

복제 과정에서 원래 ID·UUID와 새 값의 매핑을 유지했습니다. 페이지뿐 아니라 숨김 상품 pool의 요소도 이 매핑에 포함하고 참조를 다시 연결했습니다.

```text
원본 페이지 요소 ──참조── 원본 pool 요소
       ↓ 복제                  ↓ 복제
복제 페이지 요소 ──재매핑── 복제 pool 요소
```

새 값 발급과 참조 변환을 따로 끝내면 중간에 실패했을 때 불완전한 복제본이 남을 수 있습니다. 한 트랜잭션으로 처리하고 필요한 pool을 찾지 못하면 전체를 롤백했습니다.

## UUID처럼 보인다고 모두 바꾸지는 않았다

수동 URL이나 외부 UUID까지 무조건 치환하면 복제와 무관한 연결이 깨집니다. 복제 대상 pool 소속으로 확인된 상품 URL만 바꿨습니다. 그 밖의 참조는 보존했습니다.

상품 순서와 노출 기간도 함께 복제했습니다. 독립적인 편집을 가능하게 하면서 원본의 화면 구성을 유지해야 했습니다.

## 작은 변환 테스트와 API 검증은 나눠 봤다

참조 변환 단위 테스트 5건이 통과했습니다. API 회귀 테스트는 당시 DB 컬럼 누락으로 setup에서 막혀 전체 통과 결과는 없습니다. 변경은 병합됐지만 운영에서 복제 후 편집까지 확인한 기록은 추가로 필요합니다.

이번에 구현한 경계는 명확합니다. 복제 대상 내부의 연결은 새 객체로 옮기고 외부 연결은 유지합니다. 다음 복제 기능도 ID 재발급보다 이 경계부터 정해야 합니다.

운영자는 기존 상품 페이지를 복제해 새 기획전을 만들 수 있습니다. 복제한 페이지에서 필터와 상품 구성을 바꿔도 원본에는 영향을 주지 않아야 합니다. 그런데 새 페이지에 UUID를 발급했는데도 필터 편집과 탭의 상품 조회가 원본을 따라가고 있었습니다.

페이지 데이터는 한 행으로 끝나지 않았습니다. 페이지 요소와 필터가 있고, 필터는 화면 뒤에서 상품 후보를 관리하는 별도 목록인 pool을 참조했습니다. 이 연결 일부는 외래키가 아닌 JSON의 UUID와 URL로 저장돼 있었습니다. 새 행을 만든다고 JSON 속 문자열도 자동으로 바뀌지는 않습니다.

## 원본과 복사본의 ID를 짝지어 두기

예를 들어 원본 페이지 A의 필터가 상품 목록 P를 보고 있다고 해보겠습니다. 페이지 B와 새 목록 Q를 만들었어도 B의 필터에 P의 ID가 남으면 독립된 복사본이 아닙니다. 필터가 Q를 보도록 연결까지 바꿔야 합니다.

복제하면서 원본 ID·UUID와 새 값을 짝지은 매핑을 유지했습니다. 페이지 요소뿐 아니라 함께 복사하는 숨김 상품 pool의 요소도 이 매핑에 넣었습니다. 객체를 모두 만든 뒤 JSON 내부 참조를 새 값으로 변환했습니다.

```text
페이지 A의 필터 → 상품 목록 P
페이지 B의 필터 → 상품 목록 Q
                  P의 참조를 Q로 변환
```

복제 대상 내부 참조인데 대응값이 없다면 원본을 그대로 사용하지 않고 실패하도록 했습니다. 상품 순서와 노출 기간도 함께 옮기고, 생성과 참조 변환은 한 트랜잭션으로 처리했습니다. 필요한 pool을 찾지 못하면 전체를 롤백해 중간까지만 복사된 페이지를 남기지 않게 했습니다.

## 바꾸면 안 되는 링크도 있습니다

UUID처럼 보이는 문자열을 모두 치환할 수는 없습니다. 운영자가 직접 지정한 외부 URL이나 복제 범위 밖의 상품 링크는 그대로여야 합니다. 복제 대상 pool에 속하는 상품 URL인지 확인한 뒤 해당 참조만 바꿨습니다.

같은 JSON 문자열이어도 새 페이지 안에서 독립적으로 수정할 데이터인지, 원래 목적지로 계속 이동해야 할 링크인지에 따라 처리가 달랐습니다.

참조 변환 단위 테스트 5건은 통과했습니다. API 회귀 테스트는 당시 테스트 DB의 컬럼 누락으로 준비 단계에서 막혔습니다. 변경은 병합됐지만, 운영에서 페이지를 복제하고 필터를 편집하는 전체 흐름은 추가 확인이 남았습니다.

당일배송 안내는 상품 상세에서만 필요하지 않습니다. 고객은 장바구니와 결제 화면에서도 지금 주문하면 당일배송이 가능한지, 마감시각이 언제인지 확인합니다. 화면마다 계산이 다르면 같은 주문에 서로 다른 안내가 나올 수 있어, 상품 ID 목록을 받아 공통으로 판단하는 API를 만들었습니다.

그런데 기존 배송 안내에는 A/B 실험의 사용자 배정도 연결돼 있었습니다. 코드를 여러 화면에서 재사용하려면 정보를 읽는 일과 사용자를 실험에 새로 넣는 일을 구분해야 했습니다.

## 장바구니를 읽는 요청이 실험 참여가 되지 않도록

이 실험은 상품 상세 화면을 처음 배정하는 지점으로 정했습니다. 장바구니와 결제에서는 이미 정해진 그룹의 결과를 읽어야 했습니다.

예를 들어 상품 상세에서는 배정되지 않은 고객이 장바구니를 연다고 해보겠습니다. 장바구니 조회가 같은 함수를 호출한다는 이유로 새 그룹을 만들면, 원래 정한 진입 지점 외에서도 실험 참여자가 생깁니다. 배송 판정은 같아도 이 요청에 허용할 동작은 달랐습니다.

공통 API에서 요청이 어떤 화면의 조회인지 서비스까지 전달하도록 했습니다. 활성 실험의 신규 배정은 상품 상세 요청에서만 허용하고, 장바구니와 결제는 기존 배정만 읽습니다.

| 화면      | 기존 배정 사용 | 신규 배정 |
| --------- | -------------- | --------- |
| 상품 상세 | 사용           | 허용      |
| 장바구니  | 사용           | 하지 않음 |
| 결제      | 사용           | 하지 않음 |

이 표는 새 배정이 필요한 활성 실험을 전제로 합니다. 공통 함수를 쓴다는 이유만으로 데이터 조회가 사용자 상태 변경으로 이어지지 않게 한 것입니다.

## 실험 종료 후의 안내도 확인했습니다

B안을 채택하고 실험을 종료했다면 대상 상품에는 계속 안내가 나와야 합니다. 활성 실험인지만 검사하면 종료하는 순간 채택한 기능도 사라질 수 있습니다. B가 승자로 끝난 경우에는 새 배정 없이 안내를 제공하도록 했습니다. 비슷한 종료 처리는 [검색 실험](/posts/search-experiment-winner-baseline/)에서도 다뤘습니다.

비-DB 테스트 16건으로 화면별 분기를 확인하고, APIClient로 실제 camelCase 응답과 마감시각 표현도 검사했습니다. 변경은 병합됐습니다. 이번에 확인한 것은 안내와 실험 배정의 동작이며, 배송시간이나 구매 전환 효과를 측정한 결과는 아닙니다.

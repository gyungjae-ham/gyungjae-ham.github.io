당일배송 안내는 상품 상세와 장바구니, 결제 화면에서 필요했습니다. 각 화면에 같은 판정을 넣으면 cutoff와 도착 예정 응답이 조금씩 달라질 수 있습니다. 상품 ID 배열을 받는 공통 조회 API로 모았습니다.

그러나 판정 코드를 공유하면서 실험 배정까지 공유하면 다른 문제가 생깁니다. **배송 정보를 읽은 화면에 따라 실험에 들어오는 사용자가 달라질 수 있었습니다.**

## 같은 정보를 읽어도 같은 행동은 아니었다

상품 상세는 신규 실험 배정을 허용하는 지점이었습니다. 장바구니와 결제에서는 이미 배정된 결과만 읽어야 했습니다. 공통 API 내부에서 요청 맥락을 구분해 정확한 PDP 요청일 때만 ACTIVE 실험의 신규 배정을 허용했습니다.

호출부가 늘어난다는 이유로 배정 권한까지 넓히지 않았습니다. 조회 재사용과 실험 진입은 다른 책임이었습니다.

| 요청          | 실험 처리                          |
| ------------- | ---------------------------------- |
| 상품 상세     | 활성 실험 신규 배정 허용           |
| 장바구니·결제 | 기존 배정 조회                     |
| 종료 승자 B   | 신규 배정 없이 대상 상품 안내 제공 |

## 종료된 실험에서도 안내는 남아야 했다

B가 승자로 끝나면 신규 배정을 만들지 않고 대상 상품 전체에 안내하도록 했습니다. 활성 상태에서만 노출하면 실험 종료와 함께 채택한 동작도 사라집니다.

같은 문제가 [검색 실험](/posts/search-experiment-winner-baseline/)에서도 나타났습니다. 실험 상태를 읽는 함수의 재사용보다, 화면에서 원하는 기본 동작을 먼저 정해야 했습니다.

## 응답 형식과 실험 쓰기를 따로 확인했다

비-DB 테스트 16건과 APIClient로 실제 camelCase·cutoff 응답을 확인했습니다. 변경은 병합됐습니다. 실제 배송 SLA나 구매 전환 변화는 아직 측정하지 않았습니다.

공통 조회 API는 정책의 중복을 줄였습니다. 다만 조회를 모았다는 이유로 모든 호출이 실험 참여를 만드는 것은 아닙니다. 읽기는 여러 화면에서 재사용하고 새 배정은 정한 진입점에만 남겼습니다.

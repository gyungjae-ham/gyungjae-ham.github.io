당일배송 상품을 안내할 때는 상품 상세뿐 아니라 장바구니와 결제 화면에서도 같은 정보를 보여줘야 합니다. 지금 주문해도 당일배송 대상인지, 주문 마감시각은 언제인지가 화면마다 다르면 고객은 어떤 안내를 믿어야 할지 알기 어렵습니다.

상품 ID 목록을 받아 공통으로 판단하는 조회 API를 만들었습니다. 다만 안내를 보여주는 실험도 연결되어 있어, 코드를 공유하는 과정에서 실험 참여 시점까지 바뀌지 않도록 구분해야 했습니다.

## 배송 정보를 읽는 일에 실험 배정이 섞여 있었다

실험 배정은 사용자를 비교 그룹에 넣는 처리입니다. 이 실험에서는 상품 상세 화면을 신규 배정 지점으로 정했고, 장바구니와 결제 화면은 이미 정해진 결과만 읽어야 했습니다.

예를 들어 상품 상세에서 배정되지 않은 고객이 장바구니를 조회했다고 새로 배정된다면, 원래 비교하려던 방문 흐름과 다른 사용자가 실험에 들어옵니다. 같은 배송 정보를 읽는다고 모든 화면이 같은 실험 진입점인 것은 아닙니다.

공통 API는 요청 맥락을 구분해 상품 상세 요청일 때만 활성 실험의 신규 배정을 허용했습니다. 장바구니와 결제는 기존 배정만 조회했습니다. 배송 판정은 재사용하되 사용자를 새로 배정하는 권한까지 넓히지 않았습니다.

## 실험이 끝난 뒤에도 채택한 안내는 보여야 했다

B가 승자로 끝난 경우에는 새 배정을 만들지 않고 대상 상품에 안내를 제공하도록 했습니다. 활성 실험에서만 안내하면 채택을 결정하고 종료하는 순간 오히려 화면에서 사라질 수 있기 때문입니다. [검색 실험의 종료 처리](/posts/search-experiment-winner-baseline/)에서도 같은 상태 전환을 다뤘습니다.

비-DB 테스트 16건을 통해 분기를 확인했고, APIClient로 실제 camelCase 응답과 마감시각 표현도 확인했습니다. 변경은 병합됐습니다. 실제 배송시간이나 구매 전환 효과를 검증한 것은 아니지만, 적어도 안내를 읽는 화면을 늘렸다는 이유로 신규 실험 참여자까지 늘어나는 경로는 구분할 수 있었습니다.

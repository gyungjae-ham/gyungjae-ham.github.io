> 상품·장바구니·결제 화면마다 당일배송 정책을 추가하는 대신 전용 조회 API로 모았습니다. 화면 조회만으로 실험 배정이 생기지 않도록 요청 맥락도 구분했습니다.

## 같은 배송 정책이 여러 응답에 흩어질 수 있었다

상품 화면에는 도착 안내가, 장바구니와 결제에는 마감 시각과 노출 판단이 필요했습니다. 각 화면 API에 조건을 붙이면 시간 경계와 실험 상태를 서로 다르게 해석할 수 있습니다. 상품 ID 배열을 받아 필요한 정보를 모아서 반환하도록 경로를 나눴습니다.

이는 프론트의 연결 호출을 늘리는 선택입니다. 호출 수만 줄이는 것보다 정책과 응답의 의미를 한 곳에서 관리하는 편이 이번 요구에 맞았습니다. 기존 화면에 같은 분기를 복사하지 않도록 범위를 정했습니다.

## 읽기 요청이 실험의 분모를 바꿀 수 있다

실험 평가는 단순 조회가 아닐 수 있습니다. 신규 배정까지 일어나면 장바구니나 결제 정보를 읽는 행위가 실험 참여 조건을 바꿉니다. 구현에서는 정확한 PDP 요청에서만 활성 실험의 신규 배정을 허용했습니다.

다른 화면은 이미 만들어진 배정만 읽었습니다. 화면에 따라 동일 사용자가 새로 배정되거나 결과가 달라지지 않게 한 것입니다. 요청이 PDP라는 사실도 명시적인 계약으로 판단해야 하며 서버가 추측하는 화면 상태에 기대서는 안 됩니다.

## 종료된 승자는 배정 없이 적용한다

B가 승자로 끝난 실험은 신규 배정 없이 대상 상품 전체에 기능을 노출합니다. 종료 뒤에도 활성 실험의 배정 함수가 필수라면 승자 기능이 다시 숨겨질 수 있습니다. 배정이 필요한 기간과 확정 정책을 적용하는 기간을 나눴습니다.

마감 시각과 도착 정보는 같은 응답 계약으로 반환했습니다. 테스트에서는 실제 camelCase 출력과 경계 정보를 확인했습니다. 정렬된 내부 자료구조만 검증하는 것과 HTTP에서 클라이언트가 받는 필드를 검증하는 것은 다른 단계입니다.

## 배송 약속의 운영 검증은 남아 있다

원본에는 비-DB 테스트와 읽기 API 검증, 관련 PR의 병합이 남아 있습니다. 다른 PR에 포함된 변경은 독립 성과로 중복 계산하지 않았습니다. 실제 배송 SLA와 전환율은 이 검증으로 입증되지 않습니다.

확인한 구현 결과는 정책 조회를 모으고 신규 배정의 진입점을 제한했다는 점입니다. 배송 정보를 제공하는 읽기와 실험에 참여시키는 변경을 분리하면서, 화면별로 같은 의미의 응답을 사용할 수 있게 했습니다.

이미 저장된 콘텐츠 일곱 개를 홈에 보여주는 API였습니다. 첫 구현을 돌아보니 변경 파일이 47개였습니다. 요구는 작았는데 구현과 주변 정리까지 커져 있었습니다.

저는 첫 산출물을 보관하고 필요한 범위로 다시 설계했습니다. 마일스톤을 아홉 개에서 네 개로 줄이고, 관련 없는 정리와 인덱스 변경을 분리했습니다. 최종 변경은 30개 파일이었습니다. 파일 수 자체가 목표는 아니었지만, 작업의 크기를 다시 묻게 만든 계기였습니다.

## 무엇을 만들지보다 무엇을 빼야 할지 먼저 정했다

콘텐츠는 이미 동기화돼 있었습니다. 필요한 것은 홈 조회, 수동 갱신, 정기 갱신, 숨김 처리 반영이었습니다. 첫 구현에 섞인 주변 파일 정리와 추가 장치는 이번 요구에서 제외했습니다.

테스트가 많다는 이유로 범위가 적절해지는 것은 아닙니다. 이미 만든 코드라도 현재 API를 위해 필요한지를 다시 확인했습니다. 일부 인덱스는 별도 작업으로 남겼고 모델 변경도 제거했습니다.

## ID만 캐싱하면 요청마다 DB를 다시 읽는다

공개 홈 API여서 비로그인 요청도 들어옵니다. 콘텐츠 ID만 캐싱하고 응답할 때 본문과 이미지를 읽으면 매번 조회 비용이 남습니다. 그래서 카드에 필요한 데이터를 통째로 캐싱했습니다.

대신 캐시가 만들어진 뒤 본문이 수정되면 다음 갱신까지 기다립니다. 이 지연은 허용하되, 운영자가 숨긴 콘텐츠가 계속 보이는 것은 허용하지 않았습니다. 수정 종류별로 신선도 요구가 달랐습니다.

| 변경              | 반영 방식                      |
| ----------------- | ------------------------------ |
| 본문 수정         | 다음 풀 갱신에서 반영          |
| 숨김·삭제         | 커밋 이후 캐시 무효화          |
| 조회 시 순서 변경 | 캐시된 카드 목록을 섞어서 응답 |

## 캐시를 지우는 시점도 트랜잭션에 맞췄다

DB 변경 전에 캐시를 지우면 다른 요청이 이전 DB 상태로 캐시를 다시 만들 수 있습니다. 숨김 변경이 롤백되는데 캐시만 바뀌는 경우도 피해야 합니다.

숨김·삭제 mutation에서 `transaction.on_commit()`으로 무효화를 예약했습니다. 성공적으로 커밋된 뒤 캐시를 지우고 다음 조회에서 풀을 다시 만듭니다. 운영자의 클릭부터 모든 응답까지 0초를 보장한다는 의미보다 **DB 변경이 확정된 시점에 무효화한다는 의미**가 정확합니다.

처리 순서를 설명하기 위한 예시입니다.

```python
with transaction.atomic():
    hide_content(content)
    transaction.on_commit(invalidate_home_pool)
```

## 배치가 늦어져도 직전 데이터를 쓸 수 있게 했다

캐시 TTL은 정기 갱신 주기보다 길게 두었습니다. 만료와 갱신을 같은 시각에 맞추면 잡 지연만으로 캐시가 비기 쉽습니다. 갱신이 실패할 때는 직전 캐시를 유지하고 알림을 보내도록 했습니다.

갱신 주기보다 긴 TTL은 지연 여유를 주는 장치입니다. 여러 차례 실패하거나 TTL을 넘기면 별도 대응이 필요하므로 모든 만료 경쟁을 없앴다고 표현할 수는 없습니다.

## 줄인 범위에서도 확인할 것은 남겼다

캐시 적중 시 DB 조회 0회, 미적중 시 콘텐츠와 미디어 조회 2회를 테스트로 확인했습니다. 숨김 커밋과 롤백의 무효화 동작도 검증했습니다. 홈 클릭률이나 재방문율의 개선은 아직 측정하지 않았습니다.

첫 설계를 그대로 밀고 갔다면 더 많은 코드가 남았을 것입니다. 이번에는 기존 데이터를 보여주는 작은 기능에 어디까지 책임을 얹을지 되묻고, 요청 조회와 운영 변경에 꼭 필요한 부분을 남겼습니다.

쇼핑몰 고객은 상품 목록에서 가격을 보고 상세 화면을 열어 할인 혜택을 확인합니다. 일부 브랜드는 추가 쿠폰 할인가를 표시하지 않는 정책이 있었는데, 목록과 상세 화면에서 이 정책이 다르게 적용되고 있었습니다. 목록에서는 숨긴 쿠폰 할인가가 상세 화면에서 다시 나타났습니다.

상세 화면은 상품 쿠폰, 고객이 보유한 쿠폰, 첫 구매 혜택을 여러 API에서 받아 합치고 있었습니다. 한 응답에서 쿠폰을 제외해도 다른 응답의 쿠폰이 다시 합쳐질 수 있었습니다. 그렇다고 상품 자체를 쿠폰 적용 제외로 바꾸면 장바구니와 주문에서 실제로 사용할 수 있는 자격까지 바뀝니다. 10월 19일부터 20일까지 진행한 작업에서는 이 자격을 유지하면서, 상세 화면의 표시 후보와 가격을 함께 결정하는 API를 추가했습니다.

## 쿠폰을 숨겨도 판매가는 남겨야 합니다

예를 들어 정가 5만 원인 상품이 즉시할인으로 4만 원에 판매되고, 추가 쿠폰을 쓰면 3만 5천 원이 된다고 해보겠습니다. 해당 브랜드의 쿠폰 표시를 제외한다면 화면에는 즉시할인이 적용된 4만 원을 보여줘야 합니다. 쿠폰 목록만 비우고 가격은 이전 조합으로 계산하면, 목록에는 쿠폰이 없는데 3만 5천 원이 표시되는 모순이 남습니다.

새 API는 정가와 즉시할인 판매가를 가져온 다음 표시할 쿠폰을 모으고, 그 후보로 기본 추천 쿠폰과 표시 가격을 계산합니다. 표시 제외 브랜드라면 후보를 비워 추천 쿠폰도 반환하지 않습니다. 앞의 예시에서는 정가 5만 원과 판매가 4만 원은 그대로 두고, 기본 표시 가격을 4만 원으로 결정합니다. 실제 주문에서 쿠폰을 적용할 수 있는지 판단하는 상품 데이터는 변경하지 않았습니다.

브랜드 제외 설정도 목록과 상세에서 따로 읽지 않도록 공통 서비스로 옮겼습니다. 설정을 가져오는 캐시 키와 값 정규화 규칙까지 공유합니다. 화면마다 같은 이름의 규칙을 따로 구현하면 설정 형식을 해석하는 차이로 다시 어긋날 수 있기 때문입니다.

## 보유한 쿠폰과 지금 추천할 쿠폰

표시 후보를 합칠 때도 상품에 연결된 쿠폰인지, 고객이 유효하게 보유했는지, 현재 상품 가격에서 추천할 수 있는지를 구분했습니다. 만료됐거나 이미 사용한 발급분을 보유 쿠폰으로 표시하지 않고, 다른 상품에만 적용되는 쿠폰이 합쳐지지 않도록 했습니다. 웹에서는 앱 전용 쿠폰을 제외하며 첫 구매 혜택은 기존 자격·실험 판정을 공유합니다.

최소 주문금액은 목록에서 지울 조건과 추천할 조건을 나누는 사례입니다. 예를 들어 판매가 4만 원의 상품에 5만 원 이상 구매 시 쓸 수 있는 쿠폰이 있다면, 그 쿠폰의 존재는 안내하되 상품 한 개의 기본 할인가에는 적용하지 않습니다. 고객이 수량이나 주문 구성을 바꾸면 조건을 충족할 수 있지만, 이 API는 옵션·수량을 반영한 최종 주문 견적이 아니기 때문입니다.

추천에서는 할인율만 비교하지 않고 현재 가격에 실제 적용되는 할인액을 비교합니다. 할인 한도 때문에 20% 쿠폰보다 10% 쿠폰의 실제 할인액이 클 수도 있습니다. 실제 할인액이 같으면 상품 쿠폰을 장바구니 쿠폰보다 우선하도록 맞췄습니다. 이때 추천된 쿠폰만 바꾸고 표시 가격과 전체 목록의 순서는 유지했습니다.

보유 여부와 발급 만료일은 사용자마다 다릅니다. 같은 쿠폰을 여러 장 유효하게 보유했다면 가장 빨리 만료되는 발급분을 안내하고, 보유하지 않았다면 발급 만료일을 `null`로 반환합니다. 응답에 `private, no-store`를 설정해 이 사용자별 결과가 공유 캐시에 저장되지 않도록 했습니다.

## 계산을 옮기면서 기존 표시 가격 맞추기

여러 응답을 조합하던 프론트 계산을 서버로 옮기는 만큼, 제외 정책 외의 가격까지 달라지는지 확인했습니다. 특히 기존 화면은 기본 표시 가격에 최소 100원 규칙을 적용하고 있었습니다. 서버도 같은 하한을 사용하되 정가와 판매가 원본 값은 바꾸지 않았습니다. 판매가가 0원이나 50원인 입력에서는 기본 표시 가격이 100원이 됩니다. 이는 기존 화면의 표시 규칙을 옮긴 것이며 결제 금액을 100원으로 바꾸는 처리는 아닙니다.

가격 비교에는 기존 프론트의 할인 함수와 신규 서버 함수를 같은 후보·입력으로 실행했습니다. 쿠폰 없음, 최소금액 미충족, 할인 한도, 동률, 최저가 등의 대표 입력과 판매가·할인율 조합에서 기본 표시 가격이 일치하는지 확인했습니다. 서버의 쿠폰 수치는 DB에서 읽을 때와 같은 `Decimal` 타입으로 구성했습니다. 이 비교는 동일 후보에 대한 계산 호환성 검사이며, 실제 로그인 사용자의 DB 후보 조회와 HTTP 응답 전체를 검증한 결과는 아닙니다.

후속 테스트에서는 정률·정액 쿠폰과 조회 순서를 바꿔도 할인액 동률일 때 상품 쿠폰을 선택하는지 확인했습니다. 할인 한도 때문에 실제 할인액이 달라지면 더 많이 할인되는 후보를 선택해야 합니다. DB 없는 서비스·뷰 테스트는 통과했지만, 최종 변경의 DB 통합 테스트는 기존 마이그레이션이 MySQL 오류로 중단돼 실행하지 못했습니다. 앞선 장바구니 확대 회귀에서도 기존 표시명 기대값 불일치 한 건이 실패했고 변경 전에도 재현됐으므로, 관련 회귀 전체를 통과한 상태는 아닙니다.

API는 10월 21일 main에 병합됐습니다. 화면이 바뀌려면 서버 배포 뒤 프론트가 새 응답을 사용하고, 빈 쿠폰 목록에 예전 API의 보유 쿠폰을 다시 합치지 않아야 합니다. 프론트 연동은 별도 후속 작업이며 실제 화면 반영은 확인되지 않았습니다. 다음 확인에서는 제외 브랜드의 즉시할인이 유지되는지와 함께, 일반 상품에서 보유 쿠폰·추천 가격이 사용자별로 맞는지를 실제 후보 조회부터 화면까지 이어서 봐야 합니다.

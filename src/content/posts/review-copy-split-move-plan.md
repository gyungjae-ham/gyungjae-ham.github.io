기존 상품을 당일배송용과 일반 상품으로 나누는 운영 작업에서는 리뷰도 함께 다뤄야 합니다. 원본에 리뷰를 남긴 채 새 상품에 복사할 수도 있고, 특정 옵션을 구매한 고객의 리뷰만 옮길 수도 있습니다.

겉으로는 모두 리뷰 이관이지만 실행 후 남는 데이터는 다릅니다. 복사, 옵션별 분할 이동, 특정 시각 이후의 이동, 원본 삭제를 구분해 구현했습니다.

## 리뷰를 복사할 때 함께 가져갈 데이터

복사본에는 작성자, 이미지, 설문 답변을 보존했습니다. 주문과 도움돼요 같은 리액션 연결은 분리했습니다. 다른 상품에 리뷰가 생긴다고 원래 상품의 주문과 반응까지 같은 관계로 묶을 수는 없기 때문입니다.

같은 요청을 재실행했을 때 복사본이 하나 더 생기지 않도록 원본 리뷰와 대상 상품 조합을 영속적으로 식별했습니다. 예를 들어 리뷰 R을 상품 B에 복사한 뒤 다시 요청하면, 이미 R에서 B로 복사한 결과가 있는지 확인할 수 있습니다. 만료되는 캐시 키만 사용하면 이후 같은 작업을 다시 수행할 수 있어 결과에 이 관계를 남겼습니다.

## 미리보기에서 선택한 옵션이 바뀌었다면

옵션 이름을 운영자가 직접 입력하면 오타나 이름 변경 때문에 대상이 달라질 수 있습니다. 서버가 옵션 축과 그룹을 분석해 미리보기 계획을 만들고 각 항목에 ID를 발급했습니다. 화면에서는 이름을 읽고 선택하지만 실행에는 그 ID를 사용합니다.

예를 들어 미리보기에서 그룹 G1의 리뷰를 상품 B로 옮기기로 했는데, 실행 전에 원본 옵션 구성이 바뀌었다고 해보겠습니다. 예전의 G1이 같은 리뷰들을 뜻한다고 볼 수 없습니다. 이름만 다시 맞춰 진행하지 않고 계획을 새로 만들어 선택해야 합니다.

실행 직전에 구성 변경, 계획 만료, 실행 관리자, 중복 매핑을 다시 검사하도록 했습니다. 미리보기 화면을 확인한 시점과 실제 데이터가 바뀌는 시점을 분리해서 본 것입니다.

```text
현재 옵션 분석 → 미리보기에서 선택
  → 실행 직전 계획·데이터 재검증 → 리뷰 이동
```

시각 기준 이동과 원본 삭제는 별도 API로 나눠 삭제가 포함된 요청임을 드러냈습니다. 작업 후에는 상품의 리뷰 집계와 활성 AI 요약도 갱신했습니다. 리뷰 행만 옮기고 개수나 요약을 그대로 두면 화면은 이전 내용을 보여주기 때문입니다.

관련 변경은 병합됐습니다. 비-DB 분할 테스트 6건과 Serializer·URL 테스트 5건은 통과했지만 DB 의존 사례는 수집 기록만 있어 실행 성공을 확인하지 못했습니다. 실제 운영 데이터의 이관 결과는 추가 확인이 남았습니다.

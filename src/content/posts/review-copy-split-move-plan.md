기존 상품을 당일배송용 상품과 일반 상품으로 나누는 운영 작업에서는 리뷰도 어떻게 옮길지 정해야 합니다. 원본 상품에 리뷰를 남긴 채 복사할 수도 있고, 선택한 옵션에 해당하는 리뷰만 새 상품으로 이동할 수도 있습니다. 특정 시각 이후의 리뷰를 옮기거나 원본을 정리하는 동작도 필요했습니다.

이들을 모두 “리뷰 이관”이라고 부르면 사용 후 데이터가 어떻게 남는지 불분명해집니다. 복제·분할 이동·시각 기준 이동과 삭제를 구분하고, 특히 분할 이동에서는 운영자가 본 미리보기와 실제 실행 대상이 어긋나지 않도록 구현했습니다.

## 복제한 리뷰의 연결을 모두 그대로 옮기지는 않았다

복제본에는 작성자·이미지·설문 답변을 보존했습니다. 반면 주문과 도움돼요 같은 리액션 연결은 분리했습니다. 다른 상품에 리뷰를 하나 더 만든다고 원래 주문이나 반응까지 그대로 연결할 수는 없기 때문입니다.

같은 복제 요청을 다시 실행해도 리뷰가 또 생기지 않도록 원본 리뷰와 대상 상품 조합을 영속적으로 식별했습니다. 잠시 유지되는 캐시 키만 쓰면 키가 사라진 뒤 같은 작업을 다시 수행할 수 있습니다. 복제된 결과 자체에서 원본과 대상을 확인하게 했습니다.

## 미리 본 계획이 실행 때도 유효한지 확인했다

분할 이동에서 옵션 이름을 직접 입력받으면 오타나 이름 변경에 따라 대상이 달라질 수 있습니다. 서버가 옵션 축과 그룹을 분석해 미리보기 계획을 만들고, 각 항목에 서버 발급 ID를 붙였습니다. 운영자는 표시된 이름을 보고 선택하지만 실제 실행 대상은 그 ID로 구별합니다.

예를 들어 미리보기를 만든 뒤 상품 옵션 구성이 바뀌었다면, 예전 계획을 그대로 실행해서는 안 됩니다. 실행할 때 구성 변경, 계획 만료, 실행 관리자, 중복 매핑을 다시 검사했습니다. 미리보기 화면을 한 번 확인했다는 사실만으로 이후 데이터가 그대로라고 가정하지 않았습니다.

```text
현재 옵션 분석 → 미리보기에서 대상 선택
    → 실행 직전 계획·데이터 재검증 → 분할 이동
```

시각 기준 이동과 원본 삭제는 별도 API로 두어 삭제가 발생하는 요청임을 드러냈습니다. 작업 후에는 리뷰 집계와 활성 AI 요약도 갱신했습니다. 리뷰 행만 옮기고 상품의 리뷰 수나 요약을 그대로 두면 화면은 이전 상태를 보여주기 때문입니다.

관련 변경은 병합됐습니다. 비-DB 분할 테스트 6건과 Serializer·URL 테스트 5건은 통과했지만, DB 의존 사례는 수집 기록만 있어 실행 성공으로 확인하지 못했습니다. 실제 운영 데이터 이관 결과도 추가 확인이 필요합니다. 따라서 이 글의 범위는 이관 방식과 재실행·계획 검증 구현까지입니다.

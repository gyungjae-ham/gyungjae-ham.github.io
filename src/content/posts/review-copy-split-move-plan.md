당일배송 등의 이유로 상품을 나누면 리뷰도 함께 다뤄야 합니다. 원본을 남긴 복제, 옵션별 분할 이동, 특정 시각 이후 이동과 삭제는 모두 '리뷰 이관'으로 부를 수 있지만 결과는 다릅니다.

하나의 전체 이동 API에 옵션을 계속 붙이는 대신 동작을 분리했습니다. 특히 분할 이동은 운영자가 미리 확인한 계획과 실행 시점의 데이터가 같다는 보장이 필요했습니다.

## 복제는 원본을 남기고 연결은 골라 옮겼다

복제에는 작성자·이미지·설문 답변을 보존하되 주문과 리액션은 분리했습니다. 같은 리뷰를 다른 상품에 만든다고 모든 연결을 그대로 재사용할 수는 없었습니다.

재실행은 원본 리뷰와 대상 상품 조합의 영속 식별자로 막았습니다. 짧은 캐시 키만 있으면 시간이 지난 뒤 같은 작업이 다시 실행될 수 있어 복제 결과 자체에서 식별해야 했습니다.

## 옵션 문자열을 직접 입력받지 않았다

운영자가 옵션 이름을 입력하면 오타와 이름 변경을 함께 다뤄야 합니다. 서버가 분석한 축·그룹에 불투명 ID를 발급하고 그 계획에서 대상을 선택하게 했습니다.

절차는 늘지만 표시 문자열과 실제 이관 대상을 분리할 수 있습니다. 실행할 때는 구성 변경, 만료, 다른 관리자, 중복 매핑을 다시 검사했습니다.

```text
서버 분석 → 미리보기 계획 → 관리자 선택
                            ↓
                  실행 시 데이터·계획 재검증
                            ↓
                       분할 이동
```

미리보기는 실행 결과의 예약이 아닙니다. 확인 이후 데이터가 바뀌었으면 그 차이를 그대로 통과시킬 수 없습니다.

## 삭제 의도는 별도로 드러냈다

시각 기준 이동과 원본 정리는 삭제가 발생하는 별도 API로 두었습니다. 작업 뒤에는 리뷰 집계와 활성 AI 요약도 갱신했습니다. 리뷰 행만 옮기면 화면의 파생 데이터가 이전 상태를 가리킬 수 있습니다.

관련 변경은 병합됐습니다. 비-DB 분할 테스트 6건과 Serializer·URL 테스트 5건은 통과 기록이 있지만 DB 의존 사례는 수집 기록만 있어 실행 통과로 세지 않았습니다. 실제 운영 데이터 이관의 결과도 아직 이 기록에 없습니다.

이번에 남긴 구조는 편의를 위해 복사·이동·삭제를 하나로 취급하지 않은 것입니다. 운영자의 선택이 어느 데이터에 어떤 결과를 만드는지 실행 직전에도 확인하도록 했습니다.

> 비로그인 장바구니를 위한 DB 모델부터 검토했지만, 최종 구현은 클라이언트 로컬 저장으로 바뀌었습니다. 서버는 상품 정보를 채우고 기존 정렬을 적용하며, 로그인 시 회원 장바구니로 병합하는 역할을 맡았습니다.

## 저장소를 정하기 전에 유지 범위를 정해야 했다

처음에는 Redis, 별도 게스트 모델, 기존 회원 장바구니 모델의 확장을 비교했습니다. Redis의 만료와 eviction, 새 모델의 정리 배치, 레거시 모델 변경의 영향이 각각 달랐습니다. MySQL 환경에서는 조건부 유니크 제약에 기대는 설계도 그대로 적용하기 어려웠습니다.

이후 요구가 클라이언트 로컬 저장으로 바뀌면서 서버 저장소 자체가 필요 없어졌습니다. 대신 기기 변경과 로컬 데이터 삭제 시 복원되지 않는 한계를 받아들였습니다. 서버가 무상태라는 이유로 데이터 소실이 없다고 표현하면 이 결정을 잘못 설명하게 됩니다.

## 회원 정렬을 순수 함수로 둔 효과

서버는 클라이언트가 보낸 상품·옵션 목록을 일괄 조회해 현재 정보를 채웁니다. 가격과 판매 가능 상태를 클라이언트 값만으로 판단하지 않습니다. 조회된 데이터에 담은 시각을 매핑하고 저장하지 않은 장바구니 객체를 구성해 기존 정렬 함수에 넣었습니다.

회원과 게스트의 정렬을 따로 만들지 않아 동일 입력에 같은 순서를 적용할 수 있었습니다. 다만 저장하지 않은 객체는 시각 필드가 자동으로 채워지지 않으므로 조립 단계에서 값을 보장해야 했습니다. DB 모델의 기본 동작에 의존하던 가정이 드러난 부분입니다.

담을 당시 가격은 현재 판매 가격과 구분했습니다. 가격 하락 표시를 위한 과거 값은 보존하되 실제 결제 가격은 서버가 다시 확인해야 합니다. 화면을 만드는 입력과 결제의 신뢰 경계는 같지 않습니다.

## 로그인 머지는 재시도의 범위를 정했다

로그인 직후 네트워크 재시도로 같은 머지가 반복될 수 있습니다. 처음에는 DB 키를 검토했지만 최종적으로 짧은 Redis TTL을 이용한 멱등 처리를 택했습니다. 기존 담기 함수의 수량 가산과 브랜드 시각 동기화가 머지에서 그대로 실행되지 않도록 전용 변경 함수를 두었습니다.

이 보장은 영구적이지 않습니다. TTL이 지나거나 캐시가 지워지면 같은 요청을 다시 처리할 수 있습니다. 클라이언트가 성공 응답 후 로컬 목록을 비우는 흐름과 함께 사용하는 단기 중복 방지입니다. 수량 합산이 저장 타입의 상한을 넘는 경우도 저장 전에 처리했습니다.

## 구현 품질과 제품 효과를 분리했다

당시 기록에는 신규 DB 마이그레이션 없이 구현했고, 조회 쿼리 수와 회원·게스트 정렬 동일성을 테스트한 결과가 남아 있습니다. 로그인 유도에 따른 이탈이나 구매 전환 개선은 출시 후 실험 대상으로 남았습니다.

이 작업은 게스트 토큰과 서버 TTL 정리 같은 책임을 줄인 대신, 로컬 저장의 복구 한계를 받아들인 선택입니다. 가장 유용했던 기존 자산은 저장 모델이 아니라 부수 효과 없이 순서를 계산하는 함수였습니다.

상품을 둘러보다 장바구니에 담는 순간 로그인을 요구하면 아직 구매를 결정하지 않은 고객은 탐색을 멈출 수 있습니다. 비로그인 상태에서도 상품을 담고, 결제할 때 로그인하는 흐름을 만드는 작업을 맡았습니다. 로그인한 뒤에는 기기에 담아 둔 상품을 회원 장바구니와 합쳐야 했습니다.

처음에는 비회원 장바구니도 서버에 저장한다고 생각해 Redis, 새 테이블, 회원 장바구니 확장을 비교하고 새 테이블을 선택했습니다. 이후 기획·개발 논의에서 현재 기기의 로컬 저장을 사용하는 방향으로 바뀌었습니다. 서버 저장소를 고르기 전에 어느 기기까지 보관할 기능인지부터 맞춰야 했습니다.

## 기기가 목록을 보관하고 서버가 현재 정보를 채우기

앱은 상품 옵션, 수량, 담은 시각을 보관합니다. 고객이 장바구니를 열면 이 목록을 서버로 보내고, 서버는 현재 상품 정보와 가격을 채워 정렬한 결과를 반환합니다. 조회 과정에서 비회원 장바구니를 DB에 저장하지는 않습니다.

예를 들어 어제 담은 상품의 가격이 오늘 바뀌었더라도 앱에 저장한 가격만 그대로 보여주면 안 됩니다. 현재 가격은 서버에서 읽되, 가격 하락 안내에 필요한 “담았을 때 가격”은 별도 의미로 유지했습니다. 저장하지 않은 객체에는 ORM이 시각을 자동으로 넣어주지 않으므로 담은 시각도 입력에서 명시적으로 채웠습니다.

이 방식은 익명 고객의 소유권과 보관 만료를 서버에서 관리할 필요가 없습니다. 대신 다른 기기에서 이어 보거나 로컬 데이터가 지워진 뒤 복구할 수는 없습니다. 현재 기기에서 탐색을 이어가는 범위로 정한 설계입니다.

## 로그인 전후에 같은 정렬 사용하기

저장 위치가 달라도 고객이 보는 장바구니는 같습니다. 브랜드 묶음과 품절 상품의 위치가 로그인 순간 달라지지 않도록 [기존 정렬 함수](/posts/cart-sort-preserve-user-context/)를 재사용했습니다.

앱 입력으로 저장하지 않은 `CartItem` 객체를 만들고, 필요한 상품·옵션을 일괄 조회한 뒤 정렬 함수에 넘겼습니다. API 테스트에서는 서로 다른 브랜드의 옵션 항목 3개와 6개를 보내 SQL을 비교했고, 두 입력 모두 조회 3회였습니다. 빈 목록이나 다른 입력 종류까지 항상 세 번이라는 뜻은 아닙니다.

## 로그인 병합을 두 번 요청하면

로그인 후 같은 옵션이 이미 회원 장바구니에 있으면 수량을 더합니다. 예를 들어 회원 장바구니에 2개, 로컬에 1개가 있으면 합친 수량은 3개입니다. 그런데 응답을 받지 못한 앱이 같은 요청을 다시 보내면 4개가 될 수 있습니다.

짧은 시간의 반복 호출을 처리하기 위해 서버에서 사용자 ID로 만든 Redis 키를 60초간 사용했습니다. 처리 중이면 충돌 응답을 보내고, 완료 결과가 있으면 저장한 결과를 반환합니다. 성공 응답을 받은 앱은 로컬 장바구니를 비웁니다.

```text
사용자별 키 확보 → DB에서 수량 병합 → Redis에 완료 결과 저장
재요청 시 처리 중이면 충돌, 완료됐다면 이전 결과 반환
```

키가 요청 ID가 아닌 사용자 ID 기준이라는 제약도 있습니다. 같은 사용자가 60초 안에 서로 다른 목록을 보내더라도 별도 요청으로 구분하지 못합니다.

DB commit과 Redis 저장 사이에도 공백이 있습니다. DB에는 수량이 반영됐지만 완료 결과를 쓰기 전에 프로세스가 종료되면, 키가 만료된 뒤 같은 목록을 다시 더할 수 있습니다. TTL을 넘는 처리나 캐시 소실도 이 장치만으로 막지 못합니다. 영속적인 중복 방지가 필요하다면 요청별 식별자와 DB 기록을 함께 설계해야 합니다.

병합은 수량 가산과 브랜드 시각 갱신이 묶인 기존 담기 함수를 그대로 쓰지 않고 전용 저장 경로로 만들었습니다. 수량의 저장 범위도 제한했습니다. 새 DB 마이그레이션 없이 조회와 병합을 구현했고, 회원과 동일한 정렬과 병합 동작을 테스트했습니다.

로그인하지 않은 사용자도 상품을 담고, 결제할 때 로그인하게 하려는 작업이었습니다. 처음에는 비회원 장바구니를 어느 서버 저장소에 둘지 비교했습니다. Redis, 새 DB 테이블, 기존 회원 장바구니 확장을 검토한 뒤 새 테이블을 선택했습니다.

그러나 기획·개발 논의에서 프론트 로컬 저장으로 방향이 바뀌었습니다. 저는 서버 저장 설계를 내려놓고, **보내온 항목에 상품 정보를 채우고 정렬하는 역할**만 서버에 남겼습니다.

## 영속성이 필요하다는 전제부터 바뀌었다

서버 저장을 전제로 보면 Redis는 eviction 때문에 장기 보관을 보장하기 어렵고, 새 DB 모델은 익명 데이터와 정리 배치가 늘어납니다. 기존 회원 테이블을 바꾸면 레거시 스키마와 중복 제약을 함께 다뤄야 합니다.

프론트 로컬 저장은 게스트 토큰, 서버의 소유권 관리, TTL 정리 배치를 없앱니다. 반면 기기 변경이나 로컬 데이터 삭제 때 장바구니를 이어갈 수 없습니다. 어느 저장소가 더 좋은지보다 이 상품이 어느 보장까지 필요한지가 먼저였습니다.

최종 흐름에서는 서버가 비회원 장바구니를 보관하지 않습니다. 현재 기기 안에서 구매를 이어가는 목적에 맞춘 선택이며, 장기·다기기 보관과 같은 요구가 생기면 다시 판단해야 합니다.

## 저장하지 않은 항목에도 회원 정렬을 쓸 수 있었다

앞선 [장바구니 정렬 작업](/posts/cart-sort-preserve-user-context/)에서 정렬을 순수 함수로 분리해 뒀습니다. DB에 저장했는지보다 항목의 상품 정보와 시각이 중요했습니다.

프론트 입력으로 저장하지 않은 `CartItem`을 구성하고 같은 정렬 함수를 호출했습니다. 상품과 옵션은 일괄 조회해 항목별 추가 쿼리를 피했습니다. 회원·비회원 전용 정렬 두 벌을 만들지 않아도 화면 순서를 맞출 수 있었습니다.

다만 저장되지 않은 객체에는 ORM이 자동으로 채워줄 시각이 없습니다. 입력의 담기 시각을 명시적으로 넣지 않으면 정렬 중 실패했습니다. 회원의 '담았을 때 가격'도 그대로 유지해야 가격 하락 안내가 같은 의미를 가집니다.

## 로그인 병합에는 계산과 다른 책임이 남았다

조회는 서버에 상태를 남기지 않지만 로그인 후 병합은 회원 장바구니를 변경합니다. 재시도하면 수량이 다시 더해질 수 있습니다.

처음에는 DB 멱등 키를 두었다가 짧은 Redis TTL로 단순화했습니다. 성공 후 프론트가 로컬 장바구니를 비우는 흐름과 결합한 선택입니다. TTL 이후나 캐시 소실 이후의 중복 요청까지 영구적으로 막는 보장은 아닙니다.

수량 합산은 저장 필드의 범위를 넘지 않도록 제한했습니다. 기존 담기 함수에 있던 가산과 시각 동기화 부수효과를 그대로 재사용하지 않고 병합용 mutation을 둔 이유도 여기 있습니다.

## 덜 만든 부분과 포기한 보장을 함께 남겼다

신규 DB 마이그레이션 없이 구현했고, 조회의 상품 정보 보충은 고정 3쿼리로 확인했습니다. 조회·병합 테스트 75건 이상에서 회원과 같은 정렬과 병합 동작을 검증했습니다. 로그인 이탈을 얼마나 줄였는지는 출시 후 실험으로 확인할 항목입니다.

서버가 장바구니를 갖지 않는 선택은 구현을 줄였지만 데이터를 절대 잃지 않는다는 보장을 주지는 않습니다. 지금 보면 기기 변경·로컬 삭제의 소실을 허용하는 합의를 더 일찍 했어야 했습니다. 그 전제가 있었다면 저장소 비교도 더 짧아졌을 것입니다.

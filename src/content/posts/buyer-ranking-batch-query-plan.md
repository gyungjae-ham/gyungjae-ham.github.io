쇼핑몰 홈에 실제 구매자 수를 기준으로 한 상품 랭킹을 만들었습니다. 한 사람이 여러 개 산 상품보다 여러 사람이 선택한 상품을 보여주기 위해, 결제가 완료된 주문에서 상품별 구매자를 중복 없이 세는 방식이었습니다. 현재 순위뿐 아니라 일간·주간·월간 순위와 지난 기간의 확정 순위도 필요했습니다.

홈 요청이 올 때마다 주문을 집계할 수는 없어서 미리 계산한 순위를 읽도록 설계했습니다. 그런데 배치를 검증하자 데이터를 만드는 쪽에서 문제가 생겼습니다. 주문량이 늘면서 프로세스가 메모리 부족으로 종료됐고, DB의 임시 디스크 사용도 커졌습니다. 조회 API가 가벼워도 집계 작업이 원본 DB를 압박할 수 있었습니다.

## 주문 행 대신 집계 결과만 가져왔다

현재 순위와 직전 순위 비교에 쓸 데이터는 Redis에, 기간이 끝난 확정본은 DynamoDB에 보관했습니다. 정기 갱신과 수동 재집계는 별도 작업으로 실행했습니다. 하지만 HTTP 요청에서 분리했다는 사실만으로 집계 비용이 줄어드는 것은 아니었습니다.

초기에는 주문 행을 Python으로 가져와 처리했습니다. 주문이 많을수록 애플리케이션 메모리에 올리는 데이터도 늘었습니다. 상품별 구매자 수를 DB에서 계산하고, 애플리케이션에는 집계된 결과만 가져오도록 바꿨습니다.

## SQL에는 의도하지 않은 정렬이 섞여 있었다

집계를 DB로 옮긴 뒤에도 생성된 SQL을 봐야 했습니다. 집계에 불필요한 정렬이 남는지 확인했습니다. 다만 당시 사용한 Django 3.2에서는 모델의 `Meta.ordering`이 집계의 `GROUP BY`에 자동으로 들어간다고 일반화할 수 없습니다. 이 동작은 Django 3.1부터 변경됐습니다. 명시적인 `order_by()`와 커스텀 QuerySet에서 추가한 정렬은 별도로 추적해야 합니다. [Django 집계와 정렬 문서](https://docs.djangoproject.com/en/3.2/topics/db/aggregation/#interaction-with-order-by)

집계 쿼리에서 `.order_by()`로 정렬을 비웠습니다. 이 변경 자체는 불필요한 정렬을 제거하지만, 과거 부하의 원인이 모델 기본 정렬이었다고 확정하는 근거는 아닙니다. 아래는 상품별로 사용자를 중복 제거해 세는 의도를 설명한 축약 코드입니다.

```python
from django.db.models import Count

rows = (
    order_items.order_by()
    .values("product_id")
    .annotate(buyer_count=Count("user_id", distinct=True))
)
```

예를 들어 한 상품을 사용자 A가 두 번, 사용자 B가 한 번 샀다면 구매자는 두 명입니다. 상품과 주문 시각을 함께 그룹으로 삼으면 A의 주문이 여러 그룹으로 나뉠 수 있습니다. 위 쿼리가 상품 단위의 두 명을 반환하는지 확인하는 것이 집계 의미를 검증하는 작은 사례입니다.

쿼리 호출 횟수만 세면 둘 다 한 번입니다. 하지만 DB가 몇 행을 읽고 어떤 단위로 묶는지는 다를 수 있습니다. 그래서 생성된 SQL과 `EXPLAIN`으로 DB의 실행 계획을 함께 확인했습니다. 동일 조건의 전후 SQL·실행 계획 원문을 이 글에 제시할 수 없어, 정렬 유입 경로별 비용을 수치로 분리하지는 않습니다.

## 코드의 인덱스 목록과 실제 DB가 달랐다

모델의 `Meta.indexes`만 봤을 때 없다고 생각한 인덱스가 실제 DB에는 있었습니다. 수동으로 추가된 인덱스였습니다. `SHOW INDEX`로 실제 구성을 확인한 뒤 필터와 인덱스 사용을 다시 살폈고, 테스트 환경에서 전체 스캔 대신 범위를 좁혀 읽는 range scan을 확인했습니다. CPU뿐 아니라 임시 디스크 사용의 시계열도 정렬 비용을 찾는 데 도움이 됐습니다.

집계 외에 응답을 만드는 코드도 살폈습니다. 기존 상품 카드 Serializer에는 이미지 조회와 CDN 이관 작업 예약이 들어 있어, 랭킹을 읽는 요청이 새로운 작업을 만들고 있었습니다. 응답 모양은 유지하되 이 경로에서는 필요한 데이터를 읽어 직렬화하는 데 그치도록 정리했습니다.

로컬·테스트 서버에서 집계와 조회를 검증하고 관련 회귀 테스트를 통과했습니다. 여기서 확인한 것은 해당 환경의 실행 계획과 동작이며, 운영 p95 개선 수치를 측정한 것은 아닙니다. 다음에 유사한 집계를 설계한다면 결과를 어느 저장소에 둘지와 함께, 실제 주문 데이터에서 실행할 SQL부터 확인할 것입니다.

> 랭킹 조회는 캐시로 빨라졌지만 집계가 대형 주문 테이블을 무겁게 읽었습니다. 테스트 검증 중 실행 계획과 메모리 사용을 함께 확인하며 조회 API 밖의 비용을 줄였습니다.

## 같은 랭킹에도 데이터 수명이 달랐다

현재 순위는 주기적으로 바뀌고, 과거 기간의 확정 순위는 보존해야 했습니다. 현재·직전·잠정 순위는 Redis에, 확정된 과거 스냅샷은 DynamoDB에 두었습니다. RDB는 집계 원본으로 읽는 역할을 맡았습니다.

저장소를 나눈 만큼 운영할 경계도 늘었습니다. 확정 시점과 재집계 기준을 명시하고, 현재 순위와 과거 순위의 노출 정책을 구분했습니다. 현재는 구매 가능한 상품을 보충하지만, 과거 순위는 그 시점의 결과라는 의미를 유지해야 했습니다.

## 조회를 비동기로 만든다고 집계가 가벼워지지는 않는다

수동 재집계 요청은 작업을 큐에 넣고 빠르게 반환하도록 분리했습니다. HTTP timeout을 피했지만 DB와 worker의 부담까지 없어지는 것은 아니었습니다. 주문 행을 Python에 모두 적재하는 경로는 메모리를 소진했고, DB 쿼리는 많은 행과 임시 작업 공간을 사용했습니다.

상품 단위 집계 결과만 가져오도록 바꾸고 실제 DB의 인덱스와 `EXPLAIN`을 확인했습니다. 모델 선언에 인덱스가 보이지 않는다는 이유만으로 DB에 인덱스가 없다고 판단하지 않았습니다. 실행 환경의 스키마와 실제 SQL이 근거였습니다.

## 새 진입과 판매 가능 상태를 따로 계산했다

NEW 배지는 직전 갱신의 상품 집합과 현재 집합의 차이로 계산했습니다. 최초 조회한 사람마다 결과가 달라지지 않도록 비교 기준을 저장했습니다. 동률에서는 결정적인 정렬 기준도 필요했습니다.

조회에서는 캐시를 읽는 것뿐 아니라 카드 직렬화의 부수 효과도 확인했습니다. 읽기 중 이미지 관련 작업이 큐에 들어가거나 항목별 조회가 발생하면, 순위 캐시를 도입한 효과가 다른 경로에서 사라집니다. 캐시 경계 밖의 비용까지 추적한 이유입니다.

## 로컬 수치를 운영 성과로 바꾸지 않았다

원본 기록에는 테스트 서버에서의 메모리 소진과 DB 부하, 실행 계획 개선이 남아 있습니다. 합성 데이터의 로컬 응답 시간 비교도 있지만 운영 트래픽에서의 p95 변화는 확보하지 않았습니다. 내부 데이터 규모와 부하의 절대값은 공개하지 않았습니다.

확인한 결과는 원본 전체 적재를 줄이고 집계 실행 계획을 검증했으며, 조회 직렬화의 불필요한 부수 효과를 정리했다는 점입니다. 랭킹의 운영 안정성을 평가하려면 API 지연뿐 아니라 배치 시간, 메모리, DB 부하를 함께 봐야 합니다.

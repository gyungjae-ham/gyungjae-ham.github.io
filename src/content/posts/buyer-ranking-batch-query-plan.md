실제 구매자 수로 상품 랭킹을 만드는 작업이었습니다. 현재 순위는 빨리 읽고, 지난 기간의 확정 순위는 보관하는 구조를 설계했습니다. 그런데 배치를 검증하면서 주문 데이터가 많아지자 프로세스가 메모리 부족으로 종료되고 DB의 임시 디스크 사용도 커졌습니다.

읽기용 저장소를 어떻게 나눌지보다 먼저 봐야 할 것이 있었습니다. **그 저장소에 넣을 결과를 만드는 쿼리가 원본 테이블을 어떻게 읽는가**였습니다.

> 작업 시점은 2026년 6월이며 정확한 시작일은 남아 있지 않아 발행일은 월의 대표일로 표시했습니다.

## 빠른 조회 뒤에 무거운 집계가 숨어 있었다

현재 순위와 직전 순위 비교는 Redis에, 기간이 끝난 확정본은 DynamoDB에 두었습니다. 데이터 수명과 조회 방식이 달라 저장소를 나눈 것입니다. 이 구조는 저장소 두 개를 운영해야 하는 비용도 남깁니다.

정기 갱신과 수동 재집계는 요청 응답에서 분리했습니다. HTTP 요청이 작업을 예약하고 즉시 반환하더라도 배치가 가벼워지는 것은 아닙니다. 비용을 다른 프로세스로 옮긴 뒤 그 비용 자체도 줄여야 했습니다.

초기 경로는 주문 행을 Python에 가져와 처리했습니다. 메모리는 주문 수에 따라 늘어났습니다. 상품별 중복 구매자 집계를 DB에서 끝내고 결과만 가져오도록 바꿨습니다.

## GROUP BY만 넣으면 끝날 줄 알았던 부분

집계를 바꾼 뒤 생성된 SQL을 확인했습니다. 모델의 기본 `Meta.ordering`이 집계 쿼리에 영향을 주면서 시각 컬럼이 그룹과 정렬에 섞여 있었습니다. 상품 단위로 모으려던 결과가 더 잘게 쪼개지고 정렬 비용도 늘었습니다.

집계에서는 `.order_by()`로 기본 정렬을 비웠습니다. 아래는 의도를 설명한 축약 예시입니다.

```python
rows = (
    order_items.order_by()
    .values("product_id")
    .annotate(buyer_count=Count("user_id", distinct=True))
)
```

쿼리 수가 한 개라는 사실만으로 이 문제는 보이지 않습니다. SQL의 GROUP BY와 실행 계획을 함께 확인해야 했습니다.

## 모델에 없는 인덱스가 DB에는 있었다

코드의 `Meta.indexes`만 보고 인덱스가 없다고 판단한 부분도 실제 DB의 `SHOW INDEX` 결과와 달랐습니다. 수동으로 추가된 인덱스가 있었기 때문입니다.

실제 스키마와 `EXPLAIN`을 기준으로 필터와 인덱스를 다시 확인했고, 전체 스캔에서 range scan으로 바뀐 실행 계획을 검증했습니다. CPU만 보기보다 DB 부하와 임시 공간의 시계열을 같이 본 것도 디스크 정렬 비용을 좁히는 데 도움이 됐습니다.

## 조회용 Serializer도 배치의 책임을 늘리고 있었다

기존 상품 카드 Serializer를 재사용하자 이미지 조회와 CDN 이관 태스크 예약이 따라왔습니다. 화면을 위한 직렬화가 랭킹 조회에서 다시 작업을 만드는 구조였습니다.

응답 카드의 모양은 유지하되 랭킹 경로에서는 조회와 직렬화만 하도록 정리했습니다. '기존 코드 재사용'이 비용과 부수효과까지 적절하다는 뜻은 아니었습니다.

## 검증한 것은 테스트 환경의 실행 계획이었다

관련 회귀 테스트 145건과 로컬·테스트 서버에서 집계·조회 동작을 확인했습니다. 운영 p95나 랭킹의 구매 전환 효과는 아직 측정하지 않았습니다. 합성 데이터에서의 캐시 응답 시간을 운영 개선 배수로 쓰지도 않았습니다.

다시 한다면 저장소 설계와 함께 실제 집계 SQL을 먼저 실행해 볼 것입니다. 이번 작업에서 늦게 발견한 위험은 결과를 읽는 속도보다 결과를 만드는 비용에 있었습니다.

상품 상세의 리뷰에 유용한 순서와 최신순을 추가했습니다. 기존 추천순 외에 고객이 다른 기준으로도 읽을 수 있게 하는 작업이었습니다. 사진, 본문 길이, 다른 고객의 “도움돼요”, 작성 시점을 정렬에 사용했습니다.

기존 쿼리는 이미 사진 수를 세고 있었습니다. 여기에 도움돼요 수를 더할 때는 `Count`를 하나 추가하기 전에 두 관계를 JOIN한 결과를 확인해야 했습니다.

## 사진 2개와 도움돼요 3개를 함께 JOIN하면

리뷰 하나에 사진이 2개, 도움돼요가 3개 있다고 해보겠습니다. 둘을 동시에 JOIN하면 사진과 반응의 조합으로 6행이 만들어집니다.

```text
사진 A × 반응 1, 2, 3 → 3행
사진 B × 반응 1, 2, 3 → 3행
```

이 행을 그대로 세면 집계값이 부풀 수 있습니다. `distinct`로 숫자를 맞출 수 있어도 DB가 조합을 처리하는 비용은 남습니다. 도움돼요 수는 리뷰 ID를 참조하는 별도 Subquery에서 계산하도록 분리했습니다.

아래는 조회 의도만 줄인 코드입니다. `reactions`와 `reviews`는 필요한 대상 조건을 가진 QuerySet이며 `Count`, `OuterRef`, `Subquery`, `Value`, `Coalesce`를 사용합니다.

```python
helpful_counts = (
    reactions.filter(review_id=OuterRef("pk"))
    .order_by()
    .values("review_id")
    .annotate(total=Count("pk"))
    .values("total")
)
reviews = reviews.annotate(
    helpful_count=Coalesce(Subquery(helpful_counts), Value(0))
)
```

`OuterRef("pk")`는 바깥에서 읽는 리뷰를 가리킵니다. 해당 리뷰의 반응만 집계하고 없으면 0을 넣습니다. 정렬도 비워 집계에 불필요한 조건이 섞이지 않게 했습니다. 메인 쿼리의 사진 관계와 반응 관계가 곱으로 만나지 않게 만든 것입니다.

## 점수는 조회할 때 계산했습니다

점수를 별도 컬럼으로 저장하면 읽기는 단순해지지만 반응이 바뀔 때 다시 갱신해야 합니다. 배치로 계산하면 최신 반응과 순위 사이에 지연도 생깁니다. 이번에는 `annotate`로 조회 시 계산하고 새 점수 컬럼과 배치는 추가하지 않았습니다.

사진·반응·본문 길이·최신성의 영향을 맞추고 한 요소만으로 점수가 계속 커지지 않도록 상한을 뒀습니다. 기존 추천순은 도움돼요가 0일 때 이전 점수가 유지되게 했습니다. 경과일 계산에는 MySQL 함수를 사용해 DB 의존성은 남았습니다.

베스트 리뷰는 모든 정렬에서 먼저 나와야 하므로 점수보다 앞에 우선순위 키를 뒀습니다. 최신순은 작성 시각이 같은 경우 ID까지 비교합니다. `sort` 요청값은 허용 목록으로만 처리하고 다른 값이면 기존 추천순을 사용합니다.

사진과 반응이 모두 여러 개인 리뷰, 점수 경계, 동률, 페이지네이션을 테스트했습니다. 관련 조회는 3쿼리를 유지했습니다. 이는 호출 횟수의 확인이며 리뷰가 늘었을 때 각 쿼리의 실행시간은 따로 관찰해야 합니다.

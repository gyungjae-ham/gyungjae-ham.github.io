상품 상세 화면에서 리뷰를 읽는 고객이 추천순뿐 아니라 유용한 순서와 최신순도 고를 수 있도록 정렬을 추가했습니다. 유용한 리뷰를 판단하는 재료는 사진, 본문의 충실도, 다른 고객이 누른 “도움돼요”, 작성 시점이었습니다.

기존 조회는 리뷰에 연결된 사진 수를 이미 세고 있었습니다. 여기에 도움돼요 수를 더하는 일은 ORM의 `Count` 하나를 추가하면 될 것 같지만, 두 관계를 같은 쿼리에 연결했을 때 만들어지는 행을 먼저 봐야 했습니다.

## 사진 2개와 반응 3개가 만나면

예를 들어 리뷰 하나에 사진이 2개, 도움돼요 반응이 3개 있다고 해보겠습니다. 리뷰에서 사진과 반응을 동시에 JOIN하면 집계 전에는 각각의 조합으로 6행이 만들어집니다. 단순히 행을 세면 값이 부풀고, `distinct`로 숫자를 맞춰도 그 조합을 처리하는 비용은 남습니다.

도움돼요 집계는 리뷰 ID를 참조하는 별도 Subquery로 분리했습니다. 메인 쿼리의 사진 관계와 반응 관계가 곱으로 만나지 않도록 한 것입니다. 아래는 의도를 설명하기 위해 줄인 코드입니다.

```python
helpful_counts = (
    reactions.filter(review_id=OuterRef("pk"))
    .order_by()
    .values("review_id")
    .annotate(total=Count("pk"))
    .values("total")
)
reviews = reviews.annotate(
    helpful_count=Coalesce(Subquery(helpful_counts), Value(0))
)
```

`OuterRef("pk")`는 지금 집계할 리뷰를 가리키고, 반응이 없는 리뷰에는 0을 넣습니다. 기본 정렬도 비워 집계에 불필요한 정렬이 섞이지 않게 했습니다. Subquery 역시 실행 비용이 있으므로, 코드가 길어졌다는 이유나 쿼리가 하나라는 이유만으로 성능을 판단하지 않았습니다.

## 반응을 바로 반영하는 대신 읽을 때 계산했다

점수를 별도 컬럼에 저장하면 조회는 단순해질 수 있습니다. 대신 도움돼요가 바뀔 때 점수를 다시 갱신해야 하고, 배치를 쓰면 최신 반응과 순위 사이에 지연이 생깁니다. 이번에는 조회 시 `annotate`로 점수를 계산해 새 점수 컬럼과 배치를 추가하지 않았습니다.

사진·반응·본문 길이·최신성을 정규화하고 특정 요소 하나만으로 점수가 계속 커지지 않게 상한을 뒀습니다. 기존 추천순은 도움돼요가 0일 때 이전 점수가 유지되도록 했습니다. 경과일 계산에는 MySQL 함수를 사용해 DB 종속성이 남았습니다.

베스트 리뷰는 어느 정렬에서도 먼저 나와야 해서 점수보다 앞에 우선순위 키를 뒀습니다. 최신순에는 시각이 같은 리뷰를 위해 ID도 정렬 기준에 넣었습니다. 요청의 `sort`는 허용된 값에만 대응시키고, 나머지는 기존 추천순으로 처리했습니다.

테스트에서는 사진과 반응이 모두 여러 개인 리뷰의 집계, 점수 경계, 동률과 페이지네이션을 확인했습니다. 관련 조회가 3쿼리로 유지되는지도 검증했습니다. 이 결과는 호출 횟수에 대한 확인이며, 리뷰가 늘었을 때 쿼리 하나의 실행시간은 별도로 관찰해야 합니다.

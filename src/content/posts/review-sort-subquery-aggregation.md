> 리뷰 이미지 수를 세는 쿼리에 도움돼요 집계를 그대로 붙이면 행이 곱으로 늘어납니다. 반응 집계를 분리하고 추천·유용·최신 정렬을 조회 시점에 계산했습니다.

## 점수를 저장하면 갱신 책임도 생긴다

새 정렬은 사진 유무, 반응 수, 본문 길이, 최신성 등을 사용했습니다. 도움돼요는 사용자의 행동으로 바로 바뀌기 때문에 별도 점수 컬럼을 두면 갱신 작업과 지연을 관리해야 합니다. 이번에는 기존 스키마를 유지하고 쿼리의 annotate로 점수를 계산했습니다.

추천 정렬은 기존 점수에 반응을 보완하고, 최신 정렬은 작성 시각과 식별자를 사용했습니다. 유용 정렬은 신호마다 범위를 제한해 한 값의 크기가 전체 점수를 독점하지 않게 했습니다. 이런 점수는 제품 정책이며 테스트로 계산을 검증했다고 선호도를 증명한 것은 아닙니다.

## 1:N 관계 두 개는 단순히 더해지지 않는다

리뷰에 이미지가 여러 장이고 반응도 여러 개면 두 관계를 함께 JOIN한 중간 결과는 이미지 수와 반응 수의 곱이 됩니다. `Count`를 추가하는 짧은 코드가 잘못된 집계나 큰 중간 결과를 만들 수 있습니다.

반응 수는 리뷰 식별자를 기준으로 상관 서브쿼리에서 따로 계산했습니다. 아래는 구조를 단순화한 예시입니다.

```python
counts = (
    Reaction.objects.filter(review_id=OuterRef("pk"))
    .order_by()
    .values("review_id")
    .annotate(total=Count("pk"))
    .values("total")
)
reviews = reviews.annotate(
    reaction_count=Coalesce(Subquery(counts), Value(0)),
)
```

실제 구현에서는 반응 종류와 출력 타입을 지정했습니다. 집계의 기본 정렬을 제거하고, 반응이 없는 리뷰는 0으로 처리했습니다. 사용자 본인의 반응 여부도 존재 판정으로 분리했습니다.

## 페이지를 나눈 뒤 정렬하지 않았다

점수를 Python에서 계산하려면 후보 전체를 가져오거나 페이지 안에서만 재정렬하게 됩니다. 그래서 경과일 계산도 DB에서 처리했습니다. 당시 MySQL 함수를 사용한 만큼 다른 DB로 옮길 때 다시 검토할 부분이 생겼습니다.

베스트 리뷰의 우선순위는 모든 정렬의 앞에 붙이고 동률 기준을 고정했습니다. 정렬 입력은 허용된 값만 받아 실제 쿼리로 매핑했습니다. 잘못된 값은 기본 정렬로 돌아가게 하여 입력 문자열을 그대로 정렬 표현으로 사용하지 않았습니다.

## 스키마 변경 없이 끝냈지만 비용은 남는다

당시 기록에는 신규 마이그레이션 없이 구현하고 점수 경계, JOIN 집계와 페이지 동작을 테스트한 결과가 있습니다. 조회 수의 검증과 실제 SQL 실행 시간은 다른 항목입니다. 운영 데이터에서의 p95와 중간 결과 감소량은 확보하지 않았습니다.

상관 서브쿼리로 관계를 분리한 이유는 쿼리 한 개라는 숫자를 지키기 위해서가 아니라 각 집계가 무엇을 세는지 유지하기 위해서였습니다. 이후 성능 평가는 실행 계획과 데이터 분포를 함께 확인해야 합니다.

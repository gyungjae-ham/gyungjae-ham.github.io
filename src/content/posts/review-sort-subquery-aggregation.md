상품 리뷰에 추천·유용·최신 정렬을 추가했습니다. 유용한 리뷰를 위로 올리려면 사진과 본문, 도움돼요 반응을 함께 봐야 했습니다. 구현은 `Count` 하나를 추가하면 될 것처럼 보였지만 기존 쿼리는 이미 리뷰 이미지와 JOIN하고 있었습니다.

여기에 도움돼요 관계도 JOIN하면 사진 M개와 반응 N개가 **집계 전에 M×N행**으로 늘어납니다. 리뷰 수가 적어도 리뷰 하나의 관계가 많으면 비용과 집계 결과를 함께 봐야 합니다.

## 쿼리 한 개 안에도 서로 다른 비용이 있다

`distinct`로 중복 카운트를 줄여도 JOIN으로 만들어진 행을 처리하는 비용은 남습니다. 저는 도움돼요 수를 `OuterRef`로 연결한 상관 Subquery로 분리했습니다. 이미지 JOIN과 반응 집계가 메인 쿼리에서 곱으로 만나지 않도록 한 것입니다.

아래는 핵심만 남긴 설명용 예시입니다.

```python
helpful_counts = (
    reactions.filter(review_id=OuterRef("pk"))
    .order_by()
    .values("review_id")
    .annotate(total=Count("pk"))
    .values("total")
)
reviews = reviews.annotate(
    helpful_count=Coalesce(Subquery(helpful_counts), Value(0))
)
```

Subquery는 코드가 길고 실행 비용도 있습니다. 그럼에도 두 1:N 관계를 한꺼번에 JOIN하는 구조를 피하는 것이 이 작업의 기준이었습니다. 모델 기본 정렬도 집계에 섞이지 않도록 비웠습니다.

## 점수를 저장하지 않는 대신 조회 비용을 받아들였다

도움돼요는 실시간으로 바뀝니다. 점수 컬럼과 갱신 배치를 추가하면 조회는 가벼워질 수 있지만 최신 반응과 점수 사이에 지연이 생깁니다.

이번에는 런타임 `annotate`로 계산했습니다. 사진·반응·본문 길이·최신성을 정규화하고 특정 신호만 무한히 점수를 키우지 않도록 상한을 뒀습니다. 추천 정렬은 도움돼요가 0일 때 기존 점수가 유지되도록 했습니다.

이 선택으로 새 점수 저장 컬럼과 배치는 없지만 조회 시 계산은 남습니다. 경과일은 MySQL 함수로 계산해 DB 종속도 받아들였습니다.

## 점수보다 먼저 보존할 순서도 있었다

베스트 리뷰는 어느 정렬에서도 위에 유지해야 했습니다. 점수 앞에 우선순위 키를 두고 최신순에는 시각과 ID를 함께 써 동률에서 순서가 안정적이게 했습니다.

입력 `sort`는 허용값에만 매핑하고 다른 값은 기존 추천 정렬로 돌렸습니다. 문자열을 정렬 표현으로 그대로 전달하지 않았습니다. 전체 개수는 점수 집계가 필요 없는 경량 쿼리로 분리했습니다.

## 쿼리 수와 시간은 다른 검증이었다

정렬 직접 테스트 83개에 점수 경계, JOIN 곱, fallback, 페이지네이션을 넣었습니다. 관련 조회는 고정 3쿼리로 확인했습니다. 하지만 쿼리 수가 일정해도 리뷰가 늘면 각 쿼리가 느려질 수 있습니다. 운영 p95는 아직 측정하지 않았습니다.

이번에는 새 기능을 추가하면서 기존 이미지 집계를 그대로 확장하지 않은 것이 중요했습니다. ORM 코드의 길이보다 관계가 SQL 안에서 어떻게 만나는지를 먼저 확인했습니다.

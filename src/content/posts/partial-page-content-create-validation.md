쇼핑몰 운영자는 페이지에 배너나 상품 구역 같은 콘텐츠 요소를 배치합니다. 한 번의 부분 수정 요청으로 기존 요소를 바꾸면서 새 요소를 추가할 수도 있습니다. 이때 신규 요소의 표시 순서가 빠진 요청이 검증을 통과했고, DB의 NOT NULL 제약에서 실패해 서버가 500을 반환했습니다.

부분 수정은 보내지 않은 기존 값을 유지하는 기능입니다. 하지만 새 요소에는 유지할 값이 없습니다. 예를 들어 기존 배너 A의 문구만 바꾸고 새 배너 B를 추가한다고 해보겠습니다. A의 표시 순서를 생략하면 저장된 순서를 유지할 수 있지만, B의 순서까지 생략하면 어디에 배치할지 결정할 근거가 없습니다.

## 요청 전체의 partial과 요소별 생성 조건

사용 중인 DRF 3.12.4에서는 필드가 빠졌을 때 `root.partial`을 확인해 검증을 건너뜁니다. 최상위 serializer를 부분 수정으로 만들면 중첩된 요소의 필수 필드도 이 영향을 받습니다. `required=True` 선언만으로 신규 요소의 누락을 막을 수 없었던 이유입니다. [해당 버전의 Field.validate_empty_values 소스](https://github.com/encode/django-rest-framework/blob/3.12.4/rest_framework/fields.py)

모든 요소에 생성 필드를 강제하면 앞의 A처럼 정상적인 부분 수정까지 막습니다. 그래서 해당 페이지에 저장된, 삭제되지 않은 요소의 UUID 집합을 한 번 읽고 기존 요소와 신규 요소를 구분했습니다. 다른 페이지에 같은 식별자가 있다는 이유로 기존 요소로 취급하지는 않습니다.

저장 처리가 바로 사용하는 식별자와 요소 종류는 모두 요구합니다. 그 페이지에 없는 신규 요소에는 표시 순서와 UI 종류도 요구하고, 기존 요소에서는 생략한 값을 유지합니다. 누락하면 목록의 몇 번째 요소에 어떤 필드가 없는지 검증 오류로 반환해 저장 전에 400으로 거절합니다. 앞의 예시에서는 A를 문구만으로 수정할 수 있고, B에는 생성에 필요한 값을 채워야 합니다.

회귀에서는 신규 필수값 누락 시 400이면서 행도 생성되지 않는지, 정상 신규 생성은 성공하는지, 기존 부분 수정은 저장된 값을 유지하는지 확인했습니다. 새 테스트는 통과했지만 같은 파일의 기존 실패는 변경 전 main에서도 재현돼 전체 파일 통과로 볼 수 없습니다.

변경은 11월 2일 main에 병합됐습니다. 신규 UI 종류를 생략하면 과거에는 빈 문자열이 저장됐지만 이제 400이 되므로 클라이언트의 전송 값도 확인해야 합니다. 기존 식별자를 읽는 SELECT가 하나 추가되며 실행 계획과 운영 지연은 검증하지 않았습니다. 현재 구현에서 확인한 범위는 저장 단계의 필수값 오류를 입력 검증으로 옮기면서 기존 부분 수정의 생략 규칙을 유지한 것까지입니다.

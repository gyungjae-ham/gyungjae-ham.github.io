고객이 서로 다른 표현으로 검색해도 같은 상품을 찾게 하려면 검색엔진에 동의어를 등록해야 합니다. 당시에는 동의어를 텍스트 파일로 관리했고, 개발자가 S3에 올린 뒤 AWS 콘솔에서 검색엔진용 패키지를 갱신하고 OpenSearch에 연결했습니다. 운영자가 등록 화면에서 규칙을 바꾸면 이 과정까지 이어지도록 자동화하는 작업이었습니다.

패키지를 새로 만드는 것과 검색엔진에 적용하는 것은 별도 단계였습니다. 자동화 중 연결이 실패해 재시도했더니, 연결만 다시 하는 대신 새 버전이 계속 만들어졌습니다. 실패 지점과 재실행 범위를 나눠야 했고, 그 전에 새 규칙의 빌드가 왜 막히는지도 확인해야 했습니다.

## 눈으로는 정상인 단어가 분석기에서는 달랐다

새 동의어 버전이 연결되지 않을 때 처음에는 규칙 중복이나 빈 토큰을 의심했습니다. 하지만 실제 분석 결과를 확인하기 전까지는 가설이었습니다. OpenSearch의 `_analyze`로 같은 분석 과정을 실행하니, 등록되지 않은 복합어가 같은 위치에 겹치는 토큰으로 분해됐습니다. 사전 빌드는 그 결과를 받아들이지 못했습니다.

토큰 위치를 단순화하면 `복합어(position=0)`와 분해된 `부분어(position=0)`가 같은 위치에 함께 나오는 형태입니다. 이는 실제 규칙·응답을 옮긴 것이 아니라 겹침을 설명한 예입니다. `_analyze`에서는 토큰 문자열뿐 아니라 position도 확인해야 했습니다.

사용자 사전에 등록돼 한 토큰으로 나오는 기존 단어와 결과가 달랐습니다. 문자열 형식만 검사해서는 찾을 수 없는 문제였습니다. 신규 규칙을 등록·수정할 때 실제 분석 체인으로 검증하고, 반영 단계까지 간 뒤 실패하는 대신 입력 시점에 사유를 알려주도록 했습니다.

이 검사를 모든 저장 규칙에 다시 적용하는 것도 문제가 됐습니다. 후속 배치에서 이미 저장된 공백 포함 규칙까지 새 입력처럼 검사해 실행을 막았습니다. 입력 API는 새 규칙을 검증하고, 배치는 저장된 규칙을 파일로 만드는 역할로 나눴습니다. 패키지의 실제 빌드 실패는 반영 상태와 알림에서 확인하게 했습니다.

## 연결이 늦다고 버전을 다시 만들 필요는 없었다

패키지를 갱신한 직후에는 아직 빌드 중이라 연결할 수 없을 수 있습니다. 이때 전체 작업을 재시도하면 업로드와 버전 생성까지 반복합니다. 갱신 태스크와 연결 전용 태스크를 분리해, 연결 실패 시에는 같은 버전을 대상으로 다시 시도하도록 했습니다.

```text
동의어 파일 업로드 → 패키지 버전 생성 → 해당 버전 연결
                                            ↓ 실패
                                     같은 버전 연결 재시도
```

재시도는 지연 예약과 백오프를 사용했습니다. 워커에서 잠든 채 기다리는 대신 나중에 연결 작업만 다시 실행합니다. 완료 상태는 계속 폴링하지 않고 관리 목록에 진입할 때 읽어 짧게 캐싱했습니다. 즉시 완료 통지는 제공하지 않지만 관리 API 호출과 워커 점유를 줄이는 선택이었습니다.

## 색인 시점의 설정은 인덱스를 바꿔 적용했다

검색할 때 적용하는 규칙과 달리, 문서를 저장할 때 쓰는 분석 설정은 기존 문서에도 다시 적용해야 합니다. 당시 관리형 환경에서 필요한 close·reload API가 동작하지 않아 새 인덱스에 문서를 다시 넣고 검색이 가리키는 별칭(alias)을 전환하는 흐름을 만들었습니다.

여기서 일부 mapping만 복사해 새 인덱스를 만들자, 빠진 필드가 자동 추론된 타입으로 저장됐습니다. 문서 입력은 성공해도 검색 정의는 이전과 달라질 수 있었습니다. 인덱스 생성 후 필드 mapping을 검증하고 전량 색인하는 순서로 바꿨습니다. 읽기·쓰기 모두 alias를 통하는지도 확인하고, 복사 중 바뀐 데이터는 후속 upsert로 반영하도록 했습니다.

후속 upsert만으로 복사 중 삭제된 문서까지 지워지지는 않습니다. alias 전환 전에는 수정분뿐 아니라 삭제분 반영과 대표 검색 결과도 대조해야 합니다. 이 글에서 확인한 mapping·쓰기 경로 정비를, 전환 중 모든 변경의 무손실 보장으로 넓혀 해석하지는 않습니다.

정기 배치는 렌더링한 파일의 checksum이 같으면 외부 갱신을 생략하게 했습니다. 다만 checksum 기록은 갱신 요청이 성공했다는 뜻이며 검색 적용 완료와는 구분합니다. 동일 내용 생략과 강제 반영은 회귀 테스트로 확인했고, 적용 여부는 연결 상태에서 따로 확인하도록 남겼습니다.

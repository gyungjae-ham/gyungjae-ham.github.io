검색 동의어 반영은 파일을 올리고 콘솔에서 패키지를 갱신·연결하는 수동 작업이었습니다. 이를 자동화하던 중 연결 실패를 재시도했는데 새 패키지 버전이 계속 늘었습니다. 재시도하려던 것은 연결이었지만 버전을 만드는 단계까지 다시 실행되고 있었습니다.

이 작업에서는 서로 다른 실패가 겹쳤습니다. 동의어 분석 결과가 사전 빌드를 막았고, 재시도는 부작용을 반복했으며, 새 인덱스는 색인 성공만으로 검색 동작을 보장하지 못했습니다. 저는 각 단계의 성공과 재실행 범위를 따로 정리했습니다.

## 단어 하나가 사전 전체 반영을 막았다

새 버전이 연결되지 않는 상태에서 동의어 관계 중복과 빈 토큰을 먼저 의심했습니다. 실제 분석 결과를 보기 전까지는 가설이었습니다.

`_analyze`로 같은 체인을 실행하니 미등록 복합어가 같은 위치에 겹친 토큰으로 분해됐습니다. 사전 빌드가 그 결과를 받아들이지 못했습니다. 사용자 사전에 등록돼 한 토큰으로 나오는 기존 단어와 결과가 달랐습니다.

문자열을 눈으로 읽는 검사가 아니라 실제 분석 체인으로 신규 입력을 검사하도록 했습니다. 반영 단계에서 사전 전체가 막힌 뒤 알려주는 대신 등록할 때 사유를 전달했습니다.

## 검증을 반복하면 이미 승인된 규칙도 막힌다

후속 작업에서는 신규 입력 검사를 기존 저장 규칙 전체에 다시 적용하고 있었습니다. 공백이 있는 기존 규칙까지 새 입력처럼 판단해 배치가 중단됐습니다.

생성·수정 API는 신규 입력을 검사하고, 배치는 이미 저장된 규칙을 렌더링하도록 책임을 나눴습니다. 실제 패키지 빌드 실패는 반영 상태와 알림에서 드러나게 했습니다. 방어 로직도 적용 시점을 잘못 잡으면 정상 운영을 막습니다.

## 연결 재시도가 버전을 만들지 않게 했다

패키지 갱신 직후에는 아직 빌드가 끝나지 않아 연결이 실패할 수 있습니다. 전체 태스크를 재시도하면 갱신도 반복됩니다.

갱신 태스크와 연결 전용 태스크를 분리했습니다. 연결은 같은 버전을 대상으로 지연 예약과 백오프를 사용합니다. 워커 안에서 sleep하며 기다리기보다 다시 실행할 작업만 예약했습니다.

```text
렌더링·업로드 → 패키지 버전 생성 → 연결 태스크 예약
                                      ↓ 실패
                               같은 버전 연결 재시도
```

완료 확인도 계속 폴링하는 대신 목록 진입 시 상태를 읽고 짧게 캐싱했습니다. 실시간 완료 통지를 포기하는 대신 관리 API 호출과 워커 점유를 줄였습니다.

## 새 인덱스에 문서가 들어갔다고 검색이 맞지는 않았다

당시 관리형 환경에서 필요한 close·reload API가 동작하지 않는 것을 확인했습니다. 색인 시점 설정 변경은 새 인덱스를 만든 뒤 alias를 전환하는 방식으로 구성했습니다.

여기서 일부 mapping만 복제하자 나머지 필드가 dynamic mapping으로 굳었습니다. 색인은 성공했지만 검색 정의가 달라졌습니다. 생성 후 mapping 검증을 하고 전량 색인하는 순서로 바꿨습니다.

읽기·쓰기 경로 모두 alias를 통하는지 확인하고, 복사 중 바뀐 데이터는 후속 upsert로 반영하도록 했습니다. alias 전환은 짧지만 그 전에 데이터 정합성을 맞추는 일이 남습니다.

## 정기 실행의 skip도 성공 상태와 구분했다

후속 배치는 렌더링 결과의 checksum이 같으면 외부 갱신을 생략합니다. 키가 없으면 한 번 재반영하고 수동 강제 경로도 유지했습니다.

checksum은 요청 성공 후 기록하지만 실제 검색 적용 완료와 같은 상태는 아닙니다. 연결 상태 확인은 여전히 필요합니다. 정기 배치와 동일 내용 skip은 회귀 테스트로 확인했고 운영의 첫 실행과 다음 날 생략 결과는 후속 관측으로 남겼습니다.

이번에 만든 자동화는 수동 버튼을 대신 누르는 흐름에서 끝나지 않았습니다. 실패한 단계만 다시 실행할 수 있도록 분리하고, 각 성공이 무엇을 뜻하는지 확인하는 흐름을 함께 만들었습니다.

고객이 다른 표현으로 검색해도 같은 상품을 찾게 하려면 동의어를 등록해야 합니다. 당시에는 개발자가 텍스트 파일을 S3에 올리고, AWS 콘솔에서 검색엔진용 패키지를 갱신해 OpenSearch에 연결했습니다. 운영자가 등록 화면에서 규칙을 바꾸면 이 작업까지 이어지도록 자동화했습니다.

자동화 중에는 연결 실패를 재시도할 때 새 패키지 버전이 계속 생기는 문제가 있었습니다. 파일을 만드는 단계와 이미 만든 버전을 연결하는 단계를 나눌 필요가 있었습니다. 그에 앞서 일부 규칙이 왜 빌드되지 않는지도 확인했습니다.

## 입력 문자열과 분석된 토큰은 달랐습니다

처음에는 중복 규칙이나 빈 토큰을 원인으로 의심했습니다. 실제로는 `_analyze`로 같은 분석 과정을 실행한 뒤 차이를 찾았습니다. 등록되지 않은 복합어가 같은 위치에 겹치는 토큰으로 분해됐고, 동의어 사전 빌드가 이를 받아들이지 못했습니다.

단순화하면 `복합어(position=0)`와 `부분어(position=0)`가 함께 나오는 형태입니다. 눈으로 읽는 단어가 정상이어도 분석 결과는 다를 수 있습니다. 사용자 사전에 등록돼 한 토큰으로 나오는 기존 단어와도 결과가 달랐습니다.

새 규칙의 등록·수정 시 실제 분석 체인으로 검증하고 이유를 입력 단계에서 알려주도록 했습니다. 문자열 모양만 확인하고 반영 작업까지 진행했다가 실패하는 일을 줄이려는 처리였습니다.

이 검사를 모든 저장 규칙에 다시 적용했더니 기존의 공백 포함 규칙까지 새 입력처럼 검사해 배치가 막히는 문제도 있었습니다. 입력 API는 새 규칙의 검증을, 배치는 저장된 규칙의 파일 생성을 맡도록 나눴습니다. 실제 패키지 빌드 실패는 반영 상태와 알림에서 확인하게 했습니다.

## 연결 실패는 같은 버전으로 다시 시도하기

패키지를 갱신한 직후에는 아직 빌드 중이라 연결할 수 없을 수 있습니다. 이때 전체 작업을 재시도하면 업로드와 버전 생성도 반복됩니다.

갱신 태스크와 연결 전용 태스크를 분리했습니다. 연결만 실패했다면 이미 만든 버전을 대상으로 다시 시도합니다.

```text
파일 업로드 → 버전 생성 → 생성한 버전 연결
                            ↓ 실패
                       같은 버전으로 재시도
```

재시도는 지연 예약과 백오프를 사용해 워커를 잠든 채 기다리게 하지 않았습니다. 관리 화면의 완료 상태는 목록 진입 시 읽고 짧게 캐싱했습니다. 즉시 완료 통지까지 제공하는 방식은 아니지만 상태 확인을 위해 계속 API를 호출하지 않도록 했습니다.

## 새 인덱스의 구조도 먼저 확인하기

문서를 저장할 때 적용하는 분석 설정은 파일만 바꿔도 기존 문서에 소급 적용되지 않습니다. 당시 관리형 환경에서 필요한 close·reload API가 동작하지 않아, 새 인덱스에 문서를 다시 넣고 검색의 별칭인 alias를 전환하는 흐름을 만들었습니다.

이 과정에서 mapping 일부만 복사하자 빠진 필드가 자동 추론된 타입으로 저장됐습니다. 문서 입력이 성공했다고 기존 인덱스와 같은 검색 정의가 된 것은 아니었습니다. 새 인덱스를 만든 뒤 필드 mapping을 검증하고 전량 색인하는 순서로 바꿨습니다.

읽기와 쓰기가 모두 alias를 사용하는지도 확인했습니다. 복사 중 수정된 데이터는 후속 upsert로 반영하지만, 삭제된 문서는 upsert만으로 지워지지 않습니다. 전환 전에 삭제분과 대표 검색 결과도 대조해야 합니다.

정기 배치에서는 렌더링한 파일의 checksum이 같으면 외부 갱신을 생략합니다. 동일 내용 생략과 강제 반영은 회귀 테스트로 확인했습니다. checksum 저장은 갱신 요청 성공을 나타내며, 실제 검색 적용 완료는 패키지 연결 상태에서 별도로 확인하도록 했습니다.

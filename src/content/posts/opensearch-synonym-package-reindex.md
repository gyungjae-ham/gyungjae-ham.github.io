> 동의어 하나가 사전 전체의 반영을 막았고, 재시도는 새 버전을 계속 만들었습니다. 분석기 출력으로 원인을 좁히고 버전 생성·연결·재색인을 서로 다른 단계로 나눴습니다.

## 등록한 문자열이 분석기에 들어가면 달라졌다

수동으로 관리하던 동의어를 운영자가 등록하고 반영하는 경로를 만들었습니다. 진행 중 신규 버전이 연결되지 않는 상태와 자동완성 인덱스 재생성 실패가 발생했습니다. 패키지 상태만 보면 어떤 단어가 문제인지 알기 어려웠습니다.

원인을 좁힌 근거는 `_analyze` 출력이었습니다. 형태소 분석기가 미등록 복합어를 분해하면서 같은 위치에 토큰이 겹쳤고, 사전 빌드의 동의어 파서가 이를 받아들이지 못했습니다. 이미 사용자 사전에 등록된 단어와 그렇지 않은 단어의 차이도 함께 확인했습니다.

새 입력은 실제 분석 체인으로 검사하고 거절 사유를 전달하도록 했습니다. 다만 이 검증을 저장된 모든 규칙에 그대로 재적용하면 이미 운영 중인 정상 규칙까지 반영을 막습니다. 후속 개선에서는 신규 입력 보호와 기존 데이터의 렌더링 책임을 분리했습니다.

## 재시도가 새 버전을 만드는 부작용

패키지를 갱신한 직후에는 아직 빌드가 완료되지 않아 연결이 실패할 수 있었습니다. 전체 태스크를 재실행하니 갱신도 반복되어 새 버전이 계속 생겼습니다. 연결을 다시 시도하고 싶었는데 버전 생성까지 다시 수행한 것입니다.

갱신과 연결을 별도 태스크로 나눴습니다. 연결은 같은 버전을 대상으로 지연 예약과 백오프를 사용합니다. HTTP는 작업을 시작했다는 응답을 반환하고, 상태 확인은 짧은 캐시를 사용해 관리 API 호출을 줄였습니다. 실시간 완료 통지 대신 사용자가 상태를 다시 확인하는 UX를 택했습니다.

## 운영 인덱스를 지우기 전에 새 결과를 검증한다

당시 관리형 환경에서 사용할 수 있는 API를 직접 확인한 뒤 새 인덱스에 색인하고 alias를 전환하는 구조로 갔습니다. 코드의 mapping과 실제 운영 정의가 달랐던 경험 때문에 새 인덱스 생성 후 mapping을 검증하는 순서도 추가했습니다.

읽기뿐 아니라 쓰기 경로도 alias를 사용하는지 확인하고, 복사 이후 변경분을 다시 반영하는 절차를 두었습니다. alias 전환이 원자적이라는 사실만으로 데이터 변경분이 자동 동기화되는 것은 아닙니다. 실패 시 기존 인덱스로 되돌리는 경로도 이 경계에 포함됩니다.

## 변경 없는 날에는 반영을 건너뛴다

후속 배치는 렌더링한 사전의 checksum을 비교해 내용이 같으면 업로드와 갱신을 생략합니다. 체크섬이 유실되면 조용히 건너뛰지 않고 다시 반영하며, 수동 강제 반영 경로는 남겼습니다. 갱신 요청 성공과 실제 검색 적용 완료는 별도 상태로 확인해야 합니다.

기록에는 장애 진단과 재색인 검증, 기존 규칙을 유지한 배치 회귀 테스트가 남아 있습니다. 내부 인덱스 규모와 장애 세부 식별자는 공개하지 않았습니다. 운영 자동화의 결과는 버튼을 줄인 것뿐 아니라 실패한 단계를 같은 부작용 없이 다시 실행할 수 있게 만든 것이었습니다.

쇼핑몰 상품 목록은 사이즈나 색상 같은 옵션을 함께 보여줍니다. 운영자가 옵션을 편집하는 동안에도 고객은 목록을 읽습니다. 이 조회에서 옵션값을 가져온 뒤 연결된 옵션명을 따로 읽는 사이 삭제가 일어나면, 연관 객체를 찾지 못해 상품 목록 전체가 실패할 수 있었습니다. 실제로 어떤 운영 요청이 삭제했는지까지는 확인하지 못했습니다.

조회 두 번 사이의 틈은 옵션값을 읽을 때 옵션명도 JOIN으로 가져오도록 바꿨습니다. 옵션명이 있는지 먼저 확인해도 다음 조회 전에 삭제될 수 있으므로, 두 데이터를 같은 SELECT에서 읽게 한 것입니다. 이는 해당 조회 사이의 경합을 줄이며 요청 전체의 데이터를 하나의 스냅샷으로 만드는 변경은 아닙니다.

## 캐시를 먼저 지우면 이전 값이 다시 들어갑니다

옵션 편집에는 별도의 순서 문제도 있었습니다. 예를 들어 운영자가 색상 이름을 수정하는 트랜잭션에서 커밋 전에 캐시를 지웠다고 해보겠습니다. 다른 요청이 그 사이 캐시 미스를 만나면 아직 커밋되지 않은 수정 대신 이전 DB 값을 읽어 캐시를 다시 채울 수 있습니다. 수정이 끝났는데 캐시에는 옛 이름이 남습니다.

캐시 삭제를 `transaction.on_commit`에 등록해 최외곽 트랜잭션이 커밋한 뒤 실행하도록 옮겼습니다. 롤백하면 삭제도 실행하지 않습니다. 어드민의 생성·수정·삭제뿐 아니라 외부 상품 연동과 엑셀 순서 변경에도 같은 시점을 적용했습니다. 한 편집 경로만 빠져도 그 경로에서는 이전 순서가 반복되기 때문입니다. 이 동작은 사용 중인 [Django 3.2의 커밋 후 콜백 규칙](https://docs.djangoproject.com/en/3.2/topics/db/transactions/#performing-actions-after-commit)을 따릅니다.

## 커밋이 끝난 뒤의 예외는 저장을 되돌리지 못합니다

리뷰에서는 그다음 실패가 지적됐습니다. DB 커밋 후 Redis 삭제가 실패하고 예외가 요청까지 전파되면, 데이터는 저장됐는데 사용자에게는 실패 응답을 줄 수 있습니다. 이미 끝난 커밋을 콜백 예외로 되돌릴 수는 없습니다.

삭제 함수가 Redis 오류를 처리하고, 실패하면 5초 뒤 실행할 Celery 작업을 발행하도록 보완했습니다. 작업은 Redis 오류에 한해 지수 백오프로 최대 세 번 추가 재시도합니다. 브로커 연결도 실패할 수 있으므로 발행 단계의 연결·OS 오류를 기록하고 저장 완료 요청의 응답은 유지합니다.

대신 캐시 삭제를 반드시 완료한다는 보장은 없습니다. Redis와 브로커가 함께 실패하거나 재시도를 소진하면 기존 캐시가 만료될 때까지 남을 수 있습니다. 이 캐시의 TTL은 6시간입니다. 진행 중인 다른 요청의 재적재까지 완전히 직렬화하지도 않습니다. 저장 성공을 보존하는 정책과 캐시 최신성의 한계를 함께 둔 구현입니다.

로컬 검증에는 옵션값 SELECT 직후 삭제를 끼워 넣는 재현, 커밋·롤백에 따른 캐시 상태, Redis·브로커 오류와 재시도 상한을 넣었습니다. 실제 MySQL과 fakeredis를 사용했고 Celery 재시도는 eager 실행으로 확인했습니다. 삭제 재현은 단일 연결에서 실행 순서를 고정했으므로 다중 연결 부하나 운영 브로커 장애 주입과는 다릅니다. 확대 회귀에는 변경 전 main에서도 같은 실패가 남아 있습니다.

10월 30일 main에 병합됐으며 운영 배포 결과는 미확인입니다. 재시도 발행마저 실패한 경우의 로그와 캐시 잔존 시간을 확인해야, 저장 응답은 성공했지만 화면의 옵션은 오래된 상황을 추적할 수 있습니다.

> 주문 상세에서 항목 수만큼 재고 확인 쿼리가 반복되었습니다. prefetch만 추가하는 것으로 끝내지 않고, 옵션 판정 함수가 그 결과를 실제로 사용하도록 바꿨습니다.

## 응답 필드 하나가 매 항목마다 조회했다

문제는 옵션 변경 가능 여부를 계산하는 함수였습니다. 상품의 판매 상태를 확인한 뒤 새 QuerySet을 만들고, 사용 가능한 옵션이 있는지 `exists()`로 조회했습니다. 주문에 항목이 많을수록 같은 형태의 SQL이 반복되었습니다.

목록 경로에는 prefetch가 있었지만 상세 경로에는 없었습니다. 같은 응답을 만드는 진입점의 데이터 준비가 달랐습니다. 공통 판정 함수가 있다는 것만으로 조회 계약까지 공통인 것은 아니었습니다.

## 새 QuerySet은 이미 가져온 목록을 쓰지 않는다

상위 조회에 prefetch를 추가해도 판정 함수가 별도의 `ProductVariant.objects.filter(...)`를 만들면 해당 결과를 사용하지 않습니다. 미리 읽는 쿼리 하나가 생기고 항목별 exists는 그대로 남을 수 있습니다.

선택은 두 변경을 함께 적용하는 것이었습니다. 옵션을 일괄 적재하고, 판정은 준비된 옵션 목록을 순회하도록 바꿨습니다. 이미 적재된 관계를 사용하는 방식과 새로운 조건으로 DB에 묻는 방식을 구분했습니다.

이 접근은 어떤 `exists()`도 prefetch를 이용하지 못한다는 일반 규칙은 아닙니다. 이번 함수가 별도 필터 쿼리를 만들었기 때문에 캐시를 활용하지 못한 것입니다. 실제 사용 경로와 SQL을 기준으로 판단했습니다.

## 공유 판정 함수의 호출처를 함께 맞췄다

상세만 수정하면 목록에서 같은 함수가 기대하는 옵션 데이터가 빠질 수 있습니다. 공통 함수의 사용처를 확인해 적재 계약을 맞췄습니다. 필요한 관계는 직렬화 직전에 준비하고, 단순 개수 확인에 무거운 적재가 붙지 않도록 분리했습니다.

테스트는 주문 항목 수를 바꾸어 재고 확인 쿼리의 증가 여부를 비교했습니다. 변경 전 실패하는 상태를 확인하고, 수정 후에는 항목을 늘려도 반복 조회가 생기지 않는지 검증했습니다. 기능 검증에서는 옵션 변경 가능 여부의 기존 의미도 유지했습니다.

## 줄인 쿼리와 운영 지연을 구분했다

원본에는 운영에서 같은 조회가 반복된 관측과 로컬 쿼리 카운트 검증이 남아 있습니다. 배포 후 응답 시간의 변화와 전체 쿼리 총량은 별도로 측정할 항목입니다. 재고 확인 조회가 줄었다는 사실을 전체 API 지연의 동일 비율 개선으로 환산하지 않았습니다.

이번 수정의 핵심은 관계를 미리 가져오는 것과 그 관계를 소비하는 함수를 같은 변경으로 묶은 것입니다. prefetch를 넣은 코드만 보는 대신 실제 응답을 만드는 동안 실행된 SQL을 확인해야 했습니다.

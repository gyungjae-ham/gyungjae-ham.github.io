주문 상세의 재고 확인 SQL이 한 주문에서 35번 반복됐습니다. 옵션 변경이 가능한지 판단하는 함수가 각 주문 항목마다 별도 QuerySet을 만들고 `exists()`를 호출하고 있었습니다.

상위 조회에 prefetch를 넣는 것만으로는 해결되지 않았습니다. **데이터를 가져오는 쪽과 이미 가져온 데이터를 읽는 쪽을 함께 바꿔야 했습니다.**

## 캐시가 있어도 새 QuerySet은 새 조회였다

기존 함수는 `ProductVariant.objects.filter(...)`에서 QuerySet을 만들었습니다. 이 경로는 상품 객체에 미리 넣어둔 관계 캐시를 사용하지 않습니다. 따라서 prefetch만 더하면 일괄 조회 한 번과 기존 항목별 조회가 모두 남습니다.

이를 모든 `exists()`가 prefetch를 무시한다는 규칙으로 일반화하면 정확하지 않습니다. 이 코드에서는 별도 필터 QuerySet을 만들고 있었다는 것이 원인이었습니다.

상품 옵션을 미리 가져오고 관련 manager의 캐시된 목록을 순회하도록 판정을 바꿨습니다. 아래는 핵심을 단순화한 예시입니다.

```python
# 별도 QuerySet을 만들어 항목마다 조회한다.
ProductVariant.objects.filter(product=product, visible=True).exists()

# 상위 조회에서 적재한 관계를 사용한다.
any(v.visible and not v.is_sold_out
    for v in product.product_variants.all())
```

## 주문 상세만 고치면 목록의 비용이 늘 수 있었다

같은 판정 함수는 목록과 상세에서 공유됐습니다. 상세는 prefetch가 빠져 있었고 목록은 다른 관계를 미리 가져오고 있었습니다. 함수를 캐시 순회 방식으로 바꾸려면 두 진입점 모두 옵션 데이터를 준비해야 합니다.

공유 사용처를 확인해 prefetch를 보강했습니다. 개수 확인용 조회에는 불필요한 관계 로딩을 붙이지 않고 실제 직렬화 대상 조회에 적용했습니다. 응답의 옵션 변경 가능 여부는 유지했습니다.

## 전체 쿼리 수보다 문제 SQL을 비교했다

주문 항목 2개와 5개에서 재고 관련 SQL 횟수를 비교했습니다. 수정 전에는 작은 표본에서도 반복 조회가 나타났고 수정 후에는 옵션 조회 1회로 고정됐습니다. 주문 앱 관련 테스트 56건도 확인했습니다.

이 숫자는 주문 상세 전체가 1쿼리라는 뜻은 아닙니다. 운영에서 관측한 35회와 수정 테스트의 1회를 동일 주문의 HTTP 성능 개선 배수로 환산하지도 않았습니다.

이번 수정은 관계를 더 읽는 최적화가 아니라, 이미 읽은 관계를 소비하도록 맞춘 작업이었습니다. 다음 prefetch를 추가할 때도 실제 판정 함수가 어떤 QuerySet을 만드는지 먼저 확인해야 합니다.

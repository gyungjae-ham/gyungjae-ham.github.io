판매자 관리 화면에서는 고객의 주문 상품을 선택해 교환이나 반품을 접수할 수 있습니다. 이 기능은 기존 주문 상태 변경 처리를 재사용하고 있었습니다. 그런데 Datadog Django 계측이 JSON 본문을 먼저 읽는 환경에서 접수가 400으로 실패했습니다. 같은 접수 데이터인데 본문을 먼저 읽은 구성요소가 있는지에 따라 결과가 달라졌습니다.

기존 코드는 원본 HTTP 요청의 메서드를 PATCH로 바꾸고 POST 데이터에 접수 내용을 넣은 뒤, 내부 API에 다시 진입했습니다. 바깥 요청을 내부 요청처럼 보이게 만들어 처리 코드를 재사용한 것입니다. 하지만 이미 읽어 둔 JSON 바이트까지 그 변경을 따라 바뀌는 것은 아니었습니다.

## 바깥 본문을 내부 데이터로 다시 읽었습니다

설명용 예로 바깥 요청이 접수 데이터와 사진을 함께 담고, 그 안의 접수 데이터에 상품 목록이 있다고 해보겠습니다. 내부 주문 변경 처리는 그 상품 목록이 최상위에 있는 구조를 기대합니다. POST 속성만 내부 구조로 바꿔도 파서가 캐시된 바깥 JSON을 다시 읽으면, 내부 처리가 찾는 위치에는 상품 목록이 없습니다.

사용 중인 Django 3.2.25는 읽은 본문을 보관하고, DRF 3.12.4는 요청 본문 스트림을 파싱해 `request.data`를 구성합니다. JSON 요청에서 POST 속성을 바꾸는 것과 JSON 본문을 바꾸는 것은 다른 일입니다. [Django 요청 소스](https://github.com/django/django/blob/3.2.25/django/http/request.py)와 [DRF 요청 파싱 소스](https://github.com/encode/django-rest-framework/blob/3.12.4/rest_framework/request.py)를 기준으로 이 경로를 확인했습니다.

수정에서는 내부 HTTP 진입점을 다시 거치는 대신 인증된 요청과 접수 데이터를 처리 메서드에 직접 전달했습니다. 일반 주문 상태 변경 API도 같은 메서드에 자신이 파싱한 데이터를 넘깁니다. 이제 접수 데이터의 위치를 호출하는 쪽에서 결정하므로, 본문 선행 읽기 여부에 따라 처리 메서드가 다른 구조를 읽지 않습니다. 원본 요청의 메서드와 POST를 바꾸는 코드도 제거했습니다.

## 재파싱을 없애도 검증은 남아야 합니다

내부 API 재진입을 제거하면 그 앞에서 수행하던 권한과 주문·수량 검증까지 생략하지 않는지 봐야 합니다. 판매자가 처리할 수 있는 주문인지, URL이 가리키는 주문과 접수 상품이 맞는지, 전체 수량 조건이 유지되는지를 기존 흐름과 대조했습니다. 사진 저장에 실패했을 때 접수와 배송 묶음을 되돌리고, 커밋 후 회수·알림을 진행하는 경계도 유지했습니다.

회귀 테스트에는 본문을 미리 읽는 미들웨어를 넣고, 같은 접수 시나리오를 본문 캐시가 있는 경우와 없는 경우로 실행했습니다. 원본 요청이 POST인 채 유지되는지도 확인했습니다. 로컬 Docker MySQL의 API 회귀는 통과했고 변경은 10월 29일 main에 병합됐습니다. 실제 운영 배포와 재접수 결과는 아직 확인되지 않았습니다.

공통 처리는 여전히 View의 메서드에 있어 별도 서비스 계층으로 완전히 분리한 상태는 아닙니다. 이번에 제거한 결합은 처리 재사용을 위해 HTTP 요청을 변조하고 다시 파싱하던 부분입니다. [실패한 접수의 데이터 정리](/posts/return-request-owned-cleanup/)는 그다음 단계에서 따로 다뤘습니다.

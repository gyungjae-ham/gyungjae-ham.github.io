주문이 완료되면 메일을 보내는 기능을 테스트한다고 가정해 보겠습니다. 실제 메일 서버를 사용하면 계정과 네트워크를 준비해야 하고, 테스트할 때마다 메일도 발송됩니다. 주문 처리 로직을 확인하려던 테스트가 메일 서버 상태에 따라 실패할 수도 있습니다.

이때 실제 메일 발송 객체를 대신하는 객체를 넣을 수 있습니다. 이런 객체를 통틀어 테스트 대역(Test Double)이라고 부릅니다. 흔히 전부 Mock이라고 부르지만, 대역이 테스트에서 맡는 역할은 조금씩 다릅니다.

## 같은 메일 기능으로 구분해 보기

| 역할  | 이번 테스트에서 필요한 것 | 메일 기능에 대입한 예                                   |
| ----- | ------------------------- | ------------------------------------------------------- |
| Dummy | 객체를 전달하기만 하면 됨 | 메일 발송을 호출하지 않는 테스트에서 생성자 인자를 채움 |
| Stub  | 정해진 응답               | 발송 요청에 항상 성공을 반환                            |
| Spy   | 호출한 내용을 나중에 확인 | 발송 요청을 목록에 기록한 뒤 수신자를 검사              |
| Mock  | 기대한 호출을 검증        | 주문자의 주소로 정확히 한 번 요청했는지 검사            |
| Fake  | 단순하지만 동작하는 구현  | 실제 전송 대신 메모리에 메일을 저장하고 조회            |

이름은 객체의 생김새보다 사용 목적을 설명합니다. Mockito로 만든 객체라도 정해진 응답만 돌려주면 Stub으로 쓰는 것입니다. 직접 작성한 객체로 기대한 호출을 검증할 수도 있습니다. Spy 역시 반드시 실제 객체를 감싸야 하는 것은 아닙니다. Mockito의 `spy`는 그 라이브러리가 제공하는 구체적인 방식입니다.

예를 들어 “메일 발송에 실패하면 주문 상태를 어떻게 처리하는가”가 궁금하다면 실패 응답을 주는 Stub이 필요합니다. 반면 “주문이 완료된 뒤 올바른 주소에 알림을 요청하는가”를 확인하려면 호출 기록이나 상호작용 검증이 필요합니다. 같은 의존성이어도 질문이 달라지면 대역의 역할이 달라집니다.

## 모든 협력 객체를 바꿔야 할까

테스트 대상과 여러 실제 객체를 함께 사용하는 방식을 sociable, 선택한 대상을 협력자로부터 분리하는 방식을 solitary라고 구분하기도 합니다. 실제 객체를 함께 쓴다고 반드시 DB나 외부 서버까지 연결하는 것은 아닙니다. 메모리 안에서 동작하는 도메인 객체들을 그대로 사용할 수도 있습니다.

따라서 클래스마다 Mock을 만드는 것부터 시작할 필요는 없습니다. 확인하려는 결과를 정한 다음, 그 결과를 안정적으로 만들기 어려운 부분만 대역으로 바꾸면 됩니다. 이 선택을 조금 더 구체적인 코드로 풀어 본 글은 [테스트 대역 선택 예시](/posts/test-doubles-concept/)에 정리했습니다.

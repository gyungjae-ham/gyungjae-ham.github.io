쇼핑 서비스 안에서 운영자가 콘텐츠를 회차별로 등록하고 공개하는 기능을 확장했습니다. 독자는 현재 공개된 회차를 보고, 운영자는 다음 회차를 준비했다가 발행합니다. 기존에는 시리즈가 하나여서 회차 번호만으로 콘텐츠를 찾고 이전 공개 회차를 지난 콘텐츠로 전환할 수 있었습니다.

새 시리즈도 같은 에피소드 구조를 사용하면서 이 전제가 달라졌습니다. 예를 들어 기존 시리즈 A의 1회와 새 시리즈 B의 1회를 함께 등록한다고 해보겠습니다. 회차 번호에 걸린 전역 유일 제약은 두 번째 1회의 저장을 막습니다. 그렇다고 이 제약만 없애면, 기존 코드가 1회를 조회할 때 어느 시리즈를 뜻하는지 알 수 없습니다. B를 발행하는 과정에서 A의 공개 회차를 내리는 문제도 생길 수 있습니다.

10월 12일부터 19일까지 진행한 확장에서는 시리즈를 구분하는 스키마와 조회·발행 코드를 나눠 구현했습니다. 여기서는 그중 DB를 먼저 바꾸는 동안 기존 서버가 계속 저장할 수 있는지, 변경 도중 실패하면 어디서 다시 시작할지에 집중하겠습니다. 스키마와 후속 API PR은 10월 19일 main에 병합됐습니다. 실제 운영 스키마 적용과 코드 배포는 아직 확인되지 않았습니다.

## 새 컬럼을 모르는 서버도 저장할 수 있게

최종적으로 필요한 제약은 회차 번호 하나의 유일성이 아니라 `(시리즈, 회차 번호)` 조합의 유일성입니다. A의 1회와 B의 1회는 허용하되, A의 1회를 두 번 저장하는 것은 막아야 합니다. 먼저 시리즈 컬럼과 복합 유일 제약을 추가하고, 다음 마이그레이션에서 기존 회차 단독 제약을 제거하도록 순서를 잡았습니다. 기존 제약을 먼저 지웠을 때 생기는 무제약 구간을 피하기 위해서입니다.

이 순서만으로 구버전 서버와의 호환성이 해결되지는 않습니다. DB에 시리즈 컬럼을 먼저 추가하면 아직 교체되지 않은 서버는 그 컬럼을 빼고 INSERT합니다. 새 컬럼이 필수 값인데 DB 기본값이 없으면 기존 콘텐츠 등록도 실패합니다. 그래서 컬럼에 기존 시리즈를 가리키는 DB 기본값을 남겼습니다. 기존 행과 구버전의 새 입력 모두 같은 시리즈로 해석할 수 있게 한 것입니다.

사용 중인 Django 3.2.25에서는 모델 필드의 `default`만으로 이 조건을 만들 수 없습니다. Django 3.2의 기본값은 ORM이 값을 채우는 방식이며 DB에 지속되는 기본값과 다릅니다. 새 필드 자체를 모르는 구버전 모델에는 그 ORM 기본값도 없습니다. 컬럼을 만드는 SQL에는 DB 기본값을 명시하고, `RunSQL`의 `state_operations`에는 Django가 기억할 필드·제약 상태를 함께 정의했습니다. DB 구조만 바꾸고 모델의 마이그레이션 상태가 뒤처지는 것도 피해야 했습니다. [Django 3.2 마이그레이션 연산 문서](https://docs.djangoproject.com/en/3.2/ref/migration-operations/#addfield)

새 시리즈의 데이터 등록은 그보다 뒤입니다. 스키마 변경이 끝나도 기존 조회 코드는 여전히 한 시리즈만 있다고 가정하기 때문입니다. 시리즈별 조회와 발행 코드까지 배포한 다음 새 데이터를 넣는 순서로 제한했습니다. 애플리케이션을 되돌릴 때에도 확장한 컬럼과 기본값을 남기는 방침이며, 새 시리즈 데이터가 생긴 뒤에는 구버전의 조회가 안전한지 별도로 확인해야 합니다.

## 컬럼은 생겼는데 마이그레이션은 실패한 경우

다음 문제는 스키마 변경이 중간에 멈추는 상황이었습니다. 이번 변경은 컬럼 추가와 인덱스 생성을 서로 다른 DDL 문장으로 실행합니다. 첫 번째가 성공하고 두 번째가 잠금 대기로 실패하면 컬럼은 이미 남아 있습니다. 그런데 Django의 마이그레이션 적용 이력은 완료되지 않았으므로 다시 실행할 때 컬럼 추가부터 시도할 수 있습니다.

MySQL 8.0의 InnoDB가 제공하는 atomic DDL은 지원되는 개별 DDL 문장의 원자성입니다. 여러 DDL을 묶은 Django 마이그레이션 전체를 하나의 트랜잭션처럼 되돌려 주는 기능은 아닙니다. 따라서 인덱스 생성 실패가 앞서 성공한 컬럼 추가까지 취소해 줄 것이라고 가정할 수 없습니다. [MySQL 8.0 atomic DDL 문서](https://dev.mysql.com/doc/refman/8.0/en/atomic-ddl.html)

재실행에서는 현재 DB 정의를 읽고 필요한 변경만 진행하도록 했습니다. 다만 이름이 같은 컬럼이 있다는 이유만으로 건너뛰지는 않습니다. 타입, NULL 허용 여부, 기본값 등이 기대한 정의와 같을 때만 재사용합니다. 시리즈 컬럼이 있어도 기본값이 다르면 앞서 준비한 구버전 INSERT 호환성이 깨질 수 있기 때문입니다.

인덱스도 같은 기준으로 검사합니다. 컬럼 순서와 정렬 방향, 유일성, 일부 길이만 사용하는 인덱스인지, 가시성 등이 예상과 맞아야 합니다. 필요한 인덱스가 모두 정확하면 재사용하지만 일부만 있거나 정의가 다르면 중단합니다. 이를 임의로 덮어쓰면 이전 실행의 흔적인지 다른 변경인지 구분하지 못한 채 진행하게 됩니다.

이렇게 하면 컬럼 추가 후 인덱스 생성이 실패한 경우에는 컬럼을 확인한 뒤 인덱스 생성을 다시 시도할 수 있습니다. DDL은 모두 끝났지만 적용 이력을 기록하기 전에 중단된 경우에도 실제 정의가 일치하는지 확인하고 이어갈 수 있습니다. 이 재시도 처리는 컬럼·복합 인덱스를 추가하는 마이그레이션에 구현한 것으로, 저장소의 모든 마이그레이션에 적용되는 복구 기능은 아닙니다.

## 온라인 변경에도 잠금 대기는 남는다

컬럼 추가에는 `ALGORITHM=INSTANT`, 인덱스 생성·변경에는 `ALGORITHM=INPLACE, LOCK=NONE`을 명시했습니다. 지정한 방식이 지원되지 않으면 다른 방식으로 조용히 전환하기보다 실패하도록 한 선택입니다. 하지만 이 옵션이 테이블에 대한 잠금을 전혀 잡지 않는다는 뜻은 아닙니다. 온라인 DDL도 테이블 정의를 바꾸는 시점에 metadata lock을 필요로 합니다. [MySQL 온라인 DDL과 동시 실행](https://dev.mysql.com/doc/refman/8.0/en/innodb-online-ddl-performance.html)

예를 들어 다른 연결이 대상 테이블을 읽은 트랜잭션을 오래 유지하고 있으면 DDL이 그 연결을 기다릴 수 있습니다. 그래서 세션의 `lock_wait_timeout`을 일시적으로 5초로 낮췄습니다. 이 값은 각각의 metadata lock 획득 대기에 적용되므로, DDL 전체가 5초 안에 끝나거나 서비스 지연이 5초 이하라는 의미로 사용하지 않았습니다. [MySQL의 lock_wait_timeout 정의](https://dev.mysql.com/doc/refman/8.0/en/server-system-variables.html#sysvar_lock_wait_timeout)

재시도용 스키마 검사도 같은 대기 제한 안에서 수행합니다. 컬럼·인덱스 추가의 정방향 실행에서는 성공하든 예외가 발생하든 원래 세션 값을 복구하도록 했습니다. 잠금 대기를 제한하는 처리와 실패 후 실제 스키마를 확인하는 처리가 함께 있어야, 실패한 명령을 다시 실행할 수 있는 범위가 분명해집니다.

## 실제 잠금 실패 뒤 다시 실행해 보기

독립된 MySQL 8.0.42 환경에서 별도 연결로 잠금을 유지해 인덱스 생성을 실패시킨 뒤, 컬럼·인덱스 추가 마이그레이션 전체를 다시 실행하는 회귀를 검증했습니다. 이미 완료된 DDL의 재실행, 정의가 다른 컬럼·인덱스의 차단, 역방향 실행 차단도 확인했습니다. 구버전 모델의 INSERT와 서로 다른 시리즈의 같은 회차 저장은 별도의 마이그레이션 시나리오에서 검증했습니다.

후속 API 테스트에서는 같은 회차를 시리즈별로 조회하고, 새 회차를 발행할 때 해당 시리즈의 이전 공개 회차만 바뀌는지 확인했습니다. 다만 이 테스트는 현재 모델에서 만든 스키마를 사용했습니다. API 테스트의 통과를 기존 마이그레이션 이력 전체가 적용됐다는 근거로 합치지는 않았습니다.

남은 적용 순서는 스키마 배포, 조회·발행 코드 배포, 새 시리즈 데이터 등록입니다. 운영 DB의 버전과 테이블 조건에서 지정한 DDL이 가능한지, 장기 트랜잭션과 실제 데이터 규모가 잠금·실행 시간에 어떤 영향을 주는지는 배포 전에 확인해야 합니다. 로컬에서 확인한 것은 실패 후 재시도 경로와 구버전 쓰기 호환성이며, 운영 중단 없이 전환을 마쳤다는 결과까지는 아닙니다.

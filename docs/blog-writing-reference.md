# 작성 참고와 편집 예시

2026-10-13 전체 글 편집에 사용한 참고 자료다. 작성 규칙은 [voice guide](../.claude/voice-guide.md)를 따른다. 이 문서는 자동 발행 에이전트가 읽는 편집 자료이며 공개 글에 붙일 템플릿이 아니다.

## 말투는 사용자가 직접 쓴 원문에서 확인한다

- [LocalDateTime 어이없는 실수](https://luca-genie.tistory.com/entry/LocalDateTime-어이없는-실수): 최근 활동 조회의 시각이 고정된 현상에서 시작한다. 컨테이너 시간대 조사, 해결되지 않은 증상, 필드 초기화와 singleton 발견 순서가 이어진다. 수정본도 이 사건의 순서를 살린다.
- [회사 솔루션 구조를 분리한 이유](https://luca-genie.tistory.com/entry/회사-솔루션-구조를-분리한-이유): 학교 서버 제약과 한 학기 운영을 먼저 설명한다. 새 기능을 배포하는 일이 왜 출석 수집에 영향을 주는지 이해한 뒤 서비스 분리가 나온다.
- [생각하면서 개발해야 하는 이유](https://luca-genie.tistory.com/entry/생각하면서-개발해야-하는-이유): 혼자 확인할 때 통과하던 로그인이 여러 사람의 시연에서 뒤섞인 실제 사건이 중심이다. 추상적인 동시성 교훈만 남기지 않는다.
- [TDD 학습에서 배운점](https://luca-genie.tistory.com/entry/TDD-학습에서-배운점): 기존 코드에 테스트를 도입하며 느낀 구조상의 불편에서 학습으로 이어진다. 일반적인 TDD 장점 목록으로 이 계기를 대체하지 않는다.

원문에는 평서체와 구어적인 표현도 있다. 현재 블로그에서는 현대 존대체로 정리하되, 사건의 순서와 구체적인 판단을 유지한다. 원문의 자조·감정을 모든 새 글에 복제하거나 원문에 없는 감정을 만들지 않는다. 현재 저장소의 수정본과 과거 AI voice 메모리는 이 원문을 대신하지 않는다.

## 다른 개발 블로그에서 참고한 설명 방식

- [우아한형제들: 누구나 할 수 있는 10배 더 빠른 배치 만들기](https://techblog.woowahan.com/13569/): 배치가 필요한 업무 상황을 먼저 소개하고, 조회·처리 비용의 원인과 변경 코드를 연결한다. 숫자와 성과는 해당 저자의 사례이므로 우리 글로 가져오지 않는다.
- [토스: 토스 프론트엔드 개발자들이 더 이상 문서를 찾지 않는 이유](https://toss.tech/article/toss-frontend-ai-docs): 개발자가 겪는 일에서 시작해 다음 도구가 필요한 이유를 이어 설명한다. 토스의 어미나 홍보 문체를 흉내 내는 것이 목적은 아니다.

두 글을 문장 템플릿으로 사용하지 않는다. 각각의 실제 경험을 그대로 재현할 수 없으므로, 배경을 알려 주는 순서와 사례를 설명에 사용하는 방법만 참고한다.

## 제목·요약·본문을 함께 고친 예

| 이전 제목 | 수정 제목 | 본문에서 보완한 연결 |
| --- | --- | --- |
| 스케줄러를 차례로 교체하면 놓친 작업은 모두 다시 실행해도 될까 | APScheduler 순차 배포와 누락 작업 복구 | 예약을 누가 읽는지 설명한 뒤 배포 공백과 업무별 재실행 기준으로 연결 |
| 추천에서 상품 하나를 빼려면 후보 수도 다시 세야 했다 | 홈 추천에서 특정 상품 제외하기 | 후보 수로 카테고리를 고르는 과정과 최종 상품 제외가 다른 이유를 예시로 설명 |
| 결제 안내의 SELECT는 열 번인데 한 SQL이 전체를 읽고 있었다 | 결제 안내 API의 조회 범위 줄이기 | 조회 횟수와 각 쿼리가 읽는 행 수를 작은 주문 사례로 구분 |

요약에는 독자가 이해할 문제를 적는다. 예를 들어 “후보 선정 계약과 보충 경로 정합성을 정리합니다”로 끝내지 않고, 특정 상품을 뺀 뒤에도 그 상품을 포함해 계산한 수량이 카테고리 선택에 남을 수 있다는 점을 설명한다.

문장 연결도 같은 원칙을 쓴다. “존재 검증과 소속 검증은 다릅니다”만 쓰면 독자는 무엇이 잘못되는지 추측해야 한다. 주문 A에서 신발을 사고 주문 B에서 가방을 샀다는 가상 예를 먼저 든다. 문의에 A의 번호와 B의 가방을 함께 보내면 각각의 ID는 유효하지만 조합은 틀렸다는 것을 보여 준다. 이어서 부모 주문 ID 비교가 왜 필요한지 설명한다.

## 제출 전 확인

작성자는 각 글을 끝까지 읽고 제목·요약·도입이 같은 문제를 가리키는지 확인한다. 예시 뒤에 구현 이유가 이어지는지, 용어 설명 없이 넘어간 곳은 없는지 본다. 최근 글과 어미·도입·결말이 겹치면 고친다. 사실과 검증 범위를 유지하면서 문장을 손보며, 근거가 부족한 부분은 보류한다. 검토 기록은 비공개 실행 보고에 남긴다.

# Paseo 주간 블로그 발행

2026-10-01 사용자 승인: 매주 토요일 오전 10시, 한국 시간에 새 Obsidian 작업 로그로 글을 작성하고 실제 발행·커밋·push한다.

## 실행 설정

- 스케줄 이름: Obsidian 주간 개발 블로그 발행
- Paseo schedule ID: `62a0002b`

- timezone: `Asia/Seoul`
- 작업 디렉터리: 이 블로그 저장소
- 실행 방식: 매번 새 Codex 에이전트, local workspace, full-access
- 최초 예정 실행: 2026-10-03 10:00 KST
- 사용자가 승인한 범위에는 추가 확인 없이 글 작성, `draft: false`, 대응표 갱신, commit, `main` push, GitHub Pages 배포 확인이 포함된다.

## 입력과 중복 방지

Google Drive의 실제 Obsidian `📒 로그` 폴더를 읽는다. NFC/NFD 경로는 실제 목록으로 대조한다. 원본 로그와 회사 프로젝트는 읽기 전용이다. 원본 로그의 `status: draft`는 블로그의 발행 상태와 별개다.

등록 시점의 번호 로그를 로컬 상태에 기준 목록으로 보관했다. 이후 처음 나타난 번호 로그와 미처리 후보를 검토한다. 주간 범위는 이전 성공 실행부터 이번 실행 시작까지이며, 실행이 빠져도 그 사이 새 로그를 놓치지 않는다. 단순 이름 변경이나 원본 해시 변경을 신규 로그로 취급하지 않는다.

`scripts/blog-publication-map.json`과 기존 글을 대조해 이미 발행·통합한 내용은 새 글로 만들지 않는다. `withheld_editorially`는 근거가 보완되지 않으면 재발행하지 않는다. 새 로그도 글의 근거가 부족하면 사유와 해시를 기록해 보류한다. 같은 주제는 필요하면 기존 글에 후속 사례로 통합한다.

## 글과 날짜

`.claude/voice-guide.md`의 **2026-10-06 독자 맥락·가독성 기준**을 따른다. 독자는 해당 도메인을 모르는 동료 개발자와 관계자다. 서비스와 사용자 행동을 먼저 설명하고, 구체적인 문제에서 판단·구현으로 이어간다. 용어는 처음 필요한 곳에서 풀어 쓰고 한 글의 중심 질문에서 벗어나는 구현 나열은 덜어낸다. 기존 글의 목차·짧은 단정·정형 결말을 복제하지 않는다.

작성 후 모든 대상 글을 처음부터 끝까지 다시 읽고, 도입만으로 기능·사용자·문제가 이해되는지, 예시에서 구현으로 인과관계가 이어지는지, 낯선 용어와 반복적인 요약이 남는지 확인한다. 자동 형식 검사로 이 검토를 대신하지 않는다. 테스트는 개수보다 확인한 동작을 설명한다. 실제 사건과 설명용 가정, 로컬 검증과 운영 성과를 구분하며 리뷰 중·미병합·실행 실패 같은 중요한 한계는 유지한다. 부족한 사실을 지어내지 말고 발행을 보류한다.

사극체와 생성 과정의 안내는 넣지 않는다. 원본에 없는 감정·검토 과정·성과를 만들지 않는다. 회사 비공개 코드·고객 정보·비밀·내부 링크는 공개하지 않는다. 글별 독자 관점 검토 결과는 비공개 실행 보고에 남기며 공개 본문에는 내부 체크리스트나 메타데이터를 넣지 않는다.

새 글의 발행일은 관련 작업의 본인 커밋 author 날짜를 KST로 변환해 우선 사용한다. 없으면 PR 생성 날짜를 사용한다. 기간·통합 글은 관련 작업의 가장 이른 확인 날짜를 사용한다. 로그 생성일·자동화 실행일로 대체하지 않는다. 날짜 근거를 확인할 수 없으면 보류한다. 시각은 00:00 KST로 통일한다. 커밋·PR의 식별자와 날짜 근거는 비공개 실행 기록에 남긴다.

공개 글은 반드시 `draft: false`다. 기존 글의 발행일은 보존한다. 해당 날짜에 맞춘 글을 쓴다는 것은 Git 커밋 시각을 과거로 조작한다는 뜻이 아니다.

## 검증과 최신화

변경 범위의 Prettier, `git diff --check`, `npm run check`, `npm run lint`, `npm run build`를 실행한다. 사극체·근거·중복·날짜·비공개 정보·RSS·HTML·내부 링크를 확인한다. 변경이 없으면 빈 커밋이나 push 없이 종료한다.

기존 사용자 변경을 stash/reset/clean으로 지우거나 같이 커밋하지 않는다. 작업 트리와 원격 상태를 확인하고 깨끗한 main에서 fast-forward만 허용한다. 충돌이나 다른 작성 작업이 있으면 해당 실행을 보류하고 사유를 남긴다. 성공한 글과 관련 대응표·문서만 커밋해 `origin main`에 push한다. force push는 하지 않는다.

push한 SHA의 `Deploy to GitHub Pages` 실행 성공과 공개 URL·RSS를 확인한다. 실패 시 동일 글을 다시 만들지 않고 남겨둔 commit SHA에서 배포 상태를 확인·복구한다. 해결할 수 없는 실패는 다음 실행의 pending으로 보존한다.

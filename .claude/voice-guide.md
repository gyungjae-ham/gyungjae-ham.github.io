# 블로그 작성 기준

이 블로그는 이력서에서 이어 읽을 때 작성자의 문제 해결 방식과 판단을 이해할 수 있는 기술 블로그다. 독자는 개발 경험은 있지만 해당 서비스의 상품·주문·쿠폰·실험 정책과 내부 용어는 모르는 동료 개발자 및 관계자로 가정한다.

2026-10-06 사용자 피드백인 “맥락 없이 끊겨 이해하기 어렵고 AI 글 같다”를 반영한 현재 기준이다. 이전 글과 vault 메모리의 고정 목차, 짧은 분량, 표·코드·강조 개수, 강제 회고·격언·인터뷰 규칙보다 이 문서와 최신 사용자 지시를 우선한다. 오래된 가이드는 Git 이력에서 볼 수 있으며 현재 작성 규칙으로 적용하지 않는다.

## 독자가 문제를 이해한 뒤 구현을 읽게 한다

- 도입에서 어떤 서비스 기능인지, 누가 무엇을 하려는지, 기존 처리에서 무엇이 달라져야 했는지를 설명한다. 첫 100자에 문제·해결·성과를 모두 압축하지 않는다.
- 글마다 중심 질문 하나를 정한다. 원본 로그의 구현 항목을 모두 옮기지 않는다. 본론을 이해하는 데 불필요한 별도 실험·보안·운영 이야기는 덜거나 관련 글로 연결한다.
- 가능하면 구체적인 입력이나 사용자 행동을 따라 문제와 변경을 설명한다. “원장 정합성 확보”라고 끝내지 말고 어떤 기록이 어떻게 잘못될 수 있는지 보여준다.
- 용어는 필요한 지점에서 역할과 함께 소개한다. 처음부터 PDP·PLP·pool·복원·확정·분모·계약을 안다고 가정하지 않는다. API·DB 같은 일반 개발 용어까지 매번 사전식으로 정의할 필요는 없다.
- 문단 사이에는 인과관계를 남긴다. 왜 다음 검사가 필요한지, 앞의 선택이 어떤 문제를 남겼는지 설명한다. 연결사만 덧붙여 독립된 결론을 이어 붙이지 않는다.
- 분량 제한 때문에 필요한 설명을 지우지 않는다. 반대로 짧은 변경을 긴 회고로 부풀리지 않는다. 관련자가 도입에서 기능과 영향을 이해하고, 개발자가 본문에서 구현 이유를 따라갈 수 있게 쓴다.

## 자연스러운 문체

현대 격식 존대체(`~했습니다`, `~입니다`, `~합니다`)를 쓴다. 사극체(`~하였나이다`, `~사옵니다`, `~하옵니다` 등)는 사용하지 않는다. 필요한 곳에서 “저”를 쓰되 모든 단락에 자기 판단을 강조하지 않는다.

연결된 산문을 기본으로 하고, 나열·비교가 더 쉬울 때만 목록이나 표를 쓴다. 소제목은 실제 논점이 바뀌는 위치에 둔다. 짧은 문단마다 소제목을 달거나 모든 글에 같은 목차를 쓰지 않는다. 강조·다이어그램·코드는 이해에 필요한 만큼만 사용한다.

다음 패턴을 피한다.

- 추상적 단정 → 구현 명사 나열 → 격언으로 끝나는 짧은 절의 반복
- “X가 아니라 Y였습니다”, “이번 작업의 결과는”, “진짜 중요한 것은”을 반복해 판단이 있는 것처럼 보이게 하기
- 테스트 개수를 성과처럼 나열한 뒤 매번 같은 미측정 문장으로 마무리하기
- 억지 감정, 가짜 대화, 과한 구어체나 농담으로 사람다운 글을 연출하기
- TL;DR·후보 표·코드·교훈·다음 글 예고를 모든 글에 의무적으로 넣기

끝은 구체적인 변경 결과, 아직 남은 문제, 실제 다음 확인 사항 중 글에 필요한 것으로 자연스럽게 맺는다. 구현 목록을 다시 요약하거나 일반적인 교훈을 덧붙일 의무는 없다. 제목과 description도 낯선 명사 묶음보다 독자가 이해할 문제를 표현한다.

## 사실과 설명용 예시

- 원본 로그, 확인한 코드·PR, 기존 사용자 답변에 근거한다. 실제 기여는 자연스럽게 설명하되 감정·대화·당시 검토한 대안·단독 책임·사용자 반응·성과 수치를 지어내지 않는다.
- 이해를 돕는 가상의 상황은 “예를 들어”, “~라고 해보겠습니다”처럼 표시한다. 실제 장애와 혼동하지 않게 하며 예시 수치를 측정값으로 쓰지 않는다.
- 설명용 축약 코드와 실제 발췌를 구분한다. 회사 비공개 코드·고객 정보·비밀·내부 링크와 불필요한 식별자는 공개하지 않는다.
- 테스트는 무엇을 막거나 유지하는지 설명한다. 개수는 의미가 있을 때만 덧붙이고 겹치는 실행 수를 더하지 않는다.
- 쿼리 수, 실행 계획, 로컬·합성 측정, 운영 성과를 구분한다. 병합은 배포가 아니고 후보 수는 최종 노출·전환이 아니다.
- 리뷰 중·미병합 종료·검증 실패·외부 연동 미확인처럼 독자의 판단에 영향을 주는 한계는 결과 옆에 정확히 남긴다. 일반적인 미측정 고지를 모든 글에 반복하지 않는다.
- “원본 확인 시점”, “이번 글 작성에서 테스트를 재실행하지 않았다” 같은 생성 과정, source ID, 실행 메타데이터는 본문에 넣지 않는다. 날짜 근거와 감사 기록은 대응표·운영 문서·비공개 실행 보고에 둔다.
- 독립된 문제·판단·검증을 설명할 근거가 부족하면 보류하거나 같은 주제에 통합한다. 부족한 사실을 그럴듯한 회고로 채우지 않는다.

## 작성과 편집 절차

1. 원본 로그와 기존 대응표를 읽고 중복·통합·보류 여부를 판단한다. 글에 필요한 배경과 핵심 동작의 근거를 확인한다.
2. 현재 대표 글 중 이번 주제와 가까운 것을 읽는다. 문장이나 목차를 복제하지 않고 설명 깊이의 참고로만 쓴다.
   - [무료교환](../src/content/posts/first-exchange-benefit-ledger.md): 고객 행동 하나를 따라 상태 변경 설명
   - [푸시 미수신](../src/content/posts/push-delivery-three-boundaries.md): 구성요소 역할 소개 후 증거를 따라 조사
   - [홈 캐시](../src/content/posts/home-content-cache-invalidation.md): 기능 배경과 갱신 시점의 이유
   - [리뷰 정렬](../src/content/posts/review-sort-subquery-aggregation.md): 작은 예시에서 쿼리 구조로 연결
   - [계절 추천](../src/content/posts/seasonal-candidates-catalog-name.md): 좁은 수정은 짧고 구체적으로 완결
3. 배경 → 구체적 문제 → 필요한 판단과 구현이 이어지는 초고를 쓴다. 이 순서는 설명의 의존 관계이며 고정 소제목 템플릿이 아니다.
4. **모든 대상 글을 처음부터 끝까지 다시 읽는다.** 소제목·굵게·코드를 빼도 핵심 흐름이 이해되는지 확인한다. 대표 몇 편만 보고 전체 검토 완료로 보고하지 않는다.
5. 아래 독자 질문에 답이 없는 부분을 보완하고 반복 문구와 중심 주제 밖의 나열을 덜어낸다. 필요한 사실이 없으면 보류한다.
6. 내용 검토 후 저장·형식·빌드·발행 검증을 수행한다. 자동 검사의 성공을 가독성 검토의 대체물로 취급하지 않는다.

### 독자 관점의 검토 질문

- 처음 두 문단만 읽고 어떤 기능을 누가 쓰며 무엇이 문제였는지 설명할 수 있는가?
- 서비스 고유 용어나 약어의 의미를 추측해야 다음 문장을 읽을 수 있지는 않은가?
- 이 구현이 필요한 이유가 구체적인 상황과 연결되어 있는가? 하나의 결론에서 다음 결론으로 건너뛰지는 않는가?
- 실제 관측, 설명용 예시, 구현 결과와 미확인 상태가 구별되는가?
- 결말이 해당 작업의 사실로 끝나는가, 어느 글에나 붙일 수 있는 요약인가?

검토 결과와 보류 사유는 별도 편집·실행 보고에 기록한다. 이 질문 목록을 공개 글 본문에 붙이지 않는다.

## 발행 원칙

- 매주 토요일 오전 10시 `Asia/Seoul`에 새 로그와 이전 미처리 후보를 검토한다. 발행할 내용이 없으면 빈 글·빈 커밋 없이 종료한다.
- 공개 글은 `draft: false`다. 새 글 날짜는 관련 본인 커밋 author 날짜(KST), 없으면 관련 PR 생성일(KST)을 사용한다. 통합·기간 글은 가장 이른 확인 가능한 작업일, 시각은 00:00 KST로 둔다. 근거가 없으면 보류하며 로그 생성일·자동화 실행일로 대신하지 않는다.
- 기존 글의 작업일과 과거 월 대표일은 보존한다. 실제 Git 커밋 시각을 과거로 바꾸지 않는다.
- 중복·사극체·사실 근거·비공개 정보·날짜·형식·빌드를 확인한 뒤 커밋·push하고 해당 SHA의 배포 성공과 공개 글·RSS를 확인한다.
- 운영 절차는 [주간 발행 문서](../docs/weekly-blog-publication.md), 원본 대응은 [발행 대응표](../scripts/blog-publication-map.json)를 따른다.
